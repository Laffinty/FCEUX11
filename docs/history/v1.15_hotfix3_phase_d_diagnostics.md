## 二、D-2 [MEDIUM] RefreshSprites palram_op_bk 提升（**语义修正**）

### 2.1 诊断与 PLAN 描述偏差

PLAN §五 D-2 原描述有两处问题：

1. **"Hoist pal_tab_op 到 scanline 入口"** —— 实际 `pal_tab_op` 是 per-sprite 的：`VB = (atr & 3) << 2 | 0x10`，`atr & 3`（sprite attribute 的调色板位）每个 sprite 都可能不同。**不能跨 sprite 提升**。

2. **"合并 `pal_tab_op`/`pal_tab_bk` 到 `pal_tab_op[8]`，每 sprite 8 字节"** —— 需要 per-pixel 加 offset 选择 op/bk，是有损设计（per-pixel 分支移进 8 像素内层循环）。

### 2.2 正确提升对象

**完整 16 字节 `PALRAM[0x10..0x1F]`（4 sprite palette × 4 entry）是 scanline-invariant**：CPU 通过 `$2001` 写 PPU[1] 在 scanline 内不影响渲染（`$2001` 写在本 scanline 内被 PPU 已 cache 的 PPU[1] 忽略；下一 scanline 才生效）。

```
uint8_t palram_op_bk[4][2][4];   // [palette_idx][0=op,1=bk][i]
// scanline 入口一次性预计算
for (p=0;p<4;p++) for (i=0;i<4;i++) {
    const uint8_t c = PALRAM[0x10 + p*4 + i] & pal_mask;
    palram_op_bk[p][0][i] = c;
    palram_op_bk[p][1][i] = c | 0x40;
}
// sprite body
const uint8_t* pal_tab = palram_op_bk[atr & 3][(atr & SP_BACK) ? 1 : 0];
```

### 2.3 实施修复

- `src/ppu_rendering.cpp:1030-1131`（RefreshSprites）：
  - 函数顶部新增 `palram_op_bk[4][2][4]` lift（紧跟 `pal_mask` hoist 之后）
  - 每个 sprite 处 8 行 → 1 行 `pal_tab` 索引
  - `flipped = packed; if (H_FLIP) ... = bswap` → 单 ternary（机器码等价 cmov）

- [ ] `tests/ppu_rendering_lut_test.cpp::decode_lut`（65536-input sprite 矩阵覆盖）

## 三、D-3 [MEDIUM] RDo* LQ 拆分（**语义/形态修正**）

### 3.1 PLAN §五 D-3 的措辞失误

PLAN 提的 "use `if constexpr` in LQ for inline" —— **LQ/HQ 是运行时分派**：`SetSoundVariables`（`sound.cpp:1185-1217`）选函数指针到 `DoNoise`/`DoTriangle`/`DoPCM`/`DoSQ1`/`DoSQ2`。`if constexpr` 无法在运行时分支 fold。**HQ 路径不动**（小函数 + 冷调用，对 icache 共享没收益）。

PLAN 提的"RDoSQLQ 4 路拆分（silent / L-only / R-only / both）"——**有听觉语义风险**：当 `inie[ch]==0` 时跳过 ch 的 catchup，会让 RectDutyCount[ch] 不在本帧推进；下一帧 `inie[ch]` 变为非零时，初始 `ttable[ch][RectDutyCount[ch]]` 与原本不同 → totalout 改变 → 听觉差异。**改为 2 路安全拆分**（silent vs active），复杂 4 路留作后续 hotfix（需 per-game audio regression 收齐）。

### 3.2 实施修复

`src/sound.cpp` 三处独立重排：

1. **RDoNoise**（L903-966）：2 个 for-body 96% 重复（仅 `feedback_shift = 8 vs 13` 不同）。合并为 1 个 for-loop，hoist `feedback_shift` 到函数顶部。

2. **RDoSQLQ**（L621-715）：抽 `do_sq_lq_silent` + `do_sq_lq_active` 2 个 helper。`silent` 仅 `Wave[V>>4] += totalout`；`active` 是 verbatim 当前 body（2 个 `rea:`/`rea2:` catchup）。**保留原 `RectDutyCount` 状态转移语义，不激进 4 路**。

3. **RDoTriangleNoisePCMLQ**（L759-900）：抽 4 个 helper（`do_tnp_lq_silent` / `_triangle_only` / `_noise_only` / `_both`），每个标签（`rea:`/`rea2:`/`area:`/`area2:`）独占。

### 3.3 CI 盲点

所有现有 bench（`apu_frame_bench`/`apu_mix_bench`）和 `bench_tolerance_test` 都用默认 `soundq=1`（HQ）。**D-3 的 LQ 优化主张不被任何现有 CI 自动测量**。本地一次性 `--soundq 0` 跑 apu_wav_diff_test 是兜底验证路径。

### 3.4 验证清单

- [ ] HQ byte-diff：`tests/core/apu_wav_diff_test.cpp`（nrom/mmc1/vrc6）金标准不变
- [ ] LQ byte-diff：本地 `--soundq 0` 跑 apu_wav_diff_test
- [ ] bench：`tests/benchmark/apu_mix_bench.cpp` / `apu_frame_bench.cpp` 不退 ≥ 5%（§十.4）
- [ ] HQ 路径未动：`RDoTriangle` / `RDoNoise`（HQ）/ `RDoPCM` / `RDoSQ` 全保留

## 四、D-4 [LOW] WaveHi memset 删除（**形态简化**）

### 4.1 实地分析

PLAN §五 D-4 原拟 `wavehi_valid_` cursor 跟踪 WaveHi 有效长度。实地分析 (`src/sound.cpp:995-1054`)：

- WaveHi 是 `int32_t wave_hi_[40000]`（`apu.h:109`），160 KiB
- 所有 reader 都只在 `[0, SOUNDTS)` 范围内读（~1500 ints）：
  - `NeoFilterSound`（L1024）
  - `tmpo` 循环（L1014-1023）
  - `FCEU11_ExpHiFill`/`FCEU11_ExpHiSync`（L1016、L1029）
  - 全部 board-level WaveHi 写者（vrc6 / n106 / 69）也只写 `[ChannelBC[x], SOUNDTS)`
- `[SOUNDTS, 40000)` 区域**没有任何 reader**，纯防御性 housekeeping
- memmove 必须保留（FIR carryover）
- memset 完全可省——[`(left..wavehi_valid_)` 已经是下一帧 `Do*` 写入会覆盖的区域]

### 4.2 实施修复

`src/sound.cpp:1026-1027`：
```cpp
memmove(WaveHi, WaveHi+SOUNDTS-left, left*sizeof(uint32));   // ~120 字节 (保留)
// memset 1 行删除
```

边界兜底：`FCEUSND_Power()` L1158 的 `memset(WaveHi, 0, sizeof(WaveHi))` 保留（一次性启动清零）。

### 4.3 验证清单

- [ ] `tests/core/apu_wav_diff_test.cpp` byte-diff 不变
- [ ] bench：`apu_mix_bench` 不回退 ≥ 5%

## 五、D-5 [LOW] Render_logp stub 删除（**形态简化**）

### 5.1 实地分析

`src/pputile_template.cpp` 的 `FetchAndDrawTile` 模板内 5 个 stub 站点（line 171 / 183 / 189 / 206 / 210 旧版本）：

- L171: `(void)ScreenON;` 顶层 sentinel
- L183 / L189: kFlagBGFetch 路径下 `if (ScreenON) { (void)C; }`
- L206 / L210: fallback `else` 下 `if (ScreenON) { (void)C; }` / `(void)(C+8);`

`ScreenON` 在整个模板 body 内**仅出现在这 5 个站点**——用途就是守护 stub。RENDER_LOGP macro 本身已被 hotfix2 v1.5 Prism §1 后续 commit 减化为 `(void)C;` 等空操作；stub 是死代码。

### 5.2 PLAN §五 D-5 的措辞与 codebase 约定不符

PLAN 提的 `#ifndef FCEUDEF_DEBUGGER` + `if constexpr (kRenderLog)` 形态是**新形态**。`src/` 内 11+ 处现有约定是 `#ifdef`/`#ifndef`，从不用 `if constexpr` 调试钩。`ppu_rendering.cpp:165-189` 的 `RENDER_LOG/RENDER_LOGP` macro 定义已经 neutered；hotfix2 P3-3 `InputScanlineHook null guard` 与 P3-2 `ppudead edge detector` 是 codebase 已有的"删 dead stub" 模式参考。

### 5.3 实施修复

`src/pputile_template.cpp`：

- 删 `(void)ScreenON;`（L171）
- 删 `if (ScreenON) { (void)C; }` 三行块（L183 / L189 / L206）
- 删 `if (ScreenON) { (void)(C+8); }` 三行块（L210）

`src/pputile_template.h` 头注释：ScreenON 行为标注加 "hotfix3 D-5: parameter retained on signature for ABI stability"。E-phase 后续 PR 删参数。
