## 一、E-1 — 删 `FCEU_LIKELY/FCEU_UNLIKELY` 死宏 → 修复

### 1.1 诊断概览

| 项目 | 内容 |
|------|------|
| 文件 | `src/compiler_attrs.h:43-56` |
| 触发场景 | PLAN §六 E-1 提议在 MSVC 19.30+ 分支启用 `[[likely]]/[[msvc::likely]]` |
| 失败现象 / 现状 | codebase 已有 20+ 处直接 `if (cond) [[likely]] stmt` 形态；宏 `FCEU_LIKELY`/`FCEU_UNLIKELY` 全树零调用 site；宏定义是 dead code |
| 修复紧迫度 | **LOW**（清理型，无运行时改动）|

### 1.2 三种 PLAN §六 假设的形态为什么都不对

PLAN §六 E-1 L744-749 提议 `#define FCEU_LIKELY(x) (x) [[msvc::likely]]`。展开 `if (FCEU_LIKELY(x))` 后变 `if ((x) [[msvc::likely]])`。问题：

1. **属性位置错**：C++20 §9.11.8 要求 `[[likely]]`/`[[unlikely]]` 在 `if` 条件**关闭括号之后**。表达式内是非标位置，会被 `/std:c++20 /permissive-`（CMakeLists.txt:38）拒绝。
2. **vendor 命名 vs 标准**：codebase 已统一采用标准 `[[likely]]`（20+ 处），无 `[[msvc::likely]]` precedent。
3. **PLAN §六 L751 自己也注了这点**："注意：`[[msvc::likely]]` 只能用于 if/else 内表达式末尾"。

### 1.3 实施修复

`src/compiler_attrs.h:43-56` 14 行整块（3 个 `#if`/`#elif`/`#else` 分支 + LIKELY/UNLIKELY 定义）替换为 6 行 breadcrumb 注释，说明 codebase 已用直接 `[[likely]]/[[unlikely]]` 形态。

### 1.4 验证清单

- [x] `git grep FCEU_LIKELY\|FCEU_UNLIKELY src/ tests/` 返回 0 命中
- [ ] CI 编译通过（无调用 site，故不可能触发）
- [ ] bench：`tests/benchmark/ppu_render_bench.cpp` ≥ 5% 不变（删宏不可能有可测量影响）
- [ ] 20+ `[[likely]]`/`[[unlikely]]` 现存 site 行为不变

## 三、E-3 — `StackAddrBackup` fallback for non-debugger builds → **Skip**

### 3.1 PLAN §六 E-3 假设

> "`extern int StackAddrBackup;` 在非 `FCEUDEF_DEBUGGER` build 下无定义。"

### 3.2 实地确认 —— 假设不成立

实地确认（不改正）：
- `src/debug.cpp:644` 定义**无条件**：`int StackAddrBackup;`（不在 `#ifdef` 内）
- `src/x6502.cpp:436` `extern int StackAddrBackup;` 仅声明
- `src/CMakeLists.txt:84` `add_definitions(-DFCEUDEF_DEBUGGER)` 对 `fceux11_core` 全程 define
- core 编译列表同时含 `debug.cpp` + `x6502.cpp`（`src/CMakeLists.txt:161,209`）
- 测试/bench target 自身不编译 `x6502.cpp`；它们只链接已带 debugger 宏的 `fceux11_core`

**当前 build 不存在链接失败**。两种 fallback 提案都不需要：

| Fallback 形态 | 问题 |
|--------------|------|
| `static int StackAddrBackup = -1;` | 产生两个对象：`x6502.cpp` 的 static 私有 + `debug.cpp` 的全局；状态分裂，breakpoint 逻辑读不到 power 时写入的 `-1` |
| 非 static `int StackAddrBackup = -1;` | 与 `debug.cpp:644` 重复外部定义，链接失败 |

### 3.3 未来剥离 `debug.cpp` 的策略

如果未来要剥离 `debug.cpp` 形成最小 CPU-only target，应**先决定所有权**（典型方案：单一 provider 移至 `x6502.cpp`，`debug.cpp` 改 `extern`），而不是局部补丁。这属于策略性重构，独立 PR。

## 四、E-4 [LOW] `Cpu::layout_` sizeof 静态断言 → 修复

### 4.1 诊断概览

| 项目 | 内容 |
|------|------|
| 文件 | `src/cpu.cpp:14-17` |
| 现状 | 仅有 `offsetof == 0` + `alignof == 64` 断言；缺 `sizeof` 断言 |
| 风险 | 未来 `X6502` 字段添加若不影响 alignment/padding 但改 sizeof，编译期不报警，savestate layout 漂移 |
| 修复紧迫度 | **LOW**（compile-time 防御） |

### 4.2 实施修复

`src/cpu.cpp:16` 后插 `static_assert(sizeof(Cpu::layout_) == 64, ...)`。

值 64 来源（X6502 在 `x6502struct.h:16` 声明 `alignas(64)`）：
- Release payload：32 B → 64 字节倍数
- Debugger payload：32 + 24 = 56 B → 64 字节倍数
- 两种情形 sizeof 都是 64

## 五、E-5 [LOW] 死代码 + macro 卫生 → 限定 scope 修复

### 5.1 实地分析

PLAN §六 E-5 含两部分：

#### A. 真死代码（必做）

- `src/debug.cpp:522` `int u; //deleteme` —— `grep "\bu\b"` 仅一处声明
- `src/debug.cpp:523` `int skipdebug; //deleteme` —— 仅有声明，零读者

#### B. Macro 卫生

- `src/ppu_rendering.cpp:577` `#undef vofs` —— 仓库没有对应 `#define vofs`，no-op 删
- `src/pputile_template.h:6,23-26` + `pputile_template.cpp:7-10` 引用 `tests/golden/pputile.inc`，但该文件不存在（实际 legacy 是 `src/pputile.inc`）。修正文档
- "Replaces the 10 dispatcher" 应为 9（`kNumRefreshKinds = 9`）

#### C. RefreshAddr/Fixit 宏重排（**PLAN 误诊，不动**）

实地重读 `ppu_rendering.cpp:295-678`：`smorkus` 不是 debugger alias——它是 `RefreshLine()` 的 local copy of `RefreshAddr`（L319）。当前顺序：

```cpp
uint32 smorkus = RefreshAddr;  // L319 copy in
#define RefreshAddr smorkus        // L321 macro alias
// ... tile rendering updates smorkus via the alias ...
#undef RefreshAddr                // L578 ends alias
// ... write back pshift etc ...
RefreshAddr = smorkus;           // L599 sync back to global
Fixit1();                         // L633 reads synchronised global
```

**Fixit1/Fixit2 必须**在 `RefreshAddr = smorkus;` **之后**调用——它们读取已同步的全局值。"Move Fixit before #undef" 不会让 Fixit1 函数体内的 `RefreshAddr` 引用自动 alias 到 `smorkus`；macro 替换发生在预处理阶段，函数体早已在调用点之前单独编译。唯一可靠重构是给 Fixit 传 `uint32&` 参数——但那是 5 调用点的较大改动，PLAN §六 表态不充分支撑单 PR。

#### D. `TOFIXNUM` 不带 `#undef`（hotfix3 不动）

`src/ppu_rendering.cpp:398` `#define TOFIXNUM (272 - 0x4)` 缺匹配 `#undef`。该宏从 L398 泄漏到本 TU 末尾。不造成冲突（单 TU 内），但属于 macro 卫生残留。列入 §十六 follow-up，本 PR 不强加。
