## 三、各 PR 实现要点

### P2-1（ALIAS-1）`FCEU_dwmemset` 重写 + AVX2 `fill32`

**改动**:
- 新建 `src/utils/simd_fill.h`：定义 `inline void fceu11::fceu_dwmemset(uint8_t*, uint32_t pattern, size_t n_bytes)`。
- `src/utils/memory.h` 把 `FCEU_dwmemset(d,c,n)` macro body 从
  ```
  for(_x=n-4;_x>=0;_x-=4) *(uint32 *)&(d)[_x]=c;
  ```
  替换为单行重定向 `#define FCEU_dwmemset(d,c,n) fceu11::fceu_dwmemset((d),(c),(n))`。
- 无 call site 改动（macro 名字保留，redirect 透明）。

**实现要点**:
- AVX2 编译时由 `<immintrin.h>` 已有的 `defined(__AVX2__)` 守卫提供（见 `compiler_attrs.h:60-63`），运行时由 `fceu11::simd::have_avx2()` gate（默认 `false`，dev 通过 `simd::probe_cpu_features()` 切换）。
- 路径：
  - 编译期 + 运行时均无 AVX2 → 4-byte stride `std::memcpy` 循环（无别名 UB）。
  - 编译期 `__AVX2__` + `n >= 64` → 一次 `_mm256_set1_epi32(pattern)` broadcast + `_mm256_storeu_si256` × N/32 + 4-byte tail。
- `pattern` 参数语义保持：`uint32_t` 4 字节在 `set1_epi32` 下广播到 32-byte lane。

**风险 / 审计（PLAN §一 ALIAS-1 / §十七.1）**:
- 严格别名 UB 已消除（旧 macro 的 `*(uint32 *)&(d)[_x]` 不再出现）。
- AVX2 `storeu_si256` 处理 unaligned buffer；XBuf row 通过 `FCEU_amalloc(256×256, 256)` 分配，单行 256 字节对齐，row offset = `sl * 256`（恒为 256 倍），运行始终对齐；但 `__m256i` 要求 32 字节对齐，`storeu` 安全。
- **审查豁免**: 项目锁 MSVC，AVX2 通过 `/arch:AVX2` 开关；当前默认不开 → 编译时不展开 AVX2 路径，运行时探测 `false`。

### P2-2（DS-2）`PALRAM[0/4/8/0xC]` — **行为不变 + 静态检查**

**改动**:
- `src/ppu_rendering.cpp:RefreshLine` 在 `PALRAM[0] |= 64` 前添加：
  - `static_assert(std::tuple_size_v<decltype(PALRAM)> >= 0x10, ...)`
  - 长诊断注释解释为什么 `|= 0x40404040` 不安全。
- 在 restore 路径添加对应注释（保持 4 byte RMW 行为完全不变）。

**为何放弃 §十 P2-2 提议的 `|= 0x40404040` 合并读写**:
1. PALRAM 是 `alignas(64) std::array<uint8_t, 0x20>`（ppu_state.h:37 / ppu.cpp:409），**单 cache line**。
2. `[0]/[4]/[8]/[0xC]` 是 4 个**不相邻**字节，间距 4，不可一次 32-bit 操作覆盖。
3. PLAN 提议的 `memcpy(&pal0, &PALRAM[0], 4); pal0 |= 0x40404040; memcpy(&PALRAM[0], &pal0, 4)`：
   - **只在第一个 uint32 上操作**（覆盖 PALRAM[0..3]）。
   - **OR 0x40404040 会 set byte 1/2/3 的 bit 6** —— 而原代码只 set byte 0 的 bit 6，bytes 1/2/3 未触。
   - pputile.inc:25 `P[0] = S[pixdata & 0xF]` 直接把带 bit 6 的 PALRAM byte 写入 XBuf；后续 CopySprites 用 `& 64` 检查 priority。
   - **结果**：PALRAM[1/2/3] 在 RefreshLine 期间被 spurious 打上 priority 标记 → 渲染时 palette 1/2/3 的 BG 像素被错误识别为「背景优先」，sprite 合并行为偏离。
4. 测试场景（5 manual）会出现 SMB1 屋顶砖块、SMB3 草地区域、Contra 雷达框等像素差异 —— **属于 silent corruption** 类 bug，必须避免。
5. **结论**：保留 4 个 byte RMW 不动，仅加 `static_assert` 与文档。

**风险**: <1%（与 PLAN 一致）。

### P2-3（DS-4）`SPRBUF` 类型化为 `SPRB[64]`

**改动**:
1. `src/ppu.h` 上提 SPRB struct 定义（带 `static_assert(sizeof == 4)` + `static_assert(alignof == 1)` 守卫）。
2. 把 `extern uint8 SPRBUF[0x100]` 改为 `extern SPRB SPRBUF[64]`。
3. `src/ppu.cpp:109` 把 `uint8 SPRBUF[0x100]` 改为 `alignas(64) SPRB SPRBUF[64]`。
4. `src/ppu_rendering.cpp` 移除局部 SPRB typedef（重复定义已被上提版本吸收）。
5. 3 处 call site 替换：
   - ppu_rendering.cpp:857-859（`if (MMC5Hack && geniestage != 1)` 分支）：`memcpy(&tmp, &dst, 4); memcpy(&SPRBUF[ns<<2], &tmp, 4)` → `SPRBUF[ns] = dst;`
   - ppu_rendering.cpp:922-924（else 分支）：同上。
   - ppu_rendering.cpp:957（RefreshSprites 内）：`reinterpret_cast<SPRB*>(SPRBUF) + numsprites` → `&SPRBUF[numsprites]`。

**实现要点**:
- SPRB 自然对齐 1（4 个 uint8_t），sizeof = 4 —— 与 `uint8 SPRBUF[0x100]` 字节布局 byte-for-byte 一致（offset 0 = ca[0]，1 = ca[1]，2 = atr，3 = x）。
- `static_assert` 守护未来字段添加 / 重排。
- 64-byte 对齐确保 `SPRBUF[64]` 跨 4 个 cache line，对齐 fetcher 常见 stride。

**风险 / 审计（PLAN §二 DS-4 / §十七.1 F12 / F13）**:
- `reinterpret_cast<SPRB*>(SPRBUF)` 替换为 `&SPRBUF[]`，消除一处的 `reinterpret_cast` UB 疑虑。
- `SPRBUF[ns] = dst` 的 struct 赋值在类型系统保证 byte layout 与 v1.0 相同；调用方不再需要 memcpy 转换。
- `alignas(64)` 提升 fetch 局部性（每次取 4 字节，跨 64 字节边界不对齐导致 L1 split-load 概率下降）。

### P2-4（MICRO-5）`runppu` 冗余 modulo 移除

**审计结论: 已由 Phase B 完成**：
- **P1-3** (Phase B, commit `e20dfbc`) 已落地 `runppu(int x)` 的 wrap-around branch:
  ```cpp
  int c = ppur.status.cycle + x;
  if (c >= ppur.status.end_cycle) c -= ppur.status.end_cycle;
  ppur.status.cycle = c;
  ```
- **P1-4** (Phase B, 同 commit) 已落地 `FCEU_ALWAYS_INLINE inline void runppu1_inline() noexcept`，BGData::Read 内 8 处 `runppu(1)` 已替换为 `runppu1_inline()`。
- 全树 `ppur.status.cycle = …% end_cycle` 搜索为 0 命中 —— 冗余 modulo 全部消失。
- **本 PR 无新增代码**；任务标记 completed 因前置 PR 已完成。

**风险**: 等同 P1-3 + P1-4（低）。

### P2-6（DS-1）`pshift[2]` 本地化

**改动**:
- `src/ppu_rendering.cpp:RefreshLine` 入口：
  - 把
    ```cpp
    uint32 (&pshift)[2] = fceu11::g_ppu.bg_latch();
    uint32 &atlatch     = fceu11::g_ppu.bg_latch_h();
    ```
  - 替换为：
    ```cpp
    uint32_t pshift_local[2] = { fceu11::g_ppu.bg_latch()[0],
                                  fceu11::g_ppu.bg_latch()[1] };
    uint32_t atlatch_local   = fceu11::g_ppu.bg_latch_h();
    uint32 (&pshift)[2] = pshift_local;
    uint32 &atlatch     = atlatch_local;
    ```
- `RefreshLine` 末尾（`#undef vofs` / `#undef RefreshAddr` 块后）添加：
  ```cpp
  fceu11::g_ppu.bg_latch()[0] = pshift_local[0];
  fceu11::g_ppu.bg_latch()[1] = pshift_local[1];
  fceu11::g_ppu.bg_latch_h()  = atlatch_local;
  ```

**实现要点**:
- `pshift` / `atlatch` 是 `pputile.inc` 内循环使用的别名，绑定到 `pshift_local` / `atlatch_local` 后宏代码无需变更。
- `pshift_local` / `atlatch_local` 是 stack 局部，编译器可自由放入寄存器；`(pshift[0] <<= 8)` 这类取址操作仍合法（栈对齐 + 自然位置）。
- 函数末尾 write-back 一次性 3 store，把内存语义对外保留正确。

**风险 / 审计（PLAN §二 DS-1 / §十七.4）**:
- `pshift_local[]` 由编译器决定 stack slot 还是寄存器；大多数情况 `pshift[0]` / `pshift[1]` 编译为寄存器加载，但若寄存器压力高时落栈仍正确。
- 32 位循环内访问 `pshift[0]` 由 8 处 pputile.inc:21/77/78/80-81/115-136 决定；编译器 CSE 这些访问。
- write-back 顺序在函数末尾，所有 caller 通过 `g_ppu.bg_latch*` 看到的最终状态与改动前等价。

| 维度 | Phase A | Phase B | Phase C |
