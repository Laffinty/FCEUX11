## 1. 问题诊断

### 1.1 根因确认

551 个 stuck ROM 的根因是 **PPU VBlank NMI 时序偏差**。证据：
- 同一 PC 地址出现在多个 mapper 中（0xC05C 出现在 mapper 0/2/64）
- 94.4% stuck PC 在 0x8000-0xFFFF（标准 ROM 空间）
- 经典游戏受影响（超级玛丽、魂斗罗、洛克人、最终幻想）
- blargg ppu_vbl_nmi 测试确认 6/9 子测试失败

### 1.2 当前 NMI 时序流

```
sl 241, cycle 0  →  PPU_status |= 0x80 (VBL flag set)
      +5 dots    →  X6502_Run(5) (CPU budget, no PPU advance)
      after      →  TriggerNMI() (_IRQlow |= 0x080, nmi_fresh = true)
      boundary+1 →  dispatch_irq: nmi_fresh=true → defer (0 cycles)
      boundary+2 →  dispatch_irq: nmi_fresh=false → dispatch NMI (7 cycles)
```

**NMI 延迟**: 5 PPU dots + 2 instruction boundaries ≈ 2-3 CPU instructions after VBL

### 1.3 Blargg 失败清单

| 子测试 | 状态 | 根因 | 优先级 |
|--------|------|------|--------|
| 01 - VBL basics | PASS | — | — |
| 03 - clear time | PASS | — | — |
| 04 - NMI control | PASS | — | — |
| **02 - set time** | FAIL 0x01 | VBL flag 在 cycle 0 设置，硬件应在 cycle 1 | **高** |
| **05 - NMI timing** | FAIL 0x01 | NMI dispatch 延迟漂移（per-frame phase drift） | **高** |
| **06 - suppression** | FAIL 0x01 | $2002 读取抑制窗口不精确 | **高** |
| 07 - NMI on timing | FAIL 0x01 | $2000 写入后 NMI 使能时序 | 中 |
| 08 - NMI off timing | FAIL 0x01 | $2000 写入后 NMI 禁用时序 | 中 |
| 10 - even/odd timing | FAIL 0x03 | 偶/奇帧跳过周期时机不对 | 低 |

## 2. 修复计划

### Phase A: VBL flag cycle 0→1 移位（vbl_02_set_time）

**问题**: VBL flag 在 sl 241 cycle 0 设置，硬件应在 cycle 1。  
**代码位置**: `src/ppu_rendering.cpp:1627`  
**当前代码**:
```cpp
PPU_status |= 0x80;  // line 1627, at sl 241 cycle 0
```
**修复方案**: 在 VBL flag 设置前运行 1 个 PPU dot（推进 PPU 到 cycle 1）：
```cpp
runppu(1);  // advance PPU to cycle 1
PPU_status |= 0x80;  // now at sl 241 cycle 1
```
**影响**: 帧长度从 6820 变为 6819 dots。需要验证 blargg vbl_01_basics 是否仍 PASS。  
**预期收益**: 修复 vbl_02_set_time，可能影响 ~50 stuck ROM。  
**风险**: 中（帧长度变化可能影响其他测试）

### Phase B: NMI 延迟精确化（vbl_05_nmi_timing）

**问题**: NMI dispatch 延迟存在 per-frame phase drift。  
**代码位置**: `src/ppu_rendering.cpp:1662-1685`  
**当前代码**:
```cpp
if (VBlankON) {
    const int nd = e1_nmi_delay();  // 5 PPU dots
    if (nd > 0) X6502_Run(nd);      // CPU budget, no PPU advance
    if (!vbl_set_suppressed) TriggerNMI();
}
```
**问题分析**: `X6502_Run(nd)` 授予 CPU 预算但不推进 PPU。这导致 NMI 触发点相对于 PPU 周期不固定 — CPU 指令边界的位置取决于之前执行的指令，导致每帧的 NMI 触发时机漂移。  
**修复方案**: 使用 `runppu(nd)` 替代 `X6502_Run(nd)`，让 PPU 和 CPU 同步推进。这会改变帧长度（从 6820 变为 6820+nd dots），但 NMI 触发点相对于 PPU 周期会更精确。  
**备选方案**: 保持 `X6502_Run(nd)` 但调整 nd 值，使其与 CPU 指令边界对齐。  
**预期收益**: 修复 vbl_05_nmi_timing，可能影响 ~100 stuck ROM。  
**风险**: 高（帧长度变化可能影响 blargg vbl_01_basics 和其他已通过测试）

### Phase C: VBL-set 抑制窗口精确化（vbl_06_suppression）

**问题**: $2002 读取的抑制窗口（sl 240 cycle 340）可能不完全匹配硬件。  
**代码位置**: `src/ppu.cpp:626-630`  
**当前代码**:
```cpp
if (rsl == 240 && rcy == 340) {         // 1 dot before VBL set
    fceu11_ppu_mark_vbl_set_suppressed();
} else if (rsl == 241 && rcy <= 1) {    // at or 1 dot after VBL set
    X6502_IRQEnd(FCEU_IQNMI);           // cancel pending NMI
}
```
**修复方案**: 需要根据 blargg vbl_06 的具体测试逻辑调整窗口。可能需要：
1. 扩展抑制窗口到 sl 240 cycle 339-341
2. 调整 NMI 取消逻辑的时机  
**预期收益**: 修复 vbl_06_suppression，可能影响 ~30 stuck ROM。  
**风险**: 中

### Phase D: NMI 使能/禁用时序（vbl_07/08）

**问题**: $2000 写入后 NMI 使能/禁用的时序不精确。  
**代码位置**: `src/ppu.cpp` ($2000 写入处理) + `src/ppu_rendering.cpp` (VBlankON 检查)  
**分析**: 当游戏写入 $2000 使能 NMI（bit 7）时，如果 VBL flag 已经设置，NMI 应该在特定延迟后触发。当前实现可能在写入时立即检查 VBL flag，而不是等待下一个 PPU 周期。  
**修复方案**: 在 $2000 写入处理中，如果 VBL flag 已设置且 NMI 刚被使能，需要延迟 NMI 触发到下一个 CPU 指令边界。  
**预期收益**: 修复 vbl_07/08，可能影响 ~50 stuck ROM。  
**风险**: 中

### Phase E: 偶/奇帧时序（vbl_10_even_odd_timing）

**问题**: 偶/奇帧跳过周期的时机不对（"clock skipped too late"）。  
**代码位置**: `src/ppu_rendering.cpp` (帧循环)  
**分析**: NES PPU 在奇数帧跳过 1 个 PPU 周期（从 341 变为 340 dots/scanline）。当前实现可能在错误的 scanline 或 cycle 执行跳过。  
**修复方案**: 调整偶/奇帧跳过的时机，确保在 pre-render scanline (sl 261) 的 cycle 340 执行跳过。  
**预期收益**: 修复 vbl_10，可能影响 ~20 stuck ROM。  
**风险**: 低
