## 1. What was built

Phase 1 produces a **pure-Rust 2C02 PPU state machine** in a new
workspace crate `fceux11-ppu`. It contains zero the `C++` code or FFI;
the only consumer of the C ABI in Phase 2 will be `ppu_rust_bridge.cpp`,
which the existing C++ PPU will delegate to via the
`FCEUX11_RUST_PPU=OFF/ON` toggle.

## 4. State machine details worth flagging

These decisions show up in code review and might surprise the next
implementer. They're documented here so Phase 2/3/4 don't reverse them
without an explicit reason.

### 4.1 Even/odd skip is a double-advance

`tick_dot` at `(sl -1, dot 340)` with rendering on and `odd_frame == false`
performs **two** `advance()` calls instead of one: (-1, 340) → (0, 0) →
(0, 1). The intermediate (0, 0) tick never fires — its events (sprite
eval, copy_horizontal) are intentionally skipped on even frames per
nesdev's "skip one dot" semantics.

### 4.2 `NTSC_SCANLINES = 262`, not 263

The wrap condition is `next_sl >= NTSC_SCANLINES` (i.e. `>= 262`). This
gives scanline indices `-1..=261` (263 values) with `next_sl == 262`
triggering the wrap. Easy off-by-one trap; the inline test
`suppression_resets_at_frame_boundary` pins the boundary.

### 4.3 `$2002` read preserves sprite-0 hit but clears VBL

Reading `$2002` clears only the VBL flag (bit 7) and resets the
write-toggle echo. It does **not** clear sprite-0 hit (bit 6) or sprite
overflow (bit 5) — those are renderer-managed latches. The
`status_read_echoes_write_toggle_and_clears_vbl` test pins this.

### 4.4 OAM DMA is synchronous in Phase 1

`PpuState::start_oam_dma` performs the full 256-byte copy in one call,
mirroring `fceu11_cpu_trigger_oam_dma` / `DMW()` loops in C++ that run
across 256/2 = 128 CPU cycles. Phase 3 will replace this with a
per-cycle async pump driven by `NesScheduler`.

### 4.5 Sprite eval is collapsed to dot 0

Real hardware evaluates sprites across dots 0..=63 of each visible
scanline, with subtle per-dot quirks (priority rotation, sloppy overflow
detection). Phase 1 collapses the entire eval to a single call at
`(sl, dot 0)`. Phase 4 sharpens this when PPU precision becomes the
focus.

### 4.6 No cbindgen, no FFI symbols

`Cargo.toml` declares `crate-type = ["rlib"]`. There is no `cbindgen.toml`,
no `build.rs`, no `extern "C"` symbols in the public API. Phase 2 will
add these when `ppu_rust_bridge.cpp` needs to call into Rust.

## 5. What was *not* done (deliberately)

Per the plan §1.2, the following Phase 2+ items are **explicitly out of
scope** for Phase 1:

- No C++ source touched. `src/ppu.h`, `src/ppu.cpp`,
  `src/ppu_rendering.cpp`, `src/ppu_class.h` are byte-for-byte
  identical to commit `4b63d89`.
- No CMake option `FCEUX11_RUST_PPU` added. `src/rust/CMakeLists.txt`
  and `src/rust/build.rs` unchanged.
- No `cbindgen` hook. The cbindgen list in `build.rs` still enumerates
  the seven Phase-0 crates only.
- No `src/ppu_rust_bridge.{h,cpp}`. The C++ side continues to call into
  the legacy `Ppu` class for every PPU cycle; the new Rust crate is a
  parallel isolated state machine.
- No CPU sub-instruction stepping. `NesScheduler` (plan §6.2) is a
  Phase 3 deliverable.
- No frame buffer / pixel output. Phase 1 models timing + state only;
  pixel rendering remains entirely C++ (`ppu_rendering.cpp`'s BG/sprite
  fetch hot path).

## 6. Phase 2 hooks

Phase 2 (`FCEUX11_RUST_PPU=ON` switch + FFI + golden frame bit-exact)
should land without changing any of the Phase 1 types' public layout:

- `PpuBus` trait already declares the full hook surface; `ppu_rust_bridge.cpp`
  just installs real C++-side implementations.
- `tick_dot` is already a free function over `&mut PpuState + &mut dyn PpuBus`,
  so the bridge can call it from a tight render loop without FFI thrash.
- `TickOutcome::nmi_asserted` is the signal Phase 3's CPU microstepper
  will consume for the NMI latch.

The headline Phase 2 hard gate — `golden frame 0-pixel diff` — depends
on `chr_rom` reads through `PpuBus::read`, which the trait already
provides. No additional trait surface should be needed.
