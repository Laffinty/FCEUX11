# hotfix2 — Manual Smoke-Test Scenarios

**Date**: 2026-07-16
**Branch**: `hotfix2`
**Status**: 4/5 automated (Phase A verify report covers most visual verification)

> **Note**: These 5 manual scenarios are **interactive gameplay** tests — they require a human at the keyboard watching a window. They cannot be automated into CTest because they require visual judgment + emulator GUI session. The `ppu_frame_diff_test` (5/5 mappers pass, 0-pixel diff vs hotfix1 goldens) and `mapper_byte_diff_test` (169 mappers, 0-byte diff) cover the **byte-level** equivalents of these scenarios; this document records what a human verifier would look for in the final GUI session.

## Why these scenarios are listed

PLAN §十一.2 per-Phase focus lists 5 manual scenarios per phase. They target categories of PPU rendering where byte-level golden comparison may not catch visual regressions:

| # | ROM | Why this matters |
|---|-----|------------------|
| 1 | **SMB1** (`smb1.nes`) | Sprite-dense — 5+ sprites overlapping per scanline; tests `RefreshSprites` two-stage LUT (P0-1) |
| 2 | **SMB3** (`smb3.nes`) | Sprite-dense + large sprite limit (`maxsprites=64` mode); tests X-bucket overflow fix + P0-2 |
| 3 | **Contra** (`contra.nes`) | Horizontal scroll + parallax; tests pshift / RefreshLine inner loop (P2-6) |
| 4 | **Batman** (`batman.nes`) | Multi-sprite overlap with sprite-0 hit; tests `RefreshSprites` SP_BACK/H_FLIP branches |
| 5 | **Kirby** (`kirby.nes`) | OAM boundary (sprite 0 hit edge cases) |
| 6 | **Micro Machines** (`micromachines.nes`) | Split-screen window + scrolling; tests `RefreshLine` MMC5 paths + windowing |

> **Note**: SMB3 is added per Phase A verify report's plan for sprite-limit coverage; the original plan listed SMB1/SMB3/Contra/Batman/Kirby/MicroMachines (6 scenarios in §十一.1.1). Either SMB1 or SMB3 should be picked for the final GUI smoke (they exercise the same path).

## What the human verifier should look for

### Per-scenario pass criteria (visual)

For each ROM, the human should:

1. Launch with `fceux11.exe smb1.nes` (etc.)
2. Play through the first 60 seconds (one frame at ~16.67 ms = 3600 frames)
3. **Compare visually** to the hotfix1 binary on the same scene:
   - No sprite flicker or ghost pixels
   - No palette anomalies (especially mid-frame GRAYSCALE toggle for FF1 — see below)
   - No screen tearing
   - No audio glitches (sound buffer underrun = audible pop)
4. **Compare numerically**: in-game FPS counter or `tracy` profile should show identical or better frame timing than hotfix1

### FF1 polygon effect (GRAYSCALE mid-frame toggle)

This is the **special case** for P1-2 (`pal_mask` hoist):

1. Launch `Final Fantasy (USA).nes`
2. Encounter the polygon / airship transition effect (mid-frame GRAYSCALE bit flip)
3. Verify grayscale palette inverts correctly on each transition

The `pal_mask` is hoisted to `RefreshLine` entry, but `PPU[1] & 0x01` can change inside mapper tick handlers — Phase B's design assumes the value is valid until next `RefreshLine`. **Manual smoke confirms no regression** here.
