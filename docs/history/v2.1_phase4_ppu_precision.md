## 2. Algorithm

For each of 32 visible tiles (with 2 pre-loads and 1 next-tile
preload = 34 total iterations per scanline):

1. **Render 8 pixels** of the current tile using the high 8 bits of
   `bg_pshift[0..2]` (the tile fetched 2 iterations ago) and the
   per-pixel attribute from the `atlatch` quirk accumulator.
2. **Fetch** the next tile's NT byte, AT byte, PT_LO byte, PT_HI byte.
3. **Update atlatch**: `atlatch = (atlatch >> 2) | (cc << 2)`.
4. **Shift pshift**: `pshift[0..2] <<= 8; |= pt_lo, pt_hi`.
5. **Increment v** (coarse X with horizontal nametable flip).

The first two iterations (X1=0,1) skip the render step (pre-load).
The 33rd-34th are the next-tile pre-load for the next scanline.
`bg_pshift` and `bg_atlatch` persist across scanlines.

### 2.1 The `atlatch` quirk

The C++ `pputile.inc` algorithm uses a `u32 atlatch` that accumulates
two attribute quadrants across iterations: the current tile's quadrant
in bits 0..1 and the next tile's quadrant in bits 2..3, with
`atlatch >>= 2; atlatch |= cc << 2` per iteration. The render uses
`ppulut3[XOffset | (atlatch << 3)]`, which extracts pixels 0..3 from
bits 0..1 of atlatch (the current tile's quadrant) and pixels 4..7
from bits 2..3 (the next tile's quadrant). This is a quirk of the
FCEUX algorithm: a tile's last 4 pixels use the NEXT tile's
attribute. The Rust renderer replicates this for bit-exact matching
with the golden frames generated by the C++ algorithm.

### 2.2 Mirroring + v register + CPU driving

- **Mirroring** (5 modes): `map_nametable_addr(v, mode)` applies
  horizontal / vertical / single-low / single-high / four-screen.
- **v register** advances correctly across scanlines:
  `increment_fine_y` at the end of each visible scanline (sl N dot
  256), and `copy_vertical` at sl -1 dot 280 (pre-render reset).
- **CPU driving**: the bridge calls `cpu_instance().run(89342)` to
  drive the CPU for one frame's worth of cycles before the Rust PPU
  advances its own state. This wires the CPU writes to the Rust PPU
  through the bridge's $2000-$2007 handlers (re-installed after
  FCEUPPU_Power to override the C++ PPU's A200x/etc.).

### 3.4 NROM bit-exact golden frame: **DEFERRED (default-background gap)**

Running `fceux11_ppu_frame_diff_test` with `FCEUX11_RUST_PPU=ON`:
all 5 ROMs (nrom, mmc1, mmc3, vrc6, mmc5) produce a frame whose
first 16 bytes are `00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00`
instead of the golden's `80 80 80 80 80 80 80 80 ...`.

**Root cause**: the synthetic NROM test ROM
(`tests/fixtures/mapper_nrom.nes`) is a minimal NOP loop that does
NOT write to any PPU register, so the PPU's default background
palette index is what shows on screen. The C++ PPU's rendering path
fills XBuf with `0x80` during the `ppudead` window (the first few
frames after power-on, see `src/ppu_rendering.cpp:1224-1229`), and
this fill persists for the entire 60-frame test because the NOP-only
game code never updates the palette. The Rust PPU's `render_scanline`
correctly produces the palette-indexed color (0x00 when `palette[0] = 0`
and no emphasis is set); the deemphasis / ppudead fill is a C++ PPU
default that the Rust renderer doesn't replicate.

**Fix** (one of):
1. Have the Rust renderer's framebuffer initial-fill (or a
   `ppudead` early-frame counter in the C++ bridge) match the C++
   PPU's `0x80` fill.
2. Update the test ROM to actually write to the PPU (LDA #imm /
   STA $2001) so the rendering exercise is the actual algorithm
   rather than the legacy default fill.
3. Run the Rust PPU on a real game ROM (e.g. Super Mario Bros.)
   and validate the rendering against a frame snapshot.

## 4. What was *not* done (deliberately / deferred)

Per the plan Â§ Phase 4, several items remain:

1. **Sprite 0 hit / sprite overflow per-pixel/per-cycle timing** â€?   secondary OAM is populated by `state.eval_sprites` (sl 0..239
   dot 0), but sprite pixels are not composited in `render_scanline`
   (BG-only). Sprite 0 hit detection requires per-pixel overlap
   checks against BG, and sprite overflow requires per-cycle
   sprite-eval quirks. Deferred to a follow-on phase.
2. **DMC DMA + OAM DMA interleaving** â€?OAM DMA pump is in place
   (256 bytes / 256 CPU cycles), but DMC DMA (which steals CPU
   cycles for the APU's delta modulation channel) is not modeled.
3. **$2004 / $2005 / $2006 open-bus read behavior** â€?FFI returns 0
   for these (Phase 2 placeholder). Correct behavior is "last value
   placed on the CPU data bus" (open bus decay).
4. **Per-cycle CPU/PPU interleave on the C++ side** â€?Phase 3 wired
   `fceux11_ppu_tick_one_cpu_cycle` but the C++ `FCEUPPU_Loop`
   Rust-PPU branch still calls `cpu_instance().run(89342)` once per
   frame rather than per-cycle. The 30-line per-cycle patch is
   documented in Phase 3 Â§10.2 but not yet landed.
5. **ppudead / default-background fill in Rust** â€?the C++ PPU's
   `memset(XBackBuf, 0x80, 256*256)` during ppudead is not
   replicated in the Rust renderer. For the synthetic NROM test ROM
   this manifests as 0x00 vs the golden 0x80.

## 6. Path to Phase 5 (savestate) readiness

The v2.1 plan Â§ Phase 5 requires the following preconditions
(`golden_savestate_test` PASS, `savestate_regression_rust_smoke`
PASS, `mapper_byte_diff_rust_smoke` PASS, manual verification of
old `.fc0` loading). Phase 4's completion is a precondition for
Phase 5, but Phase 5's specific work is:

1. **Rust PPU snapshot/restore FFI** â€?`fceux11_ppu_snapshot` /
   `fceux11_ppu_restore` exports the full `PpuState` (registers,
   OAM, secondary OAM, v, t, pshift, atlatch, frame counters).
2. **C++ LegacyPpuMirror** â€?the C++ `ppu_state.cpp` already
   serializes the legacy `PPUREGS` / `NTARAM` / `PALRAM` / `SPRAM`
   / `v` / `t` / `XOffset` / `vtoggle` etc. chunks (see
   `FCEUPPU_STATEINFO` in `src/ppu_state.cpp:55-66`). The bridge
   needs to read these on load and populate the Rust PPU's state.
3. **C++ RPU1 extension chunk** â€?a new SFORMAT entry
   `{ ppu_rust_data, sizeof, "RPU1" }` that wraps the Rust PPU's
   internal state (pshift, atlatch, sprite_shift, etc.) for
   round-trip integrity.
4. **`ppu_state.cpp` / `state.cpp` updates** â€?call the bridge's
   snapshot/restore on `FCEUSS_Save` / `FCEUSS_Load` hooks.
