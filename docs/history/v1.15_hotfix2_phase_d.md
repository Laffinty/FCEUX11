## 三、各 PR 实现要点

### P3-1（DS-5）`bitrevlut` → `constexpr std::array`

**改动**:
- 替换 `template<typename T, int BITS> struct BITREVLUT { ... }; BITREVLUT<uint8, 8> bitrevlut;`（约 28 行，含 `new[]` 分配 + 递归 doubling 填充 + `T operator[](int)`）为：
  ```cpp
  alignas(64) inline constexpr std::array<uint8_t, 256> kBitRevLUT = []{ /* 8-bit reversal */ }();
  static constexpr const std::array<uint8_t, 256>& bitrevlut = kBitRevLUT;
  ```
- `bitrevlut[...]` 调用点（FCEUX_PPU_Loop 2 处）零改动 —— `std::array::operator[]` 与旧 `BITREVLUT::operator[]` 返回类型一致（`uint8_t`，按值）。

**风险 / 审计（PLAN §二 DS-5 / §十七.1）**:
- 字节级映射与原 BITREVLUT recursive-doubling 一致（involution + full-coverage 测试覆盖）。
- `inline constexpr`（C++17）+ `alignas(64)` 在 .rodata 落地，零堆分配；MSVC /O2 /GL 下不会触发 atexit teardown 顺序问题（OS 兜底消失）。
- 测试 `P3_1BitRevLUT.MatchesByteSwap` / `IsInvolution` / `CoversAll256` 全过（531 检查 / 0 失败）。
- 文件作用域 `static` 不影响 ODR —— `bitrevlut` 在原代码中也仅在 ppu_rendering.cpp 使用（grep 验证）。

### P3-2（MICRO-1）`ppudead` 期间 XBuf memset 单次

**改动**:
- `src/ppu_rendering.cpp` 文件作用域新增 `static bool s_ppudead_cleared = false;`（紧邻 `norecurse`，保持模块边界清晰）。
- `FCEUPPU_Loop` 的 `if (ppudead) { ... }` 分支：
  ```cpp
  // 原: memset(XBuf, 0x80, 256 * 240);  // 每帧 60 KiB
  // 新:
  if (!s_ppudead_cleared) {
      memset(XBuf, 0x80, 256 * 240);
      s_ppudead_cleared = true;
  }
  ```
- `else` 分支（ppudead 退出）追加 `s_ppudead_cleared = false;`，为下一个 power-on cycle 重新装填 leading-edge detector。

**风险 / 审计**:
- ppudead 通常持续 2-3 帧（NES power-on stabilization），节省 60 KiB memset × 1-2 帧 = ~120 KiB / power-on。
- `ResetRL(target)` 在 ppudead → 0 的下一帧立即覆盖 XBuf（`memset(target, 0xFF, 256)` 每扫描线），所以 trailing-edge 不显式清零不会污染下一帧。
- 调试器 / Game Genie 在 ppudead 期间写 XBuf 的行为 **不变**（leading edge 仍清一次，覆盖任何 pre-ppudead 残留）。
- 文件作用域 hoist 是必须的 —— 静态函数变量无法跨 if/else 分支被另一个分支访问。

### P3-3（MICRO-3）`InputScanlineHook` `[[unlikely]]` 守卫

**改动**（3 处 call site）:
- `ResetRL(uint8 *target)`：`if (InputScanlineHook) [[unlikely]] { InputScanlineHook(0, 0, 0, 0); }`
- `RefreshLine` early-exit 分支（同上）
- `RefreshLine` 末尾（同上）

**风险 / 审计**:
- 99%+ 路径 `InputScanlineHook == nullptr`（input.cpp:473 在无 TAS 录制时为 noop）；`[[unlikely]]` 让 MSVC 把分支预测为 false，I-cache layout 偏向非 TAS 路径。
- 对 TAS 用户：分支命中 → 函数指针调用，行为与改动前 byte-for-byte 等价。
- 对调试器：分支命中 → callback；未命中 → 跳过；语义不变。
- 测试 `P3_3InputScanlineHook.NullptrHookIsSafe` 验证 nullptr hook 在守卫下不崩溃。

### P3-4（MAP-2）`norecurse` 守卫收紧

**改动**:
- 删除 RefreshLine 顶部的：
  ```cpp
  static int norecurse = 0;
  if (norecurse) return;
  ```
- 替换为：
  ```cpp
  if (PPU_hook && norecurse) [[unlikely]] {
      return;
  }
  ```
- 把 `static int norecurse = 0;` hoist 到文件作用域（紧邻 `s_ppudead_cleared`），让 dispatcher 设置位（line ~451）+ Hook/HookBGFetch case 清理位（line ~520/~529）共享状态。

**风险 / 审计**:
- **正确性**：原 `if (norecurse) return;` 对所有路径付费；新条件 `PPU_hook && norecurse` 仅在 hook 路径上付费。
  - 非 hook 路径（>99% 帧）：`PPU_hook == nullptr`，短路求值跳过 `norecurse` 读，零成本。
  - Hook 路径第一次进入：`PPU_hook != nullptr`，`norecurse == 0`，不返回；dispatcher 之后将 `norecurse = 1`，内层循环跑 hook（可能递归调用 RefreshLine）。
  - Hook 路径递归进入：`PPU_hook != nullptr`，`norecurse == 1`，返回 —— 与原行为等价。
- dispatcher 与 case 体的 `norecurse = 1` / `norecurse = 0` 全部保留。
- 文件作用域 `static` hoist 是因为 RefreshLine 函数体前的 `static int norecurse` 块作用域不可被文件末尾的 `else` 触及 —— 已通过编译器 C2065 错误验证（已修）。

### P3-5（MAP-3）`vnapage` 缓存 review（仅文档）

**改动**:
- `src/pputile.inc:46` 在 `C = vnapage[(RefreshAddr >> 10) & 3];` 前添加 25 行诊断注释。
- 注释总结：
  - 选项 A（保留现状）：MSVC /O2 + Clang -O2 均已 CSE；NTARAM 2 KiB 连贯 + MMC5fill 1 KiB 跨 4 个指针对齐的 cache line，无 I-cache 抖动风险。**选 A**。
  - 选项 B（独立 `nt_ptrs[4]`）：与 boards/*.cpp / ppu_class.cpp 已有的 vnapage 同步逻辑重复，零可测增益。
  - 选项 C（`_mm_prefetch` RefreshLine 入口预取）：仅在 nametables 被 evict 后有帮助；warm NTARAM 在 L1 时纯开销。**留 v1.16 评估**。

**风险**: 无代码改动，零回退风险。
