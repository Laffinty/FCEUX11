## 1. 落地内容

### 1.1 新增行为测试 test_save_load_restores_rust_ppu_state

靶标 `savestate_core_test`，流程：

1. `emulate_n(8)` 后取 `saved = snap_rust_ppu()`，再 `FCEUSS_SaveMS` 存档；
2. 用 `fceu11::g_bus.write(0x2000..0x2007, ...)` 走与 6502 相同的 CPU 总线路径写 PPU 寄存器；
3. 取 `advanced`，断言与 `saved` 不同（证明 accessor 读到的是活的 Rust 状态）；
4. `FCEUSS_LoadFP` 载入，取 `after`，与保存点逐项比对：寄存器文件（2000-2003）、OAM 前 16 字节、scanline/dot、v/t/fine_x/write_toggle/data_bus、整个 256 字节主 OAM。

### 1.2 为什么要在 save 与 load 之间写寄存器

第一版沿用「save → 跑 5 帧 → load」：nestest 在这 5 帧里没有写任何 PPU 寄存器，寄存器 / OAM / 锁存三组断言因此恒真（负向对照下照样全绿），只有 scanline/dot 有区分度。改为主动写入后，四组断言都建立在「载入前状态确定不同」之上。

### 1.3 负向对照（本批关键证据）

临时把 `bridge_state_apply_to_rust()` 短路成 `return;`（源码已还原，未进 commit），重跑 `do_build.ps1`：

| 观测 | 值 |
|------|-----|
| `savestate_core_test` | FAILED，37 PASS / 1 FAIL |
| 唯一红项 | Rust PPU raster (scanline/dot) matches the save point after load |
| 其余 40 项 ctest | 全部不变（39 PASS / 1 SKIP） |

即 ctest 总计 40/41，唯一失败就是本条：该断言确实依赖「载入把值推回 Rust」。

### 1.4 评估后放弃的一项断言（记录在案）

同批曾尝试「save → 跑 3 帧 → load → 再跑 3 帧 → 帧缓冲 FNV-1a 哈希一致」。负向对照下它照样通过：nestest 在该区间不渲染（帧缓冲为常值），该断言对「load 是否恢复 PPU」没有区分度，因此删除而不是留作假信号。`tests/fixtures/` 除 nestest 外均为最小 mapper fixture，故不另找 ROM 替代。
