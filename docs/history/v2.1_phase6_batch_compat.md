```cpp
    if (g_ppu_state == nullptr) return;

void ppu_rust_bridge_cpu_write(uint32_t addr, uint8_t value) {
    if (g_ppu_state == nullptr) return;

    // Phase 6.1.b: B2000 rising-edge NMI-enable port.
    //   if (!(PPU[0] & 0x80) && (V & 0x80) && (PPU_status & 0x80))
    //       TriggerNMI2();  (C++ reference: src/ppu.cpp:958-962)
    if (addr == 0x2000) {
        const uint8_t old_ctrl = fceux11_ppu_get_register_state(g_ppu_state, 0);
        fceux11_ppu_cpu_write(g_ppu_state, static_cast<uint16_t>(addr), value);
        const uint8_t status = fceux11_ppu_get_register_state(g_ppu_state, 2);
        if (!(old_ctrl & 0x80) && (value & 0x80) && (status & 0x80)) {
            TriggerNMI2();
        }
    } else {
        fceux11_ppu_cpu_write(g_ppu_state, static_cast<uint16_t>(addr), value);
    }
    if (addr == 0x2007) {
        bridge_refresh_windows();
    }
}
```

### §6.1.e.v3.2 Mesen 参考确认

§6.1.e 计划文档引用"Mesen 参考 + blargg 校准"作为 dot-0 的论据，但 Mesen 实际实现查证（搜索结果）：

```cpp
// Mesen-style PPU per-cycle execution
if (_scanline == 241 && _cycle == 1) {
    SetFlag(StatusFlags::VerticalBlank);  // VBL at sl 241 dot 1
    if (_nmiOutput) {
        _nmiDelay = 1;
    }
}
```

**Mesen 实际用 dot 1，不是 dot 0**。blargg vbl_set_time ROM 校准于 Mesen，所以期望 dot 1。

但 **C++ engine `src/ppu.cpp:609-619` 注释明确说"Working-config VBL flag sets at the sl240→sl241 boundary (cycle 0 of the VBL block)"**——C++ engine 用 dot 0。

这是一个 C++ engine (dot-0) vs Mesen/blargg (dot-1) 的**校准差异**，不是简单"硬件真值"问题。

### §6.1.e.v3.3 4-configuration matrix

为了 isolate root cause，测试了 4 个配置：

| 配置 | frame.rs `dot` | bridge A2002 port | 02-vbl_set_time diag hash | 结果 |
|------|----------------|-------------------|---------------------------|------|
| (a) | dot 1 | 无 port（Phase 5.3 baseline）| — | n/a（先看 dot-0/1 影响） |
| (b) | dot 1 | 6.1.d port（sl 240/340 suppress） | `933AF95A` | FAIL |
| (c) | dot 1 | bridge suppress 改 sl 241/0（修正给 dot-1） | `C4BE5BE4` | FAIL |
| (d) | dot 0 | 6.1.d port（sl 240/340 suppress） | `C4BE5BE4` | FAIL |
| **(e) 最终** | **dot 1** | **移除 port**（净 baseline） | **`4103C340`** | **FAIL** |

**4 个 FAIL 配置的 diagnostic 全部不同**——这不是 1-dot shift 能解释的（那种情况 hash 应相同）。证明 root cause 不在 VBL set dot 选择，也不在 A2002 port。

### §6.1.e.v3.4 Root cause 推断

§6.1.e.v3 调查后定位 **root cause 在 PPU state machine 别处的 timing drift**，不在 §6.1.e / §6.1.d 触及的两块（VBL set dot、A2002 port）。

最可疑候选（需要后续 session 深入调查）：

1. **bridge_trigger_nmi 与 per-dot interleave 的 NMI latch 交互**：`fceux11_run_frame_interleaved`（lib.rs:355-374）每 dot 调用 `take_nmi_direct` → `trigger_nmi` callback → `cpu_run_with_tick`。如果 NMI 在 set dot 后某延迟点被 trigger，可能干扰 blargg 测得的 CPU $2002 read pattern。
2. **CPU/PPU phase 同步**：nestest 在 `sl 241 dot 1` 之前正好跑完某个 CPU instruction，`cpu_run_with_tick` 把 CPU 推进 1 cycle 时可能跨越 read 边界。
3. **`vbl_suppressed_this_frame` 跨帧污染**：frame.rs:152-156 在 `sl -1 dot 340` 清 suppression flag，但如果 timing 漂移导致清 flag 错过，下一帧 VBL set 被错误抑制。

`02-vbl_set_time` ROM 的 inner loop 跑 256 次 read，跨越多帧扫描。任何上述 timing drift 都会让 256-cell pattern 与 ROM 内置预期不匹配。

### §6.1.e.v3.5 Final disposition

经过 4 配置对比，决定采用**配置 (e)**：**dot-1 + 无 A2002 port**。

理由：
1. **匹配 Mesen / blargg 校准**：dot-1 是行业参考实现的标准，避免引入与社区模拟器的不可对比偏差。
2. **避免 A2002 port 的 mapper_mmc1 回归风险**：§6.1.d 加 port 时该回归已被观察到（Phase 5.3 NOTE 明确记录）。
3. **保留 $2008-$3FFF mirror 路由**：vbl_basics subtest 1（`$2002 == $200A`）需要 mirror 才能 PASS；mirror 没有 timing 影响，纯路由。
4. **Nestest goldens 完全回滚到 commit `b06388c`**：byte-identical，0 diff，6.1.e 引入的 churn 归零。

### §6.1.e follow-up.1 设计决策

将 Rust 帧状态机从"pre-render-first"（`-1, 0..=260`，262 行）改为"VBL-first"
（`241..=260, -1, 0..=240`，262 行），匹配 §6.4.3 描述的 C++ 帧边界 `sl 240
→ sl 241`。**所有 (sl, dot) 事件坐标不变**——只改变每帧被访问的顺序。

实现要点：

- `state.rs::PpuState::new()`：初始 `scanline: -1 → 241`
- `state.rs::PpuState::power()`：同上
- `frame.rs::advance()`：wrap 条件 `next_sl >= 261 → 走两条分支`（sl 240 → sl
  241 frame wrap；sl 260 → sl -1 帧内跳转）
- `frame.rs::tick_dot()`：ppudead 路径的 (sl -1, dot 0) VBL set 改为
  (sl 241, dot 0)，ppudead decrement 从 (sl 260, dot 340) 改为 (sl 240, dot
  340)；移除 sl -1 dot 1 VBL clear 的 `ppudead == 0` gate（让 ppudead 帧也
  走自然清除）
- `frame.rs::tick_to()`：max_ticks guard `(NTSC_SCANLINES + 2) *

## §6.2 — Sprite 渲染管线 ✅ 完成 (2026-08-31)

### §6.2.1 设计决策

最终落地的是 **per-scanline batch sprite composition**（而非 §6.2 草稿的 per-dot
`fetch_sprites` / `tick_sprite_pixel` / `compose_sprite_pixel` 三段 API）。原因：
草稿 API 需要把 per-cycle shift register + x-counter 时序接进 `frame.rs`
tick_dot，改动面大且难以在单 session 内验证；batch 模型在
`render_visible_scanline`（BG 写完后）一次性合成精灵像素，对 8x8 / 8x16
标准形状输出与逐周期模型 byte-identical，先解决 batch compat 的 no_video
失败主体，逐周期怪癖（mid-tile reload、left-edge clip、overflow re-scan）
留待后续 sub-task。

`render_sprites_for_scanline`（`src/rust/crates/fceux11-ppu/src/sprites.rs`）：
- 直接扫 primary OAM（绕开 secondary_oam 的 start-of-scanline 时序依赖）
- 8-sprite limit（OAM 顺序）+ 9th+ 置 `sprite_overflow`
- 8x16 tile bit 0 选 pattern table，高 7 位选 tile pair
- priority MUX：attr bit 5 = 0 前景 / 1 背景仅 BG 透明处可见
- sprite 0 hit：前景优先 + BG 不透明 + x 1..=254
- 回写 `state.sprite_shift/attr/x`、`secondary_oam_count`，保持
  `fceux11_ppu_get_*` debug 访问器与 savestate round-trip 自洽

已知简化（详见 sprites.rs 模块注释）：无逐 dot shift register、attr
flip 位（bit 6/7）未生效、left-edge 8-pixel clip 未实现、palette 查找
沿用 BG 写入方约定（0x00-0x0F 区段）。

2. **`bridge_refresh_window_contents_if_dirty()`**——逐页比较指针,仅重拷移动过的页
   （纯 C++ 内存 memcpy,**零 FFI**）。挂在 `bridge_notify_scanline`:该回调在 scheduler
   的 scanline 转换 tick 内触发,**早于**新 scanline 的 dot-0 批量渲染,故上一 scanline
   期间发生的 bank 切换对下一 scanline 可见——与 hblank 期切 bank 的设计意图一致。
   关键约束:notify 回调运行时 Rust scheduler 持有 `StateBox` 可变借用,回调内**禁止**
   再进任何 `fceux11_ppu_*` FFI（重入 = 别名 UB,Phase 5.1 bridge 递归修复同款风险）,
   所以这里只做内容重拷,Rust 侧透过 power 期安装的指针直接看到新数据,无需重推。
3. **`bridge_push_mirror_mode_if_dirty()`**——NT 页模式变化（镜像切换）重算 mirror
   mode 并推送,但推迟到帧边界（`ppu_rust_bridge_run_frame_interleaved` 入口）执行,
   理由同上（回调内不能 FFI）。帧内镜像切换的生效延迟一帧,已记录为已知限制。
4. `bridge_derive_mirror_mode()` 从原 refresh_windows 中提取复用。

**Rust 侧零改动**——渲染器本就每 scanline 透过窗口指针读数据。

**限制**(后续 session 处理,不阻塞):
- MMC5 fill/ex-attribute 模式等非 vpage 语义的取指不在指针比较覆盖内(窗口模型本身的
  已知局限,§6.2.4 同类);
- 渲染器是 batch-per-scanline 模型,scanline 中途的 bank 切换仍按 scanline 起点解析。

### §6.4.2 trace-diff 一致性修复链（§6.3.a.4 A/B 验证的直接产出）

方法:两侧构建(`build/`=RUST_PPU=ON,`build-ab-cpp/`=OFF 新开,见 §6.3.a.4)在

按分歧顺序修复(全部对照 C++ 参考逐条验证):

1. **sprite eval 门控**（首个分歧 = 开机后第 3 号访问,第一次 $2002 读:Rust 0x20 vs
   C++ 0x00）——`frame.rs::tick_dot` 的 `eval_sprites` 此前**无条件**执行;渲染全关

### §6.6.1 起点：根因定位

§6.5 同引擎 baseline 83.95% 之后，`kagamiqa_direct_matrix.json` 的 7 个 FAIL
被认为以 sprite0 hit 时序为主因。本 Session 复现了 `0x8153` 卡死的 SMB family
（`2401_Mario_1.nes`），添加三组临时探针后定位**三个独立的引擎级 bug**——任一
单修都不足以恢复：

- **Bug A — sprite 图案全 0**：`CppBus::peek_chr`（`src/rust/crates/fceux11-ppu/src/ffi.rs:74`）
  是个**返回 0 的桩**。Rust 引擎的 batch sprite 渲染对所有 sprite 图案字节
  读到 0 → 所有 sprite 不可见 → sprite0 hit 永不触发。BG 渲染不受影响
  是因为它走 `chr_window` 指针（`bridge_refresh_windows`），与 `peek_chr` 是
  两条独立路径。
- **Bug B — OAM DMA 读 PPU 空间**：`tick_oam_dma` 通过 `CppBus::read`
  → `bridge_bus_read` → `FFCEUX_PPURead` 读 DMA 源字节，但 $4014 需要读
  **CPU 空间** `$xx00-$xxFF`（C++ 引擎用 `X6502_DMR`）。OAM 一直被填 PPU 空间
  数据而不是 CPU RAM。`kagami_qa_blargg_runner` 不直接验证 OAM 但**所有**
  Rust 引擎 sprite 渲染从此就是错的——Bug A 之前被掩盖了。
- **Bug C — sprite0 hit 无 per-pixel 时序、无 per-frame 清除**：batch
  renderer 在 dot 0 一次性完成扫描线渲染并直接置 `state.sprite0_hit = true`，
  但 (1) 状态机不该在 dot 0 锁存（应该是 hit 像素 dot x+1），(2) 标志没有在
  pre-render dot 1 清除，(3) 优先级位**错误地**被用于门控 hit（硬件 + C++
  `CheckSpriteHit` 参考都不门控），(4) BG 透明判定使用“低 4 位全 0”的启发式
  会误判非透明像素（如 0x30 白色被认作透明）。

## §6.6.bis — Session B 调研结论（mapper IRQ counter 时序复审，2026-09-02，no-implementation）

### 发起

按 plan § Phase 6 优先级 2，本 Session 计划修复 BROKEN 178 第二主力的
mapper IRQ counter 时序偏差（MMC3/VRC/Namco）。目标 30+ mapper 4 卡死

### §6.6.bis.1 数据反驳：mapper IRQ counter 不是单点根因

Session A 之后 BROKEN 178（"Rust FAIL / C++ PASS" 真回归表）按 mapper 分布
top-3：**mapper 4 = 159**、mapper 0 = 82、mapper 1 = 61（其余≤37）。
mapper 4 中 33 个独立卡死 PC 中抽样反汇编**全部**：

- 0xEB91（0443 SMB2） / 0xF39F（0263 Kid Klown）/ 0xC095（0145 Defenders of
  Dynatron City）/ 0xC0FB（0202 Gold Medal）/ 0xCE8B（0332 Ninja Ryukenden 2
  / 1566 Ninja Gaiden 2 / 1569 NG2 Invincible / 1570 NG2 Plus）/ 0xE296
  （0276 Legends of the Diamond）/ 0x8006（0442 SMB Tetris）等都落在
  **NMI handler 入口或内部子程序**（`PHA TXA PHA TYA PHA` 之后、初始化
  `$2001=0` / `$2003=0` / `$4014=2` 等之后）。
- 抽样 40 个 mapper 4 ROM 的 PRG 字节，**没有一个**包含经典的
  `LDA $4010 / AND #$40 / BNE -3` MMC3 IRQ 等待环。绝大多数 mapper 4 卡死
  ROM 在轮询 `$2002` 的 VBL flag / sprite0 hit（已修）或 mapper 例程
  返回地址。

### §6.6.bis.2 0443 SMB2 等待环详查

0x961A/0x961C 反汇编（默认 MMC3 window $C000=last bank, bank 0 偏移 0x161A）：
```
961A: A5 EB    LDA $EB
961C: 10 FC    BPL $961A    ; <- infinite loop
961E: 60       RTS
961F: 20 00 DE JSR $DE00
```
Game 在等待 **CPU RAM $EB** 的 bit 7 置位。`$EB=0x9E` 时 BPL 永远 taken。

### §6.6.bis.3 C++ PPU 实测反例

§6.5 batch report 把 `0443_Super_Mario_Bros_2` 列为 C++ new PPU **PASS**。
但在本 Session 用同一 C++ PPU 构建跑 `--debug-rom 0443_... --frames 30`，
30 帧内 trace 显示**同样卡死在 0x961A/0x961C** 循环，与 Rust PPU 完全相同的
PC链：

```
f=25 pc=0xEB8E $2000=0x9E $2002=0x9E
f=26 pc=0x961A $2000=0x9E $2002=0x9E
f=27 pc=0x961A $2000=0x9E $2002=0x9E
...
failure_reason = cpu_stuck_pc=0x961C
```

这意味着 §6.5 batch report 的 "C++ PASS" 含义可能是"120 帧未崩溃"，但未
排除在 60-120 帧窗口之间 game 进入持久等待环——`pc_stuck` 的判定阈值可能
过宽，把这种子程序循环误判为 PASS。要落实需要重写 batch_compat 报告逻辑
（增加“持续 20+ 帧同一 PC”才判 FAIL），超出 Session B 的范围。

### §6.6.bis.4 mapper IRQ counter 单点修复预期

基于反汇编与样本分析，mapper 4 卡死 ROM 的真实根因很可能是 **mapper 子程序
调用链在 Rust PPU 下走的调用顺序 / 返回值与 C++ 不同**（可能是 PPU hook
触发 dot 偏移、HBlank 计数器差异、CHRBANK swap 触发点偏移等），属于**多个
sub-system 的级联时序偏差**，不是 IRQ counter 单点可修复的：

- 如果改 MMC3_hb 的 dot 触发点（at dot 256 vs at sl -1 dot 280），会再次
  重复 §6.1.e.v3 的多次尝试反复回撤——已有 4 个配置对照实验显示这是**校准
  差异而非单点 bug**。
- 需要逐 ROM 跟踪卡死子程序调用链，确定哪个 hook 在哪个 dot 没触发或
  返回值错误，工作量超出"Session B"单点修复的范围。

### §6.6.ter.2 VBL-first layout coordinate 定位（重点）

C++ engine 的 frame layout （sl 0..=239 visible, sl 240 post-render, sl 241 VBL） 与 Rust PPU VBL-first layout （sl 241..=260 VBL 在前, sl -1 pre-render, sl 0..=240 visible + post-render）完全不同。

| C++ engine 坐标 | C++ 语义 | Rust PPU VBL-first 等价坐标 | Rust PPU 语义 |
|---|---|---|---|
| sl=240, cy=340 | VBL set 边界前 1 dot | sl=240, dot=340 | post-render 末点，下一帧 wrap 到 (241, 0) 前 1 dot |
| sl=241, cy=0/1 | VBL set 边界 + 1 dot after | sl=241, dot=1 (VBL set 点) + dot=2 | Rust PPU VBL set at (241, 1)，取消窗口同步位移 |

**为什么以前两次 A2002 port 崩？**Phase 5.3 commit 6057e8d 和 Phase 6.1.d commit 946ee31 都是直接拷 C++ 坐标，但 VBL-first Rust PPU 中 VBL set 在 (241, 1) 而不是 C++ 的 (241, 0) 边界——**C++ 坐标在 Rust scheduler 中永远不触发**，使 A2002 logic 永远不生效。本 session 用 VBL-first 坐标重做，避免这个陷阱。

### §6.6.ter.3 代码实现

**修改：**src/ppu_rust_bridge.cpp::ppu_rust_bridge_cpu_read（+ +64 / -22 LOC）

- 读  时查询 Rust PPU 当前 (sl, dot)
- **(sl, dot) == (240, 340)** → ceux11_ppu_mark_vbl_set_suppressed(g_ppu_state)（下一个 (241, 1) tick 检查到后跳过 VBL set + NMI assert）
- **(sl, dot) ∈ {(241, 1), (241, 2)}** → (void)fceux11_ppu_take_nmi_pending(g_ppu_state)（清掉 pending NMI，与 C++ 的 X6502_IRQEnd(FCEU_IQNMI) 等价）
- 其他 (sl, dot) 上的  读不受影响

**为什么安全：**

1. 窗口是精确定位（(sl, dot) 严格相等），不会误触 mapper_mmc1 frame 0
2. ppudead path 的 VBL set 仍在 (241, 0) （VBL-first layout），与两个窗口 (240, 340) / (241, 1-2) 不交集 — ppudead 帧不受影响

### §6.6.ter.5 02-vbl_set_time 仍 FAIL 的根本原因分析

**两个 engine 同时 FAIL 同一 hash 表明：**§6.5.2 记录"C++ new PPU PASS 02-vbl_set_time"是错误描述（主要是 §6.5 原本就是 C++ new PPU 与 Rust PPU 跨引擎比较，引入了 "C++ PASS" 的误判）。本 session 重跑 uild-ab-cpp C++ legacy PPU，仍 FAIL hash 4103C340，与 Rust PPU 完全一致。

**该 hash 不变意味着：**

- Rust PPU 的 (sl 241, dot 1) VBL set 与 C++ engine 的 (sl 240→sl 241 boundary)（即 dot 0 of VBL block）仍有 1 dot 偏移
- 本 session 的 A2002 port 只处理 suppress/cancel，不改 VBL set 点——**VBL 仍在 (241, 1) set，blargg 期望可能是 (240, 341)（即 "1 dot after sl 240 边界"，不是 (241, 1)）**
- §6.1.e commit 946ee31 尝试将 VBL set dot 0，但 02-vbl_set_time 仍 FAIL hash C4BE5BE4（不同 hash，仍错） — 说明"shift 1 dot"不够，需要精确到"2 dot 偏移"，或者调整 NMI cancel 与 NMI assert 之间的延迟（bridge_trigger_nmi 与 per-dot interleave 的 NMI latch 交互，即 §6.1.e.v3.4 候选 1）
- 另一可能：**blargg ROM 本身是"calibrated to Mesen, not C++"**——如果 blargg 仅在 Mesen 上 PASS，而两个 engine 都不是 Mesen，那么 "修复为 Mesen 等价" 可能走错方向

**未来 Session D 需解决：**

- 选项 A：修 Rust PPU frame.rs 的 VBL set dot 到 (240, 341) （即 "1 dot after sl 240 boundary"，在 VBL-first layout 下相当于 (241, 0)，但 §6.1.e 尝试过并被报告 nestest frame 3-7 错位）

## §6.6.quater.3 — Plan §0.8 步骤 1：A2002 抑制窗口对齐 NESdev spec（2026-09-03）

### 背景与触发

v2.1 锁档 ≥84% 后，按 plan §0.7 / §0.8 转为"按需逐项清扫现存测试失败"。第一项 = plan §0.8 步骤 1：**02-vbl_set_time 根因修复**（= §6.6.quater 方向 3）。

§6.6.ter.5 / §6.1.e.v3.4 已列出 4 个候选根因：
1. NMI 2-dot delay 不对（方向 2 直接相关）
2. `vbl_suppressed_this_frame` reset 时机不对
3. A2002 read 抑制窗口边界不对
4. pre-render 行 VBL flag clear dot 不是 (sl -1, dot 1)

### 根因定位（候选 3 命中）

`PpuState::apply_a2002_suppression`（`src/rust/crates/fceux11-ppu/src/state.rs:299-317`）的实现窗口：
```rust
if sl == 240 && dot == 340 {
    self.vbl_suppressed_this_frame = true;
} else if sl == 241 && dot <= 1 {
    self.nmi_pending = false;
}
```

对照 NESdev PPU frame timing wiki（[PPU_frame_timing](https://www.nesdev.org/wiki/PPU_frame_timing)）+ PPU programmer reference（[PPUSTATUS](https://www.nesdev.org/wiki/PPU_programmer_reference)）：
- **1 PPU clock before VBL set** = `(240, 340)` AND `(241, 0)`（同 PPU tick，scanline wrap 共享时钟）→ suppress VBL+NMI for the entire frame
- **same clock / 1 later than set** = `(241, 1)` AND `(241, 2)` → reads as set, clears, suppresses NMI only

当前实现的两处偏差：
- `(241, 0)` read 只清 `nmi_pending`，**不**设 `vbl_suppressed_this_frame`——bug
- `(241, 2)` read 完全没处理——bug

§6.1.e.v3.4 的 test pin 在 `tests/vbl_nmi.rs:286-312` 明确"pins that behaviour so a future tightening of the window to the strict spec text triggers a conscious decision"——本节就是那次 conscious tightening。

### 修复（commit `c872db7`）

`state.rs::apply_a2002_suppression` 改写为 match 表达式：
```rust
match (sl, dot) {
    (240, 340) | (241, 0) => {
        self.vbl_suppressed_this_frame = true;  // 1 clock before set
        self.nmi_pending = false;
    }
    (241, 1) | (241, 2) => {
        self.nmi_pending = false;              // same clock or 1 later
    }
    _ => {}
}
```

测试更新：
- `tests/vbl_nmi.rs::nmi_pending_cleared_at_sl_241_dot_0` → `suppression_window_extends_to_sl_241_dot_0`：spec-strict 断言
- 新增 `nmi_pending_cleared_at_sl_241_dot_2`：覆盖新增的 1-dot-later cancel window
- `frame.rs` 内联测试 `vbl_set_at_sl_241_dot_1_with_nmi_enable` 等保持（PPU programmer reference 文本以 (241, 1) 为 set dot）

### 根因（发现于本 session 开工读 C++ engine baseline）

项目自身 C++ engine 在 `src/ppu.cpp:625-629` 的实现与 c872db7 解读冲突：

```cpp
if (rsl == 240 && rcy == 340) {
    fceu11_ppu_mark_vbl_set_suppressed();
} else if (rsl == 241 && rcy <= 1) {
    X6502_IRQEnd(FCEU_IQNMI);
}
```

C++ engine 把 VBL set 实现为 `(sl 240 -> sl 241)` 边界，即 `(241, 0)` 本身就是 VBL set 点（**不是** 1 dot before）。只有 `(240, 340)` 调 `mark_vbl_set_suppressed`；`(241, 0)` 和 `(241, 1)` 仅 `X6502_IRQEnd` 取消 NMI，不 mark suppressed。C++ engine 也没有 `(241, 2)` 处理。

c872db7 解读"VBL set 在 (241, 1)，所以 (241, 0) 是 1 dot before"也是合法的 NESdev 文本解读，但**与项目自身 C++ engine working config 冲突**。v2.1 目标是 Rust PPU 替代 C++ PPU（Phase 7），所以 Rust PPU 抑制窗口应与 C++ engine baseline 1:1 对齐。

```rust
match (sl, dot) {

}
```

## §6.6.quater.3.2 — Plan §0.8 步骤 2 vbl_05_nmi_timing 调查：NMI delay 假设被否决（仍 deferred）（2026-09-04）

### 背景

§6.6.quater.3.1 提到 `blargg_vbl_05_nmi_timing` 哈希不变（hash 从 c872db7 不变到 Option B），说明根因不在 `(241, 0)` 抑制窗口。本小节试验 C++ engine 的 `e1_nmi_delay()=8` 假设。

### C++ engine 参考

`src/ppu_rendering.cpp:1593-1596` 明确记录：

> "2026-08-02 Step 1.3 deep calibration: with the runppu(3) frame
> distortion removed, NMIDELAY=8 makes vbl_05_nmi_timing PASS
> (X=[4,4,4,3,3,3,3,3,3,2]); 7 -> [4,3,...], 9 -> [4,4,4,4,3,...]
> (transition 1 line late), 8 is the unique sweet spot."

代码位置 `src/ppu_rendering.cpp:1720-1722`：

```cpp
if (VBlankON) {
    const int nd = e1_nmi_delay();
    if (nd > 0) X6502_Run(nd);
    if (!vbl_set_suppressed) TriggerNMI();
}
```

C++ engine 在 VBL set 后，调用 `X6502_Run(8)` 给 CPU 8 PPU dots 不推进 PPU，然后 TriggerNMI。

### 实施（临时 commit，未提交）

在 `src/rust/crates/fceux11-ppu/src/scheduler.rs` 添加 NMI 调度延迟：

- 新增 `pub const NMI_DELAY_DOTS: i32 = 8`
- `NesScheduler` 结构新增 `nmi_delay_remaining: i32` 字段
- `NesScheduler::new()` 初始化 `nmi_delay_remaining: 0`
- 主循环中当 `outcome.nmi_asserted`，设置 `nmi_delay_remaining = 8`；各 PPU tick 减一，当达 0 时 `nmi_pending = true`（下个 CPU 指令边界调 `on_nmi`）

### 验证结果

- build-rust-ppu/ 重组完成，两个 kagami 子项状态：

  | 项 | 未加 NMI delay (Option B) | 加 NMI delay=8 |
  |---|---|---|
  | `blargg_vbl_05_nmi_timing` hash | 158D8C20 | **158D8C20**（未变）
  | `blargg_vbl_05_nmi_timing` value | 0x01 | 0x01（未变）
  | `blargg_vbl_05_nmi_timing` diag | "00 3 / 01 2 / 02 2 / 03 2 / 04 2 / 05 2 / 06 1 / 07 1 / 08 1 / 09 1" | 同上（未变）
  | `rust_ppu_vbl_nmi_timing_test` 02-vbl_set_time hash | 933AF95A | 933AF95A（未变）
  | ctest 39/41 = 95% | 95% | 95%（同 baseline）

- **未产生任何差别**—二者 hash/diag 完全一致。说明 NMI delay 并不是 vbl_05 的根因。

### 为什么不生效（推论）

三个可能原因：

1. **Rust PPU 与 C++ engine 的 PPU/CPU interleave 机制不同**—C++ engine 的 `X6502_Run(nd)` 能“PPU 不推进但 CPU 运行”，Rust 的主循环则是 1 条 CPU 指令 = 3 PPU dots。在 8 PPU dots 内只能运行 ~2-3 条指令，与 C++ 不等价
2. **NMI delay 可能只是 C++ engine 专属的“平衡”，而不是 NES 硬件规范**—NESdev 说 "NMI dispatched 1 CPU cycle later"（3 PPU dots），但 C++ 在移除 `runppu(3)` 之后才发现 8 是“唯一甜糕点”，说明 8 是 C++ 内部体系的平衡点
3. **vbl_05 ROM 的计数逻辑不依赖 NMI 分发时机**—hash 同 Option B 一致，可能是测试它不同的维度（VBL 事件同步 / $2002 读取顺序，而不是 NMI 分发时机）
