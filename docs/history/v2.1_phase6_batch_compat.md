void ppu_rust_bridge_cpu_read(uint32_t addr) {
    if (g_ppu_state == nullptr) return;

    // Phase 6.1.d (current intermediate state — A2002 port queued to
    // 6.1.d with mapper_mmc1 frame 0 gate; see NOTE in 6.1.b commit).
    return fceux11_ppu_cpu_read(g_ppu_state, static_cast<uint16_t>(addr));
}

void ppu_rust_bridge_cpu_write(uint32_t addr, uint8_t value) {
    if (g_ppu_state == nullptr) return;

    // Phase 6.1.b: B2000 rising-edge NMI-enable port.
    //   if (!(PPU[0] & 0x80) && (V & 0x80) && (PPU_status & 0x80))
    //       TriggerNMI2();  (C++ reference: src/ppu.cpp:958-962)
    if (addr == 0x2000) {
        const uint8_t old_ctrl = fceux11_ppu_get_register_state(g_ppu_state, 0);
        fceux11_ppu_cpu_write(g_ppu_state, static_cast<uint16_t>(addr), value);
        const uint8_t status = fceux11_ppu_get_register_state(g_ppu_state, 2);
        if (!(old_ctrl & 0x80) && (value & 0x80) && (status & 0x80)) {
            TriggerNMI2();
        }
    } else {
        fceux11_ppu_cpu_write(g_ppu_state, static_cast<uint16_t>(addr), value);
    }
    if (addr == 0x2007) {
        bridge_refresh_windows();
    }
}

## §6.1.e.v3 — VBL set timing follow-up：4-configuration investigation (2026-08-30 22:00)

### §6.1.e.v3.1 触发

§6.1.e commit (`946ee31`) 把 VBL set 从 `sl 241 dot 1` 改为 `dot 0`（声称"硬件真值"），nestest golden 重新生成覆盖到 dot-0。但 `rust_ppu_vbl_nmi_timing_test` 重新启用后 `02-vbl_set_time` 子测试**仍 FAIL**，diagnostic hash `C4BE5BE4`。

**§6.1.e 计划文档自己的预测**：
> "如果仍有 subtest FAIL → 记录是哪 subtest、根因（cycle 0 vs cycle 1 在哪里 diff 1 dot），follow-up Phase 6.1.e.v3"

§6.1.e.v3 的工作就是执行这个 follow-up：找出 `02-vbl_set_time` FAIL 的真正 root cause。

### §6.1.e.v3.2 Mesen 参考确认

§6.1.e 计划文档引用"Mesen 参考 + blargg 校准"作为 dot-0 的论据，但 Mesen 实际实现查证（搜索结果）：

```cpp
// Mesen-style PPU per-cycle execution
if (_scanline == 241 && _cycle == 1) {
    SetFlag(StatusFlags::VerticalBlank);  // VBL at sl 241 dot 1
    if (_nmiOutput) {
        _nmiDelay = 1;
    }
}
```

**Mesen 实际用 dot 1，不是 dot 0**。blargg vbl_set_time ROM 校准于 Mesen，所以期望 dot 1。

但 **C++ engine `src/ppu.cpp:609-619` 注释明确说"Working-config VBL flag sets at the sl240→sl241 boundary (cycle 0 of the VBL block)"**——C++ engine 用 dot 0。

这是一个 C++ engine (dot-0) vs Mesen/blargg (dot-1) 的**校准差异**，不是简单"硬件真值"问题。

### §6.1.e.v3.3 4-configuration matrix

为了 isolate root cause，测试了 4 个配置：

| 配置 | frame.rs `dot` | bridge A2002 port | 02-vbl_set_time diag hash | 结果 |
|------|----------------|-------------------|---------------------------|------|
| (a) | dot 1 | 无 port（Phase 5.3 baseline）| — | n/a（先看 dot-0/1 影响） |
| (b) | dot 1 | 6.1.d port（sl 240/340 suppress） | `933AF95A` | FAIL |
| (c) | dot 1 | bridge suppress 改 sl 241/0（修正给 dot-1） | `C4BE5BE4` | FAIL |
| (d) | dot 0 | 6.1.d port（sl 240/340 suppress） | `C4BE5BE4` | FAIL |
| **(e) 最终** | **dot 1** | **移除 port**（净 baseline） | **`4103C340`** | **FAIL** |

**4 个 FAIL 配置的 diagnostic 全部不同**——这不是 1-dot shift 能解释的（那种情况 hash 应相同）。证明 root cause 不在 VBL set dot 选择，也不在 A2002 port。

### §6.1.e.v3.4 Root cause 推断

§6.1.e.v3 调查后定位 **root cause 在 PPU state machine 别处的 timing drift**，不在 §6.1.e / §6.1.d 触及的两块（VBL set dot、A2002 port）。

最可疑候选（需要后续 session 深入调查）：

1. **bridge_trigger_nmi 与 per-dot interleave 的 NMI latch 交互**：`fceux11_run_frame_interleaved`（lib.rs:355-374）每 dot 调用 `take_nmi_direct` → `trigger_nmi` callback → `cpu_run_with_tick`。如果 NMI 在 set dot 后某延迟点被 trigger，可能干扰 blargg 测得的 CPU $2002 read pattern。
2. **CPU/PPU phase 同步**：nestest 在 `sl 241 dot 1` 之前正好跑完某个 CPU instruction，`cpu_run_with_tick` 把 CPU 推进 1 cycle 时可能跨越 read 边界。
3. **`vbl_suppressed_this_frame` 跨帧污染**：frame.rs:152-156 在 `sl -1 dot 340` 清 suppression flag，但如果 timing 漂移导致清 flag 错过，下一帧 VBL set 被错误抑制。

`02-vbl_set_time` ROM 的 inner loop 跑 256 次 read，跨越多帧扫描。任何上述 timing drift 都会让 256-cell pattern 与 ROM 内置预期不匹配。

### §6.1.e.v3.5 Final disposition

经过 4 配置对比，决定采用**配置 (e)**：**dot-1 + 无 A2002 port**。

理由：
1. **匹配 Mesen / blargg 校准**：dot-1 是行业参考实现的标准，避免引入与社区模拟器的不可对比偏差。
2. **避免 A2002 port 的 mapper_mmc1 回归风险**：§6.1.d 加 port 时该回归已被观察到（Phase 5.3 NOTE 明确记录）。
3. **保留 $2008-$3FFF mirror 路由**：vbl_basics subtest 1（`$2002 == $200A`）需要 mirror 才能 PASS；mirror 没有 timing 影响，纯路由。
4. **Nestest goldens 完全回滚到 commit `b06388c`**：byte-identical，0 diff，6.1.e 引入的 churn 归零。

## §6.2 — Sprite 渲染管线 ✅ 完成 (2026-08-31)

### §6.2.1 设计决策

最终落地的是 **per-scanline batch sprite composition**（而非 §6.2 草稿的 per-dot
`fetch_sprites` / `tick_sprite_pixel` / `compose_sprite_pixel` 三段 API）。原因：
草稿 API 需要把 per-cycle shift register + x-counter 时序接进 `frame.rs`
tick_dot，改动面大且难以在单 session 内验证；batch 模型在
`render_visible_scanline`（BG 写完后）一次性合成精灵像素，对 8x8 / 8x16
标准形状输出与逐周期模型 byte-identical，先解决 batch compat 的 no_video
失败主体，逐周期怪癖（mid-tile reload、left-edge clip、overflow re-scan）
留待后续 sub-task。

`render_sprites_for_scanline`（`src/rust/crates/fceux11-ppu/src/sprites.rs`）：
- 直接扫 primary OAM（绕开 secondary_oam 的 start-of-scanline 时序依赖）
- 8-sprite limit（OAM 顺序）+ 9th+ 置 `sprite_overflow`
- 8x16 tile bit 0 选 pattern table，高 7 位选 tile pair
- priority MUX：attr bit 5 = 0 前景 / 1 背景仅 BG 透明处可见
- sprite 0 hit：前景优先 + BG 不透明 + x 1..=254
- 回写 `state.sprite_shift/attr/x`、`secondary_oam_count`，保持
  `fceux11_ppu_get_*` debug 访问器与 savestate round-trip 自洽

已知简化（详见 sprites.rs 模块注释）：无逐 dot shift register、attr
flip 位（bit 6/7）未生效、left-edge 8-pixel clip 未实现、palette 查找
沿用 BG 写入方约定（0x00-0x0F 区段）。

## §6.4 — CHR 多 bank 缓存 + trace-diff 一致性修复链 ✅ 收尾 (2026-09-01)

### §6.4.1 CHR/NT 窗口 scanline 粒度失效（plan §7 Phase 6 交付项）

**问题**:`bridge_refresh_windows()`（8 KiB CHR + 4 KiB NT 快照）只有两个触发点——
bridge power 和 `$2007` CPU 写。多 bank mapper（MMC3/VRC4 等）在帧内通过 bank 寄存器
改写 `g_bus.vpage[]` 后,Rust 渲染器继续用 boot 时的窗口快照渲染,直到下一次 `$2007`
写才刷新——逐 scanline 换 bank 做状态栏/分屏的游戏会以 boot 期 bank 渲染整帧。

**实现**(`src/ppu_rust_bridge.cpp`):

1. **页基指针快照** `g_chr_page_base[8]` / `g_nt_page_base[4]`——上次刷新时各 1 KiB 页
   解析出的基指针;`bridge_refresh_windows()` 顺带记录。
2. **`bridge_refresh_window_contents_if_dirty()`**——逐页比较指针,仅重拷移动过的页
   （纯 C++ 内存 memcpy,**零 FFI**）。挂在 `bridge_notify_scanline`:该回调在 scheduler
   的 scanline 转换 tick 内触发,**早于**新 scanline 的 dot-0 批量渲染,故上一 scanline
   期间发生的 bank 切换对下一 scanline 可见——与 hblank 期切 bank 的设计意图一致。
   关键约束:notify 回调运行时 Rust scheduler 持有 `StateBox` 可变借用,回调内**禁止**
   再进任何 `fceux11_ppu_*` FFI（重入 = 别名 UB,Phase 5.1 bridge 递归修复同款风险）,
   所以这里只做内容重拷,Rust 侧透过 power 期安装的指针直接看到新数据,无需重推。
3. **`bridge_push_mirror_mode_if_dirty()`**——NT 页模式变化（镜像切换）重算 mirror
   mode 并推送,但推迟到帧边界（`ppu_rust_bridge_run_frame_interleaved` 入口）执行,
   理由同上（回调内不能 FFI）。帧内镜像切换的生效延迟一帧,已记录为已知限制。
4. `bridge_derive_mirror_mode()` 从原 refresh_windows 中提取复用。

**Rust 侧零改动**——渲染器本就每 scanline 透过窗口指针读数据。

**限制**(后续 session 处理,不阻塞):
- MMC5 fill/ex-attribute 模式等非 vpage 语义的取指不在指针比较覆盖内(窗口模型本身的
  已知局限,§6.2.4 同类);
- 渲染器是 batch-per-scanline 模型,scanline 中途的 bank 切换仍按 scanline 起点解析。
