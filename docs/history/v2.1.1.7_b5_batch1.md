## 3. D4（PAL/Dendy）—— **前提复核失败，已停下等 owner 裁定**

plan §B.5 D4-a 要求"接通 PAL"：`FCEUPPU_SetVideoSystem` 通知桥 + 帧预算按制式取值（Rust PAL 帧长 106392）。实施前复核发现**桥侧单独接通会造成比现在更差的行为**：

| 核查 | 结论 |
|------|------|
| Rust 调度器 | 有 `set_video_system(pal)`，`frame_cycles` 在 89342/106392 之间切换（`scheduler.rs:89-95`）——即"每帧 hook 预算"会变 |
| Rust 状态机 | **没有 PAL 扫描线布局**：`state.rs` / `frame.rs` 中 `pal` 只被存进 `StateBox`（`ffi.rs:291-293`），扫描线仍是 NTSC 的 -1..261 结构，可见区仍 240 行 |
| 若只接通帧预算 | 一个"视频帧"会推进 106392 dots，而内部一帧只有 89342 dots → **每视频帧跑约 1.19 个内部帧**（画面/音视频节奏反而变快且不同步） |
| 真正的 PAL | 需要 312 行光栅、pre-render/VBL 位置、50Hz 时序——属 `fceux11-ppu` 渲染精度范畴，而 plan §1.2 明确"不动 fceux11-ppu 的渲染精度（属 v2.2）" |

因此本批**未改任何 PAL 代码**，把 D4 原样停在决策点。plan §B.5 已登记的备选路径（owner 若选择"不接通"）：显式写明"PAL/Dendy 自 v2.1.1 起降级为不保证"，并在 CHANGELOG 与 release note 标注。

两个可选方案见 plan §B.5 的 D4 复核小节。
