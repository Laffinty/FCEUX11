## 一、A-1+A-2 [CRITICAL] Lua 引擎裸指针并发 UB + 无析构 FFI

### 1.1 诊断概览

| 项目 | 内容 |
|------|------|
| 诊断 ID | RUST-CRASH-01（裸指针并发）+ RUST-CRASH-02（Box 永不回收） |
| 文件 | `src/rust/crates/fceux11-lua/src/lib.rs` |
| 关键行 | L27（`LUA_ENGINE_PTR` 声明）、L29-38（`get_engine` / `get_engine_mut`）、L515-532（`fceux11_lua_init`） |
| 触发场景 | (a) emulator 线程与 GUI 线程并发 FFI 调用；(b) 重新 init / 应用退出路径 |
| 失败现象 | Stacked Borrow UB（编译期合法但运行时两个 `&mut LuaEngine`）；Lua 引擎永久泄漏（mlua state + Registry keys） |
| 修复紧迫度 | **最高**（CRITICAL） |

### 1.2 当前代码（原文摘录）

```rust
// lib.rs:27
static LUA_ENGINE_PTR: AtomicPtr<c_void> = AtomicPtr::new(std::ptr::null_mut());

// lib.rs:29-38
#[inline(always)]
fn get_engine<'a>() -> Option<&'a mut LuaEngine> {
    let raw = LUA_ENGINE_PTR.load(Ordering::Acquire) as *mut LuaEngine;
    unsafe { raw.as_mut() }
}

#[unsafe(no_mangle)]
pub(crate) fn get_engine_mut<'a>() -> Option<&'a mut LuaEngine> {
    get_engine()
}

// lib.rs:515-532
#[unsafe(no_mangle)]
unsafe extern "C" fn fceux11_lua_init() -> c_int {
    match LuaEngine::new() {
        Ok(engine) => {
            let boxed = Box::new(engine);
            LUA_ENGINE_PTR.store(Box::into_raw(boxed) as *mut c_void, Ordering::Release);
            0
        }
        Err(e) => { eprintln!("fceux11_lua_init failed: {:?}", e); -1 }
    }
}
```

### 1.3 问题分析

**RUST-CRASH-01（裸指针并发 UB）**:
- `AtomicPtr<c_void>` 提供发布/获取的内存顺序，但不提供互斥。
- 当 emulator 线程调用 `get_engine()` 并拿到 `&mut LuaEngine` 时，GUI 线程同时调用 `get_engine()` 也会拿到一个 `&mut LuaEngine` 引用。
- Rust 借用检查器无法在编译期发现这个问题（裸指针转 `&mut` 不会触发借用检查），但运行时两个 `&mut` 同时活跃构成 **Stacked Borrow UB**。
- 实际触发：当前 FCEUX11 是单线程 Qt 应用，所有 FFI 都在同一线程，因此 **当前未触发**。但任何代码演进（例如 QtConcurrent 调用 FFI、新增 worker 线程）会立即引爆。

**RUST-CRASH-02（Box 永不回收）**:
- `fceux11_lua_init` 用 `Box::into_raw` 把 `LuaEngine` 堆对象转裸指针存进 `LUA_ENGINE_PTR`，但代码库内 **没有对应的 `Box::from_raw`**（除了 `#[cfg(test)]` 的测试代码 L834, L866，但测试代码不会在生产构建中编译）。
- 结果：每次重新 init（例如重载 Lua 脚本）都会覆盖 `LUA_ENGINE_PTR` 而不释放旧的 `Box`，永久泄漏整个 `mlua::Lua` 状态 + Registry keys。
- 在 mlua 0.10 中 `mlua::Lua` 内部持有 `Rc<ReentrantMutex<RawLua>>`，drop 时会关闭 Lua VM；如果不 drop，泄漏的不只是 `LuaEngine`（~几 KB），还有 Lua VM 分配的所有 Lua 对象（可能 MB 级）。
- 实际触发：**当前每次重新加载 Lua 脚本都泄漏**（只是当前用户不重载脚本所以没注意到）。

### 1.4 修复方向（描述，不含代码）

**A-1 方向 — 互斥化全局指针**:
- 核心思路：在 `AtomicPtr` 外再套一层 `std::sync::Mutex`，使所有访问（init / get / shutdown）串行化。
- 关键决策点：存储类型的选择。
  - 选项 1：`Mutex<*mut LuaEngine>` — `*mut LuaEngine` 是 `Send` 但 mlua 的内部 `Rc` 不是 `Send`，所以 `Mutex<*mut LuaEngine>` 自身不是 `Sync`，**无法放入 `static`**。
  - 选项 2：`Mutex<usize>` — 用整数地址绕过 `Send/Sync` 限制（与原 `AtomicPtr<c_void>` 一致，但增加了 `Mutex` 同步）。`usize` 是 `Send + Sync`，`Mutex<usize>` 也是 `Sync`。需要 RAII 包装（如自定义 `EngineLock<'a>`）把 `MutexGuard` 的生命周期与 `&mut LuaEngine` 引用绑定。
  - 选项 3：使用 `parking_lot::Mutex` 配合 `const_new()`（绕过 Send 要求）—— 但项目惯例是不引入 parking_lot。
- **推荐**：选项 2（`Mutex<usize>` + `EngineLock`）。
- 注意：`bindings/*.rs` 中的 `if let Some(eng) = engine { eng.method(); }` 模式因为 `EngineLock` DerefMut 必须改成 `if let Some(mut eng) = ...` 以通过借用检查。

**A-2 方向 — 提供 shutdown FFI**:
- 新增 `fceux11_lua_shutdown() -> c_int`，内部在 `Mutex` 守卫内：
  1. 读出当前指针；
  2. 将全局设为 null；
  3. `Box::from_raw` 重新获得所有权；
  4. drop，触发 `mlua::Lua` 的 Drop 实现（关闭 Lua state、释放 Registry keys）。
- 返回值：成功释放返回 1，nothing to do 返回 0。
- C++ 端新增 `FCEU_LuaShutdown()` 包装，在 `fceu11::Kill()`（`src/fceu.cpp:649`）调用 `FCEU_LuaStop()` 之后调用。
- 头文件 `src/fceulua.h` 声明 `int FCEU_LuaShutdown();`。

## 二、A-3 [CRITICAL] `nes_shm` 剩余字段跨线程非原子

### 2.1 诊断概览

| 项目 | 内容 |
|------|------|
| 诊断 ID | QT-CRASH-01 |
| 文件 | `src/drivers/Qt/nes_shm.h` + 11 个 Qt driver 文件 |
| 关键行 | nes_shm.h:21-36（结构体定义）；sdl-video.cpp:141-543 等（写入方）；3 个 viewer（读取方） |
| 触发场景 | emulator 线程写 `video.ncol`/etc，GUI 线程 viewer 同帧 paintGL 读取 |
| 失败现象 | torn read（32 位写入被读端看到一半）+ reordering → 错位、闪屏 |
| 修复紧迫度 | **高**（CRITICAL） |

### 2.2 当前代码（原文摘录）

```cpp
// nes_shm.h:21-36
struct nes_shm_t {
    int   pid;
    int   run;
    uint32_t  render_count;
    uint32_t  blit_count;
    struct {
        int   ncol;
        int   nrow;
        int   pitch;
        int   xscale;
        int   yscale;
        int   xyRatio;
        int   preScaler;
        int   test;
    } video;
    // ... atomic fields already (runEmulator, blitUpdated, pixBufIdx, sndBuf) ...
};
```

### 2.3 问题分析

- hotfix1 P1-12 把 `runEmulator` / `blitUpdated` / `pixBufIdx` / `sndBuf.{head,tail,starveCounter}` 升级为 `std::atomic`。
- 但 `video.*`、`render_count`、`blit_count`、`pid`、`run` 仍是 plain int / uint32_t。
- **真实触发路径**：
  - emulator 线程在 `CalcVideoDimensions()`（sdl-video.cpp:132）或 `BlitScreen()` 期间写 `video.ncol` / `video.xscale` / `video.pitch` / `video.preScaler`。
  - GUI 线程 viewer 在 `paintGL` / SDL paint / QPainter paint 期间读这些字段（用于绘制窗口拉伸、计算 pixel pitch 等）。
  - 32 位 int 写入在 x86 上通常原子，但 **C++ 内存模型不保证**；在 ARM/AArch64 上 torn read 可能发生。
  - 即使写入原子，**reordering** 也会让 reader 看到 "new ncol + old nrow" 的不一致状态。
- **死字段 `pid` / `run`**：grep 确认 src/ 下零读零写（nes_shm.cpp:48-51 注释已说明），保留无害但删除可减少表面积。

### 2.4 字段访问矩阵（基于 `docs/history/v1.15_hotfix3_overview.md` §六.1 探索结果）

| 字段 | 写入数 | 读取数 | 生产者 | 消费者 | 推荐 ordering |
|------|--------|--------|--------|--------|---------------|
| `render_count` | 6++ + 1 reset | 0 | emu + 3 viewers | — | relaxed |
| `blit_count` | 1++ + 1 reset | 0 | emu | — | relaxed |
| `video.ncol` | 6 | ~16 | emu | GUI | release / acquire |
| `video.nrow` | 6 | ~16 | emu | GUI | release / acquire |
| `video.pitch` | 5 | 0 跨线程 | emu | — | relaxed（可保持 plain） |
| `video.xscale` | 11 | 11 | emu | GUI | release / acquire |
| `video.yscale` | 10 | 8 | emu | GUI | release / acquire |
| `video.xyRatio` | 5 | 2 | emu | GUI | release / acquire |
| `video.preScaler` | 4 | 6 | emu | GUI | release / acquire |
| `video.test` | 1（GUI 写）| 1 GUI + 1 emu | GUI | emu | acquire / release（双向） |
| `pid` | 0 | 0 | — | — | **dead — remove** |
| `run` | 0 | 0 | — | — | **dead — remove** |

### 2.5 修复方向（描述，不含代码）

**方案 A（结构嵌套法）— 推荐**:
- 在 `nes_shm_t` 内新增 `struct VideoAtomic { std::atomic<int> ncol; ... }` 子结构，把 `video` 字段类型改为 `VideoAtomic`。
- 顶层 `render_count` / `blit_count` 改为 `std::atomic<uint32_t>`。
- 删除 `pid` / `run`。
- 添加 helper 方法 `bump_render_count()` / `bump_blit_count()` / `reset_frame_counts()` 简化调用点。
- 所有调用点改用 `.load(acquire)` / `.store(v, release)`。
- `open_nes_shm` 不再用 `memset(&video, 0, ...)`，而是逐字段 `.store(seed, relaxed)`。

**方案 B（顶层平铺法）— 替代**:
- 不引入 `VideoAtomic` 子结构，直接把 `nes_shm_t::ncol` / `nrow` / 等提升为顶层 `std::atomic<int>`。
- 优点：不需要子结构包装，更直接。
- 缺点：与原 `video.X` 命名空间不同，所有调用点都要改（不是 `nes_shm->video.ncol.load()` 而是 `nes_shm->ncol_video.load()` 或类似），调用方改动更大。

**方案 C（保持 plain，加 Mutex）— 不推荐**:
- 用 `std::mutex` 保护整个 video 子结构。
- 缺点：emulator 线程每帧都要锁/解锁，开销大；与 hotfix1 P1-12 的 lock-free 哲学不一致。

**建议：方案 A**（嵌套结构 + 字段名不变 → 调用方改动最小；保留 helper 集中 RMW 语义）。

| GUI 烟测 | 调整窗口尺寸 / 切换 filter / 进入全屏 5 次 | 无闪屏、无错位 |

## 三、A-4 [CRITICAL] `consoleWin_t` 析构未等 emulatorThread → mutex UAF

### 3.1 诊断概览

| 项目 | 内容 |
|------|------|
| 诊断 ID | QT-CRASH-03 |
| 文件 | `src/drivers/Qt/ConsoleWindow.cpp:283-376` |
| 关键行 | dtor L283-376；`mutex` 字段在 `ConsoleWindow.h:133-137`；`emulatorThread` 字段在 `ConsoleWindow.h:154` |
| 触发场景 | 非 closeApp 析构路径（如命令行 `--quit-after`、异常退出、`main.cpp:487-491` 直接 `delete consoleWindow`） |
| 失败现象 | emulator 线程仍在 `fceuWrapperTryLock` → `consoleWindow->mutex`，但 mutex 已被 delete → UAF / 段错误 |
| 修复紧迫度 | **高**（CRITICAL） |

### 3.2 当前代码（关键段）

```cpp
// ConsoleWindow.cpp dtor (L283-376, 关键片段)
315:    nes_shm->runEmulator.store(0, std::memory_order_release);
...
330:    gameTimer->stop();
332:    closeGamePadConfWindow();
348:    unloadVideoDriver();
350:    delete mutex;     // ← RACE: 未等 emulatorThread 退出
```

```cpp
// ConsoleWindow.h:133-137
#if QT_VERSION >= QT_VERSION_CHECK(6,0,0)
    QRecursiveMutex *mutex;     // heap-allocated in ctor
#else
    QMutex *mutex;
#endif

// ConsoleWindow.h:154
emulatorThread_t *emulatorThread;  // QThread subclass, run() = tight poll loop
```

### 3.3 问题分析

- hotfix1 P1-2 修过 closeApp 路径（`ConsoleVideo.cpp:340-346`）：`emulatorThread->requestInterruption()` + `wait(5000)` + `terminate()`。
- **但 closeApp 只在以下位置被调用**：
  - `ConsoleMenu.cpp:335`（File→Quit）
  - `ConsoleWindow.cpp:450`（closeEvent）
  - `ConsoleWindow.cpp:706`（updatePeriodic 轮询 closeRequested）
- dtor 路径**不调用** closeApp。`main.cpp:491` 直接 `delete consoleWindow` 时：
  1. emulator 线程可能仍在 `fceuWrapperUpdate()` 内执行 `fceuWrapperTryLock()`（fceuWrapper.cpp:1272-1322）；
  2. `fceuWrapperTryLock` 调用 `consoleWindow->mutex->tryLock()`；
  3. dtor 已 `delete mutex` → **UAF on mutex** → 段错误或 heap corruption。
- 即使 mutex 没立即被释放（heap free 不一定抹零），后续 `mutex->unlock()`（fceuWrapper.cpp:1239）也会命中已释放内存。

### 3.4 修复方向（描述，不含代码）

**核心修复**: 把 closeApp 中的 emulatorThread 等待逻辑提取到 dtor 中，确保 `delete mutex` 之前 emulator 线程已退出。

```text
~consoleWin_t() {
    // 1. 如果 closeApp 已 wait 过 emulatorThread, 则 closed_ = true，直接 delete mutex
    // 2. 否则:
    //    a. requestInterruption() (signals the polling loop to exit)
    //    b. wait(5000) (graceful shutdown)
    //    c. 如果超时，terminate() + wait() 兜底
    // 3. 现在 emulatorThread 已退出，可以安全 delete mutex
    delete mutex;
}
```

**幂等性**: 加 `bool closed_ = false;` 成员：
- closeApp() 入口置 `closed_ = true` 并 wait emulatorThread；
- dtor 检查 `closed_`：若 true，跳过 wait 直接 delete。

**复用模式**: `ConsoleVideo.cpp:340-346`（hotfix1 P1-2 建立）的 `requestInterruption → wait(5000) → terminate` 三段式。

### 3.5 验证策略

| 层级 | 工具 | 检查项 |
|------|------|--------|
| 编译 | CMake | Qt 5 / Qt 6 双 ABI |
| GUI 烟测 | File→Quit 5 次 | 正常路径不破坏 |
| GUI 烟测 | 命令行 `--quit-after N`（在 N 帧后退出）5 次 | 非 closeApp 路径不崩 |
| 动态分析 | TSan + helgrind | mutex delete 后无任何访问 |
| 内存 | valgrind --tool=helgrind | 0 UAF 报告 |

### 3.6 风险与缓解

| 风险 | 等级 | 缓解 |
|------|------|------|
| dtor 中 wait 超时（emulator 线程卡死） | 低 | 已有 `terminate()` 兜底；与 closeApp 一致 |
| `closed_` 与 closeApp 的协调（closeApp 已在 main.cpp 之前调用？） | 中 | dtor 检查 `closed_`；如果 closeApp 已执行则跳过 wait；幂等 |
| 与 Phase A-3 nes_shm 原子化的协同 | 低 | A-3 改的是 `nes_shm` 字段，不涉及 ConsoleWindow |

### 4.2 当前代码

```cpp
static int   mutexLocks = 0;
static int   mutexPending = 0;
static bool  emulatorHasMutex = 0;
```

13 个访问点的详细对照见 PLAN §二 A-5 表格。

### 4.3 问题分析

- 这三个 plain int/bool 跟踪 fceuWrapperLock / TryLock / UnLock 的状态：
  - `mutexLocks`: 当前持锁计数
  - `mutexPending`: 等待获取锁的线程数
  - `emulatorHasMutex`: emulator 线程当前是否持有锁
- 在 x86 (TSO) 上，对齐的 32 位 `++` / `--` 是原子的；但**多步操作**（如 `if (mutexLocks > 0) { mutexLocks--; ... }`）即使每步原子，**整体不是原子的** —— GUI 线程和 emulator 线程可能交错执行。
- 在 ARM/AArch64 上，单步 32 位 `++` 也不是原子的（部分平台）。
- C++ 标准不保证这些操作的原子性或顺序。

### 4.4 修复方向

**方案 A（原子化静态变量）— 推荐**:
- `mutexLocks` / `mutexPending` 升级为 `std::atomic<int>`，`emulatorHasMutex` 升级为 `std::atomic<bool>`。
- 逐操作替换：
  - `mutexLocks > 0` 读 → `.load(acquire)`
  - `mutexLocks++` 写 → `.fetch_add(1, acq_rel)`
  - `mutexLocks--` 写 → `.fetch_sub(1, acq_rel)`
  - `emulatorHasMutex = true/false` 写 → `.store(v, release)`
- 注意 `mutexPending` 是松散同步（pre/post-lock 的占位计数器），可用 `relaxed`；`mutexLocks` 与持锁相关，需要 `acq_rel`。

**方案 B（合并到 QMutex 本身）— 不推荐**:
- 用 `QMutex::tryLock()` 的返回值替代 `mutexLocks` 计数。
- 缺点：`emulatorHasMutex` 还需要单独追踪（GUI 想知道是否要 wait），无法完全消除。

### 4.5 验证策略

| 层级 | 工具 | 检查项 |
|------|------|--------|
| 编译 | CMake | 13 个调用点全部替换 |
| 静态分析 | grep `mutexLocks\+\+\|mutexLocks--\|mutexPending\+\+\|mutexPending--\|emulatorHasMutex =` 应为 0 | 无 plain 写入 |
| GUI 烟测 | File→Quit / 加载 ROM / 切换窗口 5 次 | 无异常 |
| 动态分析 | TSan + 多窗口切换 | 无 race |

### 4.6 风险与缓解

| 风险 | 等级 | 缓解 |
|------|------|------|
| memory_order 选错（acq_rel vs relaxed） | 低 | 严格按"锁获取 acq_rel，锁释放 acq_rel，独立读 acquire，独立写 release"映射 |
| 性能回退（atomic 比 plain 慢 ~2x） | 低 | 状态变量非热路径（每帧 1-2 次）；不会显著影响帧时间 |

## 五、A-6 [CRITICAL] Lua movie name/filename FFI 共享 static string

### 5.1 诊断概览

| 项目 | 内容 |
|------|------|
| 诊断 ID | LUA-CRASH-02 |
| 文件 | `src/lua-engine.cpp:612-627` |
| 关键行 | L612-617（`fceux11_lua_movie_get_name`）、L619-627（`fceux11_lua_movie_get_filename`） |
| 触发场景 | 连续两次调用（同一线程或跨线程）；第二次赋值覆盖第一次的 `c_str()` 引用 |
| 失败现象 | UAF：调用方缓存第一次返回的指针，第二次调用后指针指向已释放的 buffer |
| 修复紧迫度 | **中**（当前单线程 Qt 下不易触发；Lua binding 内 Rust 端每次立即 copy，所以实际未触发） |

### 5.2 当前代码

```cpp
const char* fceux11_lua_movie_get_name() {
    static std::string name;       // ← 与 get_filename 共享同一对象（按定义是各自函数内的 static，但若符号合并则共享）
    name = fceu11::GetMovieName();
    return name.c_str();
}
const char* fceux11_lua_movie_get_filename() {
    static std::string name;       // ← 与 get_name 共享同一对象（符号合并）
    name = fceu11::GetMovieName();
    auto pos = name.find_last_of("/\\");
    if (pos != std::string::npos) name = name.substr(pos + 1);
    return name.c_str();
}
```

### 5.3 问题分析

- 两个函数内部各有一个 `static std::string name`；按 C++ 标准，每个函数内的 `static` 是独立的，**不应共享**。
- **但**：编译器/链接器在某些情况下会做字符串池合并（string pooling optimization），可能让两个静态实例指向同一 buffer。
- 更严重的是：即使不考虑符号合并，**单次调用的 `c_str()` 指针生命周期问题**：
  - 调用 1：`get_name()` 返回 `name.c_str()`，指向 `name` 的内部 buffer；
  - 调用方立即 copy bytes；
  - 调用 2：`get_filename()` 在 `name` 上赋新值，导致 `name` 的内部 buffer 被释放；
  - 此时如果调用方还持有调用 1 的指针 → **UAF**。
- Rust 端 binding（`bindings/movie.rs:61, 76`）实际立即 copy bytes，所以当前未触发；任何 C 端代码若缓存 `c_str()` 就会触发。

### 5.4 修复方向

**方案 A（`thread_local`）— 推荐**:
- 把 `static std::string name` 改为 `thread_local std::string name`。
- 优点：每线程独立 buffer；C 端在同一线程内连续调用也不冲突（前提是每线程只持有一个引用）。
- 注意：`thread_local` 在 DLL 边界有 ABI 兼容性（MSVC 与 MinGW 行为不同），但纯 C++ 项目内部使用没问题。

**方案 B（`strdup` 副本）**:
- 每次返回 `strdup(name.c_str())`；调用方负责 `free()`。
- 优点：调用方生命周期可控。
- 缺点：每次 alloc/free，且需要文档化 API 契约。

**方案 C（参数 out buffer）**:
- 函数签名改为 `fceux11_lua_movie_get_name(char* buf, size_t buflen)`。
- 调用方提供 buffer。
- 优点：无 UAF 风险。
- 缺点：ABI 破坏，与现有 Rust binding 调用方不兼容。

**建议：方案 A**（最小改动，与 `src/rust/crates/fceux11-formats/src/movie.rs:967-1006` 的 Rust 端 `with_thread_local_buf` 模式一致）。

### 5.5 验证策略

| 层级 | 工具 | 检查项 |
|------|------|--------|
| 编译 | CMake | thread_local 在 Qt + MSVC + MinGW 都 OK |
| GUI 烟测 | 加载 movie，连续调用 `movie.getname()` + `movie.getfilename()` 5 轮 | 无崩溃 |
| 内存 | valgrind / ASan | 0 stale-read 报告 |

### 5.6 风险与缓解

| 风险 | 等级 | 缓解 |
|------|------|------|
| thread_local ABI 兼容性（MSVC vs MinGW） | 低 | 纯 C++ 项目内部使用，跨 DLL 边界不存在 |
| 底层 `fceu11::GetMovieName()` 自身 race（`curMovieFilename` 是无锁全局 std::string） | 中 | **不在 Phase A 范围**；flag for v1.16 lua-rewrite |
| Rust binding 已立即 copy bytes，所以方案 A 在 Rust 路径无变化 | — | 不需要改 Rust 端 |
