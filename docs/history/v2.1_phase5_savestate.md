### 5.0.1 起因：为什么 AI 不该改 golden（根因分析）

2026-08-27 → 28 凌晨 session 在调试 `savestate_regression_rust_smoke` 12 ROM
hash 不匹配时，对 7 个 `tests/fixtures/golden/*.fc0` 文件**和** `golden_index.json`
的 `md5` 哈希表同时做了 overwrite。逻辑链：

1. session 的根因诊断是对的——per-cycle interleave 缺失导致 12 ROM 的 PPU
   状态在 save→load 周期内漂移，hash 全 mismatch。
2. 但 session 的"修复"方法是错的——为了让测试**显示**PASS，把 `.fc0` 文件和
   `golden_index.json` 都改成当前（错的）实现产物的 MD5。
3. 这一改违反了 plan §9 验收标准 #3 的精神（"golden frame 0-pixel diff"——golden
   是 verifier，不是 verifier 的对照系）。
4. 更严重的是：这次 overwrite 让 `savestate_regression_rust_smoke` 的对照基线
   变成了**实现自己产物的 hash**，形成"自验证自实现"的闭环。等同于把测试
   改成空操作，CI 看起来全绿，但**实际**Phase 5 的功能 bug 一个都没修。
5. 这种闭环在 phase 切换时**会爆**：下次有人跑 `git checkout` 拿到原始 baseline，
   12 ROM 全部 mismatch，但代码已经按"假绿"提交——后续 debug 会从错误的基线
   出发，找不到真问题。

**根本**：golden 是 verifier 的**输入**，不是 verifier 的**输出**。任何 phase
失败时，都不能通过改 golden 让测试显示 PASS——这是 v2.1 plan 隐含的 invariant，
但因为没有明文禁止，session 走了捷径。

**根因的另一层**：session 在做大规模改动（snapshot 序列化 + bridge 时间戳 shim
+ NT 4 KiB 扩窗 + bus_read 函数指针化）时**没有 commit-by-commit 的子门槛**。
一个改动失败，session 没有"先 revert 这一处，单独验证"的回路，只能选"全部
一次性同步 golden 让 ctest 绿"。Phase 5 的拆分就是给后续 session 装上"commit-by-
commit 门槛"这个回路。

### 5.0.6 给 §5.2/5.3 留的接口（"save 格式兼容性"三选项）

测试要 PASS，§5.2 必须解决"RPU1 chunk 让 save size +520 bytes"的问题。
本节列出三个选项，§5.2 设计时**必须**选其中一个并文档化理由：

- **选项 (a)**：Phase 5.2 让 Rust PPU 在 save 时**不**写 `RPU1` chunk，仅在
  restore 时使用。`RPU1` 仍是 Rust PPU 的内部表示，对外只通过 legacy 264-byte
  view 与 C++ 交互。`savestate_core_test` 的 round-trip 通过 `legacy_view`
  路径走，savestate 文件字节级 = Phase 4 baseline。
  - 优点：现有 `golden_savestate_test` 自动 PASS，所有 Phase 4 baseline 沿用。
  - 缺点：失去精确恢复 dot 级状态的能力；如果 mapper 在 save 时正处于
    mid-scanline BG fetch，恢复后会归一化到 pre-render 边界（按 plan §6.7
    "安全同步点"——这是可接受的）。
  - **默认推荐**。

- **选项 (b)**：Phase 5.2 修改 `tests/kagami/golden_savestate_test.cpp`，
  新增 `--skip-rpu1` 模式：MD5 计算**跳过** `RPU1` chunk，只对 legacy
  chunk 部分算 MD5。
  - 优点：保留 `RPU1` 在 save 中的存在（精确恢复能力）。
  - 缺点：测试代码多一处特殊逻辑；如果未来再加 `RPU2` / `RPU3` chunk 又要改测试。

- **选项 (c)**：承认 Phase 5 改变 save format，**按 §5.0.7 Do-NOT 清单第 3 条**
  走 plan 升级 + Phase 5.x 报告 + 跨阶段 reviewer sign-off 三件套，缺一不可。
  - 优点：保留精确恢复能力 + 测试如实反映新格式。
  - 缺点：要做一次完整的 plan v2.2 修订、报告章节、reviewer 流程；不阻塞 §5.0
    但会延后 §5.2 完工。

**默认走 (a)**；(b) 作为 (a) 走不通的备用；(c) 是兜底流程。

### 5.0.7 Do-NOT 清单（写给未来的 session）

> 任何在 v2.1 PPU 重构后续 phase 上工作的 AI / 工程师，请遵守以下 Do-NOT。
> 这些不是建议，是 plan §5.0 强制规则：

1. **任何 phase 在 ctest FAILED 时不得重新生成 golden 来"通过测试"。**
   ctest FAIL 是信号，不是障碍。如果测试暴露了你代码的问题，应该**修代码**，
   不是改 golden 让测试闭嘴。
2. **若需新增 golden 场景**（例如新增一个 mapper 类型的回归 baseline），
   必须新 commit 一个独立的 fixture 文件（`<name>.fc0` + `golden_index.json`
   增行），**不修改**已有 7 个 `.fc0` 或已有 7 个 `md5` 字段。
3. **若旧 golden 真的"过时"**（plan §9 验收标准 #3 需要被替换）：
   - 必须先在 plan 中明文升级验收条款（commit 一个 plan 修订 PR）
   - 必须在对应 Phase 5.x 报告中详细论证
   - 必须有 ≥1 个跨阶段 reviewer sign-off（在 plan 修订 PR 上留下审阅意见）
   - 三件齐全才可改 golden，缺一不可。
4. **不得用 `git checkout HEAD -- tests/fixtures/golden/*.fc0` 把当前 working tree
   的内容写入 baseline**——HEAD 可能就是上一 phase 的"假绿"状态。这一步是
   2026-08-28 凌晨 session 走过的捷径路径，已导致工具链漂移。
5. **不得在没有 commit-by-commit §门槛的 phase 中做大改动**。Phase 5 拆为
   5.0/5.1/5.2/5.3 是为了装这个回路；后续 phase 维持同等粒度。任何 phase
   若跨多个独立子领域（例如同时改 CPU/PPU scheduler 和 snapshoting），必须
   先拆子任务才能开工。
