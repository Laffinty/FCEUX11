## A.1-1 `blargg_vbl_05_nmi_timing`（blocking）——已修复 ✅

**证据链**：
1. blargg 官方源码（`ppu_vbl_nmi/source/05-nmi_timing.s`，[christopherpow/nes-test-roms](https://github.com/christopherpow/nes-test-roms)）给出期望表：`00 4 / 01 4 / 02 4 / 03 3 / 04 3 / 05 3 / 06 3 / 07 3 / 08 3 / 09 2`（每行把测试起点推迟 1 PPU clock，测量 NMI 落在 landing 块 `ldx #1..#5` 的哪条指令之后，CRC `$A6CCB10A` 判定）。
2. Rust 实测 `[3,2,2,2,2,2,1,1,1,1]`——整体偏早 ~1 条指令（≈2 CPU 周期）。
3. C++ 引擎 `FCEUX_PPU_Loop` 的 VBL 路径（`src/ppu_rendering.cpp:1745` 一带）在 VBL 置位后**先授予 CPU 专属预算 `nd` PPU dots（`X6502_Run(nd)`，PPU 冻结）再 `TriggerNMI()`**；`e1_nmi_delay()` 默认 **8 dots**（注释明言"为 blargg vbl_05 调定"，并记录"同 dot 派发使 vbl_05 的 NMI 早一轮——与 Rust 症状一致"的历史教训，及"单参数调不准 per-row 相位漂移"的 runppu(6) 试错记录）。
4. Rust 帧循环 `fceux11_run_frame_interleaved`（`src/rust/src/lib.rs`）在 `take_nmi_direct` 命中的**同一 dot 立即** `trigger_nmi`——缺这个预授予。facade 的 `g_e1_nmi_fresh` 一次边界推迟（Rust CPU 经 `kagami_bridge` 消费，`tick.rs` 有测试覆盖）两侧一致，不是差异源。

**修复**（`src/rust/src/lib.rs`）：`take_nmi_direct` 命中后、回调前，`fceux11_cpu_run_with_tick(cpu_state, nd)` 授予 CPU-only 预算（FFI 参数为 PPU dots，1/16-dot 内部单位，与 C++ `X6502_Run(nd)` 同量纲）。`nd` 默认 8，env `FCEUX11_E1_NMIDELAY` 可覆盖（与 C++ 同名，batch 口径对齐）。

**结果**：`vbl_05_nmi_timing` **PASS**（2.4s）；`vbl_01_basics` 保持 PASS。母套件 `ppu_vbl_nmi` 仍卡在 `02-vbl_set_time`（见 A.2）。

## A.1-2 `blargg_ppu_read_buffer`（blocking）——诊断中

**证据链（探针基建见下）**：
1. ROM 为 bisqwit/gblargg 合并版测试（[readme](https://raw.githubusercontent.com/christopherpow/nes-test-roms/master/ppu_read_buffer/readme.txt)）：~79 个子测试，文本协议回显 `$6004+`（moving zero terminator），$6000=0x80 表示运行中。卡死时文本停在 "Testing basic PPU memory I/O"。
2. 新增探针：两侧 A2002 处理器输出带 `ret` 值的读取流（C++ `E1 P2002_READ … ret=0x..`（`FCEUX11_E1_TRACE=1`）、Rust `R3 P2002_READ … ret=0x..`（`FCEUX11_PPU_PHASE_TRACE=1`））+ 独立 env 的周期性 `$6004` 文本转储（`FCEUX11_BLARGG_TEXT=1`，两侧同格式）。
3. 前 **120 帧两引擎 $2002 读取流完全同步**（27939 个共享 abs 点 (sl,ret) 全对齐；C++ 侧 `ppur.status.sl` 在启动期有 sl=0 探针伪影，ret 值不受影响）。
4. C++ 全程 ≈700 帧完成；Rust 3000 帧仍 0x80。文本时间线对比（进行中）用于定位 Rust 推进停滞的精确 abs 窗口。

**状态**：分叉窗口在 120-700 帧之间，二分定位中。
