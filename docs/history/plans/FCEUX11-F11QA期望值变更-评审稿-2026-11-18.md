### 1.3 「翻转」操作上意味着什么（影响 grade / pass_to_fail 吗）

「翻转」可落地的形态只有两种（今日体系内没有第三种）：

- **形态 A：重钉冻结基线**——用 `scripts/phase8_generate_baseline.py` 从一次新的
  矩阵实跑重建 `f11qa_baseline_frozen.json`，049/050/051 变 `true`。此后下次矩阵：
  三条进 `pass_to_pass`，`fail_to_pass` 清零，`baseline_drift` 三条消失。
- **形态 B：引入 approved 机制**——在 runner 侧加「已批准漂移清单」（新代码，
  matrix.rs 查表置 `approved: true`）。属新功能开发，需另立项；今日不存在。

对判读体系的影响（两形态等价，按形态 A 表述）：

1. **fail_to_pass：3 → 0。** R4 gate 对 fail_to_pass **本就不判红**
   （f11qa.yml ：519-544，v1.18.1 修正：「精度进展，记录不判红」）⇒
   **翻转不改变今天的 gate 读数**，只是让汇总更干净。
2. **grade：不变（B）。** 判级由 `grade.rs` 决定：D = 存在 blocking 失败或
   pass_to_fail 回归；B/C = 失败全部是 advisory 且在冻结基线内
   （`grade_reasons = "10 advisory known-limit failure(s), all within frozen baseline"`）。
   翻转不产生 blocking 失败、不产生回归 ⇒ **今日 grade 仍为 B**。
3. **pass_to_fail（未来语义）：这才是真正的变化点。** 基线翻 true 后，这三条
   任何一次 FAIL 都会成为 **pass_to_fail 回归** ⇒ R4 gate **硬红**
   （f11qa.yml ：538-542「出现即回滚该 PR」）+ grade 直接 D。
   而现状（基线 false）下，同样的 FAIL 只是 `fail_to_fail`，**无任何红**。
   ——即：翻转把三条「预算边缘测试的 FAIL」从静默变成**合并阻断**。

### 1.4 建议方案（维持不翻；翻转与实质精度改进捆绑，LT-07 口径）

- **三条全部维持现状**（冻结基线 false + `approved: false` 漂移登记 + fail_to_pass
  进展记录）。fail_to_pass=3 在现行 gate 口径下**合法且可长期存在**，不产生任何红。
- **翻转的前置条件**（满足其一才重开评审）：
  1. 对应的实质精度工作落地——049 需 M1–M3 RE（`docs/tech/ppu_2007_read_buffer_state_machine.md`
     §4 的 U1/U2 两项未实现闭合）；050 需 OAM DMA / PPU 区 dummy-write 路径建模；
     051 需 wait_vblank 相位竞争根因处置；
  2. 或至少给出「为什么当前预算下的 PASS 已代表达标语义」的**独立论证**
     （不是把预算再放宽一次）。
- **各条建议分级**（同批捆绑评审，但优先级不同）：
  - 049：**最不宜翻**（review 报告 §1.6 的帧预算来源问题；「精度已达标」假象风险最大）；
  - 050 / 051：PASS 同样是「预算内跑完」而非「语义达标」（各自 known_limit 在案），
    与 049 同批处置，不单独先翻。

### 1.5 反证（支持翻转的论点，与为何不成立）

| 支持翻转的论点 | 反证 |
|---|---|
| 「fail_to_pass=3 说明基线过时，过时就该翻」 | 基线确实过时，但处置是**重钉（需授权评审）**而非默认翻转；`approved: false` 正是体系里「未授权」的显式标记，删掉这个标记不等于获得授权 |
| 「翻了现在也没影响（fail_to_pass 不判红）」 | 成立但不完整：真实代价在**未来**——三条预算边缘测试（bisqwit 怪兽测试，预算经人治放宽）的任何 FAIL 会变成 pass_to_fail 硬红 + grade D，把**时序噪声**变成**合并阻断**；这是把 false 底座换成 true 底座的不可逆语义升级 |
| 「翻了矩阵干净（fail_to_pass=0）」 | 「干净」是通过声明「精度已达标」换来的；三条的精度缺口（M1–M3 / DMA dummy write / wait_vblank 竞争）都还登记在案，声明与事实不符 |
| 「反正是 advisory，翻基线不影响判红」 | advisory 影响的是**失败时的判红**；基线值影响的是**迁移桶归属**（fail_to_fail vs pass_to_fail）。两个维度独立，翻基线恰恰是改第二个维度——影响最大的一处 |

### 2.3 改成 blocking 会影响什么（grade 语义 / pass_to_fail）

`grade.rs` 的判级规则：**D = 任一 blocking 失败 或 任一 pass_to_fail 回归**；
B = 无 blocking 失败、无回归、其余失败全是 advisory 且在冻结基线内。
R4 gate（f11qa.yml）把 grade ∈ {D, E} 判为硬红。按「产物 advisory → 生成器 blocking」
逐组给出后果：

1. **当前 FAIL 的 10 条**（037/038/077/081/096/097/099/107/108/115）：
   翻成 blocking ⇒ 立即出现 **10 个 blocking 失败** ⇒ **grade 直接 D**
   ⇒ R4 gate 红 ⇒ CI 禁止合并。这 10 条正是 `grade_reasons` 里
   "10 advisory known-limit failure(s)" 的全部来源——现行 B 级
   **完全依赖**它们保持 advisory。
2. **当前 PASS 的 3 条 fail_to_pass**（049/050/051）：
   翻成 blocking 今日无读数变化（它们 PASS），但**未来任何一次 FAIL**
   同时成为 blocking 失败（grade D）**且**是基线 false 下的 fail_to_fail
   （不构成 pass_to_fail，gate 不红）——即 grade 会因 blocking 失败直接 D，
   gate 的 pass_to_fail 腿反而**不**红（基线仍 false）。语义 = 「这三条从
   『失败可容忍』变成『失败即禁发』」，而它们的 PASS 依赖放宽后的帧预算
   （§一 1.4）⇒ 时序噪声会被升级成禁发事件。
3. **当前 PASS 的 2 条 pass_to_pass**（056/078）：
   翻成 blocking 今日无读数变化；未来 FAIL = blocking 失败（grade D）
   **且** pass_to_fail（gate 硬红）——双红。由于这两条 known_limit 已
   RESOLVED、语义上它们**本来就是修复完成的 blocking 用例**，这一组是 15 条里
   「翻回 blocking」论据最强的，但它同样属于期望值变更，须评审放行。
4. **汇总**：全部翻 ⇒ 今日 grade B → D，CI 红；逐条翻也遵守同一规则。
   反方向（维持 advisory）对判读体系**零影响**。

### 2.4 建议：维持产物口径（advisory），理由与残留观察

**建议：15 条全部维持产物 advisory，生成器数据行不改判。**
理由（v2.0.2 业主裁决的硬依据，AGENTS.md「v2.0.2 线收口状态」§4）：

- **判红体系收益 = 0**：这 15 条全是 `failure_means: advisory` 且冻结基线 false
  （除 056/078 为 true）⇒ 修它们**不改 grade、不改 pass_to_fail**；
  反过来，把它们翻回 blocking 只会把 10 个已知限制变成禁发事件——
  「决策依据 = 用户可感 / 解锁 / 防呆 / 成本」四轴上没有任何一轴受益。
- **历次降级各有书面依据**：034/052 等 vendor_state 通道是 v1.8 设计内
  （rom-suite advisory 不 blocking）；037/038/049/050/051/107 等
  是 v2.0.2 业主裁决 + V4 逐条回源码复核的产物（known_limit 措辞与
  基线读数一致性已抽查，v2.0.4 r8）；115 是跨机不可比的墙钟 bench。
- **生成器侧处置**：数据行保持 blocking 现状也可接受（漂移被硬护栏拦住，
  不会落盘）——但更诚实的形态是**评审通过后**把这 15 条的数据行改 advisory
  并同步登记，使生成器↔产物漂移彻底清零（§四）。**在本评审通过前，
  任何一侧都不动。**

三条**残留观察**（不阻塞本评审，登记给下轮）：

1. 056/078 的「RESOLVED known_limit + advisory failure_means」组合是自相矛盾形态：
   既已 RESOLVED 且 PASS，failure_means 应随 known_limit 一起回 blocking
   （或把 RESOLVED 的 known_limit 改写为「已解决、维持 advisory 以免未来
   回归禁发」的显式裁决措辞）。二选一，需业主表态。
2. `tests.json` 顶层 `policy.r4_gate_thresholds.fail_to_pass_max = 0` 与 gate
   实际口径（fail_to_pass 进展不判红，v1.18.1 修正）**矛盾**——policy 字段是
   死文本，谁都不读它判红。随 §三 的口径评审一并裁决（改 policy 文本或改 gate）。
3. 若未来某条 advisory 用例被实质修复（FAIL → PASS），处置顺序应为：
   先翻**冻结基线**（重钉，形态 A）→ fail_to_pass 记为进展 → 
   **再**评审 failure_means 是否回升 blocking——两步都是期望值变更，各自走评审。

## 三、F11QA.md R4 gate 计数口径问题

### 3.1 现状：三个数互不一致 + 一处 policy 矛盾

| 数 | 值 | 出处 | 时点 |
|---|---|---|---|
| `tests/tests.json` 用例数 | **123**（kgmqa-001~123） | 产物 `cases` 计数 | 当前 |
| R4 gate 的 total 下限常数 | **120**（`-lt 120`） | f11qa.yml :512 | v1.8 定死，未随清单增长 |
| 矩阵产物 `summary.total` | **122** | `f11qa_migration_matrix.json` | 2026-11-10（当时清单 122 条） |
| 冻结基线条数 | **121** | `f11qa_baseline_frozen.json` | 2026-09-26 |
| F11QA.md 头表「清单条目」 | **120** | F11QA.md :10 | f19fa7d CI 快照（带 ⚠️ 条数漂移注） |

具体矛盾点：

1. **total 下限常数 120 与清单 123 脱节**。历史教训已在 yml 注释里写明
   （:487-497）：A2 批次合法新增 kgmqa-121 后，`-ne 120` 严格相等判据
   **确定性打红** main 的三个 CI run（68/69/70），当时零回归。现口径已改
   `-lt 120`（下限），但常数本身仍是 120 —— 每次合法加用例，这个「差距」
   就无声扩大一格；它不再打红 CI，但也**不再防住任何东西**（一个把清单
   删到 120 以下的回归仍会被抓，可「缓慢缩水」到 120 以内则不会）。
2. **policy 与 gate 的 fail_to_pass 口径相反**（§二 2.4 观察项 2）：
   `tests.json` 的 policy 写 `fail_to_pass_max: 0`，gate 实际按
   「精度进展，记录不判红」执行（v1.18.1，有 run 98267393461 的实测教训：
   把 fail_to_pass 判红会卡住真修复）。
3. **F11QA.md 头表是 120 时代快照**（:22-27 已自注）：清单 123（A 类 44 /
   B 类 79）、PASS/FAIL 106/14、advisory 占比 14/120 等均待下次 CI 实跑回填
   （F11QA.md §0 的数字回填纪律本就要求如此，非缺陷，登记提醒）。
4. 次要：advisory cap 的分母用 `summary.total`（矩阵 ran 数，122/123），
   与清单数差 1——量级无害，口径上可与 1) 一并统一。

### 3.2 两个可选口径

**口径 A：下限从清单推导（常数删除）**——`total -lt` 的 120 改为
`@($manifest.cases).Count`（gate step 本来就为 vendor_state 校验加载了 manifest，
r21 已有同款先例：vendor_state 总和从硬编码 78 改为清单推导）。
- 优点：加用例永不打红（68/69/70 教训根治）；「静默跳过/缩水」防护自动跟随
  清单现态；消灭一个手工同步点（坑 15 同族——手工常数 vs 产物漂移）。
- 缺点：失去**绝对下限**——若有人删清单，阈值跟着降，删 40 条也不红；
  防作弊完全依赖 runner 侧 test_set_diff/new_test 结构（matrix.rs 已有，
  但「删用例」目前只有 `test_set_diff.removed` 展示，无判红）。
  若采纳 A，建议**同时**给 `removed` 非空加一条判红（否则 A 是净放松）。

**口径 B：保留常数 + 显式 bump**——常数随每次合法加用例在**同一 PR**里
人工抬升（120 → 123），并在 F11QA.md 头表同步。
- 优点：绝对下限永在；每次抬升都是显式 diff，评审可见。
- 缺点：每次加用例**确定性打红 CI** 直到常数跟进（68/69/70 教训重演风险）；
  多一个手工同步点，且恰恰是坑 15 记录过的「半手工产物漂移」形态。

**建议**：口径 A + removed 判红。理由：gate 已有的防作弊结构
（new_test 桶隔离、test_set_diff 显式暴露、vendor_state 清单推导）说明
「从清单推导」是本体系既定演进方向（r21 注释原话：「常数不再随门禁增减漂移」）；
口径 B 的唯一优势（绝对下限）可用 removed 判红补齐，而 A 消灭的是
反复发生的确定性假红。

> ⚠️ 两个口径都是**门禁判据变更**，与 §一/§二 的期望值变更同级——
> 本稿只并列方案，落地须业主逐项确认；落地时同步改 yml 注释里的
> 「v1.8 严格 120 项」历史段（保留原文、追加修订注）与 F11QA.md 头表。
