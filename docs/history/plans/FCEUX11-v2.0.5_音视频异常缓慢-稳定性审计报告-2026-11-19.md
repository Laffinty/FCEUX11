## 一、摘要（先看这里）

### 1.1 症状拆解

「音频和视频速度异常缓慢」这一个描述其实包含**两种互斥的机制**，审计时必须分开：

| 机制 | 特征 | 可观测判据 |
|---|---|---|
| **M-阻塞型** | 每帧在某个循环里等满固定时长（如 1 秒）⇒ 音视频**同时**变慢，**且 GUI 也卡** | 窗口无响应 / 帧率骤降到 1 fps 量级 / CPU 内核态占比极高 |
| **M-计算型** | 每帧算得更久（如滤波、重采样）⇒ 帧率下降但 GUI 仍响应 | 窗口响应正常 / 帧率小幅下降 / 用户态占比升高 |

**关键**：只有 M-阻塞型能同时造成「音视频一起变慢 + 不稳定」。本次审计的主线就是
找这一类的机制。

### 1.2 最终判定

| 编号 | 缺陷 | 能否解释症状 | 状态 |
|---|---|---|---|
| **A1** | `KillSound()` 无条件 `join` 探测线程，在 GUI 线程 + wrapper 锁内 | **能**（M-阻塞型） | 机制**已钉死** + 门槛**已量化**；本机 300 ms 探测 ⇒ 不可达；**待授权修复** |
| F1 / A4 | `WriteSound` 环满自旋，在 wrapper 锁内 | 能（M-阻塞型） | **实测否证**（8 种状态 × 多次，`draining` 零出现） |
| A2 | 静态 `std::thread` 未 join ⇒ 退出时 `terminate` | 否（退出期崩溃，非变慢） | 静态已钉死，可达性条件性，未实测 |
| A3 | `SDL_setenv("SDL_AUDIODRIVER")` 进程级永久副作用 | 否 | 静态已钉死，未实测 |
| A5 | 无设备时内核仍全量合成样本并丢弃 | 否（量级 1~3% 帧时间） | 静态已钉死，量级未测 |
| A6 | 「复用已开设备」分支是死代码 | 否 | 静态已钉死 |
| A7 | `failAt == 0` 哨兵与 `SDL_GetTicks()==0` 碰撞 | 否 | 概率 ≈ 0，未实测 |
| A8 | `fillInit`/`s_BufferSize` 等非原子跨线程共享 | 否 | 形式存在，实际不可观测 |

⇒ **全表只有一个能解释症状，就是 A1。**

### 1.3 A1 的核心量化结论（本报告最有价值的一条）

实测时间轴（`act_d0c` / `act_rep1` 两组，逐字一致）：

```
窗口出现        : 554 ~ 563 ms
ROM 加载完成    : 581 ~ 593 ms
音频配置对话框出现: 1045 ~ 1046 ms   （比 ROM 加载晚约 455 ms）
设备探测耗时    : 300 ms            （timing 实验实测）
```

⇒ 探测在「ROM 加载 + 300 ms」结束，而**最早的 GUI 操作**在「ROM 加载 + 455 ms」才可能发生。
**任何 GUI 触发的 `KillSound()` 都晚于探测结束，`join` 无物可等。**

**触发门槛（可判定的判据）**：

> `A1` 可触发 ⟺ 该主机上 `SDL_OpenAudio()` 的探测耗时 **> 约 455 ms**。

- 本机 300 ms ⇒ 结构性不可达（4 组实验确认，0 ms 阻塞）
- 业主此前报告的机器 8 000 ms ⇒ **可达**，`join` 最多阻塞约 7.5 s

这就解释了「同一份代码，一台机器正常、另一台体感卡死」——不是随机性，是探测耗时差异。

## 三、静态分析：候选清单与逐条推理

### A1 · `KillSound()` 的 `join` 把探测耗时搬回 GUI 线程（★ 唯一能解释症状）

**坐标**

- `src/drivers/Qt/sdl-sound.cpp:100`（`static std::thread s_audioOpenThread;`）
- `src/drivers/Qt/sdl-sound.cpp:364-369`（`AudioEnsureDeviceOpen` 里 `join` 上一次尝试）
- `src/drivers/Qt/sdl-sound.cpp:765-769`（`KillSound()` 里 `join`）
- `src/drivers/Qt/sdl-sound.cpp:253-324`（`AudioOpenDeviceWorker`，探测实际发生在这里）
- `src/drivers/Qt/fceuWrapper.cpp:144-159`（`DriverInitialize` → `InitSound()`）
- `src/drivers/Qt/fceuWrapper.cpp:181-195`（`DriverKill` → `if(inited&1) KillSound()`）
- `src/drivers/Qt/fceuWrapper.cpp:485`（`CloseGame` → `DriverKill()`）
- `src/drivers/Qt/ConsoleSoundConf.cpp:464-469 / 663-668 / 680-685`（改设置 → `KillSound(); InitSound();`）
- `src/drivers/Qt/ConsoleVideoConf.cpp:951-954`（同上）

**推理链**

1. `36af048` 把 `SDL_OpenAudio()` 搬到后台线程（修「加载 ROM 卡十秒」），`InitSound` 不再等待。
2. 但 `KillSound()` **无条件** `join` 该线程（`:765-769`）。若此刻探测仍在飞行，`join` 要等满剩余探测时长。
3. `KillSound()` 的全部调用链都在 **GUI 线程 + `FCEU_WRAPPER_LOCK`** 之下：
   `LoadGame → CloseGame → DriverKill → KillSound`；三个设置对话框同理。
4. 持锁期间模拟线程被挡在 `consoleWindow->mutex` 外 ⇒ **画面冻结、键盘无响应** ⇒ 与业主症状一致。

**置信度**：机制 **已钉死**；触发为条件性（见 §1.3）。**归属：本次改动（`36af048`）引入。**

### A2 · 静态 `std::thread` 退出时未 join ⇒ `std::terminate`

**坐标**：`sdl-sound.cpp:100`（静态线程对象）、`:766-768`（唯一正常 join 点）、
`fceuWrapper.cpp:156-159`（`inited |= 1`）、`:190-194`（`if(inited&1) KillSound()`）、
`ConsoleSoundConf.cpp:574-598`（对话框里 `InitSound()`，**不更新 `inited`**）、
`sdl-sound.cpp:385-389`（`SDL.Sound == 0` 时 `InitSound` 提前 `return 0`）

**推理链**

1. `std::thread` 在 join/detach 前始终 joinable，析构时调用 `std::terminate()`。
2. 唯一正常 join 点是 `KillSound()`，而它只在 `DriverKill` 且 `inited&1` 时被调用。
3. `inited&1` 只在 `DriverInitialize → InitSound()` 返回非 0 时置位；`SDL.Sound = 0` 时
   `InitSound` 返回 0 ⇒ 该位不置位。
4. 用户随后在声音对话框勾选「启用声音」→ `enaSoundStateChange` → `InitSound()`
   （`ConsoleSoundConf.cpp:586`），**绕过 `DriverInitialize`，不更新 `inited`**
   ⇒ 线程被创建、跑完、仍 joinable 且无人 join。
5. 退出时 `DriverKill` 因 `inited&1 == 0` **跳过** `KillSound()` ⇒ 静态线程析构 ⇒ `terminate`。

**置信度**：C++ 语义 **已钉死**；**可达性条件性**（需：声音关闭启动 → 对话框开启 → 退出）。
**归属：本次改动引入。** 未实测。

### A3 · `SDL_setenv("SDL_AUDIODRIVER", …)` 是进程级永久副作用

**坐标**：`sdl-sound.cpp:276-290`（回退循环）、`:281`（`SDL_setenv`）、`:259-262`（`InitSubSystem` 失败时整个回退被跳过）

**推理链**

1. `SDL_setenv` 改的是**进程环境变量**（`overwrite=1`），SDL 每次 `InitSubSystem` 都重新读它。
2. 回退循环依次写入 `directsound`、`winmm`，**结束后保留最后一次的值**，进程内不再恢复。
3. ⇒ WASAPI 只在进程内首次尝试；声卡后来恢复（USB 音箱重新通电）时**音频不会自动恢复**，
   除非重启进程。子进程同样继承该变量。
4. 附带：`InitSubSystem` 本身失败时（`:259`）整个回退循环被跳过，连 directsound 都不试。

**置信度**：代码事实 **已钉死**；「声卡恢复后音频不恢复」条件性。**归属：本次改动引入。** 未实测。

### F1 / A4 · `WriteSound` 环满自旋，且发生在 wrapper 锁内

**坐标**：闸门 `sdl-sound.cpp:584-587`；三处自旋 `:638-650` / `:676-690` / `:706-720`；
锁内证据 `fceuWrapper.cpp:1392`（取锁）→ `1551`（`DoFun`）→ `1225`（`FCEUD_Update`）→ `1176`（`WriteSound`）→ `1560`（放锁）

**机制**：闸门只判「**根本没有设备**」（`s_audioDeviceOpen == false`）。若设备**已打开但无人排空**
环形缓冲，每帧撞上 `s_BufferIn == s_BufferSize` → `SDL_Delay(1)` 自旋到 `waitCount > 1000`
（`waitCount` 是每次调用内的局部量 ⇒ 每帧重付约 1 秒）。这 1 秒在 wrapper 锁内 ⇒
一帧/秒 + GUI 卡死，与业主症状逐字对应。

**旁证**：GBA 路径免疫——`fceuWrapper.cpp:1536` 先取 `GetWriteSound()`，满则不写，不进自旋。
作者知道满环会卡，只是没在 NES 侧防。

**置信度**：机制 **已钉死**；但**触发条件在 13 组实测中从未出现** ⇒ §五 判否证。

### A5 · 无设备时内核仍全量合成样本并丢弃

**坐标**：`sdl-sound.cpp:499`（无条件 `fceu11::Sound(rate + adj)`）、
`sound.cpp:1764-1768`（`FSettings.SndRate = Rate`）、`sound.cpp:1745-1749`
（`SndRate == 0` ⇒ `Dummyfunc`）、`fceu.cpp:882`（`ssize = FlushEmulateSound()`）

**推理链**：上游旧行为是「开设备失败 ⇒ `KillSound()` ⇒ `Sound(0)` ⇒ 内核用 `Dummyfunc`，
零合成开销」。PERF-01 改成「无论如何返回 1」后，`:499` 无条件把 `SndRate` 置为非 0
⇒ 内核每帧照常合成约 735 个样本，再由 PERF-02 的闸门丢弃。HQ 档每帧还要跑 FIR。

**置信度**：代码事实 **已钉死**；量级**未实测**（估计 LQ < 0.5%、HQ 1~3% 帧时间）。
**归属：PERF-01 引入、PERF-02 未回退。**

### A6 · 「复用已开设备」分支是死代码

**坐标**：`sdl-sound.cpp:338-345`（复用分支）、`:470-491`（`deviceReady` 两分支）；
调用点：`fceuWrapper.cpp:308`、`:229-231`、`ConsoleSoundConf.cpp:466/586/665/682`、`ConsoleVideoConf.cpp:953`

**推理链**：复用需 `s_audioDeviceOpen == true` 且速率一致。但**每次** `InitSound` 前必有一次
`KillSound`（把该标志清零）：ROM 切换走 `CloseGame → DriverKill`；三个设置对话框是
`KillSound(); InitSound();` 成对调用；「启用声音」路径此前也是关的。
⇒ `deviceReady == true` **不可达** ⇒ 复用分支永不执行 ⇒ PERF-01「不再每次重开设备」的收益**实际未落地**。

**实测佐证**：`act_d0c` 中改一次采样率即出现第 2 次 `Loading SDL sound` ⇒ 设备确实被重开。

**置信度**：**已钉死**（7 个 `InitSound` 调用点逐一核对）。**归属：本次改动引入（设计未达成）。**

- **A7**：`sdl-sound.cpp:107-110 / 316 / 356`，`s_audioFailAtMs` 用 `0` 表示「无失败记录」，

## 五、已被实测否证的项（不要再重排）

### 5.1 `F1` / `A4`（`WriteSound` 自旋）— **否证**

8 种状态（有声卡 / 无声卡 / 关 ROM / 重载 / 改设置 / 最高音质 / 设备不可用 / 长时），
**`Sound sink is not draining` 一次都没有出现**。且 #2 证明「无声卡」路径下帧率仍是 58.2 fps。

### 5.2 关键：**丢弃样本不影响内核时序** — 已钉死

审计初期曾怀疑 PERF-02 的闸门丢弃样本会扰乱内核音频时序，逐条核对后**不成立**：

1. 每帧样本数由 CPU 周期数决定（`sound.cpp:1425, 1446`），与驱动端无关；
2. APU 帧中断计数 `fhcnt` 由**周期**推进（`sound.cpp:837/842`），与样本数无关；
3. 视频节流是**纯时间**的（`sdl-throttle.cpp:299-343`），不依赖音频排空；
4. `WriteSound` 只把内核已算好的样本搬进环形缓冲。

### 5.3 其他已排除的怀疑点

| 怀疑点 | 为什么排除 |
|---|---|
| `deviceReady == true` 时 `s_Buffer` 悬垂 | 该状态不可达（A6）；即使可达，`SDL_CloseAudio` 保证回调线程先退出 |
| `s_BufferSize == 0` 导致 `% 0` | 不可达：`InitSound` 必先赋 ≥ 2048 才能开设备 |
| `WriteSound` 三处 `return` 泄漏 `SDL_LockAudio` | 三个 `return` 都在 `SDL_UnlockAudio()` 之后（`:648/686/716`） |
| 锁内 sleep 阻塞 GUI | `msleep(16)` / `msleep(100)` 都在 `fceuWrapperUnLock()`（`:1560`）之后 |
| `GameInfo` 锁外读导致 UAF | 两处锁外读（`:1396`、`:1574`）**只做空判定、不解引用**；解引用点在锁内（`:1421`） |
| **CPU 内核态 75% 说明卡在等待** | **错判**。这是正常节流的形状：每帧 `QThread::msleep(targetMs-1)`（15 ms）+
  亚毫秒忙等（`sdl-throttle.cpp:284/288-291`）⇒ 内核态约 75%、用户态约 25%，与实测 74.5%/25.5% 精确吻合 |
| **画面静止 = 模拟卡死** | **错判**。1942 标题画面本就在等输入；启用帧计数后读到 707 帧 ⇒ 帧在推进 |

### 5.4 一处需要纠正的既有认知

`fceuWrapper.cpp:1574-1586` 新增的 `msleep(16)` 分支**实际不可达**：它嵌在 `:1421` 的
`if (GameInfo)` 内部，需要「`:1421` 判真、`:1574` 判假」之间发生 `GameInfo` 翻转，
而所有 `GameInfo` 写点都在 wrapper 锁内。「没游戏在跑」的真实路径是 `:1597` 的 `msleep(100)`。
⇒ 该改动在节流侧**没有产生实际效果**。

## 七、为什么「13 组全正常」仍是有效结论

有人会问：测了 13 组都没问题，凭什么说 A1 是真缺陷？

因为 A1 的成立**不依赖复现**，而依赖三个可独立验证的事实：

1. `KillSound()` **无条件** `join` —— 读代码即可确认，无其他分支（`:765-769`）；
2. 调用链在 **GUI 线程 + wrapper 锁** 内 —— 读代码即可确认（`:485` → `:192`）；
3. `join` 的耗时 = **剩余探测时长** —— 由上两点逻辑必然。

本机探测 300 ms 只是让「剩余探测时长」几乎为 0，从而**观测不到**。
在探测 8 s 的机器上，同一路径就是 7.5 s 冻结。**机制与门槛都已量化，无需等待复现。**

## 八、复现与判据（零成本清单）

### 8.1 三条零成本判据（任何人可独立执行）

| 判据 | 怎么取 | 读数含义 |
|---|---|---|
| **① 帧率** | 配置 `SDL.ShowFrameCount = 1`，画面底部显示帧计数；两次截图取差 ÷ 间隔 | 接近 60 = 正常；≈1 = 阻塞型故障 |
| **② 音频健康** | 「选项 → 音频配置」：`Sink Starve Count` 与缓冲占用百分比 | Starve > 0 ⇒ 供给不足；占用 > 90% ⇒ 消费端卡住 |
| **③ 阻塞量化** | 对一个窗口循环 `SendMessageTimeout(WM_NULL, 120ms)`，记录连续失败时长 | > 0 即 GUI 线程被阻塞，值即阻塞时长 |

### 8.2 复现 A1 的唯一方式

需要一台**探测耗时 > 约 455 ms** 的主机（例如默认音频端点不可用时 WASAPI 会长时间探测）。
在该机上：加载 ROM 后 **8 秒内**再加载/关闭 ROM，或打开声音设置改任一项 ⇒ 观察窗口冻结。

本机（300 ms）无法复现，**不必再排期重测**。

### 8.3 自动化脚本

`.zcode/soundprobe/`（**gitignored，不入库**）含本轮全部脚本：`round3.ps1`（关 ROM + 重载）、
`round4.ps1`（长时采样）、`round5.ps1` / `round6.ps1`（改设置，含鼠标点击下拉框与
`Loading SDL sound` 计数验证）、`capture.ps1` + `run_capture.bat`（交付业主的一键采集）。

其中两条经验固化为结论：

1. **GUI 自动化必须验证触发成功**：`round6` 前两轮因 Tab/方向键未命中控件而**假绿**，
   加入「`Loading SDL sound` 计数 + 配置落盘」双验证才确认真的执行；
2. **Qt 对话框控件定位用鼠标点击 + 实测相对坐标**（本报告：Rate 下拉框 ≈ `(0.217, 0.462)`），
   比 Tab 遍历可靠。

## 九、结论与建议

### 9.1 结论

1. **能解释业主症状的机制只有一个**：`A1`（`KillSound` 的 `join`）。
2. **A1 的机制已钉死、门槛已量化**：探测 > 约 455 ms 才可触发；本机 300 ms ⇒ 13 组实测全正常。
3. **最初最可疑的 `F1`（`WriteSound` 自旋）已被否证**：8 种状态下 `draining` 零出现。
4. 其余 5 项（A2/A3/A5/A6/GBA 残留）**都不产生「音视频同时变慢」**，属登记项。

### 9.2 建议（单条，可否决）

**授权修复 A1**，因为它是唯一「机制已证 + 门槛已量化」的阻塞型缺陷，且修法局部、不触及 NES 行为：

- `KillSound()` 不再无条件 `join`：探测仍在飞行时 **detach 或跳过 join**（线程本身以原子标志
  收尾），仅在确已结束（`s_audioOpenInFlight == false`）时才 join；
- `SDL_CloseAudio()` / `SDL_OpenAudio()` 用 `s_audioOpenMutex` 串行化，保证不会并发进 SDL 音频子系统；
- 验收判据：在探测慢的机器上「加载 ROM 后 8 秒内关 ROM」不再冻结；本机 13 组读数不变。

**不授权则维持登记**——本机已无法复现，风险由「慢探测机器」的体感承担。

### 9.3 明确不建议做的

- **不建议**在没有探针的情况下继续盲测更多路径（13 组已覆盖主要路径）；
- **不建议**改 `GameInfo` 锁外读（§5.3）与 `fceuWrapperIsLocked()`——语义脆弱点，非当前故障；
- **不建议**为 A5（无设备时合成）先做优化——量级未测，可能不值得。

## 十一、r2 更正（2026-11-19，开工前独立复核）

> 复核方式：逐行读源码 + 两条独立只读审计线交叉验证。**A1 的机制与门槛结论全部成立**，
> 下列三处需要更正；已在 §1.2 / §三 / §六 保留原文（不重构），以本节为准。

### 11.1 A6「复用已开设备分支是死代码」——**推翻**

§三 A6 的前提「每次 `InitSound` 前必有一次 `KillSound`」不成立。反例（与 A2 同一条路径）：

1. `SDL.Sound = 0` 启动、加载 ROM ⇒ `InitSound` 在 `sdl-sound.cpp:385-389` 提前返回 0
   ⇒ `inited` 的 bit1 不置位（`fceuWrapper.cpp:156-159`）；
2. 用户在声音对话框勾选「启用声音」⇒ `ConsoleSoundConf.cpp:586` 调 `InitSound()`，
   **不更新 `inited`** ⇒ 探测线程起、设备真的打开；
3. 下一个 ROM 的 `CloseGame → DriverKill` 因 `inited&1 == 0` **跳过 `KillSound`**
   ⇒ `s_audioDeviceOpen` 仍为 true；
4. 该 ROM 的 `DriverInitialize → InitSound` 命中 `sdl-sound.cpp:338-345` 的**复用分支**。

⇒ 「PERF-01 的复用收益未落地」这一判断只在「`inited` 与真实状态一致」时才成立。
反过来说：**修 A2 时不能把复用分支当死代码删掉**，它是可达的。对照：实测 `act_d0c` 出现
第 2 次 `Loading SDL sound` 只能证明「那一组里设备被重开」，不能证明复用不可达。

### 11.2 §5.4「`msleep(16)` 分支不可达」——**推翻**

两条独立理由：

1. 该判断在 `fceuWrapper.cpp:1574`，而 `fceuWrapperUnLock()` 在 `:1560` **已经执行**
   ⇒ `:1421` 的 `if (GameInfo)` 对它没有保护力。`GameInfo` 是普通指针，GUI 线程可在
   这个窗口内把它置 0（写点：`fceu.cpp:203`/`:477`/`:596`，`fceuWrapper.cpp:478`/`:487`）。
2. 「所有 `GameInfo` 写点都在 wrapper 锁内」也不成立：`input.cpp:1356` 的 `CloseGame()`
   由 `FCEUD_UpdateInput`（`:1702-1716`）调用，跑在 GUI 线程的 `emuFrameFinish` /
   `updatePeriodic`（`ConsoleWindow.cpp:684`/`:707`）里，**完全无 wrapper 锁**。

⇒ 这是「锁外双检查一个普通指针」，窗口很窄但**不是不可达**。审计报告 §5.3 里
「不建议改 `GameInfo` 锁外读」的结论仍成立（属语义脆弱点、非当前故障），本条只更正**定性**。

### 11.3 §1.2「全表只有一个能解释症状」——**覆盖面收窄**

A1 造成的是**一次冻结**（最多「剩余探测时长」），不是持续降帧；而 §四 的 13 组实测只覆盖
「有声卡 / 无声卡 / 拔掉再启动 / 改设置 / 长时」八类状态，**没有覆盖「设备已开、回调停排空」**。
在该状态下：

- `WriteSound` 的闸门（`sdl-sound.cpp:584-587`）只判 `!s_audioDeviceOpen`；
- 三处自旋（`:641-650` / `:679-688` / `:709-718`）的 `waitCount` 是**每次调用内的局部量**
  ⇒ 每帧重付约 1 秒，**永久 1 fps**，且同样在 wrapper 锁内。

⇒ 若业主描述的是「持续变慢」而非「卡一下」，A1 不足；该状态应当在阶段 2 补测与修补。
另有一条量级更小但真实存在的持续性项：GBA 节流覆盖的 `true→false` 边不可达
（`fceuWrapper.cpp:1440-1449`）⇒ 之后所有 NES 会话被钉在 59.7275 fps（−0.618%），
已在 §六 登记，阶段 3 修。

### 11.4 复核确认成立的部分（不改）

- A1 的 `join` 无任何条件分支（`sdl-sound.cpp:765-769`），且全会话只有两个 join 点
  （`:366-367` 与 `:767-768`），无 `detach`；
- 所有 `KillSound()` 调用点均在 `FCEU_WRAPPER_LOCK` 内（`ConsoleFile.cpp:339-340`/`:347-349`/
  `:325-330` → `fceuWrapper.cpp:485` → `:192-193`；三个设置对话框亦然）；
- A2 可达（无其他 join / 无 `_Exit` / `quick_exit`）；
- A3 的 `SDL_setenv` 永久副作用成立（全仓仅一处 `setenv`、无恢复），但「声卡恢复后
  音频不恢复」应改为「**默认/WASAPI 路径**不再恢复，directsound/winmm 仍可在退避窗口
  过后重试成功」（§六 措辞按此理解）；
- A5 成立（`InitSound` 在无设备时仍返回 1 ⇒ `SndRate` 非 0 ⇒ 内核合成为空）。
