## 〇、本文档要回答的问题

> 能否通过迭代趋于权威，形成稳定模式后再追求通用化？

**结论：顺序正确，但两个环节都需要修正预期。**

1. **「趋于权威」的驱动量不是测试覆盖率，是 oracle 来源数。** 覆盖率的天花板由 blargg 语料对真实硅片的保真度决定，与工程投入无关。
2. **「通用化」必须等 n≥2。** 现有 `SutAdapter` 已经用代码演示了 n=1 抽象的失败后果。
3. 存在**一个能同时推进两条轴的动作**（第二个被测物），因此两阶段不是严格串行。
4. **方法论现在就能导出，代码必须等。** 这两件事被「通用化」一个词混在一起，成熟度差得很远。

## 一、权威性有硬天花板

### 1.1 覆盖率不是渐近线，是有限语料的耗尽过程

blargg 测试 ROM 套件是**有限固定语料**——`tests/fixtures/blargg/` 磁盘实测 177 个。覆盖率 13% → 80% → 100% 是把这**一个**来源用尽，不是逼近真理。

用尽之后：

> **KagamiQA 的权威性上限 = blargg 套件对真实硅片的保真度。**

blargg ROM 本身是硬件的**代理**，不是硬件。它测不到的行为——未文档化的边缘时序、特定 mapper 的模拟态、PPU 的模拟量特性、总线电容效应——覆盖率再高也照不亮。**这个天花板不由工程投入决定。**

### 1.2 Oracle A 永远不产生权威性

必须反复重申，因为这是最容易被覆盖率数字掩盖的一点：

| Oracle | 回答的问题 | 真理来源 |
|---|---|---|
| **A**（`mapper_byte_diff` / `apu_wav_diff` / `ppu_frame_diff` / `golden_savestate`） | 「和上一版一样吗」 | 本项目自己的历史产物 |
| **B**（blargg `$6000` 协议） | 「和真实硬件一致吗」 | 真实 NES 硅片（经 ROM 中介） |

Oracle A 是 characterization testing，**无论做到多完备，都无法回答「对吗」**。PLAN §2.4 自陈：「无一个 oracle 回答『与真实硬件是否一致』」。

因此**权威性的分子只能来自 Oracle B 侧**。Oracle A 的价值在可靠性（防回归），不在权威性——这两者在 Stage-2 §十·五 已分离陈述，Stage-3 继续沿用该口径。

### 1.3 推论：提升权威性 = 增加可彼此证伪的 oracle 来源

两个独立 oracle 判定**冲突**时才产生新信息；同一来源加测试，只是把已知的话说得更细。

Stage-2 §十·五 已把「oracle 来源数」列入度量，当前值 = **1**。Stage-3 的核心任务就是把这个数字从 1 变成 ≥2。

## 二、权威性迭代路径

### S3-1｜第二个被测物：跨实现差分 oracle 🌟

**这是 Stage-3 的第一个动作，也是唯一同时推进两条轴的动作。**

`docs/tech/KagamiQA.md` §三 已声明支持第三方模拟器，前提是：

> 「第三方模拟器必须提供一个可执行文件，接受 `--rom <path> --frames N` 参数，运行后通过 stdout 输出 `BLARGG_RESULT:` 行。」

走现成的 `SubprocessAdapter`，**不需要改 FCEUX 一行代码**。

#### 双重收益

| 轴 | 收益 |
|---|---|
| **权威性** | 跨实现差分：两个独立实现对同一 ROM 判定不一致 ⇒ 至少有一个错 ⇒ 强信号。这是**在 blargg 语料不变的前提下**提升权威性的唯一途径 |
| **通用化** | 真实的 n=2。抽象边界不再靠猜——哪些字段两边都要、哪些只有 FCEUX 要，会从两个 adapter 的差集里自己浮出来 |

#### 候选与选型（⚠️ 全部需先验证，不得凭印象采纳）

**S3-1a 是 Stage-3 的第一项任务：候选能力验证。** 网络检索对以下事实**未能给出可靠结论**，必须实机验证后再选型：

| 候选 | 需验证项 |
|---|---|
| Mesen / Mesen2 | ① 是否有 headless / test-runner CLI；② 能否直接消费 blargg ROM 并输出可解析的结果；③ 许可证是否允许在 CI 中分发或构建 |
| Nestopia UE | 同上 |
| puNES / 其他 | 同上 |

**选型硬标准**（任一不满足则淘汰）：

1. 可无 GUI 批量运行，退出码或 stdout 能表达单 ROM 的 PASS/FAIL
2. 确定性——同 ROM 同帧数两次运行结果一致（否则不能进差分）
3. 可在 CI runner 上获取（预编译或可构建），许可证兼容
4. 精度声誉独立于 FCEUX（若其代码谱系源自 FCEUX，差分价值大打折扣）

第 4 条最容易被忽略且最致命：**差分测试的前提是实现独立**。两个同源模拟器的一致，不构成任何证据。

#### 差分的固有局限：相关性失效

必须写进文档首页，防止把差分一致当成正确：

> **两个实现可以以相同方式犯错。** 共同的错误来源包括：参考同一份（有误的）文档、抄袭同一份早期实现、依赖同一个社区流传的错误结论。差分一致 ⇒ 「没有发现分歧」，**不等于**「两者都对」。

因此差分 oracle 的正确定位是：**高信噪比的分歧发现器**，而非正确性判据。分歧出现时，仍需人工或第三来源裁决。裁决结果应回写为一条带 provenance 的已知失败记录。

### S3-2｜扩充测试 ROM 来源

blargg 之外，NESdev 生态尚有多个独立作者的测试套件（mapper 类、CPU dummy read、中断时序、OAM、PPU open bus 等）。这些来源的**独立性弱于跨实现差分**（都是「ROM 断言硬件行为」这一范式），但仍能扩大照亮面积。

**接入前置条件**：必须逐套确认许可证与再分发条款。当前 `DERIVATIVE_WORK_NOTICE.txt` 已为 Shay Green / Kevin Horton 的 ROM 做了署名，新增来源须比照办理，并解决 Stage-2 C-3 提出的「`COPYRIGHT_AUDIT.md` 范围不覆盖 `tests/fixtures/`」问题。

**优先级低于 S3-1**：同范式的第 2、3 个 ROM 套件，边际权威性收益低于第一个独立实现。

### S3-3｜TASVideos 精度表作为交叉引用

`oracle/hardware.rs:38-74` 已有 TASVideos 精度表的 schema 定义。它的正确定位**不是 oracle**，而是**期望值的外部锚定**：某 ROM 在上游普遍 FAIL，则本项目 FAIL 属已知状态而非新缺陷。

这解决的是「已知失败清单的可信度」问题——让「已知失败」有外部依据，而不是自己宣布自己可以失败。

## 三、通用化：为什么必须等 n≥2

### 3.1 现有代码已经证明了 n=1 抽象的失败

`SutAdapter` 从第一天就按「可移植」设计，KagamiQA.md §4.4 列了完整的「可移植组件」表。结果（`src/rust/crates/kagami-qa/src/adapter/trait_def.rs:68-90`）：

```rust
fn step(&mut self) -> Result<(), QaError>;               // = 推进一帧
fn read_oracle_probe(&self, addr: u32) -> Result<u8>;    // = 读 CPU 地址空间
fn reset(&mut self) -> Result<(), QaError>;              // = 模拟器上电态
```

`InputSpec`（`trait_def.rs:16-38`）带 `rom_path` / `frames` / `probe_addr`，`from_manifest` 硬编码 `frames: 300` 与 `$6000`。`OracleType` 是闭合枚举 `A|B`，`TestLayer` 是闭合枚举 `core|boards|driver|lua|script|benchmark`（`manifest/schema.rs`）。

> **这不是「预留了抽象」，是「在 n=1 上把一个实例的形状命名成了抽象」。**

PLAN §1.3 写的「跨项目迁移能力通过 SutAdapter 抽象层预留」——**预留了名字，没预留形状**。这是本项目最值得记取的架构教训，应写入 KagamiQA.md 首页而非隐藏在计划文档里。

### 3.2 Stage-2 期间的纪律：不通用化，但冻结泄漏

稳定期最大的风险，是**把错误的抽象夯得更实**。Stage-2 每一个碰 schema / trait 的 PR，都在给这个模拟器形状的契约浇一层混凝土。

**冻结规则（Stage-2 生效，零成本）**：

1. **不再向共享 schema 添加任何领域专用字段**。新增的领域字段一律进 adapter 私有配置（如 `TestInput` 增加 `adapter_config: Option<serde_json::Value>` 透传）
2. **不再向 `SutAdapter` 添加方法**。direct 模式的新需求走 `Fceux11DirectAdapter` 的固有 impl，不进 trait
3. 现有的 `rom` / `probe_addr` / `frames` **不删不改**（Stage-2 不做重构），但标记 `// DOMAIN-LEAK: 见 Stage-3 §3.1`

这保住了未来的选择权，且不增加 Stage-2 任何工作量。

### 3.3 契约重构范围（n=2 达成后执行）

基于耦合分析（2,428 LOC，约 59% 领域中立 / 41% NES 专用）：

**保留基本不动**：`core/`、`manifest/parser.rs`、`adapter/subprocess.rs`、`runner/scheduler.rs`、`oracle/regression.rs`、`report/baseline.rs`、`report/matrix.rs` 的迁移计算部分。

**重构或替换**（约 800–1000 LOC 删除、350–500 LOC 重写）：

| 对象 | 改法 |
|---|---|
| `InputSpec` | 领域字段移出，改为 adapter 私有 config |
| `SutAdapter` 的 direct 半部 | 拆为独立 trait，主 trait 只保留 `init` / `run_test` |
| `OracleType` 闭合枚举 `A|B` | 改为开放式 oracle 注册表（字符串 ID + 语义标注：`regression-equivalence` / `external-truth`） |
| `TestLayer` 闭合枚举 | 改为自由字符串或项目自定义分类 |
| `adapter/direct.rs`、`oracle/hardware.rs` | 移入 FCEUX 专用 crate，从核心分离 |
| `report/matrix.rs` 的 FCEUX 元数据（MSVC 工具链串、`FCEUX11_GIT_REV`） | 改为可注入的 engine metadata |

**注意**：`OracleType` 的改造不是简单换成字符串——A/B 的**语义区分必须保留**（回归等价 vs 外部真理），因为那正是框架最有价值的设计。开放式注册表需要求每个 oracle 声明自己属于哪一类。

## 四、规范先行，代码后行

「通用化」是两件事，成熟度差得很远：

### 4.1 现在就能导出，成本近零

**核心洞见**（PLAN §6.2 已有准确表述，应提炼为独立规范文档）：

> **回归等价与外部真理必须走物理隔离的判定通道，因为在 golden-master 体系下，一次正确性修复和一次回归在数据上完全同形。**

这条对任何有外部正确性标准的项目都成立，且正是绝大多数 AI coding 场景真正缺的——**AI 最容易犯的错，就是把「让 golden test 变绿」当成「让代码正确」**。

配套的可导出规范：

| 规范项 | 内容 | 通用性 |
|---|---|---|
| A/B 通道隔离 | 回归等价与外部真理不共用判定通道 | ✅ 完全通用 |
| oracle as data | 期望值是清单字段而非代码 assert，可版本化、可 diff | ✅ 完全通用 |
| `failure_means` 强制字段 | 每条用例必须回答「失败意味什么」，无答案不得入库——防空转测试 | ✅ 完全通用 |
| 迁移矩阵四桶 + `new_test` 第五桶 | 机器可读的补丁判据（SWE-bench 同构 + Stage-2 0.5-3 修正） | ✅ 完全通用 |
| 反 gaming 规则 | 不得修改已入库 `expected`；**且用例集合变更须同级评审**（Stage-2 0.5-4 补的漏） | ✅ 完全通用 |
| 已知失败即防线 | 精确编目的失败优于未测的全绿 | ✅ 完全通用 |

**建议**：Stage-3 早期即产出 `docs/tech/KagamiQA-方法论.md`（与被测物无关的规范），与代码通用化解耦。规范可以被别的项目手工采纳，不需要等 crate 发布。

### 4.2 必须等的部分

代码抽象边界应从**两个真实 adapter 的差集**里长出来，而非从一个实例的想象里推出来。这就是 §3 的全部内容。

## 五、阶段与触发式退出条件

「先稳定再通用」最常见的失败模式**不是顺序错，是永远停在稳定期**——PLAN §十 自列的「平行王国化」风险的变体。因此用**触发条件**而非时间表：

| 阶段 | 进入下一阶段的触发条件 |
|---|---|
| **S3-α 权威性迭代** | ① Oracle B 覆盖 ≥80%；② oracle 来源数 ≥2（第二个被测物稳定运行）；③ Stage-2 §十·五 卫生门槛全绿 |
| **S3-β 抽象定型** | ① 第二个 SUT 稳定运行 ≥1 个版本周期；② 产出两个 adapter 的字段/能力差集清单；③ 差集清单经评审确认为「抽象边界」而非「临时差异」 |
| **S3-γ 代码通用化** | 按差集重构契约层（§3.3），核心与 FCEUX 专用部分分 crate |

**反向触发（止损）**：若 S3-1a 候选验证表明**不存在满足硬标准的第二个被测物**，则 S3-β/γ 无限期挂起，Stage-3 收缩为「仅 S3-2/S3-3 + 方法论文档」。**不得在 n=1 条件下强行推进代码通用化**——那是重演 §3.1 的错误。

## 六、风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 第二个被测物不存在或不满足硬标准 | 🔴 高 | 整个 S3-1 的前提。S3-1a 验证未通过前，不得规划任何依赖它的工作 |
| 差分的相关性失效被误读为「双重确认」 | 🔴 高 | 见 §S3-1。必须在报告格式上区分「一致」与「正确」，不得输出「双实现确认」这类措辞 |
| 第二个 SUT 引入维护负担 | 🟡 中 | 上游版本更新可能改变 CLI 或行为，导致差分基线漂移。需固定版本并纳入基线治理 |
| 抽象定型过早 | 🟡 中 | n=2 仍是小样本。若第二个 SUT 与 FCEUX 过于相似（都是 NES 模拟器），差集可能仍不足以支撑真正通用的抽象。诚实预期：**n=2 得到的是「模拟器类项目的抽象」，不是「任意项目的抽象」** |
| 规范文档无人采用 | 🟢 低 | 规范先行的成本极低，即使外部无人采用，对本项目内部的口径统一仍有价值 |

关于「抽象定型过早」的补充：若目标是服务于**任意** AI coding 项目，严格说需要 n≥3 且被测物形态差异足够大（如：模拟器 + 编译器 + 服务端）。Stage-3 的现实目标应表述为「**从 n=1 的伪抽象，前进到 n=2 的真实抽象**」，而非「达成通用框架」。后者需要 Stage-4 及一个真正异构的第三被测物。

## 八、一页纸总结

```
权威性的驱动量 = oracle 来源数，不是测试覆盖率
    覆盖率天花板 = blargg 语料对硅片的保真度（工程投入无法突破）
    来源数当前 = 1  →  Stage-3 目标 ≥2

通用化必须等 n≥2
    证据：现有 SutAdapter 是 n=1 伪抽象的失败样本
    纪律：Stage-2 期间冻结泄漏（不加领域字段、不加 trait 方法）

一个动作同时推进两条轴：接入第二个 NES 模拟器
    权威性 ← 跨实现差分（分歧发现器，非正确性判据）
    通用化 ← 真实 n=2，抽象从差集中长出

规范先行，代码后行
    方法论（A/B 隔离、failure_means、迁移矩阵、反 gaming）现在就能导出
    代码抽象等第二个 adapter 落地

退出用触发条件，不用时间表
    止损条件：无合格第二被测物 ⇒ 代码通用化无限期挂起
```
