## 2. 必须修正的设计错误（2 项）

### S1 · `CpuRegsLayout` 字段顺序错误（会破坏 savestate）

**方案**（`02_architecture.md §5.3`、`phase_0_foundation.md §2.1`）写的布局：

```rust
pub struct CpuRegsLayout {
    pub PC: u16, pub A: u8, pub X: u8, pub Y: u8, pub S: u8,
    pub P: u8, pub DB: u8, pub mooPI: u8, pub jammed: u8,
    pub irq_low: u32, pub tcount: i32, pub count: i32, ...
}
```

**真实** `x6502struct.h`（全文 36 行）的字段顺序：

```c
typedef struct alignas(64) X6502 {
  int32 tcount;      // 偏移 0
  uint16 PC;         // 偏移 4
  uint8 A,X,Y,S,P,mooPI;  // 偏移 6-11
  uint8 jammed;      // 偏移 12
  int32 count;       // 偏移 16
  uint32 IRQlow;     // 偏移 20
  uint8 DB;          // 偏移 24
  int preexec;       // 偏移 28
  #ifdef FCEUDEF_DEBUGGER
    void (*CPUHook)(struct X6502 *);   // 偏移 32
    uint8 (*ReadHook)(...);            // 偏移 40
    void (*WriteHook)(...);            // 偏移 48
  #endif
} X6502;
```

差异：
- **字段顺序完全不同**（`tcount` 在首位，`PC` 第二位；方案写反了）
- **缺 `preexec` 字段**（offset 28）
- **缺 debugger 三函数指针**——本项目 `src/CMakeLists.txt:85` 定义了 `FCEUDEF_DEBUGGER`，所以真实构建中 X6502 是 56 字节（含 hook），pad 到 64

**为什么严重**：`state.cpp:122-142` 通过 `&g_cpu.native_layout().PC` 等**指针直接指向 X6502 字段**做 SFORMAT 序列化。若 Rust 端布局错，C++ 侧 `memcpy`/字段访问读到的是错位数据。按方案文本实现 = savestate 字节漂移，违反 R-001 且 CI 都拦不住（因为两边"各自以为正确"）。

**修正**：Phase 0 的布局校验测试必须**逐字段 offset 断言**（`offset_of!`），且用**真实 `x6502struct.h` 转成 golden 二进制**对比，不是凭手写字段顺序。

### S2 · Savestate 不是"64 字节整块"，是 SFORMAT 分字段标签格式

**方案**（`02_architecture.md §6.2`、`phase_0_foundation.md`）：
> "savestate 序列化路径走 C++ 侧… `fwrite(&regs, 64, 1, fp)`"

**真实** `state.cpp:122-142`：

```cpp
SFORMAT SFCPU[] = {
    { &g_cpu.native_layout().PC, 2|RLSB, "PC\0"},
    { &g_cpu.native_layout().A,  1,      "A\0\0"},
    ...
    { &RAM, 0x800 | FCEUSTATE_INDIRECT, "RAM", },
};
SFORMAT SFCPUC[] = {  // 第二个 CPU 块
    { &X.jammed, 1, "JAMM"},
    { &X.IRQlow, 4|RLSB, "IQLB"},
    { &X.tcount, 4|RLSB, "ICoa"},
    { &X.count,  4|RLSB, "ICou"},
    { &timestampbase, ... "TSBS"},
    { &X.mooPI, 1, "MooP"},
    ...
};
```

**savestate 文件格式**是 **V2 chunked：`[4 字节 tag][4 字节 size][数据]`** 的流，CPU 拆成两个块（`SFCPU` + `SFCPUC`），字段按 4 字符标签逐项读写。**不是**整块 64 字节 memcpy。

**这实际上是好消息**：
- 兼容约束从"Rust 内存布局必须 byte-exact"降级为"**Rust 必须提供相同 tag 的相同值**"
- Rust 端内部布局可以自由（用 struct 或字段变量），只要序列化时按 tag 输出相同字节

**但这同时是坏消息**：
- Phase 0 的"字节布局校验"方案**整个不成立**——需要重写为"SFORMAT 值语义等价"验证（对每 tag 断言 Rust 输出 == C++ golden）
- `Cpu::layout_` 的 `static_assert`（offset 0 / size 64）保护的是**其它旧代码**（如 `oldmovie.cpp`、调试器），不是 savestate 序列化路径——方案把两者混为一谈

**修正**：Phase 0 重新设计兼容策略：
1. 列出 `SFCPU`/`SFCPUC`/`FCEUPPU_STATEINFO`/`FCEU_NEWPPU_STATEINFO`/`FCEUSND_STATEINFO`/`FCEUCTRL_STATEINFO` 全部 tag 清单
2. Rust 端按 tag 实现等价 save/load
3. 验证 = golden savestate 文件 round-trip 字节一致（不依赖结构体布局）

## 3. 必须决策的架构缺口（5 项）

### S3 · 时序模型矛盾："保持 v1.x 模型" vs `tick()` 紧交错设计

**方案**（`02_architecture.md §4`、`phase_3_ppu.md`）：
> `tick()` = 1 CPU step + 3 PPU dots 紧交错，"与 Mesen/Nestopia 同构"

**真实** `ppu_rendering.cpp`（新 PPU 主循环）+ `fceu.cpp:841`：

- 帧循环主驱动是 **`FCEUPPU_Loop(skip)`**（PPU 主、CPU 从）
- PPU 以 **scanline 段为单位**推进，通过 **`X6502_Run(N)` 给 CPU 发放周期预算**，例如：
  ```cpp
  X6502_Run(256);            // 可见段 256 周期
  X6502_Run(85);             // pre-render 段
  X6502_Run(16);             // 某些边界
  X6502_Run(256 + 69);       // 可见 + sprite eval 段
  ```
- CPU 跑到 `tcount >= 预算` 后返回，PPU 继续

这是 **"PPU master + CPU budget" 模型**，不是 dot 级紧交错。方案若按 `tick()` 重写：
- **不是移植，是行为重写**——blargg 81.4% 的通过率是 budget 模型调出来的
- 所有 `X6502_Run` 魔法常数（256/85/69/16）编码了 PPU 时序假设，dot 重写必须重新推导
- Shadow run 无法做**逐周期** diff（两个模型周期粒度不同）

**必须决策**：二选一
- **A（推荐）**：Rust 端先复刻 budget 模型（`run_ppu_scanline()` + `cpu.run(budget)`），保证与 C++ 逐帧等价，再考虑优化
- **B**：完全重写为 dot-interleaved（正确性以 blargg 重新全量验证为准）——工作量大 2-3 倍，风险高

方案目前把 A 和 B 混在一起（架构篇写 B，概述篇声称保持 A 模型）。**必须先定 A 还是 B**。

### S4 · Mapper 边界：per-range handler 注册，不是单 vtable

**方案**（`02_architecture.md §5.2`、`phase_5_mapper_adapter.md`）：
> `MapperVtable { cpu_read: fn(*mut c_void, u16) -> u8, ... }` 9 个函数

**真实** `bus.h:74-93` + `boards/mmc3.cpp:327-344`：

- mapper 通过 **`SetReadHandler(start, end, fn)` / `SetWriteHandler(start, end, fn)`** 按**地址区间**注册多个 handler
- 一个 MMC3 就注册了 5+ 个区间（$8000-$BFFF 写、$C000-$FFFF 写、$8000-$FFFF 读、$5000-$5FFF、$7000-$7FFF…）
- `CartBR`/`CartBW` 是共享兜底 handler，走 Cart 的 PRG/CHR 指针
- **Game Genie/cheat** 通过 `fceu.cpp::SetReadHandler` 包装 handler 实现

**方案的单 `cpu_read` thunk 无法表达**：适配器需要自己的 per-range 表（复制 bus 的 aread_ 机制），而这恰恰是方案说"用 match 消除"的东西。

**修正**：vNESU11 的总线必须是**两层**：
1. 固定区域（$0000-$401F）：`match`（WRAM/PPU/APU/open bus）
2. mapper 区域（$4020-$FFFF）：**小型 per-range handler 表**（如 16 项 `(start,end,fn_ptr)` 线性扫描，cache 内约 10 条指令），由 `vnesu11_set_range_handler(start, end, fn, ctx)` FFI 注册

Game Genie 包装逻辑必须保留在适配层（cheat 状态在 C++ 侧）。

### S5 · newppu 双 PPU：方案没有回答"迁移哪个"

**真实**：
- `fceu.cpp:136-147` `FCEU_TogglePPU()`——`newppu` 是**运行时切换**的全局
- `drivers/Qt/config.cpp:884`：`addOption("newppu", "SDL.NewPPU", 0)`——**GUI 默认旧 PPU**
- `kagami-qa` 的 blargg baseline 用 **newppu=1**（`tests/fixtures/blargg_full_baseline.json`："newppu=1"）
- `movie_io.cpp:138`：movie 记录 `PPUflag = (newppu != 0)`——**旧 PPU 录的 movie 必须用旧 PPU 放**

**方案**只写了"保持 v1.x 模型；Phase 7 切换时只暴露 newppu 行为"——含糊。

**必须决策**：
- Rust PPU 迁移**哪个**？（QA 验证的是 new PPU；GUI 默认是 old PPU）
- 旧 PPU movie（PPUflag=0）怎么办？三个选项：
  - ① Rust 只实现 new PPU，旧 PPU movie 拒绝播放（**用户可见回归**）
  - ② Rust 同时实现两个（工程量翻倍）
  - ③ 保留 C++ 旧 PPU 作为 movie 兼容回退路径（vNESU11 只在 newppu=1 时接管）
- 方案必须显式写这一决策，不能含糊

### S6 · NSF / FDS / VS UniSystem 完全未覆盖

**真实**：
- `fceu.cpp:1463` `FCEUXGameInterface` + `GameInterface` 分派——iNES/FDS/NSF/VS 共用**同一个** `FCEUPPU_Loop → X6502_Run` 核心
- `nsf.cpp:97` `GameInterface = NSFGI`——NSF 走同一循环（音乐模式）
- `fds.cpp:139` `X6502_IRQBegin(FCEU_IQEXT)`——FDS 通过 IRQ hook 接入 CPU

**方案**通篇只谈 iNES + mapper，未提 NSF/FDS/VS：
- NSF = CPU+APU、PPU 空转（vNESU11 需要"无 PPU"模式或空 PPU）
- FDS = 额外 IRQ + 磁盘时序（vNESU11 的 IRQ 控制器必须支持 `FCEU_IQEXT/EXT2` 外部源）
- VS = coin slot 输入
- 若 vNESU11 替换 CPU/PPU 而不支持这三类，**FCEUX11 的 FDS/NSF/VS 功能全部失效**

**修正**：Phase 范围必须加"系统类型矩阵"：iNES / FDS / NSF / VS × vNESU11 支持度，以及每类的验证 ROM。

### S7 · 隐藏的确定性依赖：RAM 初始化随机源

**真实** `fceu.cpp:910-954`：
- `RAMInitOption`（0-3）+ `RAMInitSeed` → `splitmix64` + `xoroshiro128plus` 生成 RAM 填充
- `FCEU_MemoryRand` 用**可复现随机数**初始化未初始化 RAM

**方案**未提及。但 Shadow run 要字节等价，vNESU11 必须**逐位复刻**这套随机源（同 seed → 同 RAM 模式），否则第一帧就 diff。这是"隐藏但致命"的兼容细节。

## 4. 高估的断言（3 处）

### S8 · 性能收益 5-15% 缺乏依据

`A_performance_model.md` 声称"消除跨 TU 边界 → 5-15%"。

**反证**：
- `CMakeLists.txt:77` **Release 已开 `/LTCG`**（Link-Time Code Generation），且 v1.14 起 **PGO 可选**——MSVC 的 LTCG 已经做**跨 TU 内联**，C++ 侧跨 TU 边界早已大部分消除
- Rust 静态库 `lto = true` 是 **rustc 内部 LLVM 链接**；与 MSVC 的 `link.exe` 之间**不存在跨语言 LTO**——`vnesu11` 与 C++ 之间的函数调用仍是 ABI 边界，无法内联
- 因此收益只来自"Rust crate **内部**的单态化 + match"，而这部分（CPU dispatch、PPU 渲染）**在 C++ 侧经 LTCG 后已接近最优**
- `bus.rs` 现有 benchmark 只证明了"match 不比 switch 慢"，**没有证明"比 LTCG 后的 C++ 快"**

**修正**：性能预期降为"**持平至 +3%，不排除 -2%**"，并明确"性能不是迁移的核心理由，架构统一 + 内存安全才是"。若性能是硬目标，Phase 1 末必须先出实测再决定是否继续 Phase 3。

### S9 · 影响面低估：68 个文件直接 include 核心头

`02_architecture.md §6.1` 声称"~150 个 Qt 驱动调用点零改动"。

**实测**：`grep '#include "x6502.h"|"ppu.h"|"bus.h"|"sound.h"|"x6502struct.h"'` = **68 处**（x6502.h 24、sound.h 17、ppu.h 16、bus.h 8、x6502struct.h 3），分布在 mappers / drivers / 调试器 / movie / netplay 等，**不止 Qt 驱动**。

这些文件直接读 `X`/`PPU`/`ARead` 等全局或调用内联访问器。迁移后 68 处都要走 FFI 或兼容别名——方案"零改动"承诺不成立。

### S10 · Shadow run 可做，但"逐周期 diff"不成立

`phase_6_integration.md` 声称 shadow run 逐帧/逐周期对比。

**问题**：
- C++ 与 Rust 时序模型不同（S3），**逐周期 diff 无定义**
- 双方都写 `XBuf`/`WaveFinal` 全局 → 同进程双跑需隔离全局（一个实例用 vNESU11 输出，另一个用 C++ 输出，分别存 buffer）
- RAM 随机源（S7）必须先对齐
- 帧边界逻辑（`timestampbase += g_cpu.timestamp_ref(); = 0`，fceu.cpp:858-860）必须复刻

**修正**：Shadow run 定位改为"**逐帧 XBuf CRC + 音频 SNR + savestate MD5**"三级对比（与现有 kagami-qa 的 rom_regression/savestate_regression harness 同构），不做逐周期 diff。

## 6. 结论

```
方向：可行
修正工作量：约 1-2 周（文档级修订）
未决风险：时序模型（S3）与 newppu 策略（S5）是两个真正的架构决策点，
         建议在修订后、Phase 0 开工前，由架构组评审拍板
工期影响：若选 A（budget 复刻）+ ③（旧 PPU 回退），总工期可维持 27 周估算；
         若选 B（dot 重写）或 ①/②（PPU 策略激进），工期 ×1.5-2
```

**一句话**：方案的"骨架"（crate 划分、FFI 表面、kagami-qa 门禁、灰度策略）是好的；但 **savestate 兼容描述、时序模型、mapper 边界、系统类型覆盖** 四处与真实代码不符，必须先修订再动工——否则 Phase 0 就会在错误的兼容策略上铺开。
