1. Fix the +24-27% `bench_tolerance_test` regression introduced by Phase 2.

### 3.4 Why ppu.cpp regressed (root-cause summary)

The plan §5.1.5 expected `g_bus.vpage()[i][j]` to compile to the same
machine code as `VPage[i][j]` because `vpage()` is `__forceinline` and
returns a reference to `vpage_` (whose address is known at link time via
the `g_bus` global).

**What actually happened**: MSVC 19.51 did NOT fold `g_bus.vpage()[i][j]`
to the same 3-instruction RIP-relative sequence as `VPage[i][j]`. The
suspected reason (hypothesis §5.1 below): the `uint8_t*(&)[8]` return
type (reference to array) on a `FCEUX11_CACHE_ALIGN` class with multiple
aligned members triggers a codegen path where the accessor is not fully
inlined, adding a per-call-site overhead that compounds across the ~10⁵
PPU render-loop accesses per frame.

The `VPage` `extern` reference alias, by contrast, is at namespace scope
and at the IR level is indistinguishable from a `uint8_t*[8]` global with
a known link-time address — MSVC emits a direct RIP-relative array index.

**Key insight**: the data-unification goal of Phase 3 is **already
achieved** by the `extern` reference aliases in `bus.cpp:400-425`. `VPage`,
`MMC5SPRVPage`, `ARead`, `BWrite`, `Page`, etc. all bind to `g_bus`'s
internal arrays. There is exactly one copy of each array (inside `g_bus`);
the aliases are thin references. The ppu.cpp revert only affects call-site
spelling, not data location.

## 5. Hypotheses for the ppu.cpp regression (for future v1.7 work)

Listed in order of likelihood. These remain hypotheses — the revert made
asm-level diagnosis unnecessary for Phase 3 completion. If v1.7 Cart-class
work revisits direct vpage access, these should be tested.

### 5.1 (Most likely) MSVC treats `g_bus.vpage()` as a non-trivially-inline-able call

Even with `__forceinline`, the accessor return type `uint8_t*(&)[8]`
involves a reference, and the Bus class has `alignas(64)` plus a 64-byte
aligned member array at non-zero offset. The compiler may emit an
out-of-line copy of `Bus::vpage()` and call it at every use site — even
though the body is a single `return vpage_;`.

**Test**: `cl.exe /FA` to dump asm; look for `call ?vpage@Bus@fceu11@@` in
ppu.cpp's render loop. If present, the accessor is not inlining.

**Fix candidate**: expose `vpage_` directly as a public member (or via a
`#define` macro alias) for hot paths. Or change the return type from
`uint8_t*(&)[8]` to `uint8_t**` (raw pointer to vpage_[0]).

### 5.2 (Possible) Reference alias `VPage` benefits from a special optimization path

MSVC may have a specific optimization for `extern T(&)[N]` reference-to-
array globals at namespace scope (since they're indistinguishable from
`T[N]` globals at the IR level). `g_bus.vpage()` goes through a different
code path because it's a member function on a class type.

**Fix candidate**: leave `VPage` as the alias for hot paths; only migrate
warm paths (which is what the revert does).

### 5.3 (Less likely) The `__forceinline` attribute is being silently dropped

The compiler may be ignoring `__forceinline` due to debug-info or other
quirks. Check with `/W4 /WX` build for any inline-related warnings.

### 5.4 (Cosmetic) Bench baseline is from a faster machine

Per plan §5.0.2 factor B: baseline was captured on a development machine
(`Windows_NT, 10.0.26200`); the CI runner is `Windows Server 2022,
10.0.20348`. The plan §5.1.7 calls for **re-capturing baseline on CI**.
This 5-10% delta would explain the gap from `+0.38%` / `+1.17%` / `+2.91%`
(post-cart) to a hypothetical "noise floor" — but it does NOT explain why
the **ppu.cpp migration made things worse** than just x6502 + cart.
