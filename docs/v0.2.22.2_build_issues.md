**Date**: 2026-06-01
**Status**: Blocked — C++ FFI linkage error
**Files affected**: `src/lua-engine.cpp`, `src/input.cpp`

---

## Issue: `fceux11_lua_GetJoypadState` fails to link

### Error

```
fceux11_core.lib(lua-engine.cpp.obj) : error LNK2019:
无法解析的外部符号 "unsigned char * joy"
```

When CMake links the final `fceux11.exe`, the FFI bridge function
`fceux11_lua_GetJoypadState` (defined in `lua-engine.cpp:6704`) cannot
resolve the `joy[4]` array that lives in `input.cpp`.

---

## Root Cause

In `input.cpp`:

```cpp
uint8 joy[4]={0,0,0,0}; //HACK - should be static but movie needs it
```

This is a non-static file-scope variable, so it has external linkage.
However, `lua-engine.cpp` uses `extern uint8 joy[4]` to access it:

```cpp
uint32_t fceux11_lua_GetJoypadState(int port) {
    extern uint8 joy[4];  // ← this declaration is fine per se,
                          //   but joy is defined in input.cpp
    if (port < 0 || port > 3) return 0;
    return static_cast<uint32_t>(joy[port]);
}
```

The linker's complaint suggests that when `lua-engine.cpp.obj` is compiled
and linked against `fceux11_core.lib` (which contains the compiled `input.cpp`),
the `joy` symbol is not being exported properly — or the `.lib` file does
not expose it as a public symbol.

This may be because:
1. `joy` is defined in `input.cpp` but not declared in any header that
   `lua-engine.cpp` includes.
2. The `extern` declaration in `lua-engine.cpp` resolves to nothing at
   link time because `input.cpp`'s compiled object is inside a static
   library (`.lib`), not an executable direct link.

## Fix Options

### Option A: Fix the joy linkage (recommended)

In `input.h` (or a shared header), add:
```cpp
extern uint8 joy[4];
```

This makes `joy` available to any file that includes `input.h`.
Then remove the `extern uint8 joy[4]` declaration from `lua-engine.cpp`
and let the `#include` resolve it.

### Option B: Change GetJoypadState implementation

Replace `extern uint8 joy[4]` with a call to an existing exported
function that already reads joypad state. For example, `FCEU_LuaReadJoypad`
is already defined and exported in `lua-engine.cpp` and reads from
`luajoypads1/luajoypads2` directly. However, this returns the *override*
state, not the raw joypad state — may not match the intended semantics
of `joypad.get()`.

### Option C: Add a getter function in input.cpp

Add a small export function in `input.cpp`:
```cpp
uint8_t FCEU_GetJoypadState(int port) {
    return joy[port & 3];
}
```

Then have `lua-engine.cpp`'s `fceux11_lua_GetJoypadState` call that instead.

## Prior Art

The original C++ `lua-engine.cpp` already accesses `joy[4]` via `extern uint8 joy[4]` (e.g. line 2835). The difference is that original code works because `lua-engine.cpp` and `input.cpp` are compiled into the same static library (`fceux11_core.lib`) and the linker can resolve cross-object references within the same library.

However, when the Rust FFI layer (compiled into `fceux11_rust.lib`) calls back into `lua-engine.cpp`'s FFI stubs, the chain is:

```
fceux11_rust.lib (Rust)
  → fceux11_lua_GetJoypadState (lua-engine.cpp, in fceux11_core.lib)
    → extern uint8 joy[4] (defined in input.cpp, also in fceux11_core.lib)
```

This should work — the static library should export all symbols. The
error may indicate that `joy` is being stripped as an unused symbol, or
the `extern` in `lua-engine.cpp` is not finding the definition in the
static library context.

**Needs investigation** with `dumpbin /symbols` on `fceux11_core.lib` to
confirm whether `joy` is actually exported.
