## 4. Hot-path migration priorities

The migration risk is **not** proportional to call-site count — it
is proportional to how many of those calls land in the inner
dispatch loop. The dispatch loop is:

1. **CPU instruction fetch / mem read** (`x6502.cpp` calling
   `ARead[addr](addr)`) — ~5 call sites, **CRITICAL HOT PATH**
2. **CPU DMA / DMR / DMW** (`fceu.cpp` direct array write to
   `ARead[]` / `BWrite[]`) — ~10 sites, **CRITICAL HOT PATH**
3. **PPU rendering fetch** (`ppu.cpp` calling `VPage[]`,
   `CHRptr[]`, `Page[]`) — ~28 sites, **HOT PATH**
4. **Mapper Power()** (`src/boards/*.cpp` calling `SetReadHandler`
   / `SetWriteHandler` / `setprg*` / `setchr*`) — > 2 000 sites
   across 175 files, **COLD PATH** (runs once per mapper load)
5. **Mapper bank-swap in IRQ hook** (`mmc3.cpp`, `mmc5.cpp`, etc.
   calling `setprg8` from scanline-tick handler) — small but
   real-time, **WARM PATH**

Phase 1 / Phase 2 are the only phases that touch the hot paths.
Phase 3~5 are all cold-path and can be batched. The per-file
"hotpath" column in §2.2 is the input for hot-path audit during
Phase 5 (when each hot-path board file gets a `__forceinline` /
`[[likely]]` review per v1.4 plan §6.2).
