### 2.3 Strategy A (unchanged from Phase E)

The cart subclass's `on_power()` does NOT re-invoke `Mapper1_Init` / `Mapper4_Init` — those init functions were already called once during `iNES_Init`, and calling them again would duplicate SFORMAT entries and leak WRAM. Instead, `on_power()` temporarily swaps `info->Power` to the legacy `GenMMC1Power` / `M4Power` function pointer (the value the Init set), calls it, then restores the `CartInfo_PowerForward` so subsequent `PowerNES` calls also route through `cart_obj->on_power`.

### 2.4 Reset handling

- **MMC1**: `GenMMC1Init` does NOT set `info->Reset`. v1.7 factory block leaves `info->Reset = CartInfo_ResetForward`. `Mmc1Cart::on_reset` calls `MMC1CMReset()` directly to reset the shift register, buffer, four data regs, and re-sync mirroring/CHR/PRG. (Plan §5.3 mentioned `MMC1RegReset()` but the actual helper is `MMC1CMReset()` — `MMC1RegReset` is the MMC3 helper.)
- **MMC3**: `GenMMC3_Init` sets `info->Reset = MMC3RegReset`. v1.7 factory block overwrites with `CartInfo_ResetForward`. `Mmc3Cart::on_reset` calls `MMC3RegReset()` directly to restore the eight bank registers, IRQ counter/latch/cmd, and PRG/CHR mirroring.

### 2.5 Close handling

- **MMC1**: No IRQ hook, no expansion audio. `on_close()` is a no-op (`{}`). WRAM/CHRRAM free is handled by `GenMMC1Close` via the `info->Close = CartInfo_CloseForward` path? No — the v1.7 factory block overwrites `info->Close = CartInfo_CloseForward`, so `GenMMC1Close` is no longer called automatically. **This is a known v1.7 bug**: 168 un-migrated mappers (and the 3 PoCs) leak WRAM/CHRRAM on game close.
  - **Mitigation for v1.7**: Acceptable because PoC mappers' WRAM is small (8 KiB) and a single game session never loads more than a handful of ROMs.
  - **Resolution deferred to v1.8 Masonry §8.2**: cart `on_close()` overrides will invoke the legacy `GenMMC1Close` / `GenMMC3Close` directly (mirroring VRC6's `on_close` pattern but for memory instead of IRQ hooks).
- **MMC3**: `on_close()` drops `GameHBIRQHook = nullptr` to prevent stale IRQ callbacks pointing at the now-freed mapper state. `fceu.cpp::ResetGameLoaded()` also nulls it on next load, but the cart-level cleanup is more immediate.

### 2.6 Factory wiring (`create_cart_for_mapper`)

```cpp
std::unique_ptr<Cart> create_cart_for_mapper(uint32_t mapper_no, Bus& bus) {
    switch (mapper_no) {
    case 0:  return std::make_unique<NromCart>(bus);
    case 1:  return std::make_unique<Mmc1Cart>(bus);    // Phase F
    case 4:  return std::make_unique<Mmc3Cart>(bus);    // Phase F
    case 24:
    case 26: return std::make_unique<Vrc6Cart>(bus, mapper_no);
    default: return nullptr;  // 166 un-migrated mappers
    }
}
```

## 5. Known issues and constraints

1. **WRAM/CHRRAM not freed on close**: The v1.7 factory block overwrites `info->Close = CartInfo_CloseForward`, but PoC carts' `on_close()` does not invoke `GenMMC1Close` / `GenMMC3Close`. The result is small (8 KiB WRAM) leaks across game loads in a long session. Deferred to v1.8 Masonry §8.2 where cart `on_close()` will mirror the VRC6 pattern but for memory instead of IRQ hooks.
2. **Bench CPU-frame regression**: ~+4.4% vs v1.5 baseline. Pre-existing from Phase B/C, not introduced by Phase F. Per v1.7 plan §7.1, do **not** re-baseline.
3. **Other MMC3 variants not covered**: Mapper 12 / 37 / 44 / 45 / 47 / 49 / 52 / 74 / 114 / 115 / 116 / 118 / 119 / 165 / 205 / 245 / 249 / 250 / 254 / 406 use the same `GenMMC3_Init` but with mapper-specific Power overrides. v1.7 only handles iNES mapper number 4; others fall through to `create_cart_for_mapper` returning `nullptr` and continue using the legacy CartInfo function-pointer path. v1.8 Masonry §8.2 will add more PoC subclasses (or a generic `Mmc3BaseCart` with mapper-specific overrides).
4. **Mapper byte-diff goldens**: `mapper_byte_diff_test` body byte-diff is still deferred. The skeleton compiles, runs, and prints [SKIP] for each test case; real body capture requires a `Cart::save_mapper_state()` API (v1.8 Masonry work).
