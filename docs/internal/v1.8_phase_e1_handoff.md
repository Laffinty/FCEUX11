## 2. Root cause analysis (E.1)

### 2.1 Bisect findings (from D.11 handoff §3.0)

`rom_regression_test` + `savestate_regression_test` SEGFAULT was
**introduced at Phase D.3 commit `55771fd`** (Mmc3BaseCart + Strategy
A pattern), not by D.10 or D.11.  Bisect across cb0fed9 → b8f2c23 →
19bb254 → 55771fd → 8746431 → b09bc45 confirms D.3 as the introducer.

### 2.2 E.1 diagnostic (intermediate commit)

Added a temporary `fprintf` in `MapperStrategyA::on_power` printing
`info->Power` and `CartInfo_PowerForward` addresses.  Rebuilt and ran
`rom_regression_test` — the diagnostic printed **identical addresses**
(`00007FF723765610`) for `info->Power` and `PowerForward` during the
second mapper load (UNROM).  The recursive on_power printed the
diagnostic thousands of times before stack overflow.

### 2.3 The actual bug

ROM load sequence for a Strategy A mapper (e.g. VRC2/4 mapper 21):

1. `iNESCart.clear()` (src/cart.h:105) resets cart_obj=nullptr, sets
   Power/Reset/Close = forwarders
2. `Mapper21_Init(&iNESCart)` sets `iNESCart.Power = VRC2and4_Power`
   (legacy)
3. `currCartInfo = &iNESCart`
4. `create_cart_for_mapper(21, bus)` constructs `Vrc2and4Cart` (inherits
   `MapperStrategyA`)
5. `assign_cart(cart)` → `g_cart = Vrc2and4Cart*`
6. `iNESCart.cart_obj = fceu11::g_cart`
7. **`iNESCart.Power = CartInfo_PowerForward;`** ← **overwrites the
   legacy VRC2and4_Power!**
8. `iNESCart.Reset = CartInfo_ResetForward;`
9. `iNESCart.Close = CartInfo_CloseForward;`
10. PowerNES → `currCartInfo->Power()` → `CartInfo_PowerForward` →
    `cart_obj->on_power()` → `MapperStrategyA::on_power()` →
    `currCartInfo->Power()` → `CartInfo_PowerForward` → same
    `cart_obj->on_power()` → **∞ RECURSION → stack overflow → SEGFAULT**

The 4 v1.7 PoC classes (Nrom, Mmc1, Mmc3, Vrc6) avoid this by doing a
**swap-and-restore** in on_power: temporarily set
`info->Power = <known legacy function>`, call it, then restore.  The
swap-and-restore is hardcoded per-PoC because the PoCs know which
legacy function to call (M4Power / GenMMC1Power / NROMPower / VRC6Power).

For `MapperStrategyA` and `Mmc3BaseCart`, the legacy function is set
by the per-mapper Init (Mapper21_Init, Mapper12_Init, ...) and varies
per mapper number.  Strategy A can't hardcode the function name, so
it must read from `currCartInfo->Power` — which gets overwritten by
the iNES loader.

## 3. The fix (commit `2834b6b`)

### 3.1 Pattern: capture-in-constructor

The constructor runs BEFORE the iNES loader's overwrite at step 7
above.  Capture the legacy Power/Reset at that point, store as
private members, then call them directly from on_power/on_reset.

```cpp
class MapperStrategyA : public Mapper {
public:
    explicit MapperStrategyA(Bus& bus) noexcept {
        attach_bus(bus);
        if (currCartInfo) {
            if (currCartInfo->Power &&
                currCartInfo->Power != &CartInfo_PowerForward) {
                legacy_power_ = currCartInfo->Power;
            }
            if (currCartInfo->Reset &&
                currCartInfo->Reset != &CartInfo_ResetForward) {
                legacy_reset_ = currCartInfo->Reset;
            }
        }
    }

    void on_power() noexcept override {
        if (legacy_power_) legacy_power_();
    }
    void on_reset() noexcept override {
        if (legacy_reset_) legacy_reset_();
    }
    void on_close() noexcept override {
        release_mapper_resources();
    }

private:
    void (*legacy_power_)(void) = nullptr;
    void (*legacy_reset_)(void) = nullptr;
};
```

Same pattern applied to `Mmc3BaseCart` (24 MMC3 variants: 12, 37, 44,
45, 47, 49, 52, 74, 114, 115, 116, 118, 119, 165, 192, 194, 195, 198,
205, 245, 249, 250, 254, 406).

### 3.2 Why the constructor (not swap-and-restore every call)?

The PoC classes (Nrom, Mmc1, Mmc3, Vrc6) hardcode their legacy function
names (M4Power, GenMMC1Power, NROMPower, VRC6Power) and do the
swap-and-restore every call.  Strategy A and Mmc3BaseCart don't know
the legacy function name (set by per-mapper Init), so they MUST read
it from `currCartInfo->Power`.  The constructor is the only point in
time where the legacy function is still reachable via
`currCartInfo->Power` before the iNES loader overwrites it.

A one-time capture at construction is sufficient because:
- The legacy function pointer doesn't change after Init
- The iNES loader's overwrite happens ONCE per ROM load (not per
  PowerNES call)
- Cart destruction happens at ROM unload (GI_CLOSE), before the next
  Cart's constructor runs

### 3.3 Why the guard `currCartInfo->Power != &CartInfo_PowerForward`?

Defensive check.  If somehow the constructor is called when
`currCartInfo->Power` is already a forwarder (which shouldn't happen
in the iNES loader path), don't capture the forwarder — that would
recreate the recursion.  Just leave `legacy_power_` null and
on_power becomes a no-op (which is correct for an uninitialized
Cart).

## 4. Phase E.1 followup — mapper 406 (cart_class_test 82/85)

### 4.1 What's still failing

3 cart_class_test assertions:
- "MMC3 var 406 registered" (test_find_mapper_registered)
- "MMC3 variant registered" — variant 406 (test_mmc3_variants_factory_dispatch)
- "MMC3 variant factory non-null" — variant 406

All three are `find_mapper(406)` returning null.  Other 8 MMC3
variants (12, 37, 44, 52, 74, 114, 165, 245) register correctly.

### 4.2 Bisect (E.1 diagnostic investigation)

Added temporary `fprintf` to `MapperEntryRegister::MapperEntryRegister`
and `find_mapper`.  Rebuilt + ran cart_class_test:
- `find_mapper(406)` IS called (test FAIL proves this)
- `MapperEntryRegister::ctor` for slot 406 **never runs** — the
  diagnostic only printed for 0-3, 7, 12, 13, 21, 24, 28, 36, 99,
  300, but never for 406

### 4.3 Hypotheses investigated (none confirmed)

| Hypothesis | Result |
|---|---|
| Duplicate registration overwriting slot 406 | ❌ No other file registers 406 |
| Static Init Order Fiasco (slot 406 written then cleared) | ❌ Meyers singleton is zero-init only on first call; no clear path |
| Linker DCE of `kMapper406Register` (unreferenced static) | ⚠️ Most likely — but MSVC linker did not respond to several keepalive approaches: keepalive array, extern C function, sentinel referenced from Cart::Cart(), static const address array |
| Compiled-out by MSVC's `/OPT:REF` | ⚠️ Plausible — `find_mapper(406)` constant-folds to null because no static init writes to slot 406, so the compiler removes the call. But this is normally a link-time, not compile-time, decision. |

### 4.4 Suggested followup

Apply one of these cross-cutting changes (not minimal, separate commit):

1. **`/OPT:NOREF` linker flag** for the boards library — keeps all
   unreferenced statics.  Risk: increases .exe size by ~20 KiB
   (build plan §10 risk).
2. **`__declspec(used)` attribute on `kXxxRegister`** — MSVC
   equivalent of GCC's `__attribute__((used))`.  Apply via macro
   or define a wrapper type.
3. **Explicit reference array in `src/boards/registry.cpp`** that
   takes the address of every `kXxxRegister` symbol.  Requires
   listing all 170+ mappers.

The cleanest is option 2: add a `[[gnu::used]]` or
`__declspec(noinline)` attribute to the static `kXxxRegister`
declarations (or to the MapperEntryRegister class itself).  This is
a 5-line change to `src/boards/registry.h` and resolves all 170+
mappers at once.
