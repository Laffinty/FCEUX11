## 1. `fceu11::Ppu` 类设计

### 1.1 类布局（与 Bus / Cpu 同样的模式）

```cpp
// src/ppu_class.h
#ifndef FCEU11_PPU_CLASS_H
#define FCEU11_PPU_CLASS_H

#include <cstdint>
#include <cstddef>

#include "types.h"             // PPUPHASE 等
#include "utils/cache.h"       // FCEUX11_CACHE_ALIGN, kCacheLineSize

namespace fceu11 {

class FCEUX11_CACHE_ALIGN Ppu {
public:
    // ---- 生命周期 ----
    Ppu() noexcept;
    void init() noexcept;
    void shutdown() noexcept;
    void power() noexcept;
    void reset() noexcept;
    void loop(bool skip);                       // → FCEUPPU_Loop

    // ---- 寄存器访问 ----
    uint8_t reg(uint32_t idx) const noexcept;   // → PPU[idx]
    void set_reg(uint32_t idx, uint8_t v) noexcept;

    // ---- 名称表 ----
    uint8_t* ntaram() noexcept;                 // → NTARAM[0x800] 整块
    uint8_t** vnapage() noexcept;               // → vnapage[4] 指针数组

    // ---- 渲染状态访问器（§5.2 三批逐步迁入）----
    // 批次 1（v1.5 必做）：PPU 控制寄存器镜像
    bool vtoggle() const noexcept;
    void set_vtoggle(bool v) noexcept;
    uint16_t vaddr() const noexcept;
    void set_vaddr(uint16_t v) noexcept;
    // ... vaddr_latch / temp_vaddr / fine_x_scroll / 等

    // 批次 2（v1.5 必做）：渲染行缓冲
    uint8_t* line_buffer();
    // ... 临时变量（bg_latch, sprite_latch, priority 等）

    // 批次 3（v1.5 必做）：SPR 计数器和 OAM 状态
    // ... spr_count, spr_index, oam[64+8], sprite_0_hit 等

    // ---- 帧阶段 ----
    PPUPHASE phase() const noexcept;
    void set_phase(PPUPHASE p) noexcept;

    // ---- 调试 ----
    int scanline() const noexcept;              // → newppu_get_scanline()
    int dot() const noexcept;                   // → newppu_get_dot()

    // ---- Bank-switching 入口（被 Bus 调用）----
    // Roadmap §5.2 + 后端审查 §2.5：Bus::setchr*/setmirror*/setntamem
    // 不再直接写 PPUCHRRAM/PPUNTARAM/vnapage[]/NTARAM，而是调以下成员。
    void set_chr_ram(uint32_t mask) noexcept;   // → PPUCHRRAM = mask
    void set_nt_ram(uint8_t mask) noexcept;     // → PPUNTARAM = mask
    void set_mirror_page(uint32_t idx, uint8_t* ptr) noexcept;  // → vnapage[idx] = ptr
    void set_mirror_mode(uint32_t mode) noexcept;  // 调 vnapage + PPUNTARAM
    void set_mirror_pages(uint8_t a, uint8_t b, uint8_t c, uint8_t d) noexcept;
    void notify_line_update() noexcept;         // → FCEUPPU_LineUpdate() 包装

    // ---- Savestate 兼容 ----
    // Roadmap §3.1 模式：直接暴露 native_layout() 给 savestate 序列化
    // 使用；其他模块必须走 typed accessors
    uint8_t* raw_ntaram() noexcept { return ntaram_; }
    // PPU[4] 不放在 Ppu 类内（保持 v1.0 兼容），通过 v1.0 兼容别名
    // 访问；v1.5 不重写 PPU[4] 的存储位置

private:
    // 排布规则：alignas(64) 数组在头部（hot path），控制变量居中，
    // 渲染缓冲与 NTARAM 在后（cold path 大块内存）
    alignas(64) uint8_t ntaram_[0x800];         // 名称表 RAM (2 KB)
    uint8_t* vnapage_[4];                       // 名称表指针 (4 × 8 = 32 B)
    PPUPHASE phase_ = PPUPHASE_VBL;             // 帧阶段
    // 批次 1 状态：
    bool vtoggle_ = false;
    uint16_t vaddr_ = 0;
    // ... 批次 2/3 字段在对应批次添加
};

// 全局直接实例（Roadmap §4.1 / Bus 同款，避免 Meyers singleton 阻碍 LTO）
extern Ppu g_ppu;

} // namespace fceu11

// ---- 兼容别名（v1.5 阶段 ppu.h 全局 → Ppu 内部） ----
extern uint8_t (& PPU)[4];       // → g_ppu.regs_alias()（见 §1.4）
extern uint8_t* (& NTARAM);      // → g_ppu.ntaram()
extern uint8_t* (& vnapage)[4];  // → g_ppu.vnapage()
extern uint8_t (& PPUCHRRAM);    // → g_ppu.chr_ram_mask()
extern uint8_t (& PPUNTARAM);    // → g_ppu.nt_ram_mask()

#endif // FCEU11_PPU_CLASS_H
```

### 1.2 与 Cpu / Bus 类的一致性原则

| 模式 | Cpu | Bus | Ppu（v1.5） |
|------|-----|-----|------------|
| 头文件 | `cpu.h` | `bus.h` | `ppu_class.h` |
| 全局实例 | `Cpu& cpu_instance()` (Meyers) | `Bus g_bus` (direct) | `Ppu g_ppu` (direct) |
| Savestate 兼容 | `native_layout()` | `Bus` 内部存储 + 全局别名 | `raw_ntaram()` + PPU[4] 兼容 |
| alignas(64) | 是 | 是（aread_[]） | 是（ntaram_[]） |
| 兼容别名 | `X`, `timestamp` 等 4 个 | 26 个 | 5 个 |
| __forceinline 热路径 | 是（add_cycles, read, write） | 是 | 是（reg / set_reg / vtoggle 等） |

**关键决策**：Ppu 用 `Ppu g_ppu`（与 `Bus g_bus` 同款），不用 Meyers singleton。理由：v1.14 LTO 需看穿 singleton，Roadmap §14.3 的回收点要求全局地址在 link-time 已知（与 WIP §1.4 / §1.3 一致）。

### 1.3 与 v1.0 兼容：PPU[4] 的特殊处理

`PPU[4]` 是 v1.0 的 4 字节寄存器数组（`PPU[0]=CTRL, PPU[1]=MASK, PPU[2]=STATUS, PPU[3]=OAMADDR`），被 50+ 文件以 `PPU[2] |= 0x80` 形式直接读写。`Ppu` 类**不**把 PPU[4] 迁入，因为：

1. 4 字节单独一组做 alignas(64) 浪费（cache line 64 B 只用 4 B）
2. PPU[0..3] 的语义在 Ppu 之外被密集使用，迁入会引发大量调用点修改
3. v1.0 savestate 格式对 PPU[4] 单独 chunk 序列化，迁入会破坏 v1.0 兼容

**做法**：PPU[4] 维持 v1.0 的全局数组，`Ppu` 类持有引用：
```cpp
// ppu_class.cpp
extern uint8_t PPU[4];  // ← 仍由 ppu.cpp 定义
uint8_t (& Ppu::regs_alias())[4] { return PPU; }
```

这与 v1.4 Bus 类保留 `extern uint8_t* (& PRGptr)[32]` 的做法一致。

### 1.4 性能预算的 inline 决策

按 §6.3 的性能约束，以下方法必须 `__forceinline`：

| 方法 | 调用频率 | 备注 |
|------|----------|------|
| `reg(idx)` / `set_reg(idx, v)` | 每 PPU 寄存器读写 | hot path |
| `vnapage()` 返回引用 | 每 tile fetch | hot path |
| `set_chr_ram(mask)` | 每 setchr8/4/1 | warm path |
| `set_mirror_page(idx, ptr)` | 每 setmirror* | warm path |
| `vtoggle()` / `set_vtoggle()` | 每 PPU 读周期 | hot path |
| `vaddr()` / `set_vaddr()` | 每 PPU 读周期 | hot path |

不强制 inline：

| 方法 | 备注 |
|------|------|
| `init()` / `power()` / `reset()` | 启动路径 |
| `loop()` | 调用频率适中，函数体大 |
| `scanline()` / `dot()` | 调试路径 |

## 2. 渲染状态迁移（§5.2 三批）

### 2.1 批次 1：PPU 控制寄存器镜像

**目标**：把 `ppu.cpp` 文件作用域中"轻量控制状态"迁入 `Ppu` 类。

**迁入清单**（按 grep `static bool\|static uint16\|static int` 在 ppu.cpp 渲染控制段的结果）：

| v1.0 静态变量 | 类型 | 迁入到 | 写入者 | 读取者 |
|---|---|---|---|---|
| `vtoggle` | `bool` | `Ppu::vtoggle_` | PPU 读时翻转 | PPU 读时 |
| `vaddr` | `uint16` | `Ppu::vaddr_` | 多个 set_vaddr | 多个读 vaddr |
| `vaddr_latch` | `uint16` | `Ppu::vaddr_latch_` | mmc5 同步 | PPU 读 |
| `temp_vaddr` | `uint16` | `Ppu::temp_vaddr_` | PPU 读 | PPU 读 |
| `fine_x_scroll` | `uint8` | `Ppu::fine_x_scroll_` | 写 $2005 | 读 tile |
| `ppucontrol_a` 等位运算缓存 | `uint8` | `Ppu::ppuctrl_a_` | 写 $2000 | 读 tile |
| `ppumask_*` 位运算缓存 | `uint8 × 4` | `Ppu::ppumask_*_` | 写 $2001 | 读 tile |

**保留为全局的**（不迁入）：

- `PPU[4]`（§1.3 决策）
- `NTARAM[0x800]`（按 v1.4 Bus 的 PRGptr 兼容模式保留为 `Ppu::ntaram_` 但通过 `extern uint8_t* NTARAM` 别名暴露给老代码）
- `PPUCHRRAM`, `PPUNTARAM`（按 §1.1 兼容别名模式保留）
- `vnapage[4]`（同上）

**迁移顺序**：

1. 在 `Ppu` 类加字段 + accessors
2. `ppu.cpp` 内部把所有 `vtoggle` 引用改为 `g_ppu.vtoggle()` / `g_ppu.set_vtoggle(...)`
3. 老代码（boards/、drivers/）继续读 v1.0 全局 `vtoggle`：因为 v1.5 阶段 `Ppu::vtoggle_` 是唯一来源，需要在 `Ppu` 里把 `vtoggle_` 暴露为 `extern bool& vtoggle_ref()`，然后 `bool vtoggle = fceu11::g_ppu.vtoggle_ref();` 兼容别名
4. 跑 ctest 17/17 + 视觉对比 0 差异

**风险**：vtoggle 是单 bit bool，多个 set 操作如果编译器无法折叠到寄存器会引入额外 load/store 指令。需在 §6 性能验证中确认 bench_ppu_frame 退步 < 5%。

### 2.2 批次 2：渲染行缓冲

**目标**：把 `ppu.cpp` 渲染循环的临时变量迁入 `Ppu` 类。

**迁入清单**：

| v1.0 静态变量 | 类型 | 迁入到 | 用途 |
|---|---|---|---|
| `PPU_linebuf[256+8]` | `uint8[264]` | `Ppu::line_buffer_[264]` | 1 行的最终像素输出 |
| `bg_latch[2]` | `uint8[2]` | `Ppu::bg_latch_[2]` | BG 像素锁存 |
| `bg_latch_h` | `uint8` | `Ppu::bg_latch_h_` | BG 高位属性 |
| `sprite_latch` | `uint8[8]` | `Ppu::sprite_latch_[8]` | sprite 锁存 |
| `sprite_latch_h` | `uint8[8]` | `Ppu::sprite_latch_h_[8]` | sprite 高位属性 |
| `priority_latch` | `uint8[8]` | `Ppu::priority_latch_[8]` | sprite 优先级 |

**性能关键点**：渲染行缓冲是 PPU 渲染循环里最 hot 的内存。`Ppu::line_buffer_` 必须 `alignas(64)`，且 `__forceinline` 访问器必须返回引用（避免拷贝）。

**风险**：

- 264 字节的 line buffer 在 64-byte cache line 上跨 5 行，每次访问可能引起 cache miss
- 多个渲染通道（BG / sprite 0 / sprite > 0）共享 line buffer，迁移时要保持写入顺序不变
- v1.0 写法是 `static uint8 PPU_linebuf[256+8];` 静态数组，编译器把它放在 .bss。迁入 `Ppu` 类后变成 `alignas(64)` 成员，会改变 cache 行为

**缓解**：先做小规模迁移（只迁 sprite_latch），跑视觉对比确认 0 差异，再迁 line_buffer。line_buffer 迁移时同步跑 `bench_ppu_frame`，看 cache miss 是否显著变化。

### 2.3 批次 3：SPR 计数器和 OAM 状态

**目标**：把 OAM 和 sprite 渲染状态迁入 `Ppu` 类。

**迁入清单**：

| v1.0 静态变量 | 类型 | 迁入到 | 用途 |
|---|---|---|---|
| `SPRAM[256]` | `uint8[256]` | `Ppu::oam_[256]` | OAM 主区域 |
| `Spr_Pri[8]` | `uint8[8]` | `Ppu::spr_priority_[8]` | 精灵优先级 |
| `Spr_Count` | `int` | `Ppu::spr_count_` | 当前扫描线精灵数 |
| `Spr_Index[8]` | `int[8]` | `Ppu::spr_index_[8]` | 精灵索引 |
| `Sprite0Hit` | `bool` | `Ppu::sprite_0_hit_` | sprite 0 命中标志 |
| `MaxSprites` | `int` | `Ppu::max_sprites_` | 8 |

**最复杂的迁移**：Sprite 0 hit 状态与 `PPU[2]`（STATUS）的 bit 6 强耦合，迁移时必须保持行为完全一致。

**风险**：

- OAM 状态在 $2002 / $2004 / $2007 / DMC DMA 多个路径写入
- 跨 sprite 渲染的多 line 状态（上一行的 sprite 0 hit 决策 → 下一行的 sprite 渲染）
- v1.0 中 Spr_Pri 是全局数组，渲染循环密集访问，迁入会引入 `this->` 偏移计算

**缓解**：与 v1.3 Cpu::layout_ 模式一致——`Ppu::oam_` 放 offset 0，savestate 序列化直接 memcpy 整块（OAM 区域 savestate 兼容 v1.0）。

### 2.4 三批之间的依赖

```
批次 1 (PPU 控制寄存器) ← 独立
批次 2 (渲染行缓冲)   ← 独立（但需要批次 1 完成后跑性能测试）
批次 3 (SPR / OAM)     ← 依赖批次 1（PPU[1] mask 决定 SPR 行为）
```

**合入顺序**：批次 1 → 批次 2 → 批次 3。每个批次 1 个 commit，commit message 显式标注 "v1.5 §5.2 批次 N/3"。

## 3. `Bus → PPU` 解耦（Roadmap §5.2 + 后端审查 §2.5）

### 3.1 当前硬耦合点

WIP 1fcba51 在 `bus.cpp` 顶部加的 TODO 注释定位的耦合：

```cpp
// src/bus.cpp 当前实现
void Bus::setchr1(uint32_t A, uint32_t V) noexcept {
    if (!chr_ptr_[0]) return;
    FCEUPPU_LineUpdate();
    // ...
    if (chr_ram_[0]) PPUCHRRAM |= (1u << (A >> 10));   // ← PPU 全局写
    // ...
}

void Bus::setmirror(uint32_t m) noexcept {
    FCEUPPU_LineUpdate();
    if (!mirror_hard_) {
        switch (m) {
        case 0:  // MI_H
            vnapage[0] = vnapage[1] = NTARAM;          // ← PPU 全局写
            // ...
        }
        PPUNTARAM = 0xF;                                // ← PPU 全局写
    }
}
```

这些 PPU 全局写应该改为 `Ppu` 成员调用。

### 3.2 解耦后的数据流

```
┌──────────────┐                                ┌──────────────┐
│              │   Bus::setchr1/4/8/...         │              │
│  Bus         │ ─────────────────────────────► │  Ppu         │
│  (fceu11::)  │   set_chr_ram(mask)            │  (fceu11::)  │
│              │   set_mirror_page(idx, ptr)    │              │
│              │   set_mirror_mode(mode)        │              │
│              │   notify_line_update()         │              │
└──────────────┘                                └──────────────┘
       │                                                 ▲
       │ ppu_(Ppu*)                                      │ 读 PPU 状态
       │ 注入                                            │
       ▼                                                 │
┌──────────────┐                                ┌──────────────┐
│  PPU/Ppu     │  ──────────────────────────►  │  ppu.cpp     │
│  (rendering) │   Ppu::loop()                 │  (driver)    │
└──────────────┘                                └──────────────┘
```

**注入时机**：

- `Bus` 持有 `Ppu* ppu_` 指针（`fceu11::Ppu*`）
- `Ppu` 持有 `Bus*` 或不持有（按需，**不**强行双向）
- `Ppu::power()` 调用时，把自己的地址写到 Bus：`bus_->attach_ppu(this)`；或者 `fceu.cpp::Initialize()` 时手动绑定

**推荐手动绑定**（v1.5 阶段，参考 v1.4 `Bus g_bus` 与 `fceu.cpp::PowerNES` 的关系）：

```cpp
// src/fceu.cpp::Initialize（v1.5 阶段改）
void fceu11::Initialize() {
    // ... 现有代码 ...
    g_bus.attach_ppu(&g_ppu);  // 一次性绑定
}
```

这样 `Bus::setchr*` 内部的 `PPUCHRRAM = ...` 改为 `ppu_->set_chr_ram(...)`：

```cpp
void Bus::setchr1(uint32_t A, uint32_t V) noexcept {
    if (!chr_ptr_[0]) return;
    ppu_->notify_line_update();                              // ← 改
    uint32_t bank = V & chr_mask1_[0];
    if (chr_ram_[0]) ppu_->set_chr_ram(ppu_->chr_ram_mask() | (1u << (A >> 10)));  // ← 改
    else             ppu_->set_chr_ram(ppu_->chr_ram_mask() & ~(1u << (A >> 10)));  // ← 改
    set_vpage(A >> 10, &chr_ptr_[0][bank << 10] - A);
}
```

### 3.3 注入失败兜底

`Bus::ppu_` 可能为 null（v1.5 早期阶段 Ppu 类还没接好）。需要：

```cpp
void Bus::attach_ppu(fceu11::Ppu* p) noexcept { ppu_ = p; }

void Bus::setchr1(uint32_t A, uint32_t V) noexcept {
    if (!chr_ptr_[0]) return;
    if (ppu_) ppu_->notify_line_update();   // 兜底
    else      FCEUPPU_LineUpdate();          // 旧路径（v1.5 早期）
    // ...
}
```

v1.5 release 前 `ppu_` 必须非 null，但兜底让开发期 build 不挂。

### 3.4 与 PPU 写 Cpu 的交叉耦合

WIP §2.1 已把 `overclocking` 迁入 `Cpu`，`ppu.cpp` 通过 `g_cpu.set_overclocking(...)` 写。这条 Ppu→Cpu 耦合**保留**，因为：

- 模拟器语义：PPU 控制 DMC 时序，DMC 影响 CPU 周期
- 方向正确：PPU 是控制方，CPU 是被控方
- v1.6 Apu 类会同样通过 `g_cpu.set_overclocking(...)` 调用（同样接受 PPU 的"通知"语义）

**Roadmap §0.1 全局变量消除进度**（附录 D）需要更新：

| 分类 | v1.0 数量 | v1.4 已迁入 | v1.5 迁入 Ppu | v1.6 迁入 Apu | v1.7 迁入 Cart |
|------|-----------|-------------|---------------|---------------|----------------|
| PPU | ~12 | 0 | **8**（含 PPUCHRRAM/PPUNTARAM/vnapage/NTARAM + 渲染内部状态） | 0 | 0 |

### 3.5 性能约束

`ppu_->set_chr_ram(mask)` 这条调用在 mapper 写寄存器时触发（warm path，不是 hot path），单次函数调用 ~3 周期开销可接受。**关键是不能在 PPU 渲染循环内部调用**（`Ppu::loop()` 内部），否则会爆掉 bench_ppu_frame。Roadmap §3.1 显式标注这是 §14.3 LTO 回收点，v1.5 阶段不必强求 ≤ 0 退步。

## 6. 性能预算

### 6.1 性能基线重抓

v1.4 `bench_baseline.json`（66-68ms，2026-06-22 抓）在 v1.5 启动时**必须重抓**：

**新基线流程**：


### 6.2 性能约束（vs v1.5 新基线）

| Bench | 退步预算 | 备注 |
|---|---|---|
| `bench_cpu_frame` | ≤ +1% | v1.5 不动 Cpu，理应无影响 |
| `bench_ppu_frame` | ≤ +5% | Ppu 类化引入的间接层 |
| `bench_full_frame` | ≤ +5% | 同上 |

**注意**：v1.5 不能用 v1.0 baseline 比（差 5-10%），必须用 v1.5 新基线。Roadmap §14.1 的"≤ 2% vs v1.0"是 v1.14 收官时的硬指标，不是 v1.5 的中间态约束。

### 6.3 链接时布局扰动预期

参考 WIP 1fcba51 经验 + Phase 6 经验：
- 删 / 加函数、类成员会改变 text section 体积和排列

## 9. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| PPU 渲染行为偏移 | 中 | 高（视觉差异） | 视觉对比测试 0 差异硬指标 |
| 性能退步 > +5% | 中 | 中 | §6.3 性能验证清单，超预算 §14.2 局部修正 |
| v1.0 savestate 兼容破坏 | 低 | 高 | NTARAM 走兼容别名（§2.2 风险已分析） |
| `Ppu` 字段顺序与 v1.0 不同导致 savestate 漂移 | 中 | 高 | 每批次加 `static_assert(offsetof(Ppu, oam_) == 0)`，参考 v1.3 Cpu 模式 |
| `Bus::ppu_` 注入失败（指针为 null） | 低 | 高 | §3.3 兜底分支保留 v1.0 路径 |
| 链接时布局扰动 > +10% | 中 | 中 | 接受 +5-10% 中间态，v1.14 LTO 回收 |
| 视觉对比 golden 在不同 GPU 渲染差异 | 低 | 高 | golden 用 CPU 端 PPU 输出（不是 GPU），跨机器一致 |
| `Ppu::line_buffer_` cache miss 激增 | 中 | 中 | alignas(64) + 渲染通道写入顺序保持 |
