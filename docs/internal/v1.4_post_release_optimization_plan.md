> **基线**：v1.4 Gateway（commit `509e753`，tag `v1.4`，2026-06-23）
> **范围**：v1.4 收官后、v1.5 Prism 启动前的代码审查与小 BUG / 质量优化方案
> **目标**：列出小 BUG 修复与代码质量改进项，使方案有利于 v1.5+ Roadmap 推进，**不与** `docs/v1.x_Modernization_Roadmap.md` §5~§14 冲突
> **方法**：手动审查 v1.4 核心交付物（`bus.h/cpp`、`cpu.h/cpp`）+ 热路径（`x6502.cpp`、`ppu.cpp`）+ 周边启动路径（`fceu.cpp:Initialize`）
> **本文档状态**：方案（plan），未在本文档中直接修复；每项标注推荐处理批次与所属 v1.x 阶段

## 0. 总纲

### 0.1 审查目标

v1.4 收官后，已知存在以下技术债务需要 v1.5+ 之前处理：

1. **Bus 类 API 与实际调用不一致** — `Bus::init()` 已写但未调用；真正初始化走 `fceu.cpp::PowerNES` 的 legacy `SetReadHandler(0, 0xFFFF, ANull)` 路径
2. **Cpu 类封装不完整** — `cpu_hook_`/`read_hook_`/`write_hook_` 死存储；`extern bool overclocking` 漏封装；缺 `db()` / `pi()` 等访问器
3. **Bus 与 PPU 全局的硬耦合** — `Bus::setchr*` / `setmirror*` / `setntamem` 直接写 PPU 全局（`PPUCHRRAM` / `PPUNTARAM` / `vnapage[]`），调用 `FCEUPPU_LineUpdate()`
4. **Bus 类自身的代码气味** — 22 次单独 memset；`set_read_handler` 循环有 unsigned 下溢风险；inline forwarder 类型不一致

### 0.2 与 v1.x Roadmap 的对齐

| 改进项 | 关联 Roadmap 阶段 | 关系 |
|--------|------------------|------|
| Bus 初始化路径重构 | §4.1 Bus 类定义 / §5.1.7 ctest | **支持**（让 Bus API 更自洽） |
| Bus → PPU 解耦 | §5 Prism (PPU 对象化) | **铺垫**（v1.5 启动后这部分必须迁移；提前清理 Bus 调用侧的硬耦合） |
| Cpu 访问器补全 | §3.4 验收 / §5 Prism 接口 | **支持**（v1.5 通过 Cpu 访问 PPU 寄存器，需要完整 API） |
| `overclocking` 迁入 Cpu | §3.2 全局变量迁入 | **兑现 v1.3 计划遗留**（v1.3 §3.2 列出但未迁入） |
| Cpu 死存储清理 | §13 Purify C 模式清理 | **前移**（在 v1.13 之前先清理，避免 `std::function` 死代码污染 v1.5+） |
| PPU 热路径迁移保留 | §4.3 hot-path migration / §14.3 LTO | **保留现状**（Phase 3 §5.1.5 例外；待 v1.14 LTO 后重新评估） |

### 0.3 不在本文档范围

- **新功能**（如新增 mapper、新增调试功能）—— 属于 Roadmap 子版本本身
- **结构性重构**（如把 ppu.cpp 拆为 PpuCore/PpuRendering/PpuSavestate）—— 属于 v1.12 Scissors
- **性能优化**（LTO / PGO）—— 属于 v1.14 Anvil
- **跨版本架构决策**（如 CartInfo 虚拟接口）—— 属于 v1.7 Cartograph

## 1. 已确认的 BUG / 小问题（建议尽快修复）

### 1.1 [BUG-MINOR] `Bus::init()` 是死代码

**位置**：`src/bus.cpp:86-99`、`src/bus.h:46`

**现象**：
```cpp
// src/bus.cpp
void Bus::init() noexcept {
    for (uint32_t x = 0; x < 0x10000; x++) {
        aread_[x]  = ANullImpl;
        bwrite_[x] = BNullImpl;
    }
    reset_mapping();
}
```

`git grep "g_bus.init\|bus().init"` 在全 `src/` 下零命中。该方法从未被调用。

实际初始化走 `src/fceu.cpp:1053-1054`：
```cpp
SetReadHandler(0x0000, 0xFFFF, ANull);
SetWriteHandler(0x0000, 0xFFFF, BNull);
```

这两行通过 `g_bus.set_read_handler()` 把 `ANullImpl` 装入 aread_[]，效果等同 `Bus::init()` 但分散在调用方。

**为什么是问题**：
- Bus 类 API 自相矛盾：明明有 `init()`，但调用者必须用 legacy `SetReadHandler` 全域填法
- v1.5 Prism 启动时若有新调用者参考 Bus API，可能误以为 `init()` 已经调用
- `fceu.cpp` 仍依赖 legacy 全域调用，是 v1.11 Bridge §11.1（消除 `#ifdef __QT_DRIVER__`）的过渡残留

**建议处理**：
```cpp
// src/fceu.cpp PowerNES() 开头加入
fceu11::g_bus.init();
// 移除
//   SetReadHandler(0x0000, 0xFFFF, ANull);
//   SetWriteHandler(0x0000, 0xFFFF, BNull);
```

`SetReadHandler(0, 0x7FF, ARAML)` 等具体范围注册保留。

**所属 Roadmap 阶段**：v1.11 Bridge（部分提前） / ctest 维护期

### 1.2 [BUG-MINOR] `Bus::set_read_handler` / `set_write_handler` unsigned 下溢风险

**位置**：`src/bus.cpp:156-170`

**现象**：
```cpp
void Bus::set_read_handler(uint32_t start, uint32_t end, readfunc fn) noexcept {
    if (!fn) fn = ANullImpl;
    for (uint32_t x = end; ; x--) {
        aread_[x] = fn;
        if (x == start) break;
    }
}
```

如果调用方传入 `end < start`（例如误传），`x = end` 进入 `x--` 后下溢到 `UINT32_MAX`，循环跑 4G 次。

**当前所有调用方都正确**（grep `SetReadHandler(0x8000, 0xFFFF, ...)` 等），但 invariant 不在 API 中强制。

**建议处理**：
```cpp
void Bus::set_read_handler(uint32_t start, uint32_t end, readfunc fn) noexcept {
    FCEU_DASSERT(end >= start);
    if (end < start) return;       // 防御性静默
    if (!fn) fn = ANullImpl;
    for (uint32_t x = start; x <= end; x++) {
        aread_[x] = fn;
    }
}
```

循环方向反转（升序）+ 显式 `end < start` 早退，更直观且无下溢。

**所属 Roadmap 阶段**：ctest 维护期（机械改动）

### 1.3 [BUG-MINOR] `extern uint64_t timestampbase` 函数体内重声明

**位置**：`src/cpu.cpp:62-63`

**现象**：
```cpp
uint64_t Cpu::timestamp_base() const noexcept {
    extern uint64_t timestampbase;     // ← 函数体内重声明
```

**所属 Roadmap 阶段**：v1.3 Legion 遗留兑现 / v1.5 Prism 接口对齐

### 1.4 [CODE-SMELL] `Cpu::cpu_hook_` / `read_hook_` / `write_hook_` 死存储

**位置**：`src/cpu.h:88-90`、`src/cpu.cpp:50-52`

**现象**：
```cpp
// src/cpu.h
std::function<void()> cpu_hook_;
std::function<void(uint32_t)> read_hook_;
std::function<void(uint32_t, uint8_t)> write_hook_;

// src/cpu.cpp
void Cpu::set_cpu_hook(std::function<void()> fn) { cpu_hook_ = std::move(fn); }
// ... 同 read_hook_ / write_hook_
```

`git grep "cpu_hook_\|read_hook_\|write_hook_"` 在调用方零命中 —— 这三个 `std::function` 成员只在 setter 里赋值，从不调用。

v1.3 Roadmap §3.1 注释承诺"Phase 3/4 接入 legacy hook 槽位" —— 但 Phase 3-7 实际未接入。

**风险**：未来 v1.5+ 代码若 `set_cpu_hook(...)` 会以为生效但实际不触发。

**建议处理（两个选项）**：

**选项 A：接入（推荐）**
把 hook 接到现有 legacy `FCEUI_*` 钩子槽位（如 `DBGDebuggerBreakpoint` 等），需要：
1. 调研 `fceu.cpp` / `debug.cpp` 中 hook 槽位的实际触发点
2. `Cpu::run()` / `Cpu::add_cycles()` 触发 `cpu_hook_`
3. `Bus::read()` / `Bus::write()` 触发 `read_hook_` / `write_hook_`

注意：`__forceinline` 的 hot path 上加 `std::function` 调用会击穿性能。**很可能不**适合接入 `Bus::read/write`。

**选项 B：删除**
从 `cpu.h` 移除三行 `std::function` 成员 + 三行 setter，把 Roadmap §3.1 的承诺改成"v1.13 Purify 阶段一并清理"。

**建议**：选 B（删除）。理由：
1. 死存储 = 死代码 = 删比留安全
2. v1.5+ 真要 hook，可以走 `fceu11::State::debug()` 接口（v1.2 §2.2 已规划）
3. 与 Roadmap §13 Purify "遗留 C 模式清理" 收敛方向一致

**所属 Roadmap 阶段**：v1.13 Purify（部分提前）

## 2. 代码质量改进（建议进入 v1.5 启动前的小重构批次）

### 2.1 [REFACTOR] `extern bool overclocking` 迁入 Cpu 类

**位置**：`src/cpu.h:24`、`src/cpu.cpp` (在 `add_cycles` 内使用)、`src/fceu.h:17`

**现象**：
```cpp
// src/cpu.h
extern bool overclocking;            // ← 全局仍被 Cpu 依赖

// src/cpu.cpp 内 Cpu::add_cycles
void Cpu::add_cycles(int32_t c) noexcept {
    // ...
    if (!overclocking) sound_timestamp_ += c;     // 读全局
}
```

v1.3 Roadmap §3.2 列出"timestamp / soundtimestamp / scanline / MapIRQHook"为应迁入的全局，但 `overclocking` 漏迁。这是 v1.3 Legion 的清单遗漏。

**建议处理**：
```cpp
// src/cpu.h 移除
// extern bool overclocking;

// src/cpu.h Cpu 类新增
public:
    bool overclocking() const noexcept { return overclocking_; }
    void set_overclocking(bool v) noexcept { overclocking_ = v; }
private:
    bool overclocking_ = false;

// src/cpu.cpp add_cycles 改用成员
if (!overclocking_) sound_timestamp_ += c;
```

**调用方迁移**：通过 `g_cpu.set_overclocking(...)` 设置，移除 `extern bool overclocking` 声明。

**影响范围**：`src/fceu.cpp` 等设置 overclocking 的位置（建议 grep `overclocking =` 全文）。

**所属 Roadmap 阶段**：v1.3 Legion 遗留兑现（已在 v1.3 计划内，仅漏执行）

### 2.2 [REFACTOR] `Cpu` 类访问器补全（`db()` / `pi()` 等）

**位置**：`src/cpu.h`、`src/cpu.cpp`

**现象**：`src/bus.cpp:46-47`：
```cpp
uint8_t ANullImpl(uint32_t) {
    return g_cpu.native_layout().DB;     // ← 穿透 native_layout()
}
```

`Cpu::native_layout()` 是 savestate 序列化专用 API（Roadmap §3.1），其他模块用它做普通寄存器读是绕过类型安全。

**建议处理**：在 `Cpu` 类添加访问器：
```cpp
// src/cpu.h
uint8_t db() const noexcept { return layout_.DB; }
void    set_db(uint8_t v) noexcept { layout_.DB = v; }
uint8_t pi() const noexcept { return layout_.PI; }
void    set_pi(uint8_t v) noexcept { layout_.PI = v; }
// ... 其他常用寄存器
```

然后 `ANullImpl` 改为 `return g_cpu.db();`。

**所属 Roadmap 阶段**：v1.5 Prism 启动前（Prism 需要通过 Cpu 触发 PPU 读取）

### 2.3 [REFACTOR] `Bus` 类构造函数 22 次 memset 合并

**位置**：`src/bus.cpp:55-80`

**现象**：
```cpp
Bus::Bus() noexcept {
    std::memset(aread_,  0, sizeof(aread_));
    std::memset(bwrite_, 0, sizeof(bwrite_));
    std::memset(page_,          0, sizeof(page_));
    // ... 还有 19 次
    mirror_hard_ = 0;
}
```

22 次单独 memset。每加一个 Bus 成员数组就要加一行 memset，容易漏（v1.5+ 加新成员时是潜在 BUG）。

**建议处理**：
```cpp
Bus::Bus() noexcept {
    std::memset(this, 0, sizeof(*this));  // 一次性清零所有成员
}
```

`mirror_hard_` 已为 0，`genie_a_read_`/`genie_b_write_`/`genie_r_wrap_` 已是 nullptr（类的 default initializer）。

**注意**：`static_assert(sizeof(Bus) < 512 KB)` 应同时加上，避免 Bus 类无界增长（Roadmap §13 Purify "巨型文件拆分" 的精神延伸到 class）。

**所属 Roadmap 阶段**：ctest 维护期（机械改动）

### 2.4 [REFACTOR] Inline forwarder 参数类型与 Bus 方法对齐

**位置**：`src/bus.h:285-294`

**现象**：
```cpp
// src/bus.h inline forwarder
inline void setmirror (int t) noexcept {
    fceu11::g_bus.setmirror(static_cast<uint32_t>(t));     // ← int→uint32_t cast
}
inline void setmirrorw(int a, int b, int c, int d) noexcept {
    fceu11::g_bus.setmirrorw(static_cast<uint32_t>(a), ...);
}
inline void setntamem(uint8_t* p, int ram, uint32_t b) noexcept {
    fceu11::g_bus.setntamem(p, ram, b);
}
```

Bus 成员函数本身签名是 `uint32_t`，但 inline forwarder 用 `int`，需要 `static_cast`。

**建议处理**：forwarder 改为 `uint32_t` 参数：
```cpp
inline void setmirror (uint32_t t) noexcept { fceu11::g_bus.setmirror(t); }
inline void setmirrorw(uint32_t a, uint32_t b, uint32_t c, uint32_t d) noexcept {
    fceu11::g_bus.setmirrorw(a, b, c, d);
}
inline void setntamem(uint8_t* p, int ram, uint32_t b) noexcept {
    fceu11::g_bus.setntamem(p, ram, b);
}
```

调用方几乎全是字面量（`setmirrorw(1, 1, 0, 0)`），无符号兼容。

**风险**：少数调用方传 `int` 变量（如某个 mapper 的 `setmirror(mirroring)`）。需要逐文件检查（建议 grep `setmirror[ (]` 全 boards，确认无 `int` 变量传递）。

**所属 Roadmap 阶段**：ctest 维护期（机械改动，需要 ctest 18/18 复测）

### 2.5 [DOC] Bus → PPU 硬耦合标注（不修代码）

**位置**：`src/bus.cpp:246-318`（`setchr1` / `setchr4` / `setchr8` / `setmirror` / `setmirrorw` / `setntamem`）

**现象**：Bus 成员函数直接写 PPU 全局：
```cpp
void Bus::setchr1(uint32_t A, uint32_t V) noexcept {
    // ...
    if (chr_ram_[0]) PPUCHRRAM |= (1u << (A >> 10));     // ← PPU 全局
    // ...
    FCEUPPU_LineUpdate();                                // ← PPU 函数
}

void Bus::setmirror(uint32_t m) noexcept {
    FCEUPPU_LineUpdate();                                // ← PPU 函数
    // ...
    vnapage[0] = vnapage[1] = NTARAM;                    // ← PPU 全局
    PPUNTARAM = 0xF;                                     // ← PPU 全局
}
```

**为什么这是 v1.5 启动前的天然切入点**：
- v1.5 Prism §5.1 的 Ppu 类需要持有这些状态
- Bus 当前把 PPU 全局当外部副作用写入，Ppu 类化后必须改为 `Ppu::set_chr_ram(idx, val)` 等成员调用
- 在 Bus 头文件加 `TODO(v1.5)` 注释，把"v1.5 启动后通过 Ppu* 指针调用"的契约钉死

**建议处理（仅文档）**：

在 `src/bus.cpp` 顶部加：
```cpp
// v1.5 Prism §5.x target: redirect PPU side-effects through a Ppu&
// reference (Bus would hold a Ppu* member). The current direct
// PPUCHRRAM / PPUNTARAM / vnapage[] writes are the natural seam
// where v1.5 work will pull. See
// docs/v1.x_Modernization_Roadmap.md §5.2 "渲染内部状态迁入".
```

**不改代码**：保持 v1.4 状态对象化的语义不变；v1.5 时一次性迁移。

**所属 Roadmap 阶段**：v1.5 Prism（注释先行，代码迁移在 v1.5 phase）

## 3. 性能与热路径（保留现状 / 不建议本批次动）

### 3.1 [KEEP-AS-IS] PPU 热路径 `ARead[]` / `VPage[]` 直接索引

**位置**：`src/ppu.cpp:797, 817, 983, 1756-1773, 2067-2073`

**现状**：v1.4 Gateway Phase 3 §5.1.5 例外 —— MSVC 19.51 未把 `g_bus.vpage()` 内联到与 reference-alias 等价的机器码，PPU 渲染热路径保留 `VPage[]` / `MMC5SPRVPage[]` 直接索引。`+6-8%` 退步超过 +2.5% 阈值。

**建议处理**：
1. **本批次不动** —— 这是 Roadmap 显式记录的例外，不是 BUG
2. 在 v1.14 Anvil §14.3 启用 `/LTCG` 后，重新跑 micro-benchmark，看 MSVC 19.51+ 是否能把 `g_bus.vpage()` 内联到等效机器码
3. 若可，重新迁移 PPU 热路径，回收 v1.5+ 的 0.5-1% 性能余量

**所属 Roadmap 阶段**：v1.14 Anvil（候选）

### 3.2 [KEEP-AS-IS] x6502.cpp 热路径已迁 `g_bus.read/write`

**位置**：`src/x6502.cpp:59, 69, 78, 99, 109`

**现状**：v1.4 Phase 3 已迁移成功 —— 5 个热路径调用点全部走 `fceu11::g_bus.read(...)` / `fceu11::g_bus.write(...)`，`__forceinline` 内联到 v1.3.0 等价机器码。

**建议处理**：无需改动。v1.5+ 仅在 `Cpu::run()` 内联调用 `Ppu::xxx()` 时再扩接口。

**所属 Roadmap 阶段**：v1.4 完成 / v1.5 启动前不需要额外动作
