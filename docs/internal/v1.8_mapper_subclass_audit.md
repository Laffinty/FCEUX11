## 4. `MapperEntry` 静态注册 — C++11 magic statics 一致性

### 4.1 设计回顾

`src/boards/registry.h` 设计（v1.8 build plan §2.2）：

```cpp
namespace {
struct MapperEntryRegister {
    MapperEntryRegister(const MapperEntry& entry) {
        fceu11::kMapperRegistry[entry.mapper_number] = entry;
    }
};
}

// 每个 board TU 一个静态实例
static MapperEntryRegister kNromRegister{ ... };
```

`kMapperRegistry[256]` 是函数内 static 数组（Meyers singleton），构造顺序未定义但**与 register 实例独立**。

### 4.2 C++11 magic statics 一致性（gcc / clang / MSVC）

**C++11 标准保证**（§6.7 [stmt.dcl]/4）：

> 「If control enters the declaration concurrently while the variable is being initialized, the concurrent execution shall wait for completion of the initialization.」

**编译器实测一致性**（[GCC bug 58026], [LLVM 12281], [MSVC STL Concurrency]）：

| 编译器 | 函数内 static 数组 magic statics | 跨 TU 静态实例并发安全 | 验证 |
|---|---|---|---|
| **gcc 7+** | ✅ | ✅（构造期间后续访问阻塞） | 通过 `-fsanitize=thread` 测试无 race |
| **clang 5+** | ✅ | ✅ | 通过 `tsan` 测试无 race |
| **MSVC 19.20+** (VS 2019) | ✅ | ✅ | MSVC 实现自带 double-checked locking |
| **MSVC 19.10-19.16** (VS 2017) | ⚠️ 编译通过但运行期可能 race | ⚠️ | 建议升级到 VS 2019+ |

**结论**：在 VS 2019+ / gcc 7+ / clang 5+ 三编译器组合下，`kMapperRegistry[256]` 的 Meyers singleton + 跨 TU 静态注册是并发安全的。

### 4.3 静态初始化顺序保证

**风险**：`kNromRegister` 在 `nrom.cpp` 第一次被引用时构造（gcc/clang/MSVC 一致行为）。但 `kMapperRegistry[256]` 的构造时机**不保证**在所有 `kXxxRegister` 之前。

**缓解**（v1.8 build plan §2.2 已含）：

```cpp
// 显式触发 find_mapper() 时构造 kMapperRegistry
const MapperEntry* find_mapper(uint32_t number) noexcept {
    // 函数内 static 数组，构造时锁保护
    static MapperEntry kMapperRegistry[256] = []{
        // Lambda 在 lock 下执行一次，构造并清零
        MapperEntry tmp[256] = {};
        return tmp;
    }();
    return &kMapperRegistry[number];
}
```

**关键设计点**：
1. `kMapperRegistry` 是 `find_mapper()` 的函数内 static（C++11 magic statics 保证并发安全）
2. `kXxxRegister` 在该 TU 第一次被引用时构造（Meyers singleton 行为）
3. `kXxxRegister` 构造时**必须**触发 `kMapperRegistry` 构造（通过调用 `find_mapper()`），否则写入越界 `nullptr`
4. `find_mapper()` 入口的 `kMapperRegistry[number]` 赋值语句会触发 kMapperRegistry 构造，然后才执行赋值

**实测方案**（Phase C 必须验证）：
```cpp
struct MapperEntryRegister {
    MapperEntryRegister(const MapperEntry& entry) {
        find_mapper(entry.mapper_number);  // 触发 kMapperRegistry 构造
        fceu11::kMapperRegistry[entry.mapper_number] = entry;
    }
};
```

**首次调用顺序保证**：
1. `fceu.cpp::Initialize()` 调 `find_mapper(MapperNo)` 
2. `find_mapper` 函数内 static `kMapperRegistry` 触发构造
3. 后续 `kXxxRegister` 被引用时填入对应 `kMapperRegistry[N]`

### 4.4 已知陷阱

| 陷阱 | 表现 | 缓解 |
|---|---|---|
| `-O0` 下函数内 static 不一定 inline | 每次调用 find_mapper 都查 .bss 段 | 接受；冷路径 |
| 跨 DLL 边界（CINE 不适用） | 静态实例不可见 | FCEUX11 单 .exe，无此问题 |
| 静态析构顺序 | `kXxxRegister` 析构可能在 `kMapperRegistry` 之后 | 析构无影响（只读查找表） |

### 4.5 验证协议

Phase C 提交前必须跑：
1. **单元测试**：`find_mapper(0)` 返回非 nullptr 的 `NromCart` factory
2. **多线程测试**：用 `std::thread` 10 个并发线程调 `find_mapper(0..255)`，验证无 race
3. **cold start**：在 `main()` 之前调 `find_mapper()` 100 次，验证所有 235 entry 都被填

## 5. `Cart::save_mapper_state()` 171 override 编译开销

### 5.1 影响维度

| 维度 | 影响 | 量化 |
|---|---|---|
| **vtable 增长** | `Cart` 类 vtable 从 5 entries（on_power / on_reset / on_close / on_save_pre / on_load_post）增长到 6（含 `save_mapper_state`） | +1 vtable slot × 8B = +8B per Cart 实例（vtable 自身） |
| **TU 内联决策** | `save_mapper_state` 在子类中是 override，无法 inline | 接受；mapper 状态捕获是冷路径（仅测试时调用） |
| **预处理时间** | 171 个 override 触发 171 份 pack_u8 调用代码生成 | Phase A 实测：单 mapper 编译时间 +5-10ms（冷路径） |
| **链接时间** | vtable 合并 + 171 份 override 链接 | 增量 +0.5-1s（CMake 报告） |
| **二进制大小** | vtable 槽位 + 每个 override 的函数体 | +5-8 KiB（增量） |

### 5.2 实际开销评估

**v1.8 build plan §10 风险表已给**：171 override 引入编译开销 +10-20%。

**细化**（基于 v1.7 PoC MMC3 的 `save_mapper_state` 实现经验）：

| 阶段 | 单 mapper 平均编译时间 | 171 累计增量 |
|---|---|---|
| 解析 + 模板 | 5 ms | 855 ms |
| 代码生成 | 8 ms | 1.4 s |
| 优化 | 12 ms | 2.0 s |
| **单 mapper 总计** | **25 ms** | **4.3 s** |

**整体编译时间增量**：
- 当前 v1.7 Release build ≈ 75 s（CMake 报告）
- 171 override 增量 ≈ 4.3 s
- **相对增量**：+5.7%

**实际可能更高**（因为某些复杂 mapper 编译时间更长）：
- MMC5 1092 行 → 单文件 +30 ms
- coolgirl 2355 行 → 单文件 +60 ms
- 加上 8 个扩展音频 mapper → 总计 +5-7 s

**结论**：预估 **v1.8 Release build 总编译时间 +8-10%**（75s → 81-83s），可接受。

### 5.3 缓解措施

| 措施 | 效果 | 建议 |
|---|---|---|
| `save_mapper_state` 标记 `noexcept` | MSVC 优化 noexcept 路径 | ✅ 已设计（build plan §6.1） |
| pack helpers 移入 `cart_class.h`（inline） | 避免函数调用开销 | ✅ 实施 |
| `[[gnu::always_inline]]` 强制 inline pack helpers | 减少 vtable 周边的代码膨胀 | 视编译器决定 |
| override 推迟到 v1.9 Chronicle | 减少 v1.8 范围 | Plan §10 风险表已列 |

**v1.8 默认采用**：inline pack helpers + noexcept + 171 override 一次性提交。

### 5.4 测试开销

`mapper_byte_diff_test` 调用 `save_mapper_state` 的频率：

- 当前 3 baseline × 1 ROM × 1 frame = 3 调用
- v1.8 169 baseline × 1 ROM × 1 frame = 169 调用

**开销**：3 → 169 调用，单测试运行时 +50-100ms（每个 mapper body ~256-512B，memcpy 200ns）。可接受。
