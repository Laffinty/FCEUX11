# FCEUX11 v1.4 Gateway 独立构建方案

> **目标**：在 v1.3 Legion 已交付的 `fceu11::Cpu` 类基础上，完成**内存分发总线重构（v1.4 Gateway）**：将 `ARead[]` / `BWrite[]` / `Page[]` / `VPage[]` 等内存分发表以及 `setprg*` / `setchr*` / `setmirror*` 等 bank-switching 自由函数封装为 `fceu11::Bus` 类，迁移全部 175 个 board 文件的调用点，保持 savestate 二进制兼容和性能不退步（`bench_tolerance_test` 3/3 PASS，偏差 ≤ +2.5%）。
>
> **基线版本**：v1.3.0（commit `ad1fdcf`，tag `v1.3.0` / `v1.3-phase7`）
> **目标版本 tag**：`v1.4`（按 2026-06-22 起的版本号新规，不带 patch 段；phase 节点用 `v1.4-phase0` ~ `v1.4-phase7`）
> **工具链**：MSVC 2022 19.51+ / C++20 / Rust 2024 / Qt 6.8 LTS / CMake 4.0+ / Ninja
> **文档创建**：2026-06-22

---

## 1. 总体策略

v1.4 的核心任务是**把内存分发总线从"自由函数 + 全局表"模型迁移到 `fceu11::Bus` 类**，与 v1.3 的 `Cpu` 类对称。这一步比 v1.3 范围更广：v1.3 改 67 个文件（30 个 board），v1.4 要改 175 个 board 文件 + 核心读 / 写路径 + debugger UI。

按 roadmap §0.2 的渐进式原则，v1.4 把任务拆成 8 个阶段（Phase 0 ~ Phase 7）：

1. **Phase 0（前置）**：基线锁定 + 现状清点 + 调用点全量审计
2. **Phase 1（骨架）**：新增 `src/bus.h` / `src/bus.cpp`，定义 `fceu11::Bus` 类
3. **Phase 2（兼容层）**：把现有 `ARead[]` / `BWrite[]` / `setprg*` 等符号改为 `Bus` 内部数据的 inline 引用别名（已知：引入 +24% bench 回归，Phase 3 修复）
4. **Phase 3（性能修复 + 热路径迁移）**：引入 `g_bus` 直接全局对象替换 Meyers 单例，迁移 `x6502.cpp` / `ppu.cpp` / `cart.cpp` 等核心热路径到 `g_bus.` 直接访问，CI 上重新捕获 baseline
5. **Phase 4（热 mapper board 迁移）**：迁移 5 个最常用 mapper board（mmc3/mmc1/mmc5/vrc6/vrc7）+ 3 个有直接数组索引的 board（BMW8544/onebus/sb-2000）
6. **Phase 5（剩余 board 验证 + 清理）**：验证 ~163 个仅使用转发器的 board 文件 + `cart.cpp` 温路径迁移 + 全局 grep 审计
7. **Phase 6（验证）**：savestate 布局审计、AddExState 影响面复审、性能复测
8. **Phase 7（CI 闭环）**：CI 门禁、PR checklist、`v1.4` release tag

### 关键原则

- **零中间不可用态**：每个 PR 都必须可编译、可运行、`ctest` 全绿（≥ 18 用例）
- **savestate 二进制兼容**：v1.4 完成后，v1.3 写出的 golden `.fc0` 仍能加载 / 保存往返一致
- **性能不退步**：`bench_tolerance_test` 3/3 PASS（偏差 ≤ +2.5%）；baseline 必须在 CI runner 机型上捕获
- **175 文件调用点全部走 `Bus::` 路径**：inline 转发器或 `g_bus.` 直接访问均可；热路径文件必须用 `g_bus.` 直接访问消除 reference 别名间接层
- **不引入虚函数热路径**：`Bus::read` / `Bus::write` 必须 `__forceinline`，分发表访问保持与 v0.3.x 同等机器码

### 3.2 `Bus` 类设计（与 roadmap §4.1 对齐）

```cpp
// src/bus.h
#pragma once
#include <cstdint>
#include "utils/cache.h"  // FCEUX11_CACHE_ALIGN

namespace fceu11 {

using ReadHandler  = uint8_t (*)(uint32_t a);
using WriteHandler = void    (*)(uint32_t a, uint8_t v);

class FCEUX11_CACHE_ALIGN Bus {
public:
    // 默认构造 / 生命周期
    Bus() noexcept;
    void init() noexcept;          // 把 ARead/BWrite 全部置为默认 open-bus handler
    void shutdown() noexcept;

    // 64K CPU 地址空间读 / 写分发（热路径，__forceinline）
    __forceinline uint8_t read(uint16_t addr) const noexcept {
        return aread_[addr](addr);
    }
    __forceinline void write(uint16_t addr, uint8_t val) const noexcept {
        bwrite_[addr](addr, val);
    }

    // 直接内存访问（调试 / DMR / DMW）
    uint8_t direct_read(uint32_t addr) const noexcept;
    void    direct_write(uint32_t addr, uint8_t val) noexcept;

    // 分发表注册
    void set_read_handler(uint32_t start, uint32_t end, ReadHandler fn) noexcept;
    void set_write_handler(uint32_t start, uint32_t end, WriteHandler fn) noexcept;

    // PPU 地址空间页表
    uint8_t* vpage(uint32_t idx) const noexcept       { return vpage_[idx]; }
    void set_vpage(uint32_t idx, uint8_t* ptr) noexcept { vpage_[idx] = ptr; }

    // CPU 地址空间页表
    uint8_t* page(uint32_t idx) const noexcept        { return page_[idx]; }
    void set_page(uint32_t idx, uint8_t* ptr) noexcept { page_[idx] = ptr; }

    // Bank-switching API（从 cart.cpp 迁入）
    void setprg8 (uint32_t addr, uint32_t bank) noexcept;
    void setprg16(uint32_t addr, uint32_t bank) noexcept;
    void setprg32(uint32_t addr, uint32_t bank) noexcept;
    void setchr1 (uint32_t addr, uint32_t bank) noexcept;
    void setchr4 (uint32_t addr, uint32_t bank) noexcept;
    void setchr8 (uint32_t addr, uint32_t bank) noexcept;
    void setmirror (uint32_t m) noexcept;
    void setmirrorw(uint32_t a, uint32_t b, uint32_t c, uint32_t d) noexcept;
    void setntamem(uint8_t* p, bool hr, uint32_t addr) noexcept;

    // ROM 指针表
    uint8_t* prg_ptr(uint32_t idx) const noexcept     { return prg_ptr_[idx]; }
    uint8_t* chr_ptr(uint32_t idx) const noexcept     { return chr_ptr_[idx]; }
    void setup_prg_mapping(uint32_t count, uint8_t** ptrs, uint32_t* sizes, bool ram) noexcept;
    void setup_chr_mapping(uint32_t count, uint8_t** ptrs, uint32_t* sizes, bool ram) noexcept;

    // 内部数据只读访问（仅 savestate 序列化代码使用）
    const ReadHandler*  aread_table()  const noexcept { return aread_; }
    const WriteHandler* bwrite_table() const noexcept { return bwrite_; }
    ReadHandler*        aread_table()  noexcept       { return aread_; } // 注册路径需要写

private:
    alignas(64) ReadHandler  aread_[0x10000];
    alignas(64) WriteHandler bwrite_[0x10000];
    uint8_t* page_[32];
    uint8_t* vpage_[8];
    uint8_t* prg_ptr_[32];
    uint8_t* chr_ptr_[32];
    // PRG / CHR bank tables, mask, size, ram 标志...
};

// 全局唯一实例（v1.4 仍保持单例；v1.7 Cart 类后考虑多 Bus）
Bus& bus_instance() noexcept;

} // namespace fceu11

// 兼容别名：v1.4 阶段保留原全局符号，指向 bus_instance() 的对应内部数据
inline auto& ARead  = fceu11::bus_instance().aread_table();
inline auto& BWrite = fceu11::bus_instance().bwrite_table();
```

## 5. Phase 3~5：性能回归修复 + Board 调用点迁移

### 5.0 背景与教训

#### 5.0.1 Phase 2 CI 失败事实

Phase 2 合并后（commit `8c311dc`，tag `v1.4-phase2`）的 CI 运行显示 `bench_tolerance_test` **失败**（17/18 通过）。桌面归档日志 `logs_75376768854.zip` 记录了完整 CI 输出：

| 基准 | baseline (ms) | CI 实测偏差 | 容忍度 | 结果 |
|---|---|---|---|---|
| `bench_cpu_frame` | 63.622 | +24.92% | +2.5% | FAIL |
| `bench_ppu_frame` | 65.381 | +24.10% | +2.5% | FAIL |
| `bench_full_frame` | 65.630 | +27.24% | +2.5% | FAIL |

功能性测试（`rom_regression_test`、`savestate_regression_test`、`golden_savestate_test` 等 17 项）全部通过——Phase 2 的数据迁移在功能上是正确的，但存在严重性能回归。

#### 5.0.2 根因分析

经代码审计，回归有两个叠加因素：

**因素 A —— `extern` reference-to-array 别名的 ABI 间接寻址（主因）**

`bus.h:230` 将 `ARead`/`BWrite`/`Page`/`VPage` 等声明为 `extern T (&name)[N]` 引用别名。在 MSVC/x64 ABI 下，引用是作为指针实现的——每次 `ARead[A]` 需要先从全局存储加载引用指针（一条 `mov rax, [rip+X]`），再索引数组。而 v1.3.0 的 `ARead` 是直接全局数组，编译器在编译期就知道数组地址，`ARead[A]` 是一条 RIP-relative 直接寻址。

`x6502.cpp` 的 `RdMem`/`WrMem`（每帧 ~10⁶ 次调用）和 `ppu.cpp` 的 `VPage[tmp >> 10]`（每帧 ~10⁵ 次）受此影响最大。`bus.cpp:398` 注释声称"identical to v1.3.0 machine code"是错误的——reference 别名多出一条指针加载指令。

**因素 B —— `bench_baseline.json` 在开发机上捕获，CI runner 更慢（叠加因素）**

`bench_baseline.json` 的 `captured_on` 字段为 `Windows_NT, Microsoft Windows 10.0.26200`（开发机），而 CI runner 为 `Windows Server 2022, 10.0.20348`。v1.3 baseline（66.230 / 68.678 / 67.842 ms）在 CI 上可通过，说明 v1.3 baseline 是在 CI 或同等机型上捕获的。Phase 2 将 baseline 在更快的开发机上重新捕获（63.622 / 65.381 / 65.630 ms，比 v1.3 低 3-5%），导致 CI 运行时即使代码无回归也会偏高 ~20%。

两个因素叠加：~20% 机器差异 + ~5% reference 别名开销 ≈ ~25% 表观回归。

**因素 C —— `bus_instance()` 非 inline 函数调用（次要因素）**

`bus.cpp:378` 的 `bus_instance()` 是 Meyers 单例（非 inline）。每个 `inline void setprg8(...)` 转发器在每次调用时都需要一次函数调用来解析单例地址。bank-switching 操作不在最热路径上（每帧 ~10²-10³ 次），影响较小但非零。

#### 5.0.3 原 Phase 3~5 计划的失败原因

1. **引用了不存在的符号**：原计划 §5.1 写"把 `setprg8(...)` 改为 `g_bus.setprg8(...)`"，但代码中不存在 `g_bus`——实际符号是 `fceu11::bus_instance()`
2. **未识别 Phase 2 bench 失败为前置阻塞项**：在 17/18 的基线上叠加 board 迁移，无法区分迁移引入的回归与 Phase 2 遗留的回归
3. **误判迁移规模**：Phase 2 的 inline 转发器已让所有 `setprg8(...)` / `setchr1(...)` 调用透明路由到 Bus。175 个 board 文件中，只有 3 个（`BMW8544.cpp`、`onebus.cpp`、`sb-2000.cpp`）直接索引 `ARead[]` / `BWrite[]`，其余 168 个仅使用转发器——不需要代码变更
4. **批次划分基于 mapper 编号而非热路径优先级**：真正的性能瓶颈在非 board 文件（`x6502.cpp`、`ppu.cpp`、`cart.cpp`），不在 board 文件

#### 5.0.4 修订策略

- **Phase 3**：修复性能回归（引入 `g_bus` 直接全局对象 + 迁移核心热路径非 board 文件 + 在 CI 上重新捕获 baseline）
- **Phase 4**：迁移 8 个有直接数组访问或高频调用的 board 文件（5 热 mapper + 3 直接索引 board）
- **Phase 5**：验证剩余 ~163 个仅使用转发器的 board 文件 + `cart.cpp` 温路径迁移 + 最终清理

### 5.1 Phase 3：性能回归修复 + 核心热路径迁移

#### 5.1.1 引入 `g_bus` 直接全局对象

将 `bus_instance()` Meyers 单例替换为直接全局对象 `g_bus`，与 v1.3 的 `g_cpu` 模式对称。但 `g_cpu`（`cpu.h:99`）是 `inline auto&` 引用——在 ABI 层仍是指针；`g_bus` 改为 `extern` 直接对象，编译器在链接期就知道其地址，`g_bus.aread_table()[A]` 可折叠为直接数组寻址。

**`src/bus.h` 变更**：

```cpp
// 替换：
//   Bus& bus_instance() noexcept;
// 为：
namespace fceu11 { extern Bus g_bus; }
```

**`src/bus.cpp` 变更**：

```cpp
// 替换：
```

> **Phase 3 实施结果 —— ppu.cpp 热路径保留 reference 别名（例外）**
>
> 上述 ppu.cpp 热路径迁移（VRAMADR / MMC5SPRVRAMADR 宏 + 7 处 `VPage[]` 直接索引）在实施后导致
> `bench_tolerance_test` 回归 +6-8%（所有 3 项 bench 均 FAIL，详见 `docs/v1.4_phase3_status_report.md` §3）。
> 原因分析：MSVC 19.51 未将返回 `uint8_t*(&)[8]` 的 `__forceinline` 访问器 `g_bus.vpage()` 内联到与
> `VPage[i][j]`（`extern` reference 别名，IR 层等价于已知地址的全局数组）等价的 RIP 相对寻址序列，
> 每个 `g_bus.vpage()[i][j]` 调用点多出一次函数调用 / 成员偏移加载指令。`__forceinline` 属性未能挽回。
>
> **决定**：回退 ppu.cpp 的全部 VPage / MMC5SPRVPage 热路径迁移，保留 `VPage` / `MMC5SPRVPage` 作为
> `extern` reference 别名（已在 `bus.cpp:404-407` 绑定到 `g_bus.vpage_` / `g_bus.mmc5_spr_vpage_`）。
> 数据统一目标**仍然达成**——`vpage_` 数组只存在于 `g_bus` 中一份，`VPage` 名字只是一个指向 `g_bus.vpage_`
> 的引用别名；仅调用点拼写未统一为 `g_bus.vpage()`。这等效于计划 §5.3.3 的冷路径保留策略，扩展到 ppu.cpp 热路径。
>
> 回退后 bench 恢复达标：5 次 bench_tolerance_test 中 4 次 3/3 PASS，`bench_full_frame` 偏差中位数 +1.41%
> （详见 status report §3）。ppu.cpp 的 VPage 热路径迁移留待 v1.7 Cart 类重构时用不同的访问器设计
> （如暴露 `vpage_` 为 public 成员，或改用 `uint8_t**` 返回类型）重新尝试。

#### 5.3.5 转发器层保留决策

Phase 5 末尾需决定 `bus.h` 中的 inline 转发器（`setprg8` / `setchr1` / `setmirror` / `SetReadHandler` / `SetWriteHandler` 等）的去留：

**选项 A —— 永久保留转发器层**（推荐）：

- 转发器在 Phase 3 后已零开销（路由到 `g_bus`，编译后等价于直接调用）
- 175 个 board 文件不需要逐一改为 `g_bus.setprg8(...)`——零收益、高风险
- 与 v1.3 的 `g_cpu` 宏模式（`_PC` / `_A` / `_X` 等，`x6502abbrev.h`）对称——v1.3 保留了宏而非逐一迁移
- `extern` reference 别名（`ARead` / `BWrite` / `Page` 等）也保留，供冷路径使用

**选项 B —— 消除转发器层**：

- 将 175 个 board 文件中的 `setprg8(...)` 全部改为 `g_bus.setprg8(...)`
- 删除 `bus.h` 中的 inline 转发器和 `extern` reference 别名
- 代码更"干净"但变更量巨大（~2000 call site）、回归风险高、无性能收益
- 不推荐——v1.7 Cart 类重构时再统一处理

**本计划默认采用选项 A**。如果选择选项 B，需在 Phase 5 末尾增加一个子阶段 5e（转发器消除），并相应调整验收标准。

**Phase 5 末尾正式决策：选项 A（永久保留）**

实施结果确认选项 A：

- `bus.h:279-313` 11 个 inline 转发器（`setprg8` / `setprg16` / `setprg32` / `setchr1` / `setchr4` / `setchr8` / `setmirror` / `setmirrorw` / `setntamem` / `SetupCartPRGMapping` / `SetupCartCHRMapping` / `SetupCartMirroring` / `ResetCartMapping`）保留，路由到 `fceu11::g_bus`
- `bus.cpp` 中 24 个 `extern` reference 别名（`ARead` / `BWrite` / `Page` / `VPage` / `VPageG` / `MMC5SPRVPage` / `MMC5BGVPage` / `PRGptr` / `CHRptr` / `PRGsize` / `CHRsize` / `PRGmask2-32` / `CHRmask1-8` / `PRGram` / `CHRram` / `PRGIsRAM`）保留，绑定到 `g_bus` 内部数组
- `fceu.cpp:310-368` handler 注册冷路径代码（ARead[x]=func / BWrite[x]=func）保留 reference 别名访问
- `ppu.cpp:1756-1773` PPU 寄存器映射 init（`ARead[x]=A200x` 等）保留 reference 别名访问（cold path，175x 单次执行）
- 175 个 board 文件 ~2000 个 setprg*/setchr*/SetReadHandler/SetWriteHandler 调用点**未逐一迁移** —— 编译后通过 inline 转发器路由到 `g_bus`，与 `g_bus.setprg8(...)` 直接调用机器码等价

v1.7 Cart 类重构时再统一处理转发器层（选项 B 路径），届时与 Cart 类 redesign 合并。

## 9. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| `Bus` 布局变更破坏 savestate | 中 | v1.3 已验证 `static_assert` + golden 往返；v1.4 不改变 savestate payload，只改变注册路径 |
| `extern` reference 别名导致性能退步（Phase 2 已发生 +24% 回归） | 高 | Phase 3 引入 `g_bus` 直接全局对象 + 迁移热路径到 `g_bus.` 直接访问；CI 重新捕获 baseline；`bench_tolerance_test` 3/3 PASS 才进 Phase 4 |
| `g_bus` 全局对象替换 `bus_instance()` 引入链接错误 | 中 | `extern Bus g_bus;` 是标准 C++ 全局对象声明，MSVC 完全支持；与 v1.3.0 的 `ARead` / `BWrite` 直接全局数组同模式 |
| 热路径迁移（x6502/ppu/cart）引入功能回归 | 高 | 每个文件迁移后立即跑 `ctest`；`x6502.cpp` 迁移后跑 `cpu_test` + `savestate_core_test`；`ppu.cpp` 迁移后跑 `golden_savestate_test` |
| 175 个 board 文件批量修改引入回归 | 低 | 修订后仅 3 个 board 文件需代码变更（BMW8544/onebus/sb-2000），其余 168 个仅验证；每子批 grep + `ctest` |
| VRC7 OPLL Rust FFI 阻塞 v1.4 核心 | 低 | v1.4 Phase 4 迁移 vrc7.cpp 时借机推进，但不阻塞；scalar snapshot 路径已能消除指针 |
| CMake / vcpkg / version.h 三处版本号不同步 | 低 | Phase 7 集中更新；CI 加一致性检查 |

### 回滚策略

- 每个 Phase 完成后打 `v1.4-phaseN` tag
- 若任一阶段 `ctest` / `bench_full_frame` / `golden_savestate_test` 失败，立即 `git revert` 该 PR，回到上一 phase tag 重新设计
- **Phase 2 先例**：Phase 2 合并时 `bench_tolerance_test` 失败（17/18，+24% 回归），当时未回滚而是带病推进 Phase 3，导致 Phase 3 完全失败。修订后的策略：Phase 3 的 `bench_tolerance_test` 3/3 PASS 是 Phase 4 启动的**硬性前置条件**——不通过则不开始任何 board 迁移
- `v1.4` release tag 只在所有 phase 通过 + `bench_tolerance_test` 3/3 PASS 后打
