# 陷阱清单：让测试看起来在保护你、实际不保护的四种形态

> 面向的读者：任何要给 FCEUX11 加检查的人。这四条**每一个都真的发生过**，
> 每一条都是「测试全绿 + 功能是坏的」同时成立。清单的价值在于：写完一条测试，
> 用本文件 §5 的三问过一遍再提交。

---

## 一、把「假设」写进合成夹具，于是测试固化错误

**症状**：一整类锁测试全绿，而真实输入下功能完全不工作。

**实例（r49，最严重的一次）**。stub BIOS 的启动序列从 `0x080000C0` 读取
「卡带入口地址」。而 GBA 卡带头 `0xC0` 是 *Nintendo Reserved* 槽，存的是
一条 ARM 跳转指令 —— 实测 Mario Kart 那里是 `0xE3A00012` = `mov r0, #0x12`，
是游戏自己的第一条真实指令。

于是机器跳进 `0xE3A00012`（未映射区），**每一块商业卡带的游戏代码都从未执行过
一行**。探针证据：PC 的 30,000 个采样全部在未映射区，值是 `0xEAC70DE4` 这类垃圾。

**为什么测试是绿的**：4 条 bios 测试 + gate + frame + swi 造的合成 ROM
**全部按同一个错误约定**（往 `rom[0xC0..0xC4]` 写 `0x08000000`）。自洽。

**最坏的部分**：这个约定还被写进了变更记录，当成「真收获」：

> stub BIOS 不执行卡带头 0x00 的分支，而是从字面量池读地址，
> `0xC0` 必须放入口地址字面量、代码从 `0xC4` 起

**一个假设被记成规格，又被拿去造测试 —— 于是它同时具备了三层权威外观。**

**判据**：

- 夹具是**按规格造**的，还是按**实现的行为**造的？前者会把实现错误一起固化。
- 夹具里有没有哪个字段是你**从文档抄来**的？抄来的就要回到原始规格核对。
- 真实设备/介质与夹具的**结构差异**是什么？逐条说出来，说不出来说明没想过。

## 二、断言引用了被测常量

**症状**：把被测的东西改成任意值，测试照样通过。

**实例（r49 同一轮）**。防回归写成：

```rust
assert_eq!(word(BOOT_LITERALS + 8), CART_ENTRY);   // ✗
```

`CART_ENTRY` **就是被断言的那个常量**。变异验证时把 `CART_ENTRY` 改回
`0x0800_00C0`（即原始 bug），**236 项全绿**。改成写字面量才转红。

**判据**：

- 断言的右值里，有多少标识符来自被测代码？超过零就要问「换掉它测试还转红吗」。
- 变异验证**没做过**的测试，等于没写。

## 三、守卫只能抓「已存在」，抓不到「缺失」

**症状**：所有守卫通过，某个功能完全没实现。

**实例（r50）**。GBA 的画面逻辑只写进了三个视频驱动中的一个
（`ConsoleViewerSDL`）。另外两个的 `paintEvent` / `paintGL` 里没有任何 GBA 分支，
**而它们正是有独立显卡的机器会选中的那个**（实测运行日志 `GL Version: 3.3.0
NVIDIA 582.28`）。

**为什么全部通过**：白名单守卫问的是「提到 GBA 的文件要登记」。没分支的文件
**根本不提 GBA**，守卫连看都看不到它。

**判据**：

- 这条守卫**抓不到什么**？答不上来的，守卫还没想清楚。
- 有没有**本该被引用、实际没被引用**的地方？那种地方要写成**固定清单**上的
  正向义务，不是从代码里反推。
- 补固定清单时，函数体边界要**真的**界定住：按「下一个成员」截断会在成员是
  文件最后一个时失效（扫描到文件末尾），按下一个 `void` 截断会在有辅助函数时
  提前结束。**用括号配对。**

## 四、文本守卫读到函数之外的字样

与第三条同源，但是另一个形态：守卫**找到**了正确的函数，**读到**的内容却越界。

r50 补固定清单时，第一版按「同类的下一个成员」界定函数体，而 `paintGL` 是
`ConsoleViewGL_t` 的**最后一个**成员，函数体因此一路延伸到文件末尾 ——
把后面 `renderGbaFrame` 里的 `fceu11_gba_*` 也算成了「`paintGL` 提到了 GBA」。
分支删掉，守卫照样绿。

**判据**：守卫的每一次变异验证都要能**定位到它声称覆盖的那一段**。一条只在
「函数里存在别处也有」时才出错的守卫，等于不出错。

## 五、任何测试提交前的三问

1. **变异验证做了吗？** 把「修复前的值」写回去，它转红了吗？没红就是无效测试。
2. **断言引用了被测代码里的东西吗？** 逐个标识符问一遍。
3. **这条守卫抓不到什么？** 写进注释。**没写边界的守卫会让人以为它覆盖了
   它没有覆盖的东西 —— 那比没有守卫更危险，因为它替代了人工检查。**

## 六、还有一类：把实测事实升级成结论

不是测试形态，是写作形态，但后果一样。

r50 我写下「堆损坏是 CRT 混用导致的」。实测支持「进程里确实有两套 CRT」，
但**崩溃在平台插件还没拷的时候也出现过同一个错误码** —— 顺序对不上，
所以那条因果链没有证据。真实的根因是 viewer 缺分支，CRT 只是同时存在的另一个事实。

**判据**：因果陈述要能指出「如果 A 不是原因，B 会怎样」。答不上来就写「A 与 B 同时存在」，
把因果留空。**`while` 写出来的实验日志和 `because` 写出来的是两回事。**
