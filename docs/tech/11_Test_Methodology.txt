================================================================================
FCEUX11 测试方法论（ctest / ROM 回归 / savestate 哈希）
================================================================================

适用：FCEUX11 所有 release / nightly / PR build 的质量门控。任何动 NES 内核、
savestate 序列化、mapper 寄存器组的 PR，必须跑本文档列出的所有测试。

================================================================================
1. 测试层次
================================================================================

第 1 层：单元测试（src/tests）
  测纯 C++ 逻辑，不启动 GUI，不依赖 ROM。

第 2 层：ROM 帧回归（src/tests/fceux11_rom_regression_test.cpp）
  对 13 个 mapper ROM 各跑 60 帧，CRC 全部帧与 golden_hashes.json 对比。
  覆盖 mapper 的执行语义（不是字节级）。

第 3 层：Savestate 字节级哈希（src/tests/fceux11_savestate_regression_test.cpp）
  对 12 个 ROM 跑 60 帧后，将 savestate 写入内存并计算 MD5，与
  golden_savestate_hashes.json 对比。
  覆盖 savestate 字节布局稳定性。

第 4 层：基准测试（src/tests/fceux11_bench_*.cpp）
  测 PPU render / x6502 CPU / APU mix 的耗时，禁止显著回归。

第 5 层：Rust 单元测试（src/rust）
  跨语言桥的逻辑层，cargo test --workspace 跑全。

第 6 层：手动 GUI 测试
  启动 exe + 加载 ROM + 玩 30 秒 + 验证菜单/输入/画面。ctest 覆盖不到。

================================================================================
3. 跑测试的常见坑
================================================================================

3.1 vcpkg DLL 找不到
  现象：test 启动后 STATUS_DLL_NOT_FOUND（0xc0000135），无 stdout/stderr。
  原因：archive.dll / z.dll / Qt6Core.dll 等 vcpkg 库不在 PATH。
  解决：把 vcpkg_installed/x64-windows/bin 加到 PATH。
  持久化：tests/CMakeLists.txt 配 ENVIRONMENT_MODIFICATION 自动注入。

3.2 相对路径找不到 fixture
  现象：mapper_load_test 等报 "cannot open fixtures/mapper_*.nes"。
  原因：测试用了相对路径，必须在 src/tests 下运行（不是 build/src/tests）。
  解决：
      cd src/tests
      PATH=... ctest -C Release -R mapper_load

3.3 savestate_regression_test 找不到 golden 文件
  现象：所有 ROM savestate MD5 不匹配。
  原因：golden_savestate_hashes.json 路径不对。
  解决：检查 tests/fixtures/ 目录存在 golden_savestate_hashes.json。

3.4 跨平台 / 跨 MSVC 版本
  MSVC ABI 在 14.20+ 是稳定的，但 struct 内存布局对 alignas / #pragma pack
  敏感。切换工具链版本前必须重跑所有测试。

================================================================================
4. golden hash 维护
================================================================================

src/tests/fixtures/golden_hashes.json         # ROM 帧 CRC（720 帧）
src/tests/fixtures/golden_savestate_hashes.json  # 12 ROM savestate MD5

何时更新：
  - 改 mapper 实现但保持行为正确：必须更新 hash
  - 改 PPU 行为但保持画面正确：必须更新 hash
  - 改 savestate 序列化但保证等价的二进制布局：禁止更新 hash，回归会发现
  - 修 bug 改变了 NES 行为：禁止更新 hash，这是 bug，要修回去

更新流程：
  1. 本地跑测试，定位 hash 不匹配的 ROM
  2. 手工运行 60 帧，检查画面/行为是否符合预期
  3. 如果是预期改动，记录在 PR 描述里
  4. 重新生成 hash（test 内置 --update-golden 模式）

================================================================================
5. vrc7 例外
================================================================================

vrc7 的 OPLL 音源状态通过 FCEUSTATE_INDIRECT 保存，chunk 中包含堆指针
sintbl，每次进程启动地址不同，导致 savestate 字节级非确定性。

处理：
  - vrc7 不进 savestate_regression_test 的 hash 比对
  - 但 rom_regression_test 的帧 CRC 仍然覆盖 vrc7 行为正确性

新增带动态分配状态的扩展音源时，必须评估 savestate 字节级稳定性。
策略：FCEUSTATE_INDIRECT 序列化指针会让 hash 漂移，应改用
FCEUSTATE_INDIRECT_NO_HEADER 序列化数据本身。

================================================================================
6. 性能基准
================================================================================

基线测量：v0.3.0 commit（test: 测试基建构建完成）的 benchmark 可执行
文件作为 v0.3.0 baseline。

如果 v0.3.0 在当前环境下无法构建（vcpkg / Qt 重新编译耗时过长），
使用 v0.3.11（最近 prior release）作为代理基线。

性能回归阈值（v0.3.0 基线）：
  - PPU render < 1.1× v0.3.0
  - x6502 CPU < 0.95× v0.3.0

跑法：
  tests/fceux11_bench_ppu_render.exe     # 100 iterations after 10 warmup
  tests/fceux11_bench_x6502_exec.exe
  tests/fceux11_bench_apu_mix.exe

7. Rust 测试
================================================================================

跑法：
  cd src/rust
  cargo test --workspace --release

Crate 列表（典型）：
  fceux11-core        # 跨语言桥通用工具
  fceux11-debug       # 调试器断点 / 追踪
  fceux11-formats     # NES 文件格式解析
  fceux11-lua         # Lua 桥
  fceux11-media       # 视频 / 音频
  fceux11-rom-tests    # ROM 哈希
  fceux11-utils       # 时间戳 / 哈希 / base64

新增 crate 时：在 src/rust/Cargo.toml 的 workspace 段添加成员。

================================================================================
8. 测试覆盖不到的区域
================================================================================

  - GUI 启动（Qt event loop 行为）—— 必须手动测或用 07 §8 的端到端脚本
  - 键盘 / 手柄响应 —— 详见 07 §3 案例 B 的诊断
  - 视频后端（OpenGL 3.3 Core）—— 启动崩溃由 ctest 之前的可执行文件冒烟
    测试覆盖，但实际画面正确性需手动
  - 多线程 race condition —— 罕见，需 ThreadSanitizer 显式跑
  - 国际化（zh_CN / zh_TW）—— 切换语言后启动，验证菜单 / 对话框无乱码

这些"灰色地带"在 release 前必须有专人手动测 30 分钟。
