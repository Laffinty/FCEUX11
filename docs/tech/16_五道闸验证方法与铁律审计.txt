【写在前面 / Preface】
================================================================================

  本章是 12 章「测试方法论与质量门控」的姊妹篇，专门讲 plan v3 §7
  规定的「五道闸」如何在真实 PR 中落地。第 12 章 §9 只列了五道闸的
  名字和粗略定义；本章把它们在 v0.3.15.x PHASE-5 收官时实际跑出
  的证据、踩到的坑、跨闸之间的相互约束一次性讲清楚。

  本章目标：
    1. 拆解每道闸的「判定指标 + 通过条件 + 失败后果」
    2. 复盘 v0.3.15.x PHASE-5 实际跑闸时发现的两条构建期回归
    3. 解释「铁律」(iron rules) 与五道闸的正交关系
    4. 解释如何用「跨闸相关性」发现单一闸门漏掉的问题
    5. 给出 release-day 的闸门操作清单

  阅读时间：约 25 分钟。
  前置知识：读过 12 章「测试方法论与质量门控」；知道 plan v3 §7 的
            五道闸定义；跑过 ctest / cmake --build。

1. 五道闸的正式定义（plan v3 §7 + PHASE-5 实测）
================================================================================

  +-----+--------------------+-----------------------------+----------------+
  | #   | 闸名               | 判定指标                    | 自动化程度     |
  +-----+--------------------+-----------------------------+----------------+
  | 1   | 编译闸             | cmake --build 0 errors      | 全自动 (CMake) |
  |     | Compile            | 0 new warnings (vs 基线)    |                |
  +-----+--------------------+-----------------------------+----------------+
  | 2   | 单元闸             | ctest 全过                  | 全自动 (CTest) |
  |     | Unit               | cargo test --workspace 全过 |                |
  +-----+--------------------+-----------------------------+----------------+
  | 3   | 字节级闸           | 5 ROM × 60 帧 savestate     | 全自动 (CTest) |
  |     | Byte-level         | SHA-256 与 golden 一致      |                |
  +-----+--------------------+-----------------------------+----------------+
  | 4   | 烟雾闸             | 启动 + 加载 ROM + 切语言    | 半自动         |
  |     | Smoke              | + 5+1 菜单 / F5/F7/Esc 响应 | (静态+手动)    |
  +-----+--------------------+-----------------------------+----------------+
  | 5   | 性能闸             | CPU/PPU/APU 帧耗时 < 阈值   | 全自动         |
  |     | Performance        | (Google Benchmark 风格)     | (Bench)        |
  +-----+--------------------+-----------------------------+----------------+

  1.1 闸 1 — 编译闸 (Compile Gate)

    命令：cmake --build build --config Release
    通过：exit code 0，所有 14+ targets 全部 build 成功。
    失败后果：直接阻断 PR 合并，开发者必须本地重跑直到通过。

    v0.3.16 LTS 升级：/WX- 软启动 → /WX 警告即错误。
    详见 3.1 节「铁律 11」。

    「0 new warnings」的关键性：
      新增的 warning 经常暴露 ABI 不兼容（例如 C4200 零长度数组在
      cbindgen 输出中会破坏 C struct 布局）。即使 exit 0 也要 review
      warning diff。

  1.2 闸 2 — 单元闸 (Unit Gate)

    命令：ctest --test-dir build -C Release --output-on-failure
    通过：所有 test executable 全绿（v0.3.15.x 是 9/9）。
    失败后果：直接阻断 PR。

    v0.3.15.x 跑出的 9 个 test：
      smoke_test                  - 引擎链接完整性 (v0.3.0)
      mapper_load_test            - mapper 启动表 (v0.2.15)
      mapper_reset_test           - mapper reset 语义 (v0.2.15)
      rom_regression_test         - 5 ROM 字节级 (v0.2.15)
      savestate_regression_test   - savestate 字节级 (v0.3.12.5)
      expected_api_test           - tl::expected (v0.3.3)
      enum_class_bitflags_test    - 宏展开正确性 (v0.3.8)
      i18n_regression_test        - 34 widget 翻译 (v0.3.15 PHASE-2)
      config_store_test           - TypedConfig<T> (v0.3.15 PHASE-4)

  1.3 闸 3 — 字节级闸 (Byte-Level Gate)

    命令：ctest -R savestate_regression
    通过：12 ROM × 60 帧 savestate SHA-256 与
          tests/fixtures/golden_savestate_hashes.json 完全一致。
    失败后果：直接阻断 PR（这是 plan §1.3 iron-rule 1 的强制约束）。

    重要例外：vrc7 mapper 的 savestate 块包含堆指针，跨进程运行
    非确定性，golden hash 主动排除 vrc7（详见 12 章 §3.3）。

  1.4 闸 4 — 烟雾闸 (Smoke Gate)

    半自动。静态部分由 i18n_regression_test 自动覆盖：
      - 34 widget 文件存在 retranslateUi() 私有 slot
      - 34 widget 文件存在 changeEvent override
      - 6 keyPress override 文件存在 QWidget::keyPressEvent(event) 转发
      - 99.74% zh_CN / zh_TW 覆盖率
      - 0 simp↔trad 交叉污染
    动态部分必须手动：启动 exe + 加载 ROM + 切语言 + 触发 hotkey +
    在真实显示器上观察菜单是否切中。

    PHASE-5 失败/弱化的部分：release-day 24h 烟雾测试是动态部分
    的延伸，但 24h 墙钟无法压缩进单次 agent session（详见 17 章）。

  1.5 闸 5 — 性能闸 (Performance Gate)

    命令：ctest -R bench_ （或直接跑 build/tests/fceux11_bench_*.exe）
    通过：PPU < 1.1× / CPU < 0.95× of v0.3.0 baseline。
    失败后果：阻断 PR；v0.3.x 阶段没有硬性 budget 断言，bench
              脚本只输出 RESULT: PASSED 文本。

    v0.3.15.x 跑出的实测值（Win11 24H2 Build 26100, x64, MSVC 14.51）：
      x6502 CPU:  0.760 ms/frame
      PPU render: 0.717 ms/frame
      APU mix:    0.718 ms/frame
    全部在 v0.3.0 baseline 的预算窗口内。

    性能测试方法论详见 docs/tech/21_性能基准测试方法.txt。

2. PHASE-5 实测中闸 1 抓到的两条回归（教学案例）
================================================================================

  闸 1 失败 ≠ 仅 exit code 非 0。PHASE-5 闸 1 跑出 0 errors，但
  过程中发现两条「正确编译过不了」的子问题，必须先修才能跑后续闸。

  2.1 回归 A：core_api.h 缺尾部 include guard

    现象：
      src/core_api.h 把 inline FCEUI_* 的定义放在 303-318 行，但
      #endif //__FCEU_CORE_API_H_ 只盖到 302 行（pre-PHASE-5 版本）。
      当 ConsoleWindow.cpp 间接多次 include core_api.h 时，MSVC
      报 error C2084: 函数 "int FCEUI_DecodePAR(...)" 已有主体 × 15
      （15 个 inline FCEUI_* 全部报一遍）。

    根因：
      include guard 范围只覆盖到声明区，没覆盖到 inline 定义区。
      MSVC 的「同一 TU 内 inline 函数可有多次定义」要求定义本身
      也必须在 guard 之内。

    修复（commit 252caac）：
      把 #endif //__FCEU_CORE_API_H_ 移到文件末尾。
      行为零变化（C++ inline 函数跨 TU 仍合法）。

    教训：
      include guard 的范围应该覆盖「所有该文件对外可见的 token」，
      不仅是声明；inline 定义、typedef、宏定义都要在 guard 之内。
      自动化检测工具：cppcheck 的 --enable=missingInclude 或
      include-what-you-use。

  2.2 回归 B：tests/CMakeLists.txt 缺 Qt/ConfigStore.h 的搜索路径

    现象：
      config_store_test.cpp 加了 PHASE-4 的 #include "Qt/ConfigStore.h"，
      但 tests/CMakeLists.txt:136 的 include_directories 只配了
      ${CMAKE_SOURCE_DIR}/src，ConfigStore.h 物理路径是
      src/drivers/Qt/ConfigStore.h，fatal error C1083: 无法打开
      包括文件。

    根因：
      头文件相对 include 路径与 CMake include_directories 不一致。
      原 PHASE-4 提交者只验证了编译（cl 自己找到），没验证
      test target 的 include 路径。

    修复（commit 252caac）：
      在 tests/CMakeLists.txt 加 ${CMAKE_SOURCE_DIR}/src/drivers
      到 include path，并把 config_store_test 注册到
      ENVIRONMENT_MODIFICATION 块（确保 ctest 运行时 vcpkg Qt6Core.dll
      在 PATH）。

    教训：
      提交 PR 前必须实际 ctest 跑过，不能只信「本地编译过」。新加
      的 test target 的 include 路径与 build-time 路径可能不同。

3. 铁律 (Iron Rules) — 跨闸约束
================================================================================

  铁律是 FCEUX11 的「项目宪法」级别约束，与五道闸正交：闸门测
  「这次改动是否正确」，铁律测「这次改动是否合规」。

  +-------+----------------------+--------------------------+-----------+
  | #     | 铁律                 | 内容                     | 闸门位置 |
  +-------+----------------------+--------------------------+-----------+
  | 1     | 字节级一致性         | savestate 字节布局不变   | 闸 3      |
  | 2-8   | 历史铁律 (v0.3.0~)   | 见 plan v3 §1.3          | 各闸      |
  | 9     | MSVC 独占工具链      | 仅 MSVC 14.51+，拒绝     | 闸 1      |
  |       |                      | clang-cl/gcc/MinGW/MSYS2 |           |
  | 10    | 所有 commit 直推 main | 不开 topic/release 分支  | git hook  |
  | 11    | 警告即错误 (v0.3.16) | /WX 激活                 | 闸 1      |
  +-------+----------------------+--------------------------+-----------+

  3.1 铁律 9：MSVC 独占工具链

    闸 1 编译时，cl 的版本必须在 14.51.36231（VS 18 BuildTools）。
    拒绝工具链的检测位置：CMakeLists.txt:28-34 的
    if(NOT MSVC) FATAL_ERROR。

    跨闸效应：
      闸 5（性能）的 baseline 也是 MSVC 编译的 baseline。换工具链
      跑 bench 数字会失真（gcc 寄存器分配策略、MinGW CRT 调用约定
      都不同），所以铁律 9 也是闸 5 数字可比性的前提。

  3.2 铁律 10：所有 commit 直推 main

    检测位置：scripts/_check_iron_rules.ps1（v0.3.6 引入）+ 人工 review。
    跨闸效应：所有 v0.3.15.x PHASE-1~5 的 commit 都在 main，闸 2/3/4
    的「基线」是 main 的最新 commit，不存在 release branch 的合并冲突。

  3.3 铁律 11：警告即错误 (v0.3.16 引入)

    /WX- 软启动 → /WX 激活。
    已知可接受的预存警告类目以显式 /wd 抑制，每条带文档化理由
    （详见 CMakeLists.txt:43-56）。新代码必须 /WX 干净通过。

    tr() 源串集合冻结：
      这条铁律在 v0.3.15 main PR-A/B 期间生效，PHASE-1 全量翻译完成后
      才解除。闸 4 的 i18n_regression_test 静态门控保证：PHASE-2 widget
      改造期间不能新增 tr()（新增会破坏覆盖率门）。

  3.4 弃用流程 (§6.3 跨子版本主题)

    FCEUI_* compat shim（250+ inline wrappers in core_api.h/io_api.h/
    net_api.h/diag_api.h/movie.h）+ fceuScopedPtr + FCEU_malloc* 全部
    标 [[deprecated("use fceu11::Foo")]]。
    默认 FCEUX11_NO_DEPRECATION_WARNINGS=ON 抑制噪音；外部用户可
    -DFCEUX11_SHOW_DEPRECATION_WARNINGS=ON 主动看警告。
    实际删除推迟到 v0.4.0（给外部 ≥ 1 个 major 版本迁移期）。

4. 跨闸相关性：单闸漏掉的问题如何被其他闸抓到
================================================================================

  五道闸不是 5 个独立测试，而是 5 个互相补强的角度。PHASE-5 跑闸时
  有几条跨闸相关的发现值得记录：

  4.1 闸 1 漏掉的问题被闸 2 抓到

    如果只跑「cmake --build 0 errors」，PHASE-5 的 config_store_test
    会因为缺 include path 而根本无法 link 成 executable — 但 cmake
    的 exit code 仍然是 0。
    跨闸发现：闸 1 PASS + 闸 2 失败 = 「build 成功但 test 不可执行」，
    闸 1 + 闸 2 联合保证「可执行 + 可运行」。

  4.2 闸 3 漏掉的非 savestate 改动被闸 4 抓到

    savestate 字节布局稳定 ≠ 模拟器行为稳定。例如改 mapper IRQ 时序
    不影响 savestate（savestate 不存 IRQ 计数器），但可能影响游戏。
    跨闸发现：闸 3 PASS + 闸 4（i18n_regression_test 静态）发现
    widget tr() 串变化 → 闸 4 强制要求 regression 报告里有 ROM 行为
    证据。

  4.3 闸 5 误报被闸 2 反向校正

    bench 数字的 stddev 偶尔会 > 3%，造成视觉上的「性能回归」。
    但 ctest 的 mapper_load_test / rom_regression_test 时间都在预算内，
    说明 bench 数字的抖动是测量误差，不是真实回归。
    跨闸发现：闸 5 失败 + 闸 2 全过 = 测量噪声，重跑闸 5 而不是
    退回代码。

5. Release-Day 闸门操作清单
================================================================================

  顺序固定，先闸 1 后闸 5（闸 1 不过后续闸没意义）：

  +-----+----------------------------------------+--------------------+
  | 步骤 | 命令                                   | 期望结果           |
  +-----+----------------------------------------+--------------------+
  | 1   | cmake --build build --config Release   | exit 0, 0 new warn |
  | 2   | ctest --test-dir build -C Release      | 9/9 pass           |
  | 3   | ctest -R savestate_regression          | 12 ROM match       |
  | 4   | ctest -R i18n_regression               | 34 widget 覆盖率   |
  | 5   | 手启 fceux11.exe --no-console ROM      | 5+1 菜单 + 翻译    |
  | 6   | ctest -R bench_                        | 全 RESULT: PASSED  |
  | 7   | 24h smoke（详见 17 章）                 | 8/8 criterion pass |
  +-----+----------------------------------------+--------------------+

  第 7 步的 24h smoke 物理上无法压缩进单 agent session，所以 PHASE-5
  把 7 的「protocol 定义 + 模板」先 commit 下来，actual 跑由 release
  engineer 在 release hardware 上执行。

6. 五道闸的常见反模式
================================================================================

  6.1 跳过闸 1 直接跑闸 2

    反模式：「我在 src/ 改了 cpp，本地编译过了，直接 push」。
    问题：CMake 的 include_directories / link_libraries 是累积的，
    单独 TU 编译过 ≠ link 整个 build graph 过。PHASE-5 的回归 B 就是
    这种情况：单 TU 编译过，test target link 时找不到头文件。

  6.2 用「我机器上能跑」替代闸 2

    反模式：「ctest 在我机器上跑过就行了」。
    问题：PATH 包含 Qt6Core.dll / vcpkg 库的环境是 release-day
    ctest 关键。tests/CMakeLists.txt 的 ENVIRONMENT_MODIFICATION 块
    是自动注入，缺它就会 STATUS_DLL_NOT_FOUND。

  6.3 把闸 3 当作「行为变化的审计」而非「字节级回归」

    反模式：「我故意改了 mapper 的 IRQ 时序，闸 3 不通过 → 我更新
    golden hash」。
    问题：savestate 字节布局与 IRQ 时序无关，闸 3 失败说明 savestate
    序列化逻辑改了（可能是无意）。闸 3 的正确解读是「如果 mapper
    行为变了，闸 3 不应该变；闸 3 变了 = 序列化逻辑有 bug」。

  6.4 闸 5 阈值「写死」

    反模式：把 0.95× / 1.1× 写进 bench 脚本的 hardcoded 断言。
    问题：跨硬件可比性差，Win11 不同 SKU 性能差异 ±20%。当前策略
    是「同硬件前后对比 + 阈值作为 guidance，不作 hard assertion」。

7. 闸门自动化的当前边界
================================================================================

  闸 1/2/3/5：全自动，ctest 入口。
  闸 4 的静态部分：全自动（i18n_regression_test）。
  闸 4 的动态部分（GUI 视觉验证）：手动，release-day。
  24h 烟雾测试：半自动（protocol + 模板，operator 跑）。

  未来的 v0.4.x 工作stream：
    - 闸 4 动态部分用 WinAppDriver / Appium 跑 UI 自动化（详见
      17 章 §6 的展望）。
    - 闸 5 加 ASan + perf 二合一：每个 bench run 同时输出
      ms/frame + __asan_* 触发计数。
    - 24h 烟雾测试改成 GitHub Actions matrix job（Win11 runner），
      跑通后自动 publish artifacts。

8. 总结
================================================================================

  五道闸是 plan v3 §7 规定的 release contract，PHASE-5 在 v0.3.15.x
  跑通证明了 contract 可执行。关键经验：

    1. 闸 1 失败时不要急着重跑，要看 warning diff（PHASE-5 闸 1 的
       两条回归都是从 warning 推出来的）。
    2. 铁律 9/10/11 与五道闸正交，但跨闸效应不可忽视（工具链一致性
       → 性能数字可比性；分支策略 → 基线可比性；/WX → 编译时 ABI 漂移）。
    3. 单闸的「通过」是必要不充分，跨闸相关性才是 contract 真正的
       强度。
    4. 24h 烟雾测试是 contract 的延伸，但物理上无法压进单 agent
       session；protocol 文档必须与闸门同步 commit（详见 17 章）。
