一、FCEUX11 构建指南 (Build Guide)
---------------------------------
来源：Build_Guide.md

适用版本：FCEUX11 v0.2.2+
工具链：MSVC 2022 v143+, CMake 3.28+, Ninja, vcpkg, Rust stable

前置条件：
  - Visual Studio 2022（工作负载：C++ 桌面开发）
  - CMake 3.28+、Ninja 1.11+、PowerShell 7.x、Git 2.40+
  - vcpkg（clone + bootstrap，设置 VCPKG_ROOT）
  - Rust（目标：x86_64-pc-windows-msvc）

快速构建：
  .\do_build.ps1 -Config Release

手动构建：
  .\scripts\setup_vcpkg.ps1        # 首次安装依赖（1-2 小时）
  cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
  cmake --build build
  ctest --test-dir build --output-on-failure

产物：
  - 主程序：build\src\fceux11.exe
  - 冒烟测试：build\src\tests\fceux11_smoke_test.exe
  - Mapper 测试：build\src\tests\fceux11_mapper_load_test.exe

部署：
  cmake --install build --prefix dist    # 复制 exe 与所需 DLL

Agent 标准化编译规范：
  - 强制检查工具：cmake, ninja, cl, vcpkg, rustup, cargo
  - 编译配置矩阵：
    Release (Rust ON) | Debug (Rust ON) | Rust OFF 回退验证 | 纯 C++ | Rust Lua 引擎
  - 增量构建目标：fceux11_rust_build / fceux11_utils / fceux11_core / fceux11
  - Feature-Gate 范式：C++ 保留同名 wrapper，内部 #ifdef FCEUX11_RUST_ENABLED 分支
  - 每个 Rust 重构 PR 必须通过 Rust=ON 和 Rust=OFF 两种 CI 配置

Rust Lua 引擎：
  - 使用 Rust mlua crate（vendored Lua 5.1）替代 C++ Lua
  - 启用：-DFCEUX11_RUST_ENABLED=ON -DFCEUX11_LUA_RUST_ENABLED=ON

常见错误与修复：
  - Rust target 缺失 → rustup target add x86_64-pc-windows-msvc
  - Generator 不匹配 → 删除 build/ 目录重新配置
  - vcpkg 包未找到 → 运行 setup_vcpkg.ps1
  - Qt6LinguistTools 未找到 → 添加 -DFCEUX11_ENABLE_I18N=OFF
  - 未解析外部符号 fceux11_rust_* → 删除旧 .lib 或确认 DEPENDS

新增 Rust 模块 Checklist：
  1. Cargo.toml 版本号递增
  2. 新依赖记录并附注释
  3. fceux11_rust.h 追加 extern "C" 声明
  4. C++ wrapper 保留 #ifdef 分支
  5. Rust 侧编写至少一个 #[test]
  6. CMakeLists.txt add_custom_command 声明 DEPENDS
  7. 继承模板基类结构体使用 reinterpret_cast
  8. CI 通过 Rust=ON/OFF 全量构建
  9. 更新本文档适用范围版本号


二、FCEUX11 Rust 重构手册
--------------------------
来源：rust_refactor_handbook_v1.0.md

项目背景：
  - 从 v0.2.1 开始将 C++ 模块迁移至 Rust。
  - 截至 v0.2.30，已完成 16 个模块 Rust 化，约 6500+ 行 Rust、200+ 单元测试。

核心原则：
  1. 叶子优先：优先迁移无交叉依赖的工具/格式模块
  2. 不可逆化：v0.2.12 起，Rust 化后删除 C++ 回退代码
  3. C++ 薄壳：保留 C++ 调用封装，核心逻辑在 Rust
  4. 行为等价：模拟器输出逐位一致，性能退化不超过 110%

Workspace 结构：
  src/rust/
  ├── Cargo.toml           # Workspace 根
  ├── cbindgen.toml
  ├── build.rs             # 头文件自动生成
  ├── fceux11_rust.h       # 合并后的 C 头文件（自动生成）
  └── crates/
      ├── fceux11-utils/   # 工具类（CRC32, MD5, GUID, UTF 转换, OS Utils）
      ├── fceux11-formats/ # 格式解析（iNES, UNIF, FM2, EmuFile, VS UniSystem）
      ├── fceux11-media/   # 音视频（Wave, Filter, Palette）
      ├── fceux11-debug/   # 调试辅助（Profiler, Cheat, ASM）
      ├── fceux11-lua/     # Lua 绑定
      └── fceux11-core/    # 核心模拟器抽象（v0.3.x 主场）

Crate 依赖规则：
  - 必须构成 DAG，禁止循环依赖
  - fceux11-core 在 v0.2.30 仅含 trait + state_file
  - 每个 sub-crate 为 rlib，root crate 统一 re-export 为 staticlib

添加新模块流程：
  1. 在 crate src/ 下创建 .rs 文件
  2. lib.rs 中 pub mod 声明
  3. 编写 #[unsafe(no_mangle)] pub extern "C" FFI 函数
  4. cargo build 触发 cbindgen，自动更新 fceux11_rust.h
  5. C++ 侧 #include "rust/fceux11_rust.h" 并调用
  6. 编写 #[test] 单元测试
  7. 验证 cargo test --workspace + CMake 构建 + ROM 回归测试

FFI 设计模式（5 种稳定模式）：
  1. 纯函数模式：无状态计算（CRC32, MD5）。指针检查 is_null()，用 from_raw_parts 构造 slice。
  2. Thread-Local 返回缓冲区：返回变长字符串（GUID, 错误信息）。固定 512 字节，C++ 需立即复制。
  3. Opaque Pointer + Handle：有状态组件（Profiler, Filter）。create 用 Box::into_raw，destroy 用 Box::from_raw。
  4. Slice 结构体模式：传递大块缓冲区（像素, 音频, ROM）。#[repr(C)] FceuSlice { ptr, len }。
  5. 批量回调/Chunk 编排：复杂序列化（Savestate）。Rust 负责外壳+压缩，C++ 负责每个 chunk 的 payload。

测试策略（三层金字塔）：
  层1：Rust 单元测试 (cargo test) — 每次 commit，失败阻止合并
  层2：C++ 集成测试 (ctest) — CI/本地构建，失败阻止合并
  层3：ROM 回归测试 — CI nightly/发布前，失败阻止发布

新模块测试 Checklist：
  - #[test] 覆盖正常路径、边界、错误输入
  - 纯计算模块 ≥5 个测试
  - 缓冲区模块：null 安全、零长度、越界测试
  - 文件格式模块：round-trip 测试（序列化→反序列化→逐字节比对）

性能调优：
  - 对比重构前后 1000 次调用平均耗时，阈值 ≤ 110%
  - Release Profile：panic="abort", lto=true
  - 可进一步：lto="fat", codegen-units=1, #[inline(always)]
  - Bus 解码：Rust match 在 release 下可被优化为跳转表

版本发布流程 (v0.2.x)：
  1. cargo test --workspace 通过
  2. cargo build 触发 cbindgen
  3. C++ 编译通过
  4. ctest -C Release
  5. ROM 回归测试
  6. git commit + git tag

禁止操作：
  - 未经 ROM 回归测试修改核心模拟循环
  - 在 v0.2.x 引入 nightly Rust 特性
  - 修改已冻结的 FFI 函数签名

v0.3.x 迁移目标架构：
  pub struct NesSystem<C: Cpu, P: Ppu, A: Apu, M: Mapper> { ... }
  迁移优先级：Bus+WRAM → CPU → PPU → APU → Mapper（最后，需 DSL 预研）

FFI 冻结期 (v0.2.30+)：
  - 签名变更需在 docs/tech/ 提交 RFC
  - 说明理由、影响范围、回退方案
  - 至少一次代码审查
  - 同步更新所有 C++ 调用方


三、Mapper Rust 化可行性研究报告
---------------------------------
来源：mapper_rust_feasibility.md

现状：
  - 175 个 .cpp 文件，约 48,000 行 C++，是代码库最大单一模块。
  - 模板高度一致：静态变量 + SFORMAT + AddExState + SetRead/WriteHandler + setprg/setchr。

核心问题：
  1. 全局函数指针数组 ARead[65536]/BWrite[65536] — 每次 SetReadHandler 遍历范围写入，开销大
  2. 无类型安全 — DECLFW 的 A/V 是全局宏参数，拼写错误编译期无法捕获
  3. 状态分散 — 静态全局变量不支持多实例
  4. SFORMAT 脆弱 — 字段改名后描述字符串不匹配导致旧存档无法加载

方案对比：
  A. 直接 1:1 翻译（不推荐）— 无法解决根本问题，维护负担大
  B. Proc-Macro DSL（推荐）— #[mapper] + #[state] 自动生成序列化和 dispatch
  C. 解释器/字节码 VM（不推荐）— 性能风险，不满足 cycle-accurate 要求
  D. 混合策略（最终推荐）：
       Tier 1：DSL 生成 ~140 个简单 Mapper
       Tier 2：手写 Rust trait ~25 个中等复杂 Mapper（MMC3/VRC/Sunsoft）
       Tier 3：C++ 桥接 ~10 个极端复杂 Mapper（FDS, NSF, SA-1）

DSL 设计草案：
  #[mapper(id = 222, name = "UNL-22211")]
  struct Mapper222 {
      #[state] reg: [u8; 4],
      #[state] cmd: u8,
  }
  impl Mapper for Mapper222 { ... }

风险与缓解：
  - Proc-macro 开发耗时 → v0.3.0 前用 5 个简单 Mapper 验证原型
  - 复杂 Mapper 超出 DSL → Tier 2/3 兜底
  - 性能退化 → match + #[inline] 预期 ≥ C++ 函数指针
  - 旧存档兼容性 → snapshot() 格式与旧 SFORMAT 逐字节兼容

建议路线图：
  v0.3.0：DSL 原型 + 5 个最简单 Mapper + FFI 桥接 + 回归测试
  v0.3.1-0.3.5：Tier 1 批量迁移 ~50 个 Mapper
  v0.3.6-0.3.10：Tier 2 手写迁移（MMC3/VRC/Sunsoft）
  v0.3.11+：Tier 3 桥接清理（FDS/NSF）

结论：
  Mapper Rust 化可行且高回报。推荐 Tier 1(DSL) + Tier 2(手写) + Tier 3(桥接) 混合策略。
  预计 v0.3.x 完成 90% 迁移，剩余 10% 桥接不影响整体架构。

Source: Build_Guide.md

Applicable: FCEUX11 v0.2.2+
Toolchain: MSVC 2022 v143+, CMake 3.28+, Ninja, vcpkg, Rust stable

  - Visual Studio 2022 (workload: Desktop development with C++)
  - CMake 3.28+, Ninja 1.11+, PowerShell 7.x, Git 2.40+

  cmake --install build --prefix dist    # copies exe and required DLLs

  - Enable: -DFCEUX11_RUST_ENABLED=ON -DFCEUX11_LUA_RUST_ENABLED=ON

Common errors & fixes:
  - Missing Rust target → rustup target add x86_64-pc-windows-msvc
  - Generator mismatch → delete build/ and reconfigure
  - vcpkg package not found → run setup_vcpkg.ps1
  - Qt6LinguistTools missing → add -DFCEUX11_ENABLE_I18N=OFF
  - Unresolved fceux11_rust_* → delete old .lib or confirm DEPENDS

New Rust module checklist:
  1. Bump version in Cargo.toml
  2. Document new dependencies with comments
  3. Append extern "C" declarations to fceux11_rust.h
  4. Keep #ifdef branch in C++ wrapper
  5. Write at least one #[test] on Rust side
  6. Declare DEPENDS in CMakeLists.txt add_custom_command
  7. Use reinterpret_cast for inherited template base structs
  8. CI passes full builds for Rust=ON and Rust=OFF
  9. Update applicable version in this doc


II. FCEUX11 Rust Refactor Handbook
----------------------------------
Source: rust_refactor_handbook_v1.0.md

Background:
  - C++ to Rust migration started at v0.2.1.
  - As of v0.2.30: 16 modules migrated, ~6500+ lines Rust, 200+ unit tests.

Core principles:
  1. Leaf-first: migrate tool/format modules with no cross-dependencies first.
  2. Irreversible: since v0.2.12, delete C++ fallback after Rust migration.
  3. C++ thin shell: keep C++ calling wrappers, core logic in Rust.
  4. Behavioral equivalence: bit-identical output, performance regression ≤ 110%.

Workspace structure:
  src/rust/
  ├── Cargo.toml
  ├── cbindgen.toml
  ├── build.rs
  ├── fceux11_rust.h (auto-generated)
  └── crates/
      ├── fceux11-utils/   (CRC32, MD5, GUID, UTF conversion, OS utils)
      ├── fceux11-formats/ (iNES, UNIF, FM2, EmuFile, VS UniSystem)
      ├── fceux11-media/   (Wave, Filter, Palette)
      ├── fceux11-debug/   (Profiler, Cheat, ASM)
      ├── fceux11-lua/     (Lua bindings)
      └── fceux11-core/    (core emulator abstractions, v0.3.x focus)

Crate dependency rules:
  - Must form a DAG, no circular dependencies.
  - fceux11-core at v0.2.30 contains only traits + state_file.
  - Each sub-crate is rlib; root crate re-exports as staticlib.

New module workflow:
  1. Create .rs in crate src/
  2. pub mod in lib.rs
  3. Write #[unsafe(no_mangle)] pub extern "C" FFI functions
  4. cargo build triggers cbindgen, auto-updates fceux11_rust.h
  5. C++ #include "rust/fceux11_rust.h" and call
  6. Write #[test] unit tests
  7. Verify cargo test --workspace + CMake build + ROM regression tests

FFI design patterns (5 stable patterns):
  1. Pure function: stateless computation (CRC32, MD5). Check is_null(), use from_raw_parts.
  2. Thread-Local return buffer: variable-length strings (GUID, errors). Fixed 512 bytes; C++ must copy immediately.
  3. Opaque Pointer + Handle: stateful components (Profiler, Filter). create via Box::into_raw, destroy via Box::from_raw.
  4. Slice struct: large buffers (pixels, audio, ROM). #[repr(C)] FceuSlice { ptr, len }.
  5. Batch callback / Chunk orchestration: complex serialization (Savestate). Rust handles shell+compression; C++ handles per-chunk payload.

Testing strategy (3-layer pyramid):
  L1: Rust unit tests (cargo test) — every commit, blocks merge on failure
  L2: C++ integration tests (ctest) — CI/local build, blocks merge on failure
  L3: ROM regression tests — CI nightly / pre-release, blocks release on failure

New module testing checklist:
  - #[test] covers normal path, boundaries, error inputs
  - Pure computation: ≥5 tests
  - Buffer modules: null safety, zero-length, out-of-bounds tests
  - File format modules: round-trip test (serialize → deserialize → byte-identical)

Performance tuning:
  - Compare 1000-call average before/after; threshold ≤ 110%
  - Release profile: panic="abort", lto=true
  - Further: lto="fat", codegen-units=1, #[inline(always)]
  - Bus decode: Rust match optimizes to jump table in release

Release workflow (v0.2.x):
  1. Pass cargo test --workspace
  2. cargo build triggers cbindgen
  3. C++ compile passes
  4. ctest -C Release
  5. ROM regression tests
  6. git commit + git tag

Forbidden operations:
  - Modify core emulation loop without ROM regression tests
  - Introduce nightly Rust features in v0.2.x
  - Modify frozen FFI function signatures

v0.3.x migration target architecture:
  pub struct NesSystem<C: Cpu, P: Ppu, A: Apu, M: Mapper> { ... }
  Priority: Bus+WRAM → CPU → PPU → APU → Mapper (last, requires DSL pre-study)

FFI freeze period (v0.2.30+):
  - Signature changes require RFC in docs/tech/
  - Justification, impact, fallback plan
  - At least one code review approval
  - Update all C++ callers


III. Mapper Rust Migration Feasibility Study
--------------------------------------------
Source: mapper_rust_feasibility.md

Current state:
  - 175 .cpp files, ~48,000 lines C++, largest single module.
  - Highly consistent template: static vars + SFORMAT + AddExState + SetRead/WriteHandler + setprg/setchr.

Core problems:
  1. Global function pointer arrays ARead[65536]/BWrite[65536] — SetReadHandler iterates range, high overhead.
  2. No type safety — DECLFW A/V are global macro args, typos not caught at compile time.
  3. Scattered state — static globals, no multi-instance support.
  4. SFORMAT fragility — macro reflection breaks old saves if field names change.

Solution comparison:
  A. Direct 1:1 translation (not recommended) — doesn't solve root problems, huge maintenance burden.
  B. Proc-Macro DSL (recommended) — #[mapper] + #[state] auto-generates serialization and dispatch.
  C. Interpreter / bytecode VM (not recommended) — performance risk, not cycle-accurate.
  D. Hybrid strategy (final recommendation):
       Tier 1: DSL for ~140 simple mappers
       Tier 2: Hand-written Rust trait for ~25 medium-complexity mappers (MMC3/VRC/Sunsoft)
       Tier 3: C++ bridge for ~10 extreme mappers (FDS, NSF, SA-1)

DSL draft:
  #[mapper(id = 222, name = "UNL-22211")]
  struct Mapper222 {
      #[state] reg: [u8; 4],
      #[state] cmd: u8,
  }
  impl Mapper for Mapper222 { ... }

Risks & mitigation:
  - Proc-macro dev time → validate prototype with 5 simple mappers before v0.3.0
  - Complex mappers exceed DSL → Tier 2/3 fallback
  - Performance regression → match + #[inline] expected ≥ C++ function pointers
  - Old save compatibility → snapshot() byte-compatible with old SFORMAT

Recommended roadmap:
  v0.3.0: DSL prototype + 5 simplest mappers + FFI bridge + regression tests
  v0.3.1-0.3.5: Tier 1 batch migration ~50 mappers
  v0.3.6-0.3.10: Tier 2 hand-written migration (MMC3/VRC/Sunsoft)
  v0.3.11+: Tier 3 bridge cleanup (FDS/NSF)

Conclusion:
  Mapper Rust migration is feasible and high-return. Recommended hybrid strategy.
  Expected 90% migration by v0.3.x, remaining 10% bridged without affecting architecture.
