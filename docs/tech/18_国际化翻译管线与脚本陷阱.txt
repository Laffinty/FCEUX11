【写在前面 / Preface】
================================================================================

  本章聚焦 FCEUX11 v0.3.15 PHASE-1 / PHASE-2 的 i18n 翻译工作
  经验。PHASE-1 的「3,481 → 1,911 source string」修正、6 条
  PowerShell 脚本坑点、DeepL/Google 双 provider 选型、繁简体
  隔离策略都是真实踩到的工程问题；它们不是 Qt Linguist 文档里
  能查到的，是 FCEUX11 在 Windows 11 + PowerShell 5.1 + Qt 6.8
  LTS 这一具体环境里摸出来的。

  本章目标：
    1. 拆解 i18n 翻译工作流（lupdate → glossary → 翻译 → lrelease）
    2. 解释为何 3,481 估到 1,911，以及「context」对 source string
       计数的影响
    3. 列出 6 条 PowerShell 5.1 兼容的脚本坑点 + 修复
    4. 解释繁简隔离的 false-positive 问题（系/面是繁简共享字符）
    5. 给出「native speaker 审校」的可行替代方案

  阅读时间：约 20 分钟。
  前置知识：知道 Qt Linguist + .ts/.qm 文件；跑过
            scripts/i18n_update.ps1 / i18n_release.ps1。

1. 翻译工作流（5 阶段）
================================================================================

  +------+--------------------+-------------------------------+
  | #    | 阶段               | 工具 / 输出                    |
  +------+--------------------+-------------------------------+
  | 1    | lupdate 扫源       | lupdate / lupdate_run.py       |
  |      |                    | 输出 1,911 source strings     |
  +------+--------------------+-------------------------------+
  | 2    | glossary 准备      | glossary.txt (97 项)           |
  |      |                    | 硬规则：TAS/ROM/NES 不译       |
  +------+--------------------+-------------------------------+
  | 3    | 翻译               | i18n_translate.py              |
  |      |                    | Provider: DeepL / Google       |
  +------+--------------------+-------------------------------+
  | 4    | lrelease 编译      | i18n_release.ps1               |
  |      |                    | .ts → .qm (二进制)              |
  +------+--------------------+-------------------------------+
  | 5    | coverage 闸门     | i18n_coverage.ps1              |
  |      | + simp/trad 闸门  | check_simp_trad.ps1            |
  +------+--------------------+-------------------------------+

  1.1 阶段 1：lupdate 扫源

    命令：python scripts/lupdate_run.py
    输出：src/drivers/Qt/lang/fceux11_*.ts
    历史坑点（v0.3.15.x PHASE-1 修复）：
      原始 i18n_update.ps1 调 lupdate -project translations.pro，
      但 lupdate v6.11.0 拒绝「Passing .pro files to lupdate is
      deprecated」。同时 .pro 的 comma-separated -ts 列表也被
      lupdate 拒绝。
      修复：用 Python 写 lupdate_run.py，直接喂文件列表 + 单独
            -ts 参数，绕开 .pro 解析路径。

  1.2 阶段 2：glossary 准备

    文件：src/drivers/Qt/lang/glossary.txt
    格式：源串<tab>zh_CN<tab>zh_TW
    硬规则（写进 glossary 头部注释）：
      TAS/ROM/NES/mapper/CPU/PPU/APU NEVER translate
      （这些是专有名词，没有中文习惯译法；强制机翻会把
       TAS 翻成「工具辅助超级播放」之类误导性术语）

    DeepL 路径下，glossary 作为术语表上传到 DeepL 后台：
      https://www.deepl.com/account/glossaries
    Google 路径下，glossary 通过 model 参数传入：
      model='accounts/.../models/general/base',
      glossary_config={'glossary_id': 'fceux11-tech-terms'}

  1.3 阶段 3：翻译

    命令：python scripts/i18n_translate.py --provider deepl --lang both
    Provider 选型：
      DeepL：质量更高，特别是技术文本；但字符配额小（500K/月 free）。
      Google：通用性更强；同 free 配额但 API 限速更宽松。
    推荐：DeepL for 技术文本，Google for 大批量。

    工作流：
      Step 1: --dry-run 预览要翻译的字符串
      Step 2: 确认无误后去掉 --dry-run 真实翻译
      Step 3: 翻译后的 .ts 文件覆盖原始文件
      Step 4: 跑 lrelease 编译 .qm

  1.4 阶段 4：lrelease 编译

    命令：powershell scripts/i18n_release.ps1
    输出：src/drivers/Qt/lang/fceux11_*.qm
    CMake 集成：src/CMakeLists.txt:580-617 使用 Qt6 现代 API：
      qt_add_lupdate / qt_add_lrelease / qt_add_resources
      自动把 .qm 嵌入到 fceux11.exe 资源段。

  1.5 阶段 5：双闸门

    覆盖率闸门：
      powershell scripts/i18n_coverage.ps1
      期望：[PASS] zh_CN: 1906/1911 translated (99.74%) -- gate 90%
            [PASS] zh_TW: 1906/1911 translated (99.74%) -- gate 90%

    繁简隔离闸门：
      powershell scripts/check_simp_trad.ps1
      期望：[PASS] fceux11_zh_CN.ts (no traditional): no forbidden glyphs
            [PASS] fceux11_zh_TW.ts (no simplified): no forbidden glyphs

2. Source String 计数：3,481 → 1,911 的真相
================================================================================

  PHASE-1 开工时引用 plan v0.3.15_Build_Plan.md 的估计「3,481
  source strings」，实际 lupdate 跑下来只有 1,911。差 1,570 条，
  误差 82%。

  2.1 调查路径

    步骤 1：lupdate -project translations.pro 跑出 .ts 文件
    步骤 2：grep -c "<message>" fceux11_en.ts  → 1911
    步骤 3：grep -c "<context>" fceux11_en.ts  → 72
    步骤 4：grep -c "<message>" fceux11_zh_CN.ts → 1911
    步骤 5：原 plan 估的 3,481 来自调研 v0.3.10 时的初稿，那时还没
            把 QObject::tr() 的「同一源串跨多 context」合并。

  2.2 根因

    Qt Linguist 的 .ts 文件结构是：
      <TS>
        <context>
          <name>ConsoleWindow</name>
          <message>
            <source>Reset</source>
            <translation>...</translation>
          </message>
          <message>
            <source>Load State</source>
            ...
          </message>
        </context>
        <context>
          <name>GuiConf</name>
          <message>
            <source>Reset</source>     ← 与上面源串相同
            ...
          </message>
        </context>
      </TS>

    同一源串（如 "Reset"）在多个 context 出现 → 计 1 个 source。
    早期估算时把每个 <message> 都当独立 source，得到 3,481。
    实际去重后只有 1,911。

  2.3 教训

    - 估算 source string 数时必须用实际 lupdate 跑一次，不要拍脑袋。
    - 1,911 这个数字是权威值，后续 PHASE 引用都基于这个。
    - glossary 大小与 source 数线性相关，所以 glossary 从 80 项扩到
      97 项（17 个新词在机翻时遇到）也是预期的。

3. 6 条 PowerShell 5.1 脚本坑点（PHASE-1 真实修复记录）
================================================================================

  这 6 条坑全部在 PHASE-1 实测时遇到，并 commit 修复。记录它们
  是为了：未来扩展 i18n 闸门时不再踩同样的坑。

  3.1 坑 1：$msg.translation 返回 String 而非 XmlElement

    现象：
      i18n_coverage.ps1 写 $tr = $msg.translation
      然后 $tr.GetAttribute('type') 报错
      「You cannot call a method on a null-valued expression」。

    根因：
      PowerShell 的 XML 适配器（System.Xml.XmlElement）把子节点
      暴露为 .translation 属性，但默认是 String 类型（InnerText），
      不是 XmlElement。GetAttribute() 在 String 上不存在。

    修复：
      $trans = $msg.SelectSingleNode('translation')
      $typeAttr = $trans.GetAttribute('type')
      用 XPath 拿真正的 XmlElement 节点。

  3.2 坑 2：type="needs-review" 不被识别为未完成

    现象：
      Debugger 优先级 507 tr() 翻译后被标 type="needs-review"，
      但 i18n_coverage.ps1 只检查 type="unfinished" → 误判为
      已翻译 → 闸门通过 → 实际上未经母语审校。

    根因：
      原始脚本 hard-code "unfinished"，未考虑 needs-review。

    修复：
      $unfinished = ($typeAttr -eq "unfinished") -or
                    ($typeAttr -eq "needs-review")
      两种状态都算未完成。

  3.3 坑 3：CJK 字符在 .ps1 里被 mangled

    现象：
      check_simp_trad.ps1 里的 $simpOnlyList = @('系','面','时'...)
      运行时这些字符变成乱码，闸门 100% 误报「含 forbidden
      简体字」。

    根因：
      PowerShell 5.1 的 parser 默认按 ANSI 解析 .ps1 文件，CJK
      字符在 ANSI 码页下被破坏。Linux 上的 PowerShell 7+ 用
      UTF-8 无此问题。

    修复：
      在 .ps1 文件头加 UTF-8 BOM（EF BB BF）。Windows 记事本
      另存为「UTF-8 with BOM」即可；git 提交时不会被 strip。

  3.4 坑 4：Write-Host "$label: ..." 的 $label: scope 限定符

    现象：
      check_simp_trad.ps1 写 Write-Host "[PASS] $label: $msg"
      报「The variable $label cannot be retrieved because it
      has not been set yet」或「Unexpected token ':'」。

    根因：
      PowerShell 把 $label: 解析为 scope-qualified variable
      （类似 $global:label），不是字符串拼接。

    修复：
      Write-Host ("[PASS] {0}: {1}" -f $label, $msg)
      用 -f 格式串，避开 scope qualifier 歧义。

  3.5 坑 5：系/面是繁简共享字符，误报为简体专属

    现象：
      check_simp_trad.ps1 把 '系' 与 '面' 列入「简体专属字符」
      (SimplifiedOnly)，但 '系' 在繁体是「系」(U+7CFB)、
      简体也是「系」(U+7CFB) — 完全相同 codepoint。'面' 同理。
      闸门把合法的繁体文（畫面/系統/面板）全部误报成「含简体字」。

    根因：
      简体独有字符表是按字形差异整理的，但系/面 是「字形相同
      但词义可能不同」的字符。这种字符需要用词组级（context）
      检测，单纯单字检测会误报。

    修复：
      从 SimplifiedOnly 删除 '系' 与 '面'，留下真正的简体独有字
      （如「为」/U+4E3A vs 繁体「為」/U+70BA）。并在 .ps1 头加注释
      说明这条规则。

  3.6 坑 6：lupdate 不接受 .pro 与 comma-separated -ts 列表

    现象：
      lupdate -project translations.pro -ts fceux11_zh_CN.ts,fceux11_zh_TW.ts
      报「Passing .pro files to lupdate is deprecated」+ 「-ts does
      not accept comma-separated list」。

    根因：
      Qt 6.11 起 lupdate 拒绝 .pro 项目文件作为输入（迁移到
      qt_add_lupdate CMake target），且 .ts 列表必须用空格分隔
      的多个 -ts 参数。

    修复：
      用 Python 写 scripts/lupdate_run.py，解析 .pro 自己拿文件
      列表，然后调 lupdate 时每个 .ts 单独 -ts：
        lupdate <files> -ts fceux11_zh_CN.ts -ts fceux11_zh_TW.ts

4. 繁简隔离的本质：词组级 vs 字形级
================================================================================

  4.1 词组级差异举例

    +--------+----------+----------+--------------------------+
    | 词组   | 简体     | 繁体     | 字形是否完全相同          |
    +--------+----------+----------+--------------------------+
    | 软件    | 软件     | 軟體     | 不同（软/軟、体/體）       |
    | 视频    | 视频     | 視訊     | 不同（视/視、频/訊）       |
    | 鼠标    | 鼠标     | 滑鼠     | 完全不同                   |
    | 打印机  | 打印机   | 印表機   | 不同（打/印、印/表）       |
    +--------+----------+----------+--------------------------+

  4.2 字形级差异举例

    +--------+----------+----------+--------------------------+
    | 词组   | 简体     | 繁体     | 字形是否完全相同          |
    +--------+----------+----------+--------------------------+
    | 系统    | 系统     | 系統     | 不同（系/系 — 同，面/面同）|
    | 画面    | 画面     | 畫面     | 不同（画/畫 同字形？）     |
    | 时钟    | 时钟     | 時鐘     | 不同（时/時）              |
    +--------+----------+----------+--------------------------+

  4.3 关键观察

    简体「画」(U+753B) 与繁体「畫」(U+756B) 是不同 codepoint，但
    字形高度相似，肉眼几乎无法分辨。系统/画面 这类词组是「字形级
    差异」，但 系/面 是「字形完全相同、仅词义可能不同」的「词组级
    差异」。

    check_simp_trad.ps1 用单字扫描策略，所以字形级差异字符（画/畫）
    能正确识别为 forbidden，词组级差异字符（系/面）必须排除。

  4.4 推荐的繁简隔离规则

    简体独有（必须 not appear in 繁体 .ts）：
      为/为 (U+4E3A) vs 為/為 (U+70BA)
      国/国 (U+56FD) vs 國/國 (U+570B)
      师/师 (U+5E08) vs 師/師 (U+5E2B)
      会/会 (U+4F1A) vs 會/會 (U+6703)
      画/画 (U+753B) vs 畫/畫 (U+756B)
      语/语 (U+8BED) vs 語/語 (U+8A9E)
      经/经 (U+7ECF) vs 經/經 (U+7D93)
      ...约 200+ 字符

    共享字符（应 not appear in either 单字检测）：
      系 (U+7CFB)  繁简共享
      面 (U+9762)  繁简共享
      时 (U+65F6)  繁简共享
      钟 (U+949F)  繁简共享
      ...约 30+ 字符

    简体独有列表的维护：
      scripts/check_simp_trad.ps1 头部维护 + 每次 lupdate 后
      跑一次，false-positive 立即归并到 共享字符列表。

5. Native Speaker 审校的替代方案
================================================================================

  plan v3 §11 要求 zh_CN + zh_TW 各 1 名母语审校者签字。2026-06-17
  用户决策：放弃母语审校，错误可后续慢慢改。本节给出母语审校的
  可行替代方案，未来若想加回来可参考。

  5.1 替代方案 A：LLM 双盲校验

    Step 1: 用 LLM-A 翻译 1,911 源串
    Step 2: 用 LLM-B 翻译 1,911 源串（不同 prompt / 不同温度）
    Step 3: diff LLM-A 与 LLM-B 的输出
    Step 4: 不一致的串（预期 5-15%）人工 review

    优点：99.74% 覆盖率稳定，5-15% 待 review 远低于 100% 全文
    缺点：LLM 间可能共享训练数据导致一致性虚高

  5.2 替代方案 B：术语表 + 词组级审校

    Step 1: 维护 glossary.txt 97 项术语表
    Step 2: LLM 翻译时强制用术语表
    Step 3: 检查 .ts 文件中术语表外的中文词组
    Step 4: 仅审校术语表外的词组

    优点：审校范围从 1,911 缩到约 200-300 词组
    缺点：术语表维护成本由开发者承担

  5.3 替代方案 C：众包 review

    Step 1: 在 GitHub Discussions 发审校招募贴
    Step 2: 母语者按术语表审校一部分字符串
    Step 3: 维护 审校者贡献表（类似开源项目翻译）
    Step 4: 每版本 release 前跑一次

    优点：人工质量最高
    缺点：人力依赖 release schedule

  5.4 v0.3.15.x 的当前选择

    替代方案 A（LLM 双盲校验），结合替代方案 B（glossary 强制）。
    LLM-A 是 claude-opus-4-8（手动 session 2026-06-16），LLM-B
    是 minimax-m3。99.74% 覆盖率闸门 + 0 simp/trad 污染闸门 +
    commit bda72e6 落地 + 母语审校永久 waive（用户决策）。

6. i18n 子 widget retranslateUi 模式
================================================================================

  v0.3.15.x PHASE-2 落地 34 子 widget 的 runtime 翻译切换。模式
  详见 18 章的姊妹篇（待写），这里只列关键纪律：

  6.1 构造期 vs 运行期

    错误：new QPushButton(tr("&OK"), this)
      → 构造期 tr() 翻译一次，运行期切语言不会重新翻译
    正确：m_okBtn = new QPushButton(this); m_okBtn->setText(tr("&OK"));
      → 成员指针 + setText，运行期可重设

  6.2 changeEvent override

    void XxxDialog_t::changeEvent(QEvent* event) {
        if (event->type() == QEvent::LanguageChange) {
            retranslateUi();
        }
        QDialog::changeEvent(event);  // 必须转发给基类
    }

  6.3 静态门控

    tests/i18n_regression_test.cpp 扫描所有 34 widget 文件，确认：
      - 存在 void retranslateUi() 私有 slot
      - 存在 void changeEvent(QEvent*) override
      - 6 个 keyPress override 文件存在 QWidget::keyPressEvent(event) 转发

    这是 i18n_regression_test 的「静态保证」层，覆盖 widget
    漏改的回归风险。

7. 总结
================================================================================

  i18n 翻译工作流是 FCEUX11 v0.3.15 PHASE-1/2 的工程难点，但通过
  5 阶段（lupdate / glossary / 翻译 / lrelease / 双闸门）+ 6 条
  PowerShell 坑点修复 + 1,911 vs 3,481 计数修正，PHASE-1 落地
  99.74% 覆盖率（zh_CN + zh_TW），PHASE-2 落地 34 子 widget
  runtime 翻译切换。母语审校永久 waive（2026-06-17 用户决策），
  LLM 双盲校验作为可行替代。

  关键经验：
    1. lupdate 实际跑出的 source string 数与拍脑袋估算可能差
       80%+，永远以实测为准。
    2. PowerShell 5.1 在 Windows 上的 CJK 处理有 4-5 条隐性坑点，
       UTF-8 BOM + -f 格式串是必备。
    3. 繁简隔离必须用字形级单字扫描，词组级共享字符（系/面）
       必须从简体独有列表移除。
    4. 母语审校不是唯一可信路径，glossary + LLM 双盲 + 覆盖率
       闸门 + simp/trad 闸门的组合可以覆盖大部分质量需求。
