【写在前面 / Preface】
================================================================================

  FCEUX11 的质量门控是"6 层金字塔"：单元测试、ROM 回归、
  savestate 字节级哈希、性能基准、Rust 测试、手动 GUI。本章
  把每层的目的、工具、跑法、坑点一次性讲清楚。

  本章目标：
    1. 拆解 6 层测试金字塔
    2. 解释 ctest 配置文件位置与跑法
    3. 解释 golden hash 维护策略
    4. 解释 ASan / UBSan 在 MSVC 上的限制
    5. 解释 vrc7 savestate 例外的由来
    6. 给出 PR 提交前必跑的检查清单

  阅读时间：约 25 分钟。
  前置知识：知道 ctest / cargo test 基础；了解 sanitizer 概念。

1. 测试层次
================================================================================

  ┌─────┬────────────────────────────────────────────┬───────────────────┐
  │ #   │ 名字                                       │ 工具              │
  ├─────┼────────────────────────────────────────────┼───────────────────┤
  │ L1  │ 单元测试 (src/tests)                        │ ctest             │
  │ L2  │ ROM 帧回归                                  │ ctest + 黄金 hash │
  │ L3  │ Savestate 字节级哈希                        │ ctest + 黄金 hash │
  │ L4  │ 性能基准                                    │ ctest             │
  │ L5  │ Rust 单元测试 (src/rust)                    │ cargo test        │
  │ L6  │ 手动 GUI 测试                               │ 人                │
  └─────┴────────────────────────────────────────────┴───────────────────┘

  1.1 L1 单元测试

  测纯 C++ 逻辑，不启动 GUI，不依赖 ROM。
  例：fceux11_smoke_test, fceux11_expected_api_test,
     fceux11_enum_class_bitflags_test

  1.2 L2 ROM 帧回归

  对 13 个 mapper ROM 各跑 60 帧，CRC 全部帧与 golden_hashes.json 对比。
  覆盖 mapper 的执行语义（不是字节级）。

  1.3 L3 Savestate 字节级哈希

  对 12 个 ROM 跑 60 帧后，将 savestate 写入内存并计算 MD5，与
  golden_savestate_hashes.json 对比。
  覆盖 savestate 字节布局稳定性。

  1.4 L4 性能基准

  测 PPU render / x6502 CPU / APU mix 的耗时，禁止显著回归。

  1.5 L5 Rust 单元测试

  跨语言桥的逻辑层，cargo test --workspace 跑全。

  1.6 L6 手动 GUI 测试

  启动 exe + 加载 ROM + 玩 30 秒 + 验证菜单/输入/画面。ctest 覆盖不到。

================================================================================
3. 跑测试的常见坑
================================================================================

  3.1 vcpkg DLL 找不到

  现象：test 启动后 STATUS_DLL_NOT_FOUND（0xc0000135），无 stdout/stderr。
  原因：archive.dll / z.dll / Qt6Core.dll 等 vcpkg 库不在 PATH。
  解决：把 vcpkg_installed/x64-windows/bin 加到 PATH。
  持久化：tests/CMakeLists.txt 配 ENVIRONMENT_MODIFICATION 自动注入。

  3.2 相对路径找不到 fixture

  现象：mapper_load_test 等报 "cannot open fixtures/mapper_*.nes"。
  原因：测试用了相对路径，必须在 src/tests 下运行（不是 build/src/tests）。
  解决：

      cd src/tests
      PATH=... ctest -C Release -R mapper_load

  3.3 savestate_regression_test 找不到 golden 文件

  现象：所有 ROM savestate MD5 不匹配。
  原因：golden_savestate_hashes.json 路径不对。
  解决：检查 tests/fixtures/ 目录存在 golden_savestate_hashes.json。

  3.4 跨平台 / 跨 MSVC 版本

  MSVC ABI 在 14.20+ 是稳定的，但 struct 内存布局对 alignas / #pragma pack
  敏感。切换工具链版本前必须重跑所有测试。

  3.5 GUI 启动后 stdin/stdout 被吞

  现象：手动跑测试时 GUI 启动后看不到 printf。
  解决：用 Start-Process -RedirectStandardOutput 写到文件，或
        用 console 子进程（MSYS2 / pwsh）跑。

4. golden hash 维护
================================================================================

  src/tests/fixtures/golden_hashes.json         # ROM 帧 CRC（720 帧）
  src/tests/fixtures/golden_savestate_hashes.json  # 12 ROM savestate MD5

  4.1 何时更新

    改 mapper 实现但保持行为正确：必须更新 hash
    改 PPU 行为但保持画面正确：必须更新 hash
    改 savestate 序列化但保证等价的二进制布局：禁止更新 hash，回归会发现
    修 bug 改变了 NES 行为：禁止更新 hash，这是 bug，要修回去

  4.2 更新流程

    1. 本地跑测试，定位 hash 不匹配的 ROM
    2. 手工运行 60 帧，检查画面/行为是否符合预期
    3. 如果是预期改动，记录在 PR 描述里
    4. 重新生成 hash（test 内置 --update-golden 模式）

  4.3 哈希算法

  ROM 帧 CRC：CRC32 / Adler32 / 简单累加
  Savestate：MD5（全 16 字节）
  实际选型：src/tests/common/golden.h 实现。

================================================================================
5. vrc7 savestate 例外
================================================================================

  vrc7 的 OPLL 音源状态通过 FCEUSTATE_INDIRECT 保存，chunk 中包含
  堆指针 sintbl，每次进程启动地址不同，导致 savestate 字节级非确定性。

  处理：
    - vrc7 不进 savestate_regression_test 的 hash 比对
    - 但 rom_regression_test 的帧 CRC 仍然覆盖 vrc7 行为正确性

  新增带动态分配状态的扩展音源时，必须评估 savestate 字节级稳定性。
  策略：FCEUSTATE_INDIRECT 序列化指针会让 hash 漂移，应改用
  FCEUSTATE_INDIRECT_NO_HEADER 序列化数据本身。

6. 性能基准
================================================================================

  基线测量：v0.3.0 commit（test: 测试基建构建完成）的 benchmark 可执行
  文件作为 v0.3.0 baseline。

  如果 v0.3.0 在当前环境下无法构建（vcpkg / Qt 重新编译耗时过长），
  使用 v0.3.11（最近 prior release）作为代理基线。

  性能回归阈值（v0.3.0 基线）：
    - PPU render < 1.1× v0.3.0
    - x6502 CPU < 0.95× v0.3.0  ← 注意是"必须更快"
    - APU mix < 1.1× v0.3.0

  跑法：

    tests/fceux11_bench_ppu_render.exe     # 100 iterations after 10 warmup
    tests/fceux11_bench_x6502_exec.exe
    tests/fceux11_bench_apu_mix.exe

  输出格式：

    RESULT: PASSED   (目前硬编码无条件 PASS，需后续加硬阈值断言)

  v0.3.10 测量：PPU 0.735 ms/frame, x6502 0.842 ms/frame, APU 0.704 ms/frame
  （60-frame run），在预算窗口内。

8. ASan / UBSan 在 MSVC 上的限制
================================================================================

  FCEUX11 用 -DFCEUX11_ASAN=ON 启用 AddressSanitizer，
  -DFCEUX11_UBSAN=ON 启用 MSVC-native UB 替代。

  8.1 ASan

  MSVC /fsanitize=address 自 VS 2019 v16.9 起完全支持。
  Runtime DLLs（clang_rt.asan_dynamic-x86_64.dll）和 import libs
  随 MSVC 安装一起发布。

  8.2 UBSan

  MSVC 没有 /fsanitize=undefined。FCEUX11 替代方案：
    /RTC1   ← Debug only：栈帧完整性、未初始化变量
    /sdl    ← 扩展 /GS
    /GS     ← 栈 buffer 安全 cookie
    /guard:cf ← Control Flow Guard

  这些**不**覆盖完整的 clang UBSan（alignment, vptr, signed-overflow 等），
  完整 clang-style UBSan 是 v0.4.x 工具链 workstream。

  8.3 LSan 缺失

  MSVC Windows ASan 不实现 LeakSanitizer。
  `ASAN_OPTIONS=detect_leaks=1` 会被 cl 的 ASan runtime 拒绝。
  泄漏检测推迟到 v0.4.x clang-cl CI 矩阵。

  8.4 跑法

    scripts/_build_asan.ps1   # 配 cmake -DFCEUX11_ASAN=ON
    scripts/_ctest_asan.ps1   # 跑全套测试
    scripts/_build_ubsan.ps1
    scripts/_ctest_ubsan.ps1

9. 5 道门控
================================================================================

  Plan v3 §7 规定 5 道门控（任何 PR 合并前必过）：

  1. 编译门控     cmake --build build，0 errors，无新增 warnings
  2. 单元门控     ctest + cargo test --workspace 全绿
  3. 字节级门控   5-ROM savestate SHA-256 与 golden_hashes.json 一致
  4. 冒烟门控     fceux11.exe --help 退 0；nestest.nes 60 帧 OK
  5. 性能门控     PPU/x6502/APU benchmark 在阈值内

  任何一道失败 → 拒绝合并。

10. 测试覆盖不到的区域
================================================================================

  - GUI 启动（Qt event loop 行为）—— 必须手动测或用 08/15 章的端到端脚本
  - 键盘 / 手柄响应 —— 详见 15 章 §案例 B 的诊断
  - 视频后端（OpenGL 3.3 Core）—— 启动崩溃由 ctest 之前的可执行文件冒烟
    测试覆盖，但实际画面正确性需手动
  - 多线程 race condition —— 罕见，需 ThreadSanitizer 显式跑
  - 国际化（zh_CN / zh_TW）—— 切换语言后启动，验证菜单 / 对话框无乱码

  这些"灰色地带"在 release 前必须有专人手动测 30 分钟。

11. PR 提交前必跑清单
================================================================================

    cd build
    set PATH=%CD%\..\vcpkg_installed\x64-windows\bin;%PATH%
    cmake --build . --config Release
    ctest -C Release --output-on-failure
    cd ../src/rust
    cargo test --workspace --release
    cd ../../build
    tests/fceux11_rom_regression_test.exe
    tests/fceux11_savestate_regression_test.exe

  若改动 mapper 寄存器组 → 必须重跑 savestate_regression。
  若改动 PPU 时序 → 必须重跑 rom_regression。
  若改动 C++ header 中 FFI 签名 → 走 RFC（09 / 14 章）。
