【写在前面 / Preface】
================================================================================

  FCEUX11 在 v0.3.x 评估过 PPU 后端 PAL→RGBA 的 SIMD 优化。本章
  把这次评估的方法、结果、决策门槛沉淀下来，供后人参考。

  本章目标：
    1. 解释为什么 SIMD 优化要做"探测性"评估
    2. 拆解 PAL→RGBA 工作负载的 SIMD 实现
    3. 解释 MSVC /arch:AVX2 的实际效果
    4. 解释 FCEUX11 的 1.20× 决策门槛
    5. 解释为什么 SIMD 在 PPU 后端没有足够收益

  阅读时间：约 20 分钟。
  前置知识：懂基础 SIMD 概念（SSE/AVX）；懂 C++ 编译开关。

================================================================================
1. 为什么要先做"探测"再决定合入？
================================================================================

  SIMD 优化有显著代价：
    - 多份代码（标量 / SSE4.2 / AVX2 / 可能的 AVX-512）维护成本高
    - 自动向量化有时比手写慢
    - 跨平台兼容性（不同 CPU 支持不同指令集）
    - 测试矩阵大（每个优化都要 5 项 gate 全过）

  FCEUX11 的策略：先用 standalone probe 评估，若加速比 ≥ 1.20×
  且能解决兼容性，才合入主代码。

================================================================================
2. 探测设置
================================================================================

  工作负载：    palette-index → RGBA 转换，256x240 帧
  迭代次数：    100（10 个预热帧后开始计时）
  对比变体：
    - 标量（关闭自动向量化）
    - SSE4.2 /arch:SSE2
    - AVX2 /arch:AVX2

  每个变体在 Release 配置下编译，独立可执行文件，避免互相污染。

  2.1 工作负载代码（标量版）

    void pal_to_rgba_scalar(const uint8_t* idx, RGBA* out, int n) {
        for (int i = 0; i < n; i++) {
            uint8_t p = idx[i];
            out[i] = palette[p];
        }
    }

  2.2 工作负载代码（AVX2 版）

    void pal_to_rgba_avx2(const uint8_t* idx, RGBA* out, int n) {
        const __m256i mask = _mm256_set1_epi8(0xFF);
        for (int i = 0; i < n; i += 32) {
            __m256i b = _mm256_loadu_si256((__m256i*)&idx[i]);
            // 32 个 palette 索引展开成 32 个 RGBA
            // （实际展开需要更复杂的 gather + shuffle）
            // ...
        }
    }

  实际 AVX2 版的展开比 SSE 复杂，因为 RGBA 是 4 字节而 idx 是 1 字节，
  需要 4× gather（_mm256_i32gather_epi32）。

3. 典型结果（参考基线）
================================================================================

  | 变体                          | 标量 ms/frame | 自动向量化 ms/frame | 加速比 |
  |-------------------------------|--------------:|-------------------:|------:|
  | 标量（无向量化）               |       0.0233  |             0.0233 | 0.998 |
  | SSE4.2 (/arch:SSE2)            |       0.0234  |             0.0232 | 1.007 |
  | AVX2 (/arch:AVX2)              |       0.0233  |             0.0235 | 0.991 |

  结论：AVX2 加速比 < 20% 阈值，对 PAL→RGBA 这个代表 PPU 工作负载，
  SIMD 优化没有足够收益。

  3.1 为什么加速比不显著？

  1. 工作负载太轻：单帧 256×240 = 61440 像素，标量 0.023 ms
     （即 ~5 ns/像素），AVX2 理论上限 4× 加速，但 4× × 5 = 20 ns
     总节省 ≈ 0.013 ms。
  2. 内存带宽受限：PAL→RGBA 是"读 1 字节 + 写 4 字节"，主存
     带宽就是瓶颈，SIMD 解决不了。
  3. gather 指令开销：_mm256_i32gather_epi32 在 Skylake 之前延迟
     15-20 cycles，削弱了向量化收益。

================================================================================
4. 决策门槛
================================================================================

  SIMD 优化合入 FCEUX11 主线需满足：

  - 加速比 >= 1.20×（在代表性工作负载上）
  - 代码复杂度增加不超过 50% 行数
  - 不引入跨平台兼容性问题
  - savestate 字节布局不变

  低于 1.20× 加速比 → 不值得维护多份代码，留在 probe / 旁路分支。

  为什么是 1.20×？
    - 1.10× 处于"测量噪声边缘"（同一份代码两次跑差 5% 是常事）
    - 1.20× 是"95% 置信度下显著"的保守门槛
    - 维护 3 份代码的"机会成本" ≈ 1.15× 加速，所以 1.20× 留 buffer

================================================================================
5. 探测的代表性工作负载
================================================================================

  选工作负载时必须代表真实热路径：

  - 内存带宽受限（典型 PPU 后端、mapper 寄存器读取）
  - 数据并行（无强跨元素依赖）
  - 调用频率高（每帧多次）

  不能用作代表性工作负载的：
    - 一次性初始化（启动时的格式解析）
    - 强分支（CPU dispatch 的 op switch）
    - 跨元素数据共享（mapper 状态机的更新链）

================================================================================
6. 探测与主代码隔离
================================================================================

  SIMD probe 必须与主 emulator 隔离，原因：

  - 主 emulator 的复杂度会污染测量（Icache miss、cache thrashing）
  - 主 emulator 的 savestate 兼容性约束阻碍 SIMD 寄存器布局调整
  - 主 emulator 的 C++ 风格（异常 / RTTI / 多态）阻碍自动向量化

  实现：
    - 单独的 standalone 测试可执行文件
    - 不依赖 fceu11 任何模块，仅模拟数据布局
    - 输出纯耗时（microseconds），不输出 NES 模拟状态

  FCEUX11 的 SIMD probe：
    src/tests/fceux11_ppu_simd_probe_scalar.exe
    src/tests/fceux11_ppu_simd_probe_sse42.exe
    src/tests/fceux11_ppu_simd_probe_avx2.exe

7. 工具链注意
================================================================================

  - MSVC /arch:AVX2 需要 CPUID 支持
    （验证：cat /proc/cpuinfo | grep avx2）
  - 自动向量化需要 /O2 + 关闭 /fp:strict
  - SSE4.2 通常用 /arch:SSE2 触发（编译器自动用更高的指令）
  - AVX-512 同理但需要更严格的 /arch:AVX512 显式声明

  如果用户机器不支持对应指令集，probed exe 启动时会崩溃。
  必须做 CPUID 探测，probed exe 内部 gracefully 降级到 SSE2 fallback。

  7.1 CPUID 探测代码

    bool cpu_supports_avx2() {
        int info[4];
        __cpuid(info, 0);
        if (info[0] < 7) return false;
        __cpuidex(info, 7, 0);
        return (info[1] & (1 << 5)) != 0;   // EBX bit 5
    }

8. 何时重做探测
================================================================================

  - Qt 升级到新主版本（堆内存布局变化影响 cache 行为）
  - MSVC 工具链升级
  - 加入新的色彩空间（10-bit / HDR）—— 工作负载特征会变
  - 关键 PR：内存分配器、NUMA 感知、cache-line 调整

9. 探测结果归档
================================================================================

  所有 SIMD probe 结果应记录在 docs/tech/，格式：

  - 工作负载描述
  - 编译选项
  - 硬件（CPU 型号、内存频率）
  - 每次运行的 ms/frame（多次运行取中位数）
  - 加速比
  - 决策（合入 / 拒绝 / 留作 probe）

  v0.3.12 PAL→RGBA 决策：拒绝合入，理由 1.0× 加速比无收益。
  当前 SIMD probe 代码仍保留在 src/tests/，作为未来重新评估的起点。

10. 替代方案：继续手动展开而不引入 SIMD
================================================================================

  PAL→RGBA 的另一种优化：用 256 项的 4 字节调色板直接查表。
  这种 4 字节查表 vs 1 字节查表 + 展开：
    - 标量查 4 字节：每次 memmove 4 字节，自动向量化空间小
    - 4 字节查 4 字节：与原 1 字节查表同结构，但少一次拼装

  实际收益：~5-10%。远低于 SIMD 但也远低于维护成本，所以也未合入。
