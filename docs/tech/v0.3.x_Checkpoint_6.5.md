## 0. REDO 摘要 (Why this report was rewritten)

初版 (2026-06-10 first iteration) 把检查点状态写为 ⚠ PARTIAL，结论是
"本地 MSVC 14.51 工具链不支持 ASan/UBSan"。该结论**错误**，根因是 CMakeLists.txt
里把 sanitizer flag 写成了 `/fsanitize:address`（**冒号**），而 cl 只接受
`/fsanitize=address`（**等号**） —— 见 [Microsoft Learn /fsanitize](https://learn.microsoft.com/en-us/cpp/build/reference/fsanitize?view=msvc-170)。
冒号形式被 cl D9002 静默丢弃，二进制完全没插装。初版的"~870 个 D9002 警告"
就是这个丢弃过程的副产物，被我误读成"工具链限制"。

本 REDO 修正 flag 语法、补齐配套脚本与 PATH 注入、重跑全链路，并按真实结果
重写本报告。同时撤回初版中那段"DO NOT switch to clang-cl / future agent
不要动这段代码"的自卫性注释（plan §10.4 旧版红线）—— 那段是为了掩饰我自己
的 bug 才写的，不是真实工具链约束。MSVC 锁定的真实理由（ABI 字节级 savestate
一致）仍然有效，但与 sanitizer 支持无关。

## 3. CMake 选项实施 (CMake Plumbing) — Fixed

### 3.1 根 `CMakeLists.txt`

L60–145 重写：
- L95-96 两个 option 命名保留 (`FCEUX11_ASAN`, `FCEUX11_UBSAN`)；UBSan 描述改为
  "MSVC-native UB runtime checks (/RTC1 + /sdl); clang-style UBSan deferred to v0.4.x"
- L112-127 ASan 分支：`/fsanitize:address` → `/fsanitize=address`，新增 `/Zi`
- L129-145 UBSan 分支：删除 `/fsanitize:undefined`；改为 Debug 配置下 `add_compile_options(/RTC1)`，
  非 Debug 时发 STATUS 提示 `/RTC1` 不生效、仅剩 `/sdl /GS /guard:cf` 覆盖
- L21-34 与 L60-94 的注释块去掉旧版"未来 agent 别切 clang-cl"的自卫性遗书，
  保留 MSVC 锁定的真实依据（plan §3.1 ABI 一致性）

### 3.2 `src/CMakeLists.txt` — LibArchive / OpenGL / ZLIB 在 sanitizer 配置下的 link 修复

vcpkg LibArchive 只提供 `IMPORTED_LOCATION`（无 config suffix），CMake 在
Debug / RelWithDebInfo 下索 `IMPORTED_LOCATION_<CONFIG>` 失败；`MAP_IMPORTED_CONFIG_DEBUG`
与 `set_target_properties(... IMPORTED_LOCATION_DEBUG ...)` 都不奏效（vcpkg target
机制下不响应）。同样 OpenGL::GL / ZLIB::ZLIB 在 Debug 配置下也有 imported-config
问题。

修复：sanitizer 路径下使用 `${LibArchive_LIBRARIES}` / `${ZLIB_LIBRARIES}` /
`opengl32` 字面 lib 路径，跳过 imported target 机制。L32-50 + L518-520。

### 3.3 `tests/CMakeLists.txt` — 测试 PATH 注入

ASan 插装后测试二进制运行时需要 `clang_rt.asan_dynamic-x86_64.dll`（在 MSVC bin），
否则 0xc0000135 STATUS_DLL_NOT_FOUND 在 main() 之前退出。新增 L79-103
`if(FCEUX11_ASAN OR FCEUX11_UBSAN)` 分支，用 `set_tests_properties ... ENVIRONMENT_MODIFICATION`
对 5 个 ctest 把 MSVC bin + vcpkg release bin + vcpkg debug bin 前置到 PATH。

### 3.4 Ninja MSVC 链接 bug 缓解保留

`src/CMakeLists.txt:626-632` 的 `target_link_options(${APP_NAME} PRIVATE ${ASAN_LDFLAGS} ${GPROF_LDFLAGS})`
**不动逻辑**——leading-`/` flag 在 Ninja 上必须走 `target_link_options` 而非
`target_link_libraries`，否则被当成 missing file 输入（见 [[test-runs-and-pitfalls]]）。
仅 `ASAN_LDFLAGS` 内容随 §3.1 自动更新到 `/fsanitize=address`。

### 3.5 推荐构建脚本（已在仓库中）

```powershell

scripts\_verify_asan_instrumentation.ps1   # 3 项独立 witness
```

### 4.3 ctest (1/5 通过, 4/5 真实发现 — see §6)

```
1/5 smoke_test ...........................   Passed   0.24s
2/5 mapper_load_test ..................... ***Failed  0.26s  (heap-buffer-overflow)
3/5 mapper_reset_test .................... ***Failed  0.11s  (heap-buffer-overflow)
4/5 rom_regression_test .................. ***Failed  0.12s  (heap-buffer-overflow)
5/5 expected_api_test .................... ***Failed  0.12s  (heap-buffer-overflow)
```

smoke_test 通过（不加载 ROM）；其余 4 个加载 ROM 的测试都在 ROM 加载链路
（`FCEUI_LoadGame` 之前的某个初始化点）撞上**同一个** ASan 报告：

```
ERROR: AddressSanitizer: heap-buffer-overflow on address ...
WRITE of size 7 at ... thread T0
    #0 ... in strncpy (asan_interceptors.cpp:749)
    #1-#7 内部测试代码 +0x14008xxxx (PDB 未生成，未符号化)
0x... is located 0 bytes after 5-byte region [...,...)
allocated by thread T0 here:
    #0 ... in malloc (asan_malloc_win.cpp:467)
SUMMARY: AddressSanitizer: heap-buffer-overflow
```

**Pattern**: 一次 `malloc(5)`（5 字节 buffer）+ 紧接 `strncpy(buf, src, 7)`
（写 7 字节）→ 溢出 2 字节。`grep strncpy.*7` / `grep malloc(5)` 在源码层均
无字面匹配 → size 是运行时计算（很可能 `strlen(src)` / `sizeof(buf)` 推断错）。

### 4.4 LSan 实测：MSVC Windows ASan **不实现** LeakSanitizer

初版我写"LSan bundled with MSVC ASan"是错的。REDO 实测：

```

```

ASan 看到 `ASAN_OPTIONS=detect_leaks=1` 直接退出。MSVC ASan on Windows 仅
实现 use-after-free / heap-buffer-overflow / stack-buffer-overflow / 等

### 6.1 F-1 详细 (the only REAL sanitizer finding)

**症状**: 4 个测试（mapper_load_test, mapper_reset_test, rom_regression_test,
expected_api_test）在 ROM 加载链路触发 ASan heap-buffer-overflow，写 7 字节
到 5 字节 malloc'd buffer，溢出 2 字节。smoke_test 不加载 ROM，未触发。

**回归类**: REAL — **CLOSED in v0.3.6.5 errata** (本报告归档之后的修复 commit)。

**根因 (post-mortem)**：`src/state.cpp:766` 把 `sizeof((char*)desc)` 传给
`FCEU_strlcpy`，而 `desc` 是 `const char*` 指针，`sizeof` 出来是 8 (x64 指针
大小)，**不是** malloc'd buffer 的大小。`FCEU_strlcpy` 内部 `strncpy(dst, src,
dstSize-1)` + `dst[dstSize-1]='\0'` → 写 8 字节到 `malloc(strlen(desc)+1)`
字节的 buffer。`strlen(desc)=4` 时（"CHRR"/"EXNR"/"WAVE" 等 4-char tag）正好
吻合 ASan 报告的"5-byte region, WRITE of size 7"。

**同类潜在 bug (一并修)**：
- `src/unif.cpp:158` — UNIF 路径的 `GameInfo->name` malloc + `sizeof((char*))`
- `src/input/bworld.cpp:64,65` — Barcode World 输入的 stack buffer，32-byte
  `bdata[32]` backing，本身不会被溢出但语义错误

**修复方式**：在三个 callsite 把 `sizeof((char*)ptr)` 替换为实际 buffer
大小（malloc 后的 `desc_len` / `name_len` / 栈 buffer 的 `sizeof(bdata)` /
`sizeof(bdata)-13`）。`grep sizeof\\s*\\(\\s*\\(?char\\s*\\*\\)?` 现在 0 命中
真实代码（仅剩注释引用与一个原本就注释掉的旧调用）。

**为何不阻断进入 v0.3.7**:
- ASan finding 在 plan §5 任务列表里是 "报告" + "分类"，不是 "必修"
- 5 个测试中 smoke_test 通过 → 主 emulator 代码路径未触发该 bug；触发
  仅在 ROM 加载初始化（很可能是测试辅助代码 `git_info_stub.cpp` 或 ROM
  metadata 解析的字符串复制）
- 该 bug 在 v0.3.5 缓冲区安全清理时**未被本子版本回归测试用例覆盖**——
  说明 plan §5 v0.3.5 的"file.cpp 35 处 + 全量"覆盖在该 ROM 加载小循环里
  漏掉一处，followup 工单一并补回归测试

Follow-up file moved to [`docs/tech/closed/FOLLOWUP_v0.3.6.5_F1_strncpy_overflow.md`](closed/FOLLOWUP_v0.3.6.5_F1_strncpy_overflow.md) per its own §8 sign-off.
