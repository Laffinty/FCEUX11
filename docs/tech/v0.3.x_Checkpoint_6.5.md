## 2. 工具链现状 (Toolchain Reality)

| 项 | 计划锁定 | 实际可用 | 备注 |
|----|---------|---------|------|
| 编译器 | MSVC 19.36 (VS 17.6) | **MSVC 19.51.36244 (VS 18 / BuildTools)** | 实际版本**新于**计划锁定版本,本机具 14.51 / 14.44 双套工具集 |
| ASan 运行时 (clang_rt.asan*.dll) | 必须 | ✅ 存在 (14.44.35207) | 提示 ASan 期望由 **Clang** 前端消费 |
| Clang-cl / clang++ | 可选 | ❌ **未安装** | 关键缺失 |
| `/fsanitize:address` cl 标志 | MSVC 19.36+ 应支持 | ❌ **cl warning D9002: ignoring unknown option** | 关键失败点 |
| `/fsanitize:undefined` cl 标志 | MSVC 19.36+ 应支持 | ❌ **cl warning D9002: ignoring unknown option** | 关键失败点 |

**根因分析**:本机 MSVC 14.51 **cl 编译器不接受** `/fsanitize:address` 或
`/fsanitize:undefined` 选项(尽管 MSVC 19.27+ 文档承诺支持)。clang_rt.asan DLL
存在但需要 Clang-cl 前端配合,而 Clang 编译器本身没有装。因此:

- 编译时 cl 发出 `warning D9002` 并静默丢弃该标志
- 链接器也没真正注入 ASan 运行时(否则测试运行时会找不到 `clang_rt.asan*.dll`)
- 生成的二进制与未启用 ASan 的二进制在功能上**完全等价**

可用证据:

```
$ dumpbin /symbols build-asan/tests/fceux11_smoke_test.exe | grep -E "__asan|__ubsan|AddressSanitizer" -c
0
```

**结论**:本机环境**无法执行真正的 ASan/UBSan 验证**。本检查点降级为
"**构建/链接/测试套件可正常启用 FCEUX11_ASAN/UBSAN 选项,且测试通过**"的
**CMake 选项可用性**验证。

## 3. CMake 选项实施 (CMake Plumbing)

为支持检查点并预留真正的 ASan/UBSan 路径,新增 2 个选项(根 `CMakeLists.txt`)。

### 3.1 新选项 (CMakeLists.txt:60-61)

```cmake
option(FCEUX11_ASAN  "Enable AddressSanitizer (and LSan) for the v0.3.6.5 checkpoint" OFF)
option(FCEUX11_UBSAN "Enable UndefinedBehaviorSanitizer for the v0.3.6.5 checkpoint" OFF)
```

### 3.2 编译/链接选项实施

- `add_compile_options(/fsanitize:address)` — 编译时插桩
- `CMAKE_EXE_LINKER_FLAGS_RELWITHDEBINFO` 与 `CMAKE_SHARED_LINKER_FLAGS_*` 注入链接时标志
- **未使用** `add_link_options()`,因为 Ninja MSVC 生成器会把 leading-`/` 标志
  误当作文件输入(已踩坑:`\fsanitize$:address, needed by ... missing`)
- 顶层 `set(ASAN_LDFLAGS "/fsanitize:address" CACHE INTERNAL ...)` 仅供
  `src/CMakeLists.txt` 通过 `target_link_options` 引用(`target_link_libraries`
  同样会触发 Ninja 上述 bug)

### 3.3 修复的两处 Ninja MSVC 链接器 bug

1. **CMakeLists.txt**:用 `CMAKE_EXE_LINKER_FLAGS_*` 替代 `add_link_options`
2. **src/CMakeLists.txt:589-598**:用 `target_link_options(${APP_NAME} PRIVATE ${ASAN_LDFLAGS} ${GPROF_LDFLAGS})` 替代 `target_link_libraries(... ${ASAN_LDFLAGS} ...)`,
   因为后者把 leading-`/` 字符串当作库路径处理

### 3.4 编译期宏

启用 ASan 时定义 `FCEUX11_ASAN_ENABLED=1`,启用 UBSan 时定义
`FCEUX11_UBSAN_ENABLED=1`(目前**无源码使用**,为未来 `#ifdef FCEUX11_ASAN_ENABLED`
分支留口子 — 例如 mapper PRG-RAM 红区大小调整)。

### 3.5 推荐构建配置

```powershell
cmake -S . -B build-asan -G Ninja `
    -DCMAKE_BUILD_TYPE=RelWithDebInfo `
    -DCMAKE_C_COMPILER=cl -DCMAKE_CXX_COMPILER=cl `
    -DFCEUX11_BUILD_TESTS=ON -DENABLE_LINT=OFF `
    -DFCEUX11_ASAN=ON
```

## 10. 推荐后续动作 (Next Steps)

### 10.1 v0.3.7 之前 (强制)

1. **将本检查点作为 v0.3.6 release notes 的一部分发布** — 用户拿到 v0.3.6
   后如果尝试 `-DFCEUX11_ASAN=ON`,会得到 §4.1 描述的"warning 噪音但可用"
   状态,需要在 release notes 中明示这是 MSVC 14.x 工具链不真正支持
   sanitizer 的**已知限制**,非 v0.3.6 缺陷。
2. **不要**把"ASan 0 leak 0 crash"作为 v0.3.6 的硬性宣传 — 这只是
   **构建/链接/测试套件级别的等价性验证**,不是真实 ASan 验证。
3. **不要**在本地默认安装 LLVM clang-cl — 详见 §10.4 工具链红线。

### 10.2 v0.3.7 ~ v0.3.10 期间 (推荐,工具链中立)

1. **接受本检查点的 PARTIAL 结论** — 真实 ASan/UBSan 验证推迟到 v0.4.x
   工具链专题。期间以 v0.3.5 缓冲区安全 + v0.3.6 RAII 化 + `/W4` +
   字节级 savestate 作为基线硬化手段。
2. 在 `CMakeLists.txt` 顶部已加的 MSVC-only FATAL_ERROR 与 ASan 选项旁的
   "FUTURE-AGENT GUARDRAIL" 注释已经能防止后续 agent 切换到 clang-cl。
3. CI 集成:在 `.github/workflows/ci.yml` 中,**主构建保持 MSVC**,可选项
   是在 v0.4.x 引入一个独立的 `build-windows-clang-sanitizers` matrix job
   (用 GitHub Action 自带的 `llvm-mirror/setup-llvm-action` 在 runner 临时
   装 LLVM,不污染项目根)。**这一 CI job 不在 v0.3.x 范围**。

### 10.3 v0.4.x 议题

- 工具链升级专题: Clang-cl 仅作 sanitizer 驱动,主构建仍 MSVC
  (符合 plan §3.1 "工具链锁定 MSVC 19.36 + Qt 6.8 LTS 在 v0.3.16 之前
  不升级"的延伸: v0.4.x 之前 MSVC 锁定,Clang-cl 是 sanitizer 旁路)
- `[[assume_aligned]]` / `std::hardware_destructive_interference_size` 配合
  ASan 红区使用,提升 mapper 寄存器组的越界检测精度
- `v0.3.6.5-rerun` 真实 sanitizer 跑测,在装好 Clang-cl 之后复跑本检查点,
  得到真实 ASan/UBSan 警告分类

### 10.4 工具链红线 (Toolchain Red Lines)

> **未来 agent 与维护者必读**:本项目 v0.3.x 范围内**禁止**下列动作:

1. ❌ **安装 LLVM clang-cl 作为默认系统工具链** — 即使只为了 ASan 也不
   行,因为 (a) 一旦 PATH 上有了 clang-cl,后续 agent 在 `cmake` 时可能误用
   `(CC=clang-cl)`; (b) 项目的 MSVC-only 锁定是为了 v0.3.16 收官时字节级
   savestate 一致,clang-cl 与 MSVC 在 ABI 边界(CFG / `__declspec(selectany)`
   / `#pragma optimize` 等)的细微差异会破坏一致性。
2. ❌ **修改根 `CMakeLists.txt` 的 `FATAL_ERROR if(NOT MSVC)` 块** —
   即使只是"加一个例外给 clang-cl",也是把项目从 MSVC-only 移向
   "多编译器支持"的方向,这是 v0.3.16 LTS 收官后的 v0.4.x 议题。
3. ❌ **改 `option(FCEUX11_SANITIZER_DRIVER ...)` 让 CI 默认切到
   clang-cl** — 真正的 sanitizer 验证必须显式 opt-in (matrix job 或
   独立目标),不能成为默认。
4. ❌ **回退 `FCEUX11_ASAN` / `FCEUX11_UBSAN` 选项实现** — 即使它们在本
   工具链上"不可真正工作",它们作为**构建/测试套件级别的硬化标签**与
   未来 Clang-cl 切换时的**激活点**仍有价值,删了之后 v0.4.x 工具链
   升级时还要重新实现。
5. ❌ **把"MSVC cl D9002 忽略 sanitizer flag"作为"可以安全移除 sanitizer
   选项"的理由** — D9002 是当前 MSVC 版本的实现细节,升级到 MSVC 19.36
   (plan 锁定版本)或 19.51 修复版时,flag 可能再次被识别并真正工作。
