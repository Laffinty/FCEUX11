## 0. 评级规则（决定"怎么算达标"）

KagamiQA 评级由 `src/rust/crates/kagami-qa/src/report/grade.rs::compute_grade`
机器计算，规则为：

| 评级 | 含义 | 全部满足的条件 |
|---|---|---|
| A | 完美 | 0 失败、0 跳过 |
| B | 发布标准 | 无 blocking 失败、无 PASS→FAIL 回归、剩余失败全部是冻结基线内 `fail_to_fail`（且带 `--baseline` 运行） |
| C | 可接受 | 无 blocking 失败、无回归；但存在不在冻结基线内的新失败，或未提供基线证明 |
| D | 不可发布 | 任一 blocking 失败，或任一 PASS→FAIL 回归 |
| E | 核心损坏 | 引擎启动测试（smoke / headless）失败 |

关键点：
- **B 与 C 的分界是冻结基线**：只要当前所有失败都能证明"基线里就是 FAIL"（fail_to_fail），
  即使仍有失败也判 B；有任何一个失败不在基线内（new_test FAIL）或没带基线，最多 C。
- **D 的门槛很低**：一条 PASS→FAIL 或一个 blocking 失败即 D，与失败比例无关。
- 冻结基线文件：`tests/fixtures/kagamiqa_baseline_frozen.json`
  （v1.17 时代快照，run_id `20260808-022802-1777cc-frozen`）。

## 2. 根因分析

### R1 —— `blargg_cpu_instrs`（instr_v5_all，阻断 + 回归）【已修复】

**现象**：`kagami_qa_blargg_runner --rom fixtures/blargg/cpu/instr_v5_all.nes --frames 3000`
输出 `value=0x01 diag=[0xDE,0xB0,0x61]`，diag_string：

```
AB ATX #n
03-immediate
Failed
While running test 3 of 16
```

即 instr_v5 第 3 组（立即数）的 **0xAB（ATX = LAX #imm）** 子测试失败。

**根因**（`src/rust/crates/fceux11-core/src/cpu/execute.rs::do_unofficial`）：
0xAB 与内存寻址的 LAX（A3/A7/AF/B3/B7/BF）共用同一分支；`AddrMode::Imm` 分支写成
`(imm(state, bus).addr, 0)` 后再 `state.rd(bus, addr)`——按 `ModeResult` 契约，Imm 的
`addr` 字段携带的是**已取出的立即数值**，不是地址；`rd()` 把它当零页地址又读了一次。
结果 `LAX #$nn` 变成 `A = X = mem[$00nn]`。

C++ 参考（`git show 97000948^:src/ops.inc`）：

```c
/* ATX(OAL) ... constant to be OR with $FF for NES */
case 0xAB: LD_IM(_A|=0xFF;AND;_X=_A);   /* 即 A = X = imm */
```

Phase 7 preflight 修过 ANC/ALR/ARR/XAA/AXS 五个立即数 handler（"把立即数当内存地址读"），
但 0xAB 因与内存模式 LAX 合并而漏网；`lax_imm_loads_a_and_x` 旧测试用 imm=0x00、
零页 $00 也默认 0x00，"碰巧"通过，未暴露该 bug。

**修复**（本方案已实施，见 §3）。

### R2 —— `rom_regression_test`（nestest 第 4 帧，阻断 + 回归）【待决策】

**现象**：仅 nestest 第 4 帧（第 5 个仿真帧）CRC32 不一致：
`expected 0x6a65307c actual 0x7f4f43bf`；其余 779 帧全部一致，确定性复现。

**既有诊断**（已归档进 ChangeLog 的 Phase 4 收口报告 §4）：
- 差异为过渡帧 row 22 的 **16-pixel 水平偏移**（palette 0x0F 的一行从列 40 变成列 56），
  帧 0-3 与 6-59 均渲染一致。
- CPU 侧**全部可观测量字节一致**：逐调用 PC/count/IRQ/timestamps、总线轨迹、
  $2005/$2006/$2007 写入时序（sl=0 cyc=0，值一致）、帧 4/60 savestate（含 XBackBuf）
  均与 C++ 基线逐字节相同。
- 结论：legacy（newppu=0）PPU 渲染器的 per-dot 渲染时序产物，与 vbl_05 / mmc3_4 等
  PPU-timing known-fail 同族，**不是 CPU 精度缺口**（本方案本地复现也确认：修复 R1 后
  该帧差异不变）。

**含义**：R2 不是 CPU 代码 bug，而是 PPU 渲染器在特定过渡帧的时序工件；要消除它属于
PPU 精度工程（Phase 6/7 遗留的 accuracy 范畴），不是简单的 CPU 修补。

### R3 —— 其余 8 个失败（advisory，fail_to_fail，非阻塞）

## 4. 达到 B 级的两条路径

### 路径 A（推荐）：修复 R2，保持精度不后退

预期结果：`rom_regression_test` 转 PASS → 47 项 39P/8F，8 个失败全部 fail_to_fail
→ **Grade B**，且不修改冻结基线。

实施要点（有界排查，建议 1-2 个工作日，超时转路径 B）：
1. 复现与快照：写一个临时 frame-dump（在 `kagami_qa_rom_regression_runner` 的
   `extract_frame` 处把第 4 帧 XBuf 导出为 `.xbuf`/PNG），与 C++ 参考帧
   （`git worktree add` 到 `97000948^` 或 v1.17 tag，用旧树构建同 runner）逐行 diff，
   确认 16-pixel 差异的精确行列与 palette 值。
2. 聚焦 legacy（newppu=0）渲染器的过渡帧路径：row 22 的 scroll latch / 行预取 /
   精灵求值；`ppu.cpp` 中该帧 `$2005/$2006` 写入已在 phase4-closeout 证实时序一致，
   因此优先检查**渲染器内部瞬态**（dot 计数器、行缓冲预取、VBL 标志在帧边界的确切
   采样点），而不是 CPU 侧。
3. 每次修改后跑 `kagami_qa_rom_regression_runner` 与 `cargo test -p fceux11-core`，
   确认 0/780 且 221 PASS；再跑全量 runner 确认 39P/8F Grade B。

### 路径 B（回退/治理冻结）：把 R2 记为 approved known-limit

若 R2 判定为"过渡帧渲染工件、修复成本超出收尾范围"，可按项目既有治理把该测试

`fail_to_fail` against the frozen set）：

1. 修改 `tests/fixtures/kagamiqa_baseline_frozen.json`：
   `"rom_regression_test": true` → `false`；更新 `generated_at` / `run_id`，

   该残差已在 ChangeLog「Known limits / 发布评审」与本文档记录，标注
   `expected_to_eventually_pass=true`（精度债，非永久接受）。
3. 预期结果：重跑 `kagami-qa-runner --baseline` → 47 项 38P/9F，9 个失败全部
   fail_to_fail → **Grade B**；R4 门禁通过（total≥39、git_rev 有效、fail_to_pass=0、
   grade=B）。
4. 代价：接受一处与 C++ 基线不同的渲染帧作为 advisory 已知限制，后续由 PPU 精度
   工程（vbl_05/mmc3_4 同族）一并消解。

> 路径 B 不是"改测试骗评级"：评级机制本身以冻结基线为发布标准，冻结行为有
> baseline_drift（approved）字段显式留痕，R4 门禁的 anti-gaming 规则仍要求

## 7. 风险与回滚

- **R1 修复风险**：改动面极小（仅 LAX #imm 分支），221 个单测 + 12 项 blargg 直接
  测试全绿；如意外回归可用 `git revert` 单文件回退，且本方案已留修复前后矩阵对比。
- **路径 B 风险**：冻结基线变更会被 `baseline_drift` 标记为 approved 变更，评审需
  在 PR 中显式体现；若后续 PPU 修复落地，该条目会以 fail_to_pass 形式自然转绿。
- **CI 环境差异**：本地与 CI 均为 Rust-only 构建后结果一致（本地逐字节复现 CI 失败），
  因此不存在"本地过、CI 挂"的构建差异问题；发布前以 CI 全量 run 为最终裁决。
- **构建环境**：本地构建需 MSVC vcvars64 + vcpkg PATH；CI 使用 windows-2022 托管
  runner，工具链差异不影响正确性（两处失败模式已完全复现一致）。
