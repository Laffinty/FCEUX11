## 1. 升级依据（Do-NOT 触发条件）

### 1.1 修复 #1 NMI dispatch delay 的 NESdev spec 校准性（**非"为测试改"**）

**修复内容**（commit `b50e685` `fix(ppu-v2.1.1): NMI dispatch delay`）：

- `src/rust/src/lib.rs` 在 `fceux11_run_frame_interleaved` 的 `take_nmi_direct != 0` 分支中，于 `trigger_nmi` 之前先 grant `nmi_delay_cycles`（默认 8）CPU cycles 的 CPU-only budget
- 单文件 +46/-0，与 C++ engine 老 PPU 在 VBL_NMI dispatch 上的语义对齐

**NESdev wiki `NMI_interrupts` + 6502 timing 章节**（权威 spec）：

- VBL NMI 在 PPU 进入 VBL flag 设置时（sl 241, dot 1）由 PPU 触发
- CPU 在收到 NMI 信号后，需完成当前指令再进入 NMI handler
- 这中间有约 7 cycles 的开销（push PCH, push PCL, push P, fetch vector hi, fetch vector lo, fetch opcode）
- 修复 #1 的 8 CPU cycles grant 模拟了"CPU 还在执行当前指令"的开销

**C++ engine 对照**（`src/ppu_rendering.cpp:1612-1631` `e1_nmi_delay`）：

- C++ engine `X6502_Run(8)` 在 `TriggerNMI()` 之前 grant 8 CPU cycles
- C++ 注释明确"X6502_Run(nd) grants the same CPU budget (1 CPU cycle per 3 dots) with zero PPU advance"
- **单位澄清**：`X6502_Run` 取 CPU cycles；`FCEUX11_E1_NMIDELAY=8` 是 C++ engine hand-tuned magic number，**不是** "8 PPU dots"（C++ `ppu_rendering.cpp:1614` 注释 "Units are PPU dots" 是误导）
- 修复 #1 单 commit 验证（详见 §1.3）：**`blargg_vbl_05_nmi_timing: PASS`**

### 1.2 旧 savestate golden（`cc0c87deb64f695d50d4cf07d8422150`）的形成历史

- 旧 golden 来自 `0f6291c` `test(ppu-v2.1.1): regenerate nestest golden hashes (Do-NOT 三件套第 2 步)`，捕获自 0958848 状态（fix #2 + fix #3）
- 旧 golden 不含 fix #1 的 8-cycle NMI delay
- 修复 #1 grant 8 CPU cycles → CPU 多执行 5-8 条指令 → savestate 捕获的 register state 不同 → MD5 漂移到 `6a10f655d3eb0b15fe263cfc9327f9ba`

**根因定性**：旧 savestate golden 与 fix #1 实现的"NMI dispatch delay 8 CPU cycles"行为**不一致**—— 旧 golden **确实**过时，需按 Do-NOT 第 3 条走 plan 升级。
