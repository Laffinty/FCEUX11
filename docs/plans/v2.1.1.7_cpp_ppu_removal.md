## 0. 摘要

### 0.1 解耦度评估结论（2026-09-10）

Rust PPU **已经驱动了真实运行路径**（frame loop、$2000-$2007 / $4014、open-bus、NMI、DMC DMA、CHR/NT/palette window），但 **C++ PPU 并没有被"移除"**——它被降级为"状态存储 + 旧渲染引擎"的双重身份，**和 Rust PPU 共享一份存储**。这种结构是故意保留的：`FCEUX11_RUST_PPU=OFF` 走 C++ new-PPU（`newppu != 0`），`=ON` 走 Rust PPU，但**两边读写的都是同一份 `PPU[4]` / `NTARAM[0x800]` / `PALRAM` / `SPRAM` / `vnapage[4]` 全局**。

`build-rust-ppu/CMakeCache.txt:366` 确认 `FCEUX11_RUST_PPU:BOOL=ON` 为当前默认与唯一运行路径；`src/CMakeLists.txt:224-230` 把 `ppu.cpp / ppu_rendering.cpp / ppu_state.cpp / ppu_sprite_lut.cpp / pputile_template.cpp / ppu_core.cpp / ppu_class.cpp` **无条件编进 `SRC_CORE`**，与 `FCEUX11_RUST_PPU` 无关——这是 §0.3 "C++ PPU 仍在编译"现状的根因。

### 0.2 Rust PPU FFI 表面盘点

`src/rust/crates/fceux11-ppu/src/ffi.rs` 已实现、覆盖默认 ON build 的全部运行需求：

- **生命周期**：`fceux11_ppu_create` / `destroy` / `emergency_reset`
- **总线 callback vtable**（`fceux11_ppu_bus_callbacks`）：read / write / cpu_read / notify_a12_rising / notify_hblank / notify_hblank2 / notify_scanline / notify_vblank
- **窗口**：`set_chr_window` / `set_nt_window` / `set_palette_window` / `set_mirror_mode`
- **CPU 寄存器**：`cpu_read` / `cpu_write`（含 $4014 OAM DMA）
- **每帧驱动**：`tick_dots` / `tick_dots_direct`（lock-free 热路径）/ `take_nmi_pending` / `take_nmi_direct` / `take_dmc_dma_stall` / `set_current_cpu_cycle` / `check_data_bus_decay` / `refresh_data_bus`
- **调试/状态**：`get_scanline` / `get_dot` / `get_frame_count` / `get_register_state` / `get_v_state` / `get_framebuffer`
- **互斥**：`take_vbl_set_suppressed` / `set_status_vbl_set_suppressed` / `mark_vbl_set_suppressed`

`src/ppu_rust_bridge.h/.cpp` 的 C++ 侧把上述 FFI 包装成 `ppu_rust_bridge_*` 一族，并在 `ppu_rendering.cpp:1207-1256` 的 `FCEUPPU_Loop` 里以 `[[unlikely]]` 形式抢先 short-circuit。**这条 fast path 是默认且唯一的运行路径**。

### 0.4 当前 `FCEUX11_RUST_PPU=OFF` 的实际可达性

**可以 build，但已经是 nobody-home 的兼容壳。**

- `src/CMakeLists.txt:792` 的 `option(FCEUX11_RUST_PPU ... ON)` 是缓存 CMake 选项（AGENTS.md Gotcha 11）；OFF 时 `ppu_rendering.cpp:1208` 的 `#ifdef FCEUX11_RUST_PPU` 让 Rust fast path 被预编译剔除，回退到 `newppu` 旧 PPU 路径
- `scripts/run_matrix.ps1` 把 `build/` 路径写死（plan §0.8 遗留），实际 OFF build 现在只服务于**回归对账**和**新 PPU 引擎 ABC 选型**（`build-ab-cpp/` 之类），不在用户/产品路径上
- v2.1.1 build plan §C 已把"删 C++ PPU 编译分支"作为 Phase C 目标，本 sub-plan 是该段的展开

## 1. 目标与非目标

### 1.1 目标

1. Rust PPU FFI 表面补齐到能完全替代 C++ PPU 的 8 个耦合点对外暴露的能力
2. C++ PPU 编译分支从 `SRC_CORE` 删除；`option(FCEUX11_RUST_PPU)` 改为 configure error（与 `FCEUX11_RUST_CPU=OFF` 同款报错）
3. 共享状态（`PPU[4]` / `NTARAM` / `PALRAM` / `SPRAM` / `vnapage[4]`）显式标注 `BRIDGE-OWNED`，所有权归 `ppu_rust_bridge.cpp`
4. Qt GUI 直读 `PPU[]` / `vnapage` 的 20+ 处全部迁移到 bridge accessor
5. Savestate 字节级兼容（chunk-3 + chunk-31）保持 LTS 契约
6. 全套 gate 重跑：ctest 40/40、kagami-qa Grade ≥ B、batch_compat ≥ 84%、golden_savestate_test 字节级 PASS

### 1.2 非目标

- 不追 batch_compat 90%（维持 ≥84% 锁档承诺口径）
- 不做新功能、不动 APU 架构、不引入新 mapper
- 不为测试改逻辑（NESdev spec 为准）；不重生成 golden 除非按 Phase 5.1 Do-NOT 三件套流程
- 不新建分支（仅 `wip2.1`）
- 不破坏 MSVC-only 与 ABI/savestate 字节级兼容承诺
- 不动 `fceux11-ppu` 的渲染精度（属于 v2.2 Phase 7+ 范围）

### Step B. FFI 表面补齐（5 条新 FFI + cbindgen 头）

#### B.1 Savestate 序列化 FFI

**问题**：`state.cpp:335/594/673` 的 `FCEUPPU_STATEINFO[]` 存的是 C++ PPU 全局（NTARAM / PALRAM / SPRAM / PPU[4] / kook / ppudead / PPUSPL / XOffset / vtoggle / VRAMBuffer / PPUGenLatch），Rust PPU 自己的 `PpuState`（`state.rs`）**没有**走这条 savestate 路径。

**方案选择（owner 拍板）**：

| 方案 | 改动 | 风险 | 锁档兼容 |
|------|------|------|----------|
| **B.1.a**：加 2 条 FFI（`fceux11_ppu_serialize/deserialize`） | 新增 Rust 侧 PpuState 全字段编/解码；C++ 侧 `FCEUPPU_SaveState/LoadState` 改为调 FFI；chunk-3 数据布局从 C++ 全局改为 Rust 序列化 | **高**。SFORMAT 标签（`NTAR` / `PRAM` / `SPRA` / `PPUR` 等）的 LTS 契约**必须按现有位级兼容**——不能加字段、不能重排序 | ✅ 字节级 |
| **B.1.b**：bridge 暴露内部指针（`fceux11_ppu_get_ntaram_ptr` / `fceux11_ppu_get_register_ptr` 等 6 个） | SFORMAT 仍指向 C++ 内存，bridge 是读写代理 | **中**。隐式契约"bridge 拥有这块存储"——任何 owner 错位都破坏 PPU 同步 | ✅ 字节级（指针兼容） |
| **B.1.c**：把 Rust PPU 状态完全编到独立 chunk（如 chunk-32 `RPU1`） | 老 savestate 文件不兼容；需要 v2.1.1.1 / v2.1.1.2 sub-plan 的 savestate regen 配合 | **高**。破坏 ABI | ❌ 字节级破坏 |

**实现**：

- Step C 删 C++ PPU 后第二分支移除

**验收**：
- 跑 blargg mmc3_test_6 / nestest / 003.smb（mmc3 写时序最敏感）
- mapper 写 → PPU 主循环读之间无 ghost scanline

#### B.3 Bank window pointer FFI

**问题**：bridge 当前的 `bridge_refresh_windows` 在每次 `setchr1r/8r` 之后做 `memcpy` 全 8 KiB CHR + 4 KiB NT，性能差且破坏 Rust PPU 内部的"page base pointer"优化（Phase 6.4 dirty 比较失效）。

**实现**：
- `src/rust/crates/fceux11-ppu/src/ffi.rs` 新增：
  - `fceux11_ppu_set_chr_bank(slot: u32, ptr: *const u8, len: u32, is_ram: bool)`
  - `fceux11_ppu_set_nt_bank(page: u32, ptr: *const u8, len: u32)`
- `src/ppu_rust_bridge.cpp` 把 `setchr1r/2r/4r/8r` 的 C++ mapper hook 改为直接调 FFI（**绕开 `bridge_refresh_windows` 的全拷贝**）
