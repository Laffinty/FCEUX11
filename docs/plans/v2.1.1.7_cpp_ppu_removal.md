**两条方向性结论（本 plan 地基，替代一审"两边读写同一份存储"）：**

1. **Rust → C++ 无任何寄存器/OAM 回写**。GUI、mapper、savestate 读到的 `PPU[]`/`SPRAM` 是墓碑值；默认构建下 `PPU[0..3]` 恒为 power 时的 0。这是**既存缺陷**，不是本 plan 引入的。
2. **C++ → Rust 的 NT/CHR 是拷贝而非共享**。(a) GUI 直接写 `vnapage` 不会立刻进入渲染；(b) savestate 载入后 `NTARAM` 已恢复，但 Rust 渲染器仍读旧副本，直到下一次 $2007 写或页指针移动才刷新。

### 0.2 Rust PPU FFI 表面盘点

默认 ON build 的运行需求已全部覆盖（生命周期 / bus vtable / 窗口 / CPU 寄存器 / 每帧驱动 / 调试状态 / VBL 抑制互斥），清单与一审一致。**缺口三条**：

1. **无"整块状态导出/应用"FFI**：`fceux11_ppu_get_register_state` 只能逐字节读，没有任何写回 Rust 的入口 → savestate 载入无法恢复 Rust 状态。
2. Rust 侧**已存在**为这件事准备的机制：`snapshot.rs` 的 `serialize_rpu1`/`deserialize_rpu1`（RPU1 v1，380 B payload）与 `LegacyView`（264 B：`regs[4]`+`oam[256]`+`write_toggle`+`vram_buffer`+2 B pad），但文件头明确写着"**故意不上线（option (a)）**——只有让 RPU1 不上线，才能保证 `golden_savestate_test` 字节同一"。本 plan 必须正面处理该设计约束（D1）。
3. `fceux11_ppu_set_video_system` 存在、scheduler 支持 PAL（106392 dots），但 bridge 在 power 时**硬编码 `false`**（`ppu_rust_bridge.cpp:391`），且没有任何路径在制式变化时通知 Rust（见 §0.6 / D4）。

### 0.6 newppu / PAL / 电影格式：三个未决语义（一审未覆盖）

#### B.3 原方案（bank window 指针 FFI）—— **永久否决（not-do）**

| 维度 | 核查结论 | 证据 |
|------|----------|------|
| 前提 | 不成立。"每次 `setchr1r/8r` 后 memcpy 全 8 KiB"在当前实现里不存在 | `bridge_refresh_window_contents_if_dirty()` 逐页比指针、只拷移动过的 1 KiB 页（`ppu_rust_bridge.cpp:194-212`），由 `bridge_notify_scanline()` 在扫描线转换时调用（`:299-317`） |
| 收益 | 零。Rust 渲染器早已**直接解引用** power 时安装的窗口指针，既不经过 FFI、也不做每帧拷贝，指针共享换不来任何一次更少的内存访问 | `fceux11-ppu/src/ffi.rs:635-660`（`&*(chr_window_ptr as *const [u8; 8192])`）；指针只在 `bridge_refresh_windows()` 安装（`ppu_rust_bridge.cpp:111/133`） |
| 替换对象 | 不存在。`ppu_rust_bridge_set_chr_window/set_nt_window` 全仓仅定义与声明、零调用者（`ppu_rust_bridge.cpp:610-624`、`ppu_rust_bridge.h:98-99`），方案想替换的那条接口是死接口 | 全仓 `rg` 命中 6 处，全为定义/声明 |
| 风险 | 实。① 该刷新点运行在 Rust 调度器回调内、`StateBox` 借用被持有，**禁止**再进 PPU crate FFI（Phase 5.1 修过的借用别名 bug）；② 裸指针指向 mapper bank 缓冲，换 ROM / PowerNES / 银行重绑时会移动甚至释放；③ 指针共享会绕过 `g_bus.set_vpage` 的 `ptr - addr` 编码层 | `ppu_rust_bridge.cpp:176-193`、`:314-317`、`:101-104` |
| 收益上界 | 小。最坏情况（8 页 CHR + 4 页 NT 每扫描线全动）也只有 12 KiB × 241 ≈ 2.8 MiB/帧；真实语料中典型值为 0 页变动 | 静态上界（算术）；无实测反例 |

#### B.3a 替换项：`$2007` 写路径的窗口**全量**重建 —— 成本问题，度量前置

重估发现真正无界的拷贝量不在 bank 切换，而在 **CPU 空间 `$2007` 写**：

| 现象 | 证据 |
|------|------|
| 每次 `$2007` 写都无条件重建 CHR 8 KiB + NT 4 KiB，并重装 3 个窗口指针 + 重推 mirror mode | `ppu_rust_bridge.cpp:734-736` → `bridge_refresh_windows()`（`:99-145`，其中 `:111/133/135` 为三次 `fceux11_ppu_set_*_window`) |
| 重建与写入目标无关：写 `$3Fxx` 调色板、甚至写 CHR-ROM（硬件忽略）都要付全量代价；而 palette 窗口本就走 `PALRAM` 指针直读，**不需要**任何拷贝 | `ppu_rust_bridge.cpp:135`；`fceux11-ppu/src/ffi.rs:653-659` |
| 无脏检测：与扫描线路径不同，该路径没有页级过滤，代价随 `$2007` 写次数线性增长 | 对比 `:194-212` 的页脏检测 |
| 最坏量化：一次 8 KiB CHR-RAM 全量上传 = 4096 次 `$2007` 写 → 现行实现约 **48 MiB** 拷贝 + **16,384** 次 FFI；理论下界 8 MiB + 0 次 FFI | 算术（按现行实现推导）；单次 FFI 含 StateBox 互斥与重入检查 |

**判定**：这是**成本问题、不是正确性问题**（`$2007` 语义与窗口内容均正确，只是重建过宽）。因此**先度量、后改码**，且不阻塞 B.4。
