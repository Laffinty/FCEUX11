## 0. 依据材料分析结论

### 0.1 GitHub CI 失败（依据①，runs 92249102273 / 92249102410，2026-09-06）

两个 job（`build-windows`、`kagami-qa`）失败原因完全一致，均在 v2.1.0 收口代码上复现：

1. **ctest 38/40，2 个失败**：
   - `kagami_qa_direct_smoke`：直接 runner（进程内 C ABI 桥）跑 12 个 blargg 子测试，**3P/9F**。
     FAIL：`blargg_cpu_int_2_nmi_brk`、`blargg_instr_misc`、`blargg_mmc3_4_scanline_timing`、`blargg_mmc3_v2_4_scanline_timing`、`blargg_oam_stress`、`blargg_ppu_read_buffer`、`blargg_ppu_vbl_nmi`、`blargg_sprdma_dmc_dma`、`blargg_vbl_05_nmi_timing`。
     PASS：`blargg_cpu_instrs`、`blargg_cpu_timing`、`blargg_smoke`。
   - `rust_ppu_vbl_nmi_timing_test`：`ppu_vbl_nmi.nes` 子测试 2/10（**02-vbl_set_time**）FAIL，诊断 hash **`933AF95A`** —— 与 v2.1 收尾存档记录的 hash 完全一致（确定性失败，可稳定复现）。
2. **kagami-qa job 的 R4 gate**：47 项迁移矩阵 37P/10F → **Grade D（blocked）**；其中 **PASS→FAIL 回归 2 项**（`blargg_ppu_read_buffer`、`blargg_vbl_05_nmi_timing`，对照冻结基线 `tests/fixtures/kagamiqa_baseline_frozen.json`，2026-08-08 冻结时这两项是 PASS）。
3. **评分规则**（`src/rust/crates/kagami-qa/src/report/grade.rs:77`）：D = 任一 blocking 失败或任一 PASS→FAIL 回归；B = 无 blocking、无回归、剩余失败全部在冻结基线内；A = 全绿。
   - manifest（`tests/tests.json`）中 severity=**blocking** 的恰为那 2 个回归项；其余 7 个 FAIL 均 advisory。
   - **结论：修好 2 个 blocking 回归 → Grade B；ctest 的 `rust_ppu_vbl_nmi_timing_test` 要求 02-vbl_set_time 真实转绿，无法再 defer**（v2.1.0 的 deferred-accepted 路线在 v2.1.1 行不通，CI gate 是硬约束）。

基线事实：冻结基线（2026-08-08）本身含 8 个 FAIL（7 个 blargg 项 + `blargg_suite`），故当前 10F = 基线 8 项 - `blargg_suite`（现 PASS）+ 2 个真回归。v2.1 收尾存档（`docs/history/v2.1_ppu_rust_refactor_plan_2026-09-07_done.md` §6.6.quater.3.5）已确认：NMI/timing drift 家族**不是** NMI delay 或 VBL set dot 的单点问题，4 组 sweep 均失败，当时以"Mesen 校准假设"deferred。v2.1.1 必须换思路真正解决。

**指控核实（本计划制订时逐条在代码库验证）：**

**对报告的批判性修正（存档备查，防止过度采信）：**
- 环境限制如实声明过：SI_NONE 输入不可用，"静止/无画面变化"无法区分真死与等输入；"画面活动 342"不等于可玩。v2.1.1 结论范围仅限其可证明的部分（启动黑屏、单色、崩溃）。
- 报告正文与 CSV 的分类计数有出入（正文 180 黑屏 vs CSV E-no-render 183；正文含 4 个"静止转黑"等），执行时**以 CSV 明细为准**，不引用正文数字做验收。
- 报告称测试对象为"v2.0 源码包"，实际快照含 v2.1 Phase 6/7 的 Rust PPU 默认 ON 代码（引用了 `FCEUX11_RUST_PPU` 与桥接口）；引用行号需在执行时重新核对。
- 两引擎实测帧数不同（legacy 240 帧 / 默认 900 帧），但 no-render 在 900 帧仍为均匀帧，结论方向不受影响。
- **联动信号**：v2.1 收尾的 batch_compat 全量重跑 2879/3451 = 83.4%（-0.6pp），其 572 个 mismatch 中应包含这批渲染缺失 ROM——执行 B2 时先交叉比对 mismatch 清单与 `final_matrix.csv`，可快速缩小嫌疑集。

### 0.3 代码库现状（Phase C 范围盘点）

- **引擎双轨**：`FCEUX11_RUST_PPU` 为缓存 CMake 选项（`src/CMakeLists.txt:792`，默认 ON）。`build/` 缓存残留 OFF（AGENTS.md Gotcha 11 的陷阱）、`build-rust-ppu/` 为 v2.1 收尾标准目录（ON）、`build-ab-cpp/` 为 C++ 回退对照构建。CI 每次全新 configure，取默认 ON。v2.1 计划预留的运行时开关 `FCEUX11_PPU_ENGINE=Cpp` **从未实现**（代码中无此 env），现唯一回退方式是构建期 OFF。
- **C++ PPU 仍在编译**（`src/CMakeLists.txt:224-230`）：`ppu.cpp`（40KB：A2002/A2007/B2000 等寄存器处理器 + PALRAM + PPU 空间规范访问器 + opendecay 探针 + mapper hack 全局量）、`ppu_rendering.cpp`（82KB：旧引擎 + `FCEUPPU_Loop` 派发）、`ppu_class.cpp/h`（`Ppu` 类：ntaram/vnapage/OAM/latch，**被桥和 mapper 共享**）、`ppu_core.cpp`、`ppu_sprite_lut.cpp`、`pputile_template.cpp`、`ppu_state.cpp`（savestate）。
- **桥**（`src/ppu_rust_bridge.cpp`，715 行）：窗口快照复制、扫描线粒度指针脏检测刷新、镜像模式推导、$2000-$2007/$4014 路由、Rust 内逐点交错帧循环（`fceux11_run_frame_interleaved`）、NMI 锁存、DMC DMA 仲裁、open-bus 衰减。Phase C 必须保留其全部职责，仅摘除对 C++ 引擎的依赖。
- **CPU 已无 C++ 实现**（`FCEUX11_RUST_CPU=OFF` 为 configure error）——Phase C 的 PPU 退役向此模式对齐。

## 1. 目标与非目标

### 1.1 目标（按优先序）

1. **Phase A**：GitHub CI 两 job 转绿 —— ctest 40/40，R4 gate Grade **B** 起步（修 2 blocking 回归 + `rust_ppu_vbl_nmi_timing_test`），**冲刺 Grade A**（47/47 全绿）；batch_compat 不低于 83.4% 锁档。
2. **Phase B**：第三方发现的 P0/P1/P2 全部处置完毕 —— UNIF 崩溃清零、渲染缺失根因定位并修复（或给出明确证据链的结论）、头部污染清理扩展、UX 报错；KagamiQA 补上"真实游戏帧哈希"回归盲区。
3. **Phase C**：C++ PPU 完全退役，Rust CPU/PPU 成为唯一实现 —— `FCEUX11_RUST_PPU=OFF` 改为 configure error，删除旧引擎代码与双构建产物，文档/CI/脚本同步。

### 1.2 非目标

- 不追 batch_compat 90%（维持 ≥84% 锁档承诺口径，v2.1.1 底线 83.4%）。
- 不做新功能、不动 APU 架构、不引入新 mapper。
- 不为测试改逻辑（NESdev spec 为准）；不重生成 golden 除非按 Phase 5.1 Do-NOT 三件套流程。
- 不新建分支、不改 MSVC-only 与 ABI/savestate 字节级兼容承诺。

- 产物存 `docs/history/v2.1.1_phase_a_ci_fixes.md`（Phase A 过程记录文档，逐项追加）。

### A.1 修复 2 个 PASS→FAIL 回归（blocking，Grade D 的直接原因）

- 对象：`blargg_ppu_read_buffer`、`blargg_vbl_05_nmi_timing`。
- 手段：以冻结基线 run_id `20260808-022802-1777cc` 对应 commit 为锚，`git bisect` 两项测试（本地 kagami-qa runner 单测该两项，每步 <2 min）。嫌疑区间：2026-08-08 之后合入的 Phase 6.3.a（open-bus 衰减重写）、6.4（CHR 窗口缓存）、Phase 7（退役标记）系列提交。

### A.2 修复 02-vbl_set_time（`rust_ppu_vbl_nmi_timing_test` 转绿的前提）

- 现状：确定性 hash `933AF95A`；v2.1 四组 sweep（NMI delay / A2002 抑制窗口 / VBL set dot / 帧布局对齐）均未能定位，deferred 为"Mesen 校准假设"。
- v2.1.1 新手段（不重复 v2.1 已排除的路径）：
  1. **黄金对照 tracediff**：同一 ROM 分别在 C++ 引擎（`build-ab-cpp/` 产物，Phase C 删除前仍是合法对照）与 Rust 引擎运行，启用 `FCEUX11_PPU_PHASE_TRACE=1` 与 E1 探针，逐指令 diff $2002 读取流 / NMI 断言点 / 帧内 (sl, dot) 序列，找首个分叉点；
  2. 按 NESdev wiki `ppu_frame_timing` 精确核对 Rust 帧循环 pre-render 行（sl -1）dot 1 清 flag、sl 241 dot 1 set flag 的两点时序与 VBL suppress/cancel 窗口的相互作用（v2.1 步骤 1 的抑制窗口修复改变了 read 触发路径，可能引入了新的交互缺陷）；
  3. blargg 测试 2 的测量原理（对齐 T+ 偏移读 flag）反向约束：其期望表即 spec 的可执行形式，直接对着期望表修。
- 此项若根因触及 VBL 家族共性，预期同时改善 A.4 的 `blargg_ppu_vbl_nmi` / `blargg_vbl_05_nmi_timing` / `blargg_cpu_int_2_nmi_brk`。

### A.3 修复 blocking-adjacent advisory（v2.1 显式移交 v2.2 的两项）

### A.4 清扫剩余 advisory

- `blargg_instr_misc`（指令杂项）：先跑单项定位具体子项，判断是否 CPU/PPU 交互类。
- `blargg_mmc3_4_scanline_timing` / `blargg_mmc3_v2_4_scanline_timing`：v2.1 方向 4 候选（A12 rising 等价性）——核对 Rust 调度器 `bridge_notify_a12_rising` 的触发点（dot 256 BG fetch）与 C++ 引擎 `runppu` 热路径的一致性；`bridge_notify_a12_rising` 当前为空实现注释（`ppu_rust_bridge.cpp:258-266`），A12 全靠 C++ 侧遗留路径，属重点怀疑对象。

## 3. Phase B —— 第三方发现批判性研究与修复（任务 2）

> 原则：先核实、后修复；报告仅作线索，一切以本库代码 + NESdev spec + oracle 数据为准（0.2 节核实表为准绳）。

### B.1 P0 —— UNIF 崩溃双缺陷（改动小、收益确定，最先做）

1. `src/rust/crates/fceux11-formats/src/unif.rs`（PRG/CHR 两处）：
   `let idx = (chunk_id[3].wrapping_sub(b'0')) as usize; if idx < 32 { ... }`。
2. `src/cart.cpp:98` `DECLFR(CartBR)`：增加与 `CartBROB` 一致的空页保护（`if (!p) return open-bus/0xFF;`）。
3. 防御：UNIF 加载路径在板卡初始化后校验 `PRGsize[0]==0` → 显式报错拒绝上电（`unif_load.cpp`），杜绝"半加载"状态静默进 Power。
4. 回归测试：**构造合成 UNIF fixture**（测试代码内生成最小 UNIF 文件：MAPR=已实现板卡 + PRG0/CHR0 块），加入 Rust parser 单测 + C++ 加载路径测试；不依赖版权 ROM。验收：`1604/1605/1606_Fast_Contra.nes`（FAILROM 语料）加载不再崩溃、能进帧循环。

### B.2 P0 —— Rust PPU 渲染缺失诊断与修复（本版最大不确定性，投入最大）

1. **复现与最小化**：用第三方 harness（已与黄金基线校准）跑 FAILROM 语料，按"mapper 覆盖面 + 头部干净度"排序取最小复现集：首选 `0226_ICE_CLIMBER_JE.nes`（NROM，无 bank 切换干扰）。同时在 GUI 环境人工复核一次（报告亦建议）。
2. **假设清单（按嫌疑排序）**：
   - H1（时序族）：游戏启动期等待 VBL/NMI 挂死 → 永不使能渲染。若 A.2 的 VBL 根因修复后该类 ROM 成批转好，则同根因，直接闭环；
   - H2（窗口失效盲区）：`bridge_refresh_window_contents_if_dirty` 仅按页基址指针变化重拷内容，"指针不动内容变"（如 mapper 直写 CHR-RAM、同 bank 重映射）不感知；以及窗口快照与 mapper 写的相位差；
   - H3（$2007 刷新路径）：每 $2007 写全量刷新 12KB 窗口（`bridge_refresh_windows`），带宽与时机正确性需对照 C++ 引擎逐帧 diff 验证；
   - H4（mapper 特异）：污染头 mapper（230/249/254/244/176…）与 mapper 4+CHR-RAM（吞食天地系列 28 个干净头 ROM）各自归因——前者多属 B.3 头部清理范畴，后者重点查 CHR-RAM 初始化/呈现。
3. **交叉比对**：batch_compat 572 mismatch 清单 × `final_matrix.csv` E 类 ROM 求交集，缩小嫌疑集后逐个归因。
4. **修复后新增回归**（堵盲区，报告建议采纳）：
