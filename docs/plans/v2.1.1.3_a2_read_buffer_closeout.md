## 2. A.1-2 read_buffer 0x1B=27 现状

### 2.1 修复 #2 进展

`commit ef2ba86` `fix(ppu-v2.1.1): skip v-walk when rendering off` 让 kagami read_buffer 从 **0x80 卡死** 推进到 **0x1B=27**（ROM 验证循环现在能完成 0x1B 步）。剩余 53% 失败归因：

> 引用 523059b commit message 修复 #2: "Now completes (0x1B, remaining failures in the sprite0-hit/DMA phase)."

### 2.2 根因定性（plan §A.3 / §A.4 范围）

- **sprite0 hit 误报**（sprite 0 hit 状态在 sprite 0 OAM 数据未就绪时不应 set）
- **DMA 仲裁**（$4014 OAM DMA 与 DMC fetch 的周期占位；`fceux11_ppu_dmc_dma_arbitration` Phase 6.3.c.2 follow-up 未实现）
- **`$2007` 写时序**（VRAM address increment 在不同 PPU 模式下的差异）

三者可能共根因（VBL 家族的同源 timing 漂移），也可能独立。

### 2.3 父 plan §B.2 联动（rendering-missing 大问题）

> 引用 v2.1.1_build_plan.md §B.2: "183 个 no-render 可能与 02-vbl_set_time 的 VBL 时序漂移同族（游戏在启动期等 VBL/NMI 挂死，永远不使能渲染）。"

若 A.2 VBL 时序根因修复，read_buffer 的剩余 53% 失败可能连带改善。**优先 A.2 修复 → 再评估 read_buffer**。

## 3. v2.1.1.3 修复策略

### 3.1 顺序

```
Step 1: A.2 tracediff 诊断（用 build-ab-cpp/ 对照）
   ↓
Step 2: A.2 修复（按诊断结果，可能是 A2002 抑制窗口 / 帧对齐 / 其他）
   ↓
Step 3: A.2 Do-NOT（如有 golden 变化）—— v2.1.1.3 sub-plan 第 2 步
   ↓
Step 4: A.1-2 read_buffer 复测（看 A.2 修复是否连带改善）
   ↓
Step 5: A.1-2 read_buffer 独立修复（如需要）
   ↓
Step 6: 全量 ctest + kagami matrix 验证
   ↓
Step 7: Phase A 验收 gate 全绿
   ↓
Step 8: tag v2.1.1
```

### 3.2 A.2 诊断细节

1. 在 `build-ab-cpp/` 编译 C++ 引擎产物（`FCEUX11_RUST_PPU=OFF`）
2. 启用 `FCEUX11_PPU_PHASE_TRACE=1` 与 E1 探针（`FCEUX11_E1_TRACE=1`）
3. C++ + Rust 同时跑 `tests/fixtures/blargg/ppu/ppu_vbl_nmi.nes` 30 frames
4. 对比两引擎的 $2002 read 流、NMI 断言点、帧内 (sl, dot) 序列
5. 找首个分叉点（按指令地址或 scanline+dot 坐标）
6. 修 Rust 端对应代码
7. 单 commit 验证（test 33 + test 34 + test 35）

### 3.3 预算

- 诊断：1-2 session
- 修复：1 session
- Do-NOT（如需）：1 session
- 总计：3-4 session

### 3.4 风险

- **高风险**：A.2 4-sweep 失败史 + NESdev spec 与 Mesen 校准的微妙差异
- **缓解**：
  - 单 commit verify 模式（与本次 Phase A 一致）
  - C++ 引擎 tracediff 作为黄金对照
  - 若根因触及 VBL 家族共性，连带改善 A.1-2 read_buffer + A.4 advisory
  - 如仍无法解决，按父 plan §A.5 收尾标准使用 SKIP_RETURN_CODE（需 owner 批准）
