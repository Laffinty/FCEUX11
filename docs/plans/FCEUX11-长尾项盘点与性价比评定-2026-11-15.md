### 0.2 每条必须带什么（新增条目守此）

1. **一句话描述** —— 说清「什么坏了/什么没做」，不是抽象名词。
2. **为什么还没做** —— 区分三种：**外部阻塞**（缺文件/缺工具/缺权威材料）、**已裁决暂缓**、**被更高优先级挤掉**。三种的处置完全不同，不能混写。
3. **影响面** —— 对用户可感什么、对不变式（NES 零回归 / GBA 不阻塞本体）有没有影响。
4. **修复方式** —— 具体到「改哪个文件 / 加什么判据 / 跑哪条命令」，**只读现有档案里已备好的做法**，不重新发明。
5. **验收命令** —— 一条可复制即跑的判据（退出码 + 可观测副作用）。
6. **反向守卫** —— 这条做完后，**什么必须仍然是红的**，防止「为了让门禁变绿而放松判据」。
7. **非目标** —— 明确划出「这条不包含什么」，防止范围蔓延。

### 0.3 评级口径（三档制，不打小数）

- **重要性**：对**用户可感**的影响（崩溃 > 功能不对 > 内部不一致 > 纯记录）。
  另标 ⛔ 是否**阻塞本体发版**（本仓库口径：GBA 永不阻塞本体，见 `AGENTS.md` GBA 不变式）。
- **难度**：工作量 × 前置依赖 × 风险。**前置依赖是硬阻塞时，难度按「解锁后」计**。
- **性价比** = 重要性 ÷ 难度，再扣掉「是否为其它项的前置」（是则加权）。**负**表示做完反而引入风险。

## 三、逐条详述

### LT-09 · 人工验收未闭合（NES 侧 7 项）

**一句话**：v2.0.4 有 7 项**机器判据已过、但缺人证**的条目，CHANGELOG 已如实登记为「人工验收未闭合」。

**为什么还没做**：这些项要么需要**真机硬件**（麦克风吹气、真实键鼠），要么需要**长时压测**（录 10 分钟 AVI），机器跑不出来。

**影响面**：不违反任何不变式（代码已落地且门禁绿）；但**发布说明里挂着一条未闭合项**，对用户是「有些承诺还没验完」。

**修复方式（逐项，验收判据已在计划里备好）**：

| 子项 | 做什么 | 验收判据 |
|---|---|---|
| V11 | 进程 A 存 VRC7 存档 → 进程 B 加载 | 不崩；音色连续（相位不变） |
| V13 | 录 AVI ≥ 10 分钟 | 文件大小/帧数正常、尾部不丢帧、能正常关闭 |
| V15 | movie 回放比对 | 回放与实时推进逐帧一致 |
| V14 | CDL 一致性读数 | `codecount + datacount + undefinedcount == cdloggerdataSize` |
| V7 | profiler 构建下真实点击 `Advanced → Misc Tools → Profiler Report` | 弹出只读对话框、报告有 sum/%total/avg/min/max/calls/func |
| V25 + V22 | 真机 Lua 读值 + 鼠标 | `input.get()` 键名与实物一致；三键 toggle 正确；鼠标双键/中键读数正确 |
| V6 | 真机吹气（Famicom 麦克风） | 按住时 `$4016` bit2 恒为 1、松开为 0 |

**验收命令**：
```powershell
ctest --test-dir build --build-config Release --output-on-failure -LE perf   # 期望 41/41
```

**反向守卫**：**人工验收不得反过来修改 `expected` / `failure_means` / `pass_to_fail`** —— 人工项是**确认**，不是**调判据**。若人工验收发现问题，走新缺陷条目，不在本条里改基线。

**非目标**：不做「人工验收自动化」；V6 的真机吹气不可用脚本替代。

**成本**：本机可做的 4 项约 1 次会话；需业主真机的 3 项需配合。

### LT-10 · 人工验收未闭合（GBA 3 张卡带）

**一句话**：GBA 侧 4 张失败卡带里**只有 FireRed 经业主人工复核确认兼容**，其余 3 张机器判据全过但**人工未确认**。

**为什么还没做**：需要业主手上的实体卡带；且 GBA 线**不阻塞本体发版** ⇒ 优先级天然靠后。

**影响面**：仅 GBA（Alpha 阶段）。**⛔ 不阻塞本体发版**（`AGENTS.md` GBA 不变式 1–2）。

**修复方式**：用已有的 `cartprobe` / 诊断探针跑出读数（哪张卡、卡在哪个 PC、踩了哪些未实现 SWI、有无 panic），
**进仓库的是夹具读数，不是卡带读数**（沿用 v2.0.3 计划 S4 的纪律）；再由业主肉眼确认画面与音效。

**验收命令**：
```powershell
# 夹具与守卫在 Rust 侧；基线跑法（与 v2.0.3 线同款）
cargo test -p gba-core --lib
cargo test -p f11qa --lib
```

**反向守卫**：**不得**因为「人工看起来没问题」就把 GBA 的**兜底语义**（未实现 SWI 返回并记录）改成「已实现」——
`swi_unimpl_1a` 这条锁**故意**钉住「不实现」，别动它。

**非目标**：不追求这三张卡的画面与真机完全一致；只要「不崩、不卡、能出画面」+ 人工确认。

**成本**：低（探针已就绪，业主侧几分钟）。

### LT-03 · V12：3GO.nes 的 CRC 矫正条目 —— ✅ **已闭合（实测证伪前提：不需要矫正条目）**

**一句话**：本条的前提（「加一条 CRC 矫正条目 ⇒ 3GO.nes 就能正常显示」）**被实测证伪**；
**能正常跑的那份 dump 头部本来就是对的 ⇒ 一条条目都不需要加**。

**实测结论（2026-11-15，业主提供两份 dump + 桌面 ROM 库内两份同源文件）**：

| dump | 大小 | 头部（按本仓 `ines.rs:552/573/580` 位语义） | 本仓口径 CRC | 实跑结果（FCEUX11 v2.0.4 发布包） |
|---|---|---|---|---|
| **A（可用）** | 262,160 B | mapper **19** / 垂直 / 电池 | `0xE64B8975` | ✅ **画面正常**（日文竖排剧情页） |
| **B（上游 issue 那份）** | 393,232 B | mapper **252** / 垂直 / 电池 | `0xBE1713C7` | ❌ **纯蓝屏**：5/10/20/40/70 秒连拍 9 张快照 **MD5 全同**（145 秒一帧未变）；Mesen 里为红白乱码 |

- 两个 dump 的 **PRG+CHR 逐字节不同**（128K vs 256K PRG）⇒ **是两款板，不是同一款的两个头**；
  dump B 与上游 issue 附件 `roms/3GO.nes` 的 PRG+CHR **逐字节相同**（393,216 B 零差异），
  只有 16 字节 iNES 头不同（上游那份 `flags6=0x03/flags7=0x00` ⇒ mapper 0，错误）。
- dump B 在 FCEUX 与 Mesen **都**跑不出画面；本仓 `src/boards/252.cpp` 与上游 2.7.0
  **除 RAII 移植差异外逐行等价**（`MapIRQHook` → `g_cpu.set_map_irq_hook`）⇒ 不是本仓少实现。
  ⇒ 与 loong2snow 的判断一致（该份是 **SMYNES 专用版**，「no standard emulator can run these encrypted ROMs」）。
- ⇒ **mapper 0 → 252 的矫正条目救不回这份 ROM**：mapper 0 时是「乱码」，mapper 252 时是「蓝屏」；
  加条目只会把一种坏画面换成另一种。**上游 issue 的真正原因不是「缺一条表项」。**

**三处坐标更正（本条原文有错，照做会白做）**：
1. **矫正表的活表在 Rust**：`src/rust/crates/fceux11-formats/src/ines/ines_data.rs:1055-2336`
   `ROM_CORRECTIONS`（实测 **256 条**，结构 `{crc32, mapper, mirror}`）；
   `src/ines-correct.h`（278 条）**全仓无 include ＝ 死表** ⇒ 原文「在 `src/ines-correct.h` 加条目」**不生效**。
2. **查表键口径**：`CRC32(padded(PRG) ‖ CHR)`，**不含 16 字节 iNES 头**（`ines.rs:759-781 feed_padded`）。
   原文引用的 `0xF3C85DC3` 是**整文件 CRC**（= 上游 issue 附件那份的整文件值）⇒ **不是查表键**，
   照抄必然查不中（表现为「以为修好了、其实没生效」）。本条两枚真键是 `0xE64B8975` / `0xBE1713C7`，
   手算值与模拟器加载日志逐字一致（`ROM CRC32: 0xbe1713c7`）。
3. **电池位不由矫正表管**：`RomCorrection` 只有 `crc32/mapper/mirror`；电池位走
   `SAVIE_WHITELIST`（按 partial MD5）。本条两份 dump 的头部**本来就带电池位** ⇒ 无需处理。

**影响面**：**已消除** —— 用户手上若拿到 dump A（mapper 19），现有 v2.0.4 直接正常显示；
若拿到 dump B，任何模拟器都跑不出画面（属上游问题，不属本仓缺陷）。

**验收命令（已执行）**：
```powershell
# 加载日志（本仓口径 CRC 与 mapper 取自真实加载器输出）
#   PRG ROM: 8 x 16KiB = 128 KiB / ROM CRC32: 0xe64b8975 / Mapper #: 19 / Namcot 106
#   PRG ROM: 16 x 16KiB = 256 KiB / ROM CRC32: 0xbe1713c7 / Mapper #: 252 / SAN GUO ZHI PIRATE
# 活表未新增任何条目（保持 256 条），两个键均保持零命中：
Select-String -Path src\rust\crates\fceux11-formats\src\ines\ines_data.rs -Pattern 'BE1713C7|E64B8975|F3C85DC3'   # 期望：无命中
```

**反向守卫**：`0xF3C85DC3` 继续**保持查不中**（口径反证锚点）；
**不得**为「让上游 issue 的 dump 至少能装载」而加 `0xBE1713C7 → 252` 条目（画面仍是蓝屏，属无效变更）；
矫正表**只加不改**既有条目。

**非目标**：不实现 SMYNES 加密 ROM 的解密（上游明确无人实现）；不改 dump A（它已经是对的）；
不重算其它卡的 CRC；不重新钉冻结基线。

**成本**：0（**无代码改动**；结论由实测得出）。

### LT-04 · V5：PGO 一组可复现读数

**一句话**：PGO（profile-guided optimization）在本仓**从未被评估过**，开关现成但没有读数。

**为什么还没做**：业主 r16 裁决 **defer 转长尾**；**重启条件 = 训练 ROM 到位**（SMB3 / Akumajou / Zelda）。
⇒ ✅ **2026-11-15：条件已满足**（业主桌面 `roms\` 库内三张都有，副本已存 `Research_only/w204/pgo_train/`）。

**影响面**：只影响**性能**，不影响精度。且已有旁证表明收益上限可能很低 —— V8 的 A7 实验读数
（S1 nestest −0.67% / S2 `instr_v5_all` +1.32%，**方向相反、±1.3% 属噪声**）
说明本代模拟器的热点未必在 dispatch 路径。

**修复方式（只取证，不改代码）**：
1. `cmake -DFCEUX11_PGO=ON` 构建（`CMakeLists.txt:96-119`，Phase 1 `/GENPROFILE`）；
2. 跑训练场景（SMB3 / Akumajou / Zelda）；
3. `cmake -DFCEUX11_PGO_USE=ON` 重建（Phase 2 `/USEPROFILE`）；
4. 产出**基准表**：训练场景 + 构建命令 + 前后读数 + 结论。

**⚠️ 本轮实测出来的操作事实（照做才不会踩空）**：
- **Phase-1 插桩树已存在**：`build-pgo\src\Release\fceux11.exe`（00:24 产物，8.7 MB）；
  缓存 `FCEUX11_PGO=ON` / `FCEUX11_PGO_USE=OFF`，生成器 **Visual Studio 18 2026**。
  ⇒ 现有 `.pgc`（6 个，全在 `build-pgo\tests\Release\`）是**跑测试套件**产生的，
  **不是训练场景** ⇒ 不足以支撑收益结论。
- **插桩 exe 必须带 `pgort140.DLL`**（MSVC 的 PGO 运行时，静态 CRT 版）：
  位置 `VC\Tools\MSVC\<ver>\bin\HostX64\x64\pgort140.dll`；缺失时 exe 直接

- **同生成器基线**：读数必须用**同一生成器**的两棵树对比（`build-pgo-base` = VS 18 / Release / 无 PGO），
  否则 Ninja 树（`build\`）与 VS 树混比不干净。

**非目标**：不动 Step Over 的交互语义。

**成本**：中。

### LT-11 · BIOS SWI 声音家族 12 号 + `0x2A`

**一句话**：GBA 的 BIOS 声音相关 SWI（`0x1A`–`0x1E` / `0x20`–`0x24` / `0x28` / `0x29`）与 `0x2A`
**维持兜底**（返回 + 记录，未实现）；`0x2A` 的 36 项函数表 **GBATEK 零记载 ⇒ 已 BLOCKED**。

**为什么还没做**：① 声音家族需逐条按 GBATEK 取证 + 参照实现背书，工作量大；
② `0x2A` **没有权威材料** ⇒ 认领成 no-op 会违背「未实现必须可见」纪律；
③ GBA 线**不阻塞本体发版**（`AGENTS.md` 不变式 1–2）。

**影响面**：仅 GBA 音频（部分音乐/音效依赖这些 SWI 的游戏可能无声音或表现不对）；
**⛔ 不阻塞本体**。

**修复方式（若启动）**：
1. 逐号取 GBATEK 权威格式（**不凭记忆写位级格式** —— 仓库纪律 4，本项目已因此翻车两次）；
2. 与参照实现只做**格式比对，不抄代码**（外部参考实现只读不抄，仓库纪律 4）；
3. 实现 + 锁测试（断言「返回值逐字等于 GBATEK 公布的向量」）；
4. `0x2A` 保持 BLOCKED，**不认领**。

**验收命令**：
```powershell
cargo test -p gba-core --lib
cargo test -p f11qa --lib
```

**反向守卫**：`swi_unimpl_1a` 这条锁**故意**钉住「`0x1A` 不实现」——实现 `0x1A` 时**必须同时改写这条锁**
（不是删掉它）；生产侧的 `note_unimplemented_swi` 计数口径不得为了让读数好看而改。

**非目标**：不实现 `0x2A`；不做 GBA 音频的整体精度宣称。

**成本**：高（取证密集）。

### LT-12 · BIOS SWI `0x26` HardReset 结构障碍

**一句话**：`0x26`（HardReset）**结构障碍挂起** —— 它会重置整个系统状态，与「正在执行的脚本上下文」冲突。

**为什么还没做**：结构性冲突（不是缺代码，是语义上做不了），且 GBA 侧价值低。

**影响面**：仅 GBA（用 `0x26` 的游戏会表现异常）；**⛔ 不阻塞本体**。

**修复方式**：需先定义「脚本上下文中 HardReset 后如何续跑」的语义，再谈实现 —— 属**设计问题**。

**验收命令**：`cargo test -p gba-core --lib`

**反向守卫**：在语义未定义前**不得**实现为「近似行为」（宁可保持兜底可见）。

**非目标**：不为此改脚本引擎的 yield 语义。

**成本**：中高（设计 + 实现）。

### LT-13 · GBA GPIO / RTC

**一句话**：GBA 的 GPIO 与 RTC（实时时钟）**未做**。

**为什么还没做**：需按 GBATEK 取证并建模硬件行为；GBA 仍是 Alpha，**长期不阻塞本体发版**。

**影响面**：仅依赖 RTC/GPIO 的少数 GBA 游戏/外设；**⛔ 不阻塞本体**。

**修复方式**：取证基线见 v2.0.3 计划**附录 A.6（GPIO/RTC）**（GBATEK 快照，**不凭记忆写**）⇒

**验收命令**：
```powershell
cargo test -p gba-core --lib
```

**反向守卫**：未取证的功能**不得**用「看起来合理」的默认值实现（仓库纪律 4：外部材料取不到就**停下来记录**，不要写）。

**非目标**：不做 RTC 电池/掉电语义；不追求与真机毫秒级一致。

**成本**：中高。

### LT-14 · FireRed 的 init 竞态根因

**一句话**：《宝可梦 火红》的 init **时序竞争**（入口 `0x030000C0` 锁 + `0x03000060` 队列 + flusher `0x08000A18`）
**根因未解** —— 现在是**越过**了它，不是修好了它。

**为什么还没做**：属 GBA 精度范畴；r19 的实证结论是「BIOS 侧 `0x01` 强制空白写入」是让该竞争被**确定性越过**
的触发点 ⇒ **绕过方案已生效**，深挖根因的边际收益下降。

**影响面**：仅 GBA；当前机器判据「出画面」达成、业主 2026-11-12 人工复核确认兼容。

**修复方式（若启动）**：建**影子 apply 链**的精确模型（初始化写 → 影子寄存器 → apply 时序），
并对游戏自身 init 顺序建模；产出可复现夹具。

**验收命令**：
```powershell
cargo test -p gba-core --lib
```

**反向守卫**：⚠️ **`0x01` RegisterRamReset 的强制空白写入不得回退** ——
摘掉它会立即回到 FROZEN（r19 实测逐字同 pre-r17）。**这条是硬红线。**

**非目标**：不做「FireRed 之外的一般化 init 竞争框架」（除非出现第二个同因案例）。

**成本**：高。

### LT-15 · GBA DMA 剩余两项机制 RE（DISPLAY START / PRIORITY）

**一句话**：DMA 的两个失败面仍未做 —— `DMA DISPLAY START`（timing=3 的「显示开始」触发，
本核只实现了立即/VBlank/HBlank 三种）与 `DMA PRIORITY`（多通道同时请求的仲裁序）。

**为什么还没做**：两者**各需自己的 RE**（触发条件 + 判卷标准），不能借 P1 逐单元计时的结论顺带结案。

**影响面**：仅 GBA DMA 触发模式覆盖度；**⛔ 不阻塞本体**。

**修复方式**：沿用 P1 的做法（`ags_aging` 反编译仓 → 解出判卷标准 → 再动实现），
**先解码判卷标准再写实现**（r30 教训：判卷标准没解就改实现 = 白做）。

**验收命令**：
```powershell
cargo test -p gba-core --lib
```

**反向守卫**：AGS 判卷标准必须**逐项**取证，不接受「看起来像」；DMA 触发模式的实现不得**顺手改**
P1 已验收的逐单元计时（MEMORY 9/9 是硬基线）。

**非目标**：不重开 P1 逐单元计费（已验收关闭）。

**成本**：高。

### LT-16 · `start_delay = 2` 的独立来源取证

**一句话**：定时器启动延迟 `start_delay = 2` 虽已被**三个独立 AGS 测试**共同约束，
但它仍是**以 AGS 为准绳的标定值** —— 需要一个**独立于 AGS** 的来源才能摆脱「拟合」性质。

**为什么还没做**：纯取证待办，**不阻塞任何 Phase**，故长期挂着。

**影响面**：仅 GBA 定时器语义的可信度（实现本身已被三个 AGS 测试约束）。

**修复方式**：从 GBATEK 的 **TMxCNT_H 写入时序说明**取源；或引入**第二套参照实现**交叉验证。

**验收命令**：
```powershell
cargo test -p gba-core --lib
```

**反向守卫**：**AGS 三个测试的期望值不得为了让新来源「看起来一致」而调整**；
若新来源与 AGS 冲突 ⇒ 记为**待裁决**，不做静默取舍。

**非目标**：不因此改写定时器实现（除非新来源给出**不同**且可裁决的结论）。

**成本**：中（纯取证）。

### LT-17 · 计划外 E：SFORMAT 短标签的定长 `memcpy` 越界（**上游继承缺陷，已修**）

**一句话**：`AddExState()` 把 SFORMAT 的 `desc`（标签）**定长拷 4 字节**，而板子可以用
**1~2 字符的短标签**（本仓：`supervision.cpp` 的 `"L1"`/`"L2"`）⇒ 字面量只有 3 字节 ⇒ **读穿 1 字节**。

**怎么发现的**：2026-11-15 重建 `build-asan` 后跑门禁 ⇒ `mapper_byte_diff_rust_smoke` 报
```
ERROR: AddressSanitizer: global-buffer-overflow  READ of size 4
  #1 AddExState(void*, unsigned int, int, char const*)   src/state.cpp:926
  #2 Supervision16_Init(CartInfo*)                      src/boards/supervision.cpp:87
  #3 iNES_Init(int)                                     src/ines_init.cpp:78
0x... is located 0 bytes after global variable 'L1' defined in 'supervision.cpp:27:13' of size 3
```
⇒ **此前没人跑过这条验收**：`build-asan` 的产物停在 **2026-11-14 14:39**（V10 修复提交是 16:48），
ASan 门禁自那以后**没有被真正执行过** ⇒ 缺陷被"过期的绿"掩盖。

**上游同款**：FCEUX 2.7.0 `src/state.cpp:907` 是同一行 `memcpy(tmp,sf->desc,4)`，
`src/boards/supervision.cpp` 也是同一对 `"L1"/"L2"` ⇒ **上游同款缺陷**（上游没有 ASan 门禁遮它）。
本仓只有这 2 个 ≤2 字符标签会触发（3 字符标签含 NUL 正好 4 字节 ⇒ 安全；1 字符会越 2 字节）。

**修法（已落地，2026-11-15）**：`src/state.cpp` 的 `AddExState` 改为**按实际长度拷贝**：
```cpp
char tmp[5] = {0};
size_t tag_len = 0;
while (tag_len < 4 && sf->desc[tag_len] != '\0') tag_len++;
memcpy(tmp, sf->desc, tag_len);
```
⇒ **4 字符标签逐字不变**（`"CHRR"` 仍为 `"CHRR"`）；短标签不再越界。
⚠️ `tmp` 只用于「重名检测」的 map 键，**不参与存档块名** ⇒ **不改存档格式**、不需要版本迁移说明；
但它顺带修掉了一个潜在假阳性（两个不同短标签若越读到同一字节 ⇒ 曾可能被判成"重名"并 `exit(0)`）。

**验收命令**：
```powershell
# ASan 门禁（重建后）：41/41 全绿；修复前是 40/41（mapper_byte_diff_rust_smoke 失败）
ctest --test-dir build-asan --build-config RelWithDebInfo --output-on-failure -LE perf
# 常规门禁不受影响（越界只读 1 字节，非 ASan 构建不报错）
ctest --test-dir build --build-config Release --output-on-failure -LE perf
```

**反向守卫**：**不得**把 `desc` 改回定长 4 字节拷贝；**不得**为了「和上游逐字一致」把短标签改写成
4 字符（那会**改存档块名** ⇒ 存档格式变更 ⇒ 需要版本迁移说明）；
**不得**用「非 ASan 构建下不报错」当作该缺陷已修的证据（越界在普通构建里是静默的）。

**非目标**：不改上游；不改各板子的标签命名；不追 `1` 字符标签（本仓没有）。

**成本**：低（一处 3 行改动 + ASan 门禁复跑）。
