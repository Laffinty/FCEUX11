# FCEUX11 v2.1.2 sub-plan - MMC3 IRQ 时钟、渲染门控与 IRQ 行回写

- 记录时间：2026-09-12
- 触发：owner 实测 KIRA.nes（mapper 4 / MMC3，256 KiB PRG + 256 KiB CHR + 8 KiB 电池存档，NTSC）
- 症状：首屏整体发白、只见轮廓、声音正常、无法进入下一屏
- 目标：修复 Rust PPU 在渲染关闭期间仍然驱动 MMC3 扫描线计数器的问题
- 范围：Rust PPU 调度器（主改动）、bridge 死代码注释、新增 Rust 单测；不改 C++ mapper 逻辑
## 1. 实测证据（2026-09-12，build-rust-ppu Release）

- ROM：mapper 4，256 KiB PRG + 256 KiB CHR + 8 KiB 电池 NVRAM，NTSC；IRQ 向量 = 0xF8DF，NMI = 0xFEB0。
- 帧缓冲直方图：帧 120 时 96.5% 的像素是调色板索引 0x20（白，backdrop），其余约 1900 像素为彩色（只有精灵/零散图形）。
- 帧 400 之后整屏只剩 backdrop（索引 0x0F = 黑），且帧 CRC 从帧 400 到 1800 完全不变（冻结 30 秒）。
- 同期 PPU 状态是正常的：命名表 960 格里 528 格有 tile，256 个被引用 tile 中 230 个在 CHR 有图案数据，调色板已写入。
- PC 采样（batch_compat last_pc）：
- 帧 400：Rust 0xFA60 / C++ 0xFE9C
- 帧 500：Rust 0xFA4E / C++ 0xFE9C
- 帧 600：Rust 0xFA4B / C++ 0xFE9C
- 帧 700：Rust 0xFA66 / C++ 0xFE9C
- 帧 800：Rust 0xFA74 / C++ 0xFE9A

0xF8DF 是该 ROM 的 IRQ 入口，0xFA49 到 0xFA74 全落在 IRQ 处理程序内：Rust 构建的 CPU 从约帧 400 起被 IRQ 风暴困住，主循环（0xFE8F 处的 JSR 等帧循环）再也不执行；C++ 构建则停在等帧循环 0xFE9A / 0xFE9C（正常）。

## 2. 根因

Rust 调度器在每个可见扫描线 dot 256 无条件触发 mapper IRQ 时钟（src/rust/crates/fceux11-ppu/src/scheduler.rs 的 tick_one_ppu_dot）：扫描线在 0..239 且 dot 等于 256 时调 bus.notify_hblank()，没有 rendering_enabled() 门控。

notify_hblank 经 bridge_notify_hblank 调到 GameHBIRQHook（即 mmc3.cpp 的 MMC3_hb 到 ClockMMC3Counter），因此渲染关闭时计数器仍按每帧约 240 次前进。

同一 tick 里的 A12 钩子反倒有 rendering_enabled() 门控，但它在 C++ 侧是死代码：ppu_rust_bridge.cpp 的 bridge_notify_a12_rising() 是空函数，注释还写着由已被 Step C 删除的 C++ new PPU 驱动。

后果：游戏切屏时关闭渲染，期望 MMC3 计数器停走；Rust 引擎下计数器继续走并不断触发 IRQ，IRQ 处理程序饿死主循环，游戏永远走不到重新打开渲染的那一步，画面停在 backdrop（先白后黑）。

## 3. 权威参照

1. 本仓库自己的 C++ 参照实现（字节级对齐的基准）：git show 8f9e69c$1:src/ppu_rendering.cpp，约 2136 到 2152 行，MMC3 计数器的唯一调用点带三重门控：pattern table 选择不等于 0x18、精灵槽 s 等于 2、以及 PPUON（渲染开启）。注释明确写 MMC3 计数基于 PPU A12 上升沿，并列出 Crystalis / Kirby / SMB3 的相位调校与 Dragon Lair (Europe) 的 PPUON 特例。
2. Mesen2（公认精度参照）：Core/NES/Mappers/A12Watcher.h 用 VRAM 地址变化跟踪 A12，只有 A12 低电平持续超过 minDelay（MMC3 用 10 个 dot）才判为 Rise；Core/NES/Mappers/Nintendo/MMC3.h 的 IsA12RisingEdge 要求 A12 低电平持续至少 3 个 master clock，并在 Rise 时重载/递减计数器、计到 0 且 IRQ 使能时触发；同时区分 MMC3 RevA / RevB 语义。
3. NESdev wiki 的 MMC3 页面在本环境被 Cloudflare 拦截（与 docs/history/v2.1.1.7_cpp_ppu_removal_archived_2026-09-12.md 的 B.5 D4.1 记录一致），上述规则由 1 和 2 交叉核验。

## 4. 修复设计（分批）

### 批次 1（本 plan 主修，最小且与参照一致）

- Rust 调度器：把 mapper IRQ 时钟的门控补齐，与 C++ 参照一致：仅当该扫描线渲染开启（rendering_enabled）、且 PPU 控制寄存器的 bit3 与 bit4 不同时为 0（对应参照的 PPU[0] 0x38 不等于 0x18）、且处于可见扫描线的精灵取样槽时才触发。
- 保持单一时钟路径（notify_hblank 到 GameHBIRQHook），避免同一扫描线被计两次。
- 把 bridge_notify_a12_rising() 的死代码注释改为明确说明：A12 硬件级检测尚未接入，当前由门控后的 hblank 路径代行。
- 新增 Rust 单测：渲染关闭时不得触发 mapper IRQ 时钟；渲染开启时每个可见扫描线恰好一次。

### 批次 2（保真度，可选，独立提交）

- 把时钟相位从 dot 256 移到参照的精灵取样槽（s 等于 2 附近），并用真实 A12 watcher（低电平过滤）替换近似门控，接通 notify_a12_rising。
- 以 SMB3 / Crystalis 类 ROM 与既有 byte-diff / frame-diff gate 验证，单独成批以便定位。

### 批次 3（回归固化）

- 新增 gate：载入一个 MMC3 ROM 跑 600 帧，断言 PC 不会连续多帧停留在 IRQ 处理程序区间，且帧 CRC 随时间变化（不冻结）。KIRA.nes 属于 owner 私有 ROM，不进仓库，只作本地人工复现。

## 6. 风险与回滚

- 风险：某些 MMC3 变体在渲染关闭时确实依赖计数（罕见）。缓解：门控完全照抄本仓库 C++ 参照实现；byte-diff 与 frame-diff gate 全量回归。
- 回滚：改动集中在 scheduler.rs 一处门控加减，revert 单 commit 即可恢复；不涉及 savestate 布局。

## 7. 不在范围

- VRC 系列的 GameHBIRQHook2 路径（本次只改可见扫描线的 MMC3 通路；如需一并对齐另开批次）。

## 9. 新的决定性证据（2026-09-12，修复后实测）

- 帧 600：PPU 掩码寄存器镜像 = 0x1E（BG 与精灵都开启，无灰度或强调位），控制寄存器 = 0x88（NMI 开，BG pattern table 取 0x1000）。渲染确实是开着的。
- 同一帧：权威命名表 960 格中 528 格有 tile，被引用 tile 里 230/256 在 CHR 有图案数据，调色板正常。
- 但渲染结果是整屏单一颜色（backdrop），且长时间不变。
- 结论：渲染开关与权威数据都没问题，问题在渲染器看到的那份数据上，即 C++ 到 Rust 的 CHR/NT 窗口副本没有被及时刷新。首要嫌疑是 ppu_rust_bridge.cpp 的 bridge_refresh_window_contents_if_dirty()：它只用页指针是否移动来判断脏，而命名表内容是在固定地址上原地改写的，指针不动就永远不重新拷贝；完整拷贝 bridge_refresh_windows() 目前只在 CPU 的 2007 写路径调用。

## 12. 求证结论与修订后的方向

1. 批次 1 的门控与上游 FCEUX 一致：旧 PPU 路径用 ScreenON 或 SpriteON 加 pattern-table 条件，新 PPU 路径用 s 等于 2 加 PPUON。它是补齐 Rust 侧漏掉的门控，不是把旧代码覆盖到新实现；但它不是 KIRA 的根因。
2. KIRA 的故障面在显示数据链而不是 MMC3：实测渲染开着（掩码 0x1E）、权威命名表与 CHR 数据完整、调色板正确，渲染结果却只有 backdrop。

3. 修订后的定位顺序（每步都能得出可判定结论）：
 - 第 1 步：把 Rust 渲染器引用的 g_nt_window 与 g_chr_window 在同一帧导出，与权威 NTARAM 和 CHR 逐字节比对。不一致则问题在 bridge 的窗口刷新契约；一致则进入第 2 步。
 - 第 2 步：比对 C++ 与 Rust 的镜像模式与 NT 页映射（bridge_derive_mirror_mode 与 Rust set_mirror_mode 的同步时机）。映射不一致会让渲染器读到同一个 4KB 副本里的空白页。
 - 第 3 步：前两步都正常时，再查 Rust 渲染器的取 tile 与取 pattern 路径（rendering.rs 的 nt_window 与 chr_window 索引、pattern-table 选择）。
4. 修复落在 bridge 与 Rust 新模块（窗口刷新契约、镜像模式推送、渲染取址），不回退也不复制 C++ PPU 的实现体。
5. 验收：KIRA 帧 400 之后帧 CRC 必须变化且能进入下一屏；全量 ctest 41 项保持 40 PASS / 1 SKIP / 0 FAIL；kagami 矩阵保持 Grade B 且无新增 PASS 到 FAIL。


## 13. 根因定位与修复（2026-09-12，batch 2：IRQ 行回写覆盖）

batch 1（`5186cc8`）与 `c302cfc` 都不是 KIRA 的真正根因。本批次定位到 Rust FFI 的整块寄存器回写会覆盖 C++ 侧在本次 run 中间写入的 IRQ 行状态。

### 13.1 决定性证据链（全部为实测）

1. 逐帧 IRQlow 时序（`kagami_qa_cycle_trace`，每帧记录一次 `Cpu::run` 边界的 `IRQlow`）：
   - 帧 0-367：只有 0x000 / 0x080(NMI) / 首帧 0x020(RESET)；
   - 帧 368 起变成 0x001（FCEU_IQEXT）并永久保持，PC 从主循环 0xFECD 跳进 IRQ 处理程序区 0xFA5A-0xFA76。
2. MMC3 探针（`FCEUX11_MMC3_PROBE=1`）：游戏在帧 360 写 `C000`=0x80（latch）、`C001`（reload）、`E001`（IRQ enable，共 3 次）；扫描线 128 触发 `CLOCK_IRQ`（IRQa=1），紧接着一条 `IRQWRITE addr=E000`（应答 ack）。
   → MMC3 侧完全正常：中断被正确使能、正确触发、正确处理程序应答。
3. 于是只剩一种解释：应答导致的 `X6502_IRQEnd(FCEU_IQEXT)`（清零）在本次 CPU run 结束时的整块回写中被旧快照覆盖，下一帧又看到 0x001，处理程序无限重入 → 画面冻结。
4. 根因代码（src/rust/crates/fceux11-core/src/cpu/ffi.rs，三个 run 入口）：整个 blob 用「调用开始时的快照 + 本调用内 Rust 的改动」整块写回 C++ 共享内存，而 irq_low 是 C++ 侧拥有、并且会在一次调用中间被 mapper/APU 改写的字段（X6502_IRQBegin/End 直接写这块 blob）。

### 13.2 修复（全部落在 Rust/bridge 新代码，未回退 C++ 旧实现）

- `bus.rs`：新增 `RUST_MANAGED_IRQ_BITS`（RESET / NMI2 / NMI / TEMP）与 `merge_post_run_irq_low(host_now, rust_now)`：host 拥有的 mapper/APU 线位（EXTERNAL / EXTERNAL2 / DPCM / FRAME）一律取 host 当前值；只有 Rust 调度器自己管理的位取自 Rust。
- `ffi.rs`：三处整块回写改为 `store_post_run_regs()`，按上述合并语义写回。
- 新增两个 Rust 单测：
  - `post_run_irq_merge_takes_each_bit_from_its_owner`：位归属；
  - `run_writeback_keeps_host_irq_acknowledge`：端到端模拟 `STA E000` 式应答必须活过回写（反向验证时该测试以 left: 1 right: 0 失败，正是 KIRA 症状）。

### 13.3 KIRA 复现验证（修复后，Release / build-rust-ppu）

- 420 帧内 `irq_low` 不再出现 0x001（只有 0 / 0x080 / 首帧 0x020）；帧 368 之后 PC 从 0xFA5A 区回到主循环 0xFECD / 0xFED0。
- `fceux11_batch_compat_test KIRA.nes --frames 600`：PASS（pc_stuck=false，last_pc=0xE05B，video_active=true，frames_blank=2）。
- 逐帧像素金标准（`ppu_frame_diff_test` 的 5 个 ROM）与帧哈希（`rom_regression` / `mapper_byte_diff` 的 12 个 ROM）在修复前后完全一致：该修复不改变任何已验证 ROM 的渲染与执行结果。

### 13.4 基准再生成（差异只有 `IQLB`）
- 用 `fceux11_golden_savestate_test` 的布局对比模式：7 份 golden 与当前实现的差异只在 `IQLB` 字段（intra-field 偏移 9）：旧 0x00000000 变成新 0x00000200。
- 0x200 = `FCEU_IQFCOUNT`（APU 帧中断线）：C++ `sound.cpp` 的 `FrameIRQEnd()` 在 mode 0 下会持续重新置位该线，只有 CPU 读 `4015` 才清零，因此帧边界上它本来就应当保持置位；旧的 0 值正是被整块回写吞掉的产物。
- 按仓库既有做法（b75aa42 / 6057e8d / 26fa8a7 均有 golden regeneration 先例）重生成：`tests/fixtures/golden` 下 7 份 .fc0、`golden_index.json`、`tests/fixtures/golden_savestate_hashes.json`。
- 验收：全量 ctest 41 项 = 40 PASS / 1 SKIP / 0 FAIL；`cargo test -p fceux11-core --lib` 94/94。

### 13.5 结论与后续

- KIRA 的冻结（画面整体发白、只见轮廓、有声、无法进入下一屏）由本批次修复：IRQ 应答不再被回写覆盖，中断风暴消失，主循环恢复。
- 首屏观感（是否仍显发白）需在桌面环境复核；渲染管线本身由像素金标准与帧哈希全部守住。
- 本批次不涉及 MMC3 时钟门控（batch 1）与 savestate 布局；两者保持不变。

## 14. 渲染根因修复（2026-09-13，batch 3：dot 257 应为水平复制）

owner 实测：IRQ 修复后游戏可正常玩且流畅，但几乎所有游戏画面异常（花屏/只见噪点）。本批次定位到 Rust 帧驱动器的 loopy 寄存器处理错误。

### 14.1 证据链（全部实测）
1. 用无头导帧工具把 KIRA 的 XBuf 导出为 ASCII 和统计：整屏约 98 是单一底色，只有零星像素不同，即 BG 完全没画出来。
2. 逐帧插桩（临时探针，已全部回退）显示：可见扫描线渲染时 loopy 寄存器 v 恒为 0x0400，取到的 nt_byte 和 pt_lo 全为 0，像素全部落回 backdrop。
3. 同时插桩验证渲染器实际读的 CHR、NT、palette 窗口与 C++ 权威数组逐字节相同（差异 0 字节），因此排除窗口刷新与数据源问题。
4. 根因：frame.rs 在可见扫描线 dot 257 调用 copy_vertical()。硬件与已退役的 C++ 引擎（ppu_rendering.cpp 的 Fixit2()）在 dot 257 复制的是水平位（t 到 v 的 coarse_x 与 nametable_x）；垂直位只在预渲染行（dots 280 到 304，代码里 sl 等于 -1 处已有实现）复制。
5. 后果：每行都把垂直滚动重置回 t，于是每一行都取同一行 tile；同时 v 的水平位一直带着批式取块的 34 步 coarse 偏移，真实游戏只剩底色加精灵噪点，只有纯色测试 ROM 能通过像素门禁。

### 14.2 修复

- frame.rs：dot 257 分支由 copy_vertical() 改为 copy_horizontal()；相关注释与 registers.rs 的文档同步更正（垂直复制只属于预渲染行）。
- 改写单测 frame::tests::dot_257_copies_horizontal_bits_from_t：断言 dot 257 后 v 的水平位来自 t，且垂直位没有被复制（原测试断言的是旧的错误行为）。

### 14.3 验证

- KIRA：修复后首屏与标题能看出真实 tile 与文字结构（ASCII 导帧），不再是纯底色；batch_compat 仍 PASS。
- nestest：修复后渲染出正确的文字界面；帧 3 到 7 的 CRC 由旧值 0x433de396 变为 0x25ac91e1（旧值正是坏渲染的产物）。
- 其余 12 个地图 ROM 的帧哈希、全部 mapper byte-diff 门禁、ppu_frame_diff 像素门禁均不变。
- 基准再生成（仓库既有做法）：tests/fixtures/golden_hashes.json 与 tests/fixtures/golden_savestate_hashes.json，仅 nestest 条目变化。
- 验收：cargo test -p fceux11-ppu 83/83；全量 ctest 41 项等于 40 PASS / 1 SKIP / 0 FAIL。
