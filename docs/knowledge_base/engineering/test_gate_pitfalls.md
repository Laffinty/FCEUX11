# 模拟器测试门禁的陷阱与设计

> 来源：FCEUX11 v2.1.2（2026-09-13）排障沉淀。工程经验，不是硬件事实。

## 1. 本次踩到的最大陷阱：弱基准

tests/fixtures/golden_frames/*.xbuf 五个文件的**全部 61440 字节都是 0x80**（空白帧）。也就是说 ppu_frame_diff 的像素门禁一直在比较两份空白：Rust PPU 把真实游戏渲染成一片底色加精灵噪点时，它照样全绿。

教训：黄金值必须来自**有内容的场景**；记录时若源本身就是均匀屏，这个门禁等于没有。


## 2. 有效门禁的设计要点

- **内容相关**：不要只比 CRC 是否相等，还要断言非空、颜色与图块多样性、随时间变化（动画应改变帧 CRC）。
- **覆盖真实行为**：至少有一个使用精灵、滚动、调色板切换与 mapper IRQ 的 ROM；纯色测试 ROM 会掩盖渲染问题。
- **状态与画面分开**：画面门禁抓不住 CPU 与 PPU 内部状态错误（如 IRQ 行、滚动寄存器），需要 savestate 哈希或状态轨迹。
- **反向验证**：每个修复都应有把修复去掉就会失败的单测或复现步骤（本次 IRQ 修复与调色板折叠修复都做过）。


## 3. 基准再生成的纪律

1. 只在有意的行为变更时重生成，并在提交信息里写清差异根因。
2. 优先用对比工具证明差异范围（本次用 golden_savestate_test 的布局对比模式证明七份 golden 只差 IQLB 一个字段）。
3. 重生成后确认其余门禁不变（本次四条修复各自都确认了其它 ROM 与 mapper 门禁不受影响）。
4. 基准文件与生成它的构建版本要能对应；历史条目见 docs/plans 与 docs/ChangeLog.md。
