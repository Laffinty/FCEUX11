# PPU 画面回归排障方法论

> 来源：FCEUX11 v2.1.2（2026-09-12 与 09-13）KIRA.nes 全链路排障的沉淀。工程经验，不是硬件事实；硬件依据见 ../ppu/。

## 1. 症状到检查点的映射


| 症状 | 先查什么 | 典型原因 |
|---|---|---|
| 画面完全冻结、声音正常、PC 停在某段 | CPU 侧 IRQ 风暴 | IRQ 行被重复置位、应答被吞 |
| 只剩底色加零星精灵噪点 | PPU 侧 loopy 寄存器 v | 滚动位被逐行重置（dot 257 语义错） |
| 结构正确但颜色系统性不对 | 调色板链路 | 地址折叠、窗口刷新、调色板区选错 |
| 角色纯灰或颜色不对 | 精灵调色板 | 读了背景调色板区、精灵调色板为空 |
| 角色朝向或位置错 | OAM 属性与 8x16 寻址 | 翻转未实现、tile 对取址错 |


## 2. 可复用的工具手段

1. **无头导帧**：把 XBuf（256x240 调色板索引）导出成文件，同时输出统计（非零数、颜色分布、CRC）。
2. **ASCII 亮度渲染**：把帧降采样成 64x30 字符画；没有图形界面时也能判断画面有没有结构。
3. **逐帧状态轨迹**：kagami_qa_cycle_trace 记录每个 Cpu::run 边界的 PC 与 IRQlow，可直接看出第几帧开始异常。
4. **env 门控探针**：在可疑函数入口打印帧号、扫描线、关键输入（窗口内容、v、mask、取址结果），限制输出条数。
5. **指针穿透**：C++ 侧取 Rust 保存的窗口指针，把渲染器实际读的数据与权威数组逐字节比对。

## 3. 定位顺序（本次验证有效）

1. 先确认**数据源**：渲染器读的 CHR/NT/palette 窗口与 C++ 权威数组逐字节比对（本次 diff = 0，排除了窗口陈旧）。
2. 再确认**寄存器/状态**：mask、ctrl、loopy v、fine_x、取到的 tile 字节；本次发现 v 恒为 0x0400。
3. 最后才怀疑**算法**：对照该算法的权威描述（本次是 dot 256/257 的 loopy 语义）。
4. 修复后用同一工具复测：画面结构是否恢复、颜色分布是否合理、帧 CRC 是否随时间变化。


## 4. 注意事项与踩过的坑

- **探针要门控**：env 变量加帧号或扫描线条件加输出上限；否则一次 400 帧会刷出三十万行，网络盘上要等几十分钟。
- **stdout 与 stderr 重定向到文件再过滤**，不要直接灌进终端。
- **帧门控要核对计数器语义**：本次一度写错判断条件，探针看起来没触发；改成按调用序号加帧号双条件后立刻定位。
- **旧实现是规格、不是补丁来源**：把退役的 C++ 实现当行为参照（例如 Fixit2 的 dot 257 水平复制），修复仍落在 Rust 新代码里。
- **临时探针必须回退**：用 git show HEAD 加路径显式还原被污染的 TU，再只提交真实修复。
- **先做 A/B**：同一 ROM 在修复前与修复后各导一帧，用 ASCII 与统计对比，避免凭感觉判断。
