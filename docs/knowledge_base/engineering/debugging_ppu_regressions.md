# PPU 画面回归排障方法论

> 来源：FCEUX11 v2.1.2（2026-09-12 与 09-13）KIRA.nes 全链路排障的沉淀。工程经验，不是硬件事实；硬件依据见 ../ppu/。

## 1. 症状到检查点的映射


| 症状 | 先查什么 | 典型原因 |
|---|---|---|
| 画面完全冻结、声音正常、PC 停在某段 | CPU 侧 IRQ 风暴 | IRQ 行被重复置位、应答被吞 |
| 只剩底色加零星精灵噪点 | PPU 侧 loopy 寄存器 v | 滚动位被逐行重置（dot 257 语义错） |
| 结构正确但颜色系统性不对 | 调色板链路 | 地址折叠、窗口刷新、调色板区选错 |
| 角色纯灰或颜色不对 | 精灵调色板 | 读了背景调色板区、精灵调色板为空 |
| 角色朝向或位置错 | OAM 属性与 8x16 寻址 | 翻转未实现、tile 对取址错 |


## 2. 可复用的工具手段

1. **无头导帧**：把 XBuf（256x240 调色板索引）导出成文件，同时输出统计（非零数、颜色分布、CRC）。
2. **ASCII 亮度渲染**：把帧降采样成 64x30 字符画；没有图形界面时也能判断画面有没有结构。
3. **逐帧状态轨迹**：kagami_qa_cycle_trace 记录每个 Cpu::run 边界的 PC 与 IRQlow，可直接看出第几帧开始异常。
4. **env 门控探针**：在可疑函数入口打印帧号、扫描线、关键输入（窗口内容、v、mask、取址结果），限制输出条数。
5. **指针穿透**：C++ 侧取 Rust 保存的窗口指针，把渲染器实际读的数据与权威数组逐字节比对。

## 3. 定位顺序（本次验证有效）

1. 先确认**数据源**：渲染器读的 CHR/NT/palette 窗口与 C++ 权威数组逐字节比对（本次 diff = 0，排除了窗口陈旧）。
2. 再确认**寄存器/状态**：mask、ctrl、loopy v、fine_x、取到的 tile 字节；本次发现 v 恒为 0x0400。
3. 最后才怀疑**算法**：对照该算法的权威描述（本次是 dot 256/257 的 loopy 语义）。
4. 修复后用同一工具复测：画面结构是否恢复、颜色分布是否合理、帧 CRC 是否随时间变化。


## 4. 注意事项与踩过的坑

- **探针要门控**：env 变量加帧号或扫描线条件加输出上限；否则一次 400 帧会刷出三十万行，网络盘上要等几十分钟。
- **stdout 与 stderr 重定向到文件再过滤**，不要直接灌进终端。
- **帧门控要核对计数器语义**：本次一度写错判断条件，探针看起来没触发；改成按调用序号加帧号双条件后立刻定位。
- **旧实现是规格、不是补丁来源**：把退役的 C++ 实现当行为参照（例如 Fixit2 的 dot 257 水平复制），修复仍落在 Rust 新代码里。
- **临时探针必须回退**：用 git show HEAD 加路径显式还原被污染的 TU，再只提交真实修复。
- **先做 A/B**：同一 ROM 在修复前与修复后各导一帧，用 ASCII 与统计对比，避免凭感觉判断。

## 5. v2.1.3 批次 1 补充（2026-09-13，MMC3 A12 watcher 排障沉淀）

- **先验 ROM 文件完整性，再怀疑代码**：blargg ROM 截断下载（实测 `mmc3_2_details.nes` 14948/40976 字节）表现为 `kagami_bridge: LoadGame failed`、结果 `value=0xFE diag=[00,00,00]`——与精度失败完全不同。校验式：文件大小 ≥ 16 + 头[4]×16384 + 头[5]×8192。fix = 从 christopherpow/nes-test-roms 对应路径重新下载。
- **Rust 调度器回调内禁止 fceux11_ppu_* FFI——日志参数会被急切求值**：env 门控探针里把 FFI 写成 `log(..., ppu_rust_bridge_get_dot(), ...)` 的参数，探针关闭时**照样执行**（C/C++ 实参先于形参求值），在 StateBox &mut 借用存活期间重入 Rust 引发间歇性 SegFault（本次 rust_ppu_smoke_test 复现）。正确做法：包一层惰性访问器（内部先查 env 开关再调 FFI）。
- **bench_tolerance_test 对机器负载敏感**：与构建/其他测试并行时 CPU/全帧基准会虚高 +6~+17%（阈值 max-regression +2.5%）。判定真实回归前必须静机单独复跑；本次 +16.8% 的"回归"静机复测为 PASS。
- **git stash 是零成本回归归因工具**：可疑项（本例 3 个"known-fail 清单外失败"）在改动状态与 HEAD 状态各跑一次，1 个增量重建就能区分"我的回归"与"预存失败"；untracked 新文件要先移出工作树再 stash。
- **C++ 文件行尾**：仓库 blob 实际是 LF（尽管 .editorconfig 写 CRLF）；编辑工具可能把整个文件归一成 CRLF 导致 900+ 行假 diff。提交前 `sed -i 's/
$//'` 恢复，保持 diff 只含真实改动。
- **探针观测 CPU 域量化**：CPU 时间戳按 CPU 周期（3 PPU dot）量化——移动 1 dot 的边沿若不跨周期边界，探针 ts 不变；调校 ±1 dot 级时序时先算清量子边界（也解释了 ±1 dot 测试对逐指令 CPU 不可稳定命中）。

## 6. 批次 2 验收补充（2026-09-13，逐 dot 流水线落地）

- **稳态帧判别法**：golden 逐帧哈希出现偏差时，先看"稳态帧"是否一致——若只有最开头一两帧不同、其后几十帧哈希完全相等，这是流水线填充时机的合法语义变化（新流水线更快进入稳态），不是像素回归。本次 nestest 仅 frame 2/3 变化、frame 4 起与基线全同，据此把偏差定性为"首帧填充时序差"并重生基线。
- **A/B 版本二分法**：把可疑 ROM 丢进**上一版发布的 exe**（桌面留档）跑同一场景——旧版伪影更重 → 存量缺陷（本批已改善）；旧版干净 → 本批回归。比 git stash + 全量重建便宜得多，适合给 owner 做验收演示。本次 3186_Mario_1.nes 在 v2.1.2 上伪影为大块标题招牌碎片、批次 2 收敛为左侧细竖条，据此判定"早于两批次的存量缺口"。
- **零输入复现路径**：SMB1 类游戏的标题画面停留约 20 秒后自动进演示模式打关——无需任何输入即可复现游玩期伪影，适合做回归观测点与录屏取证。
- **NTAM-vs-像素判别**：同一帧既导命名表内容又导渲染像素——NTAM 已是正确内容而像素错 → 取指/渲染侧问题；NTAM 本身缺内容 → 写入路径问题（$2007 寻址/可见时机）。本次据此排除了"渲染器读陈旧窗口"假设。
- **基线重生的最小差异纪律**：重生后的 diff 应当极小且每处都可叙述机理（本次 golden_hashes.json 仅 1 行：nestest 由"2 帧过渡"变"1 帧过渡"，第 3 帧提前到达稳态值）。若重生 diff 很大或说不清机理，停下——那说明是回归而不是语义变化。
